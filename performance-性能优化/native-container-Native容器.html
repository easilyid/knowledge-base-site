NativeContainer 与 Allocator

是什么

NativeContainer 是一组线程安全的 C# 结构体，封装了 unmanaged native 内存。它解决两个核心问题：

  1. 跨线程数据共享：让 Job 能在工作线程上访问主线程创建的数据，由安全系统自动检测竞争
  2. 绕过 GC：底层是 native 内存，不参与托管堆管理，避免 GC 开销与碎片

所有 NativeContainer 共享以下特征：

  • 值类型：都是 struct，赋值 = 浅拷贝，多个 copy 共享同一块 native 内存
  • 必须手动 Dispose：没有终结器，忘记释放 = native 内存泄漏
  • 创建时必须指定 Allocator：Allocator 决定分配速度与生命周期约束
  • 内建安全系统：在 Editor 和 Development Build 中检测竞争、use-after-free、double-dispose

Unity.Collections 命名空间内置 NativeArray<T> 和 NativeSlice<T>。com.unity.collections 包扩展了完整集合族（NativeList、NativeHashMap、NativeQueue 等）。

分配器（Allocator）

每个 NativeContainer 构造时必须指定 Allocator，它决定内存从哪个池分配、速度如何、生命周期约束是什么。

Allocator速度生命周期约束能否传入 Job适用场景
Allocator.Temp最快（栈式线性分配）当前帧末自动释放不能主线程一帧内的临时缓冲区
Allocator.TempJob中等创建后 4 帧内必须 Dispose能Job 临时数据的标准选择
Allocator.Persistent最慢（等价 malloc）无限制，手动 Dispose能跨帧/跨场景的长生命周期数据

Temp 的细节

  • 主线程上用 Allocator.Temp 创建的容器，在当前帧末由 Unity 统一回收
  • Job 内部用 Allocator.Temp 创建的容器，在 Job 执行完毕时统一回收
  • 不能把 Allocator.Temp 容器存入 Job struct 字段——调度时会抛异常

TempJob 的 4 帧规则

Allocator.TempJob 要求在创建后 4 帧内调用 Dispose()。超时未释放时，native 层会打印警告。这个约束让 Unity 可以使用更激进的分配策略，换取更快的分配速度。

TempJob 泄漏警告

4 帧规则是”最迟”底线，不是”建议”延迟到第 4 帧再释放。最佳实践是：Job Complete 后立刻 Dispose，或者用 Dispose(JobHandle) 把释放挂到依赖链末端。

Persistent 的代价

Allocator.Persistent 底层调用 malloc，是最慢的分配路径。在 hot loop 中频繁 new + Dispose Persistent 容器会造成严重的分配抖动。应考虑预分配复用或改用 TempJob。

延迟释放：Dispose(JobHandle)

当容器被 Job 使用时，不要在 Job 完成前直接 Dispose()。所有 NativeContainer 都提供 Dispose(JobHandle) 重载，把释放动作排入依赖链：

这个模式让主线程无需调用 Complete() 即可安全释放内存，最大化并行窗口。

NativeArray

NativeArray<T> 是最基础的 NativeContainer——固定长度的连续 native 内存数组。泛型参数 T 必须是 unmanaged 类型。

ParallelFor 中的使用

NativeArray 是 IJobParallelFor 的标准数据载体。并行访问时每个 Worker 独占一段索引区间，写入 output[i] 不与其他 Worker 冲突，但 input 被所有 Worker 同时读取，必须标记 [ReadOnly]：

双缓冲（Double Buffering）模式

当需要”上一帧的输出作为当前帧的输入”时，双缓冲是标准模式——无需每帧重新分配，也无需在读写间插入同步点：

NativeSlice 与 Alias

NativeSlice<T> 是 NativeArray 的子段视图，不拥有内存。NativeList.AsArray() 返回共享原 allocation 的 alias，不是拷贝——修改 alias 影响原 list，只需释放原 collection。

NativeList

NativeList<T> 是可变长的 NativeContainer，类似 List<T> 但底层是 native 内存。

基本用法

动态增长机制

NativeList 内部维护 Length（实际元素数）和 Capacity（已分配容量）：

  • Add() 时若 Length < Capacity，直接写入，O(1)
  • Add() 时若 Length == Capacity，执行 realloc：分配新缓冲区（通常翻倍）、memcpy 旧数据、释放旧缓冲区

预分配容量避免增长

在 hot loop 中应避免频繁触发增长。构造时传入预计容量：new NativeList<int>(expectedCount, Allocator.TempJob)，避免 Add 不断触发 realloc。

Add vs AddRange vs AddNoResize

ParallelFor 中的限制

NativeList 支持多线程并行 Add——通过 AsParallelWriter() 获取 NativeList<T>.ParallelWriter。但 ParallelWriter 只支持 AddNoResize（不能触发容量增长），因此使用前必须预分配足够容量：

ParallelWriter 只能 AddNoResize

NativeList<T>.ParallelWriter 不支持 Add（可能触发 realloc，破坏并发安全），只支持 AddNoResize 和 AddRangeNoResize。如果运行时可能超容量，应改用 NativeStream 或预分配 NativeArray + 原子计数器。

多个 Worker 需要各自收集可变长结果时，标准模式是用 NativeStream 或预分配 NativeArray + 原子计数器。

NativeHashMap / NativeMultiHashMap

Collections 2.1+ 类型改名

NativeHashMap → NativeParallelHashMap，NativeMultiHashMap → NativeParallelMultiHashMap。旧名称仍可用但为别名，新项目建议使用带 Parallel 前缀的名称。

NativeHashMap<TKey, TValue> 是无序 key-value 关联数组，类似 Dictionary 的 native 版本。

基本用法（单线程）

NativeMultiHashMap：允许重复 key

NativeMultiHashMap<TKey, TValue> 允许多个 value 共享同一个 key，典型用途是空间分桶和邻接表：

并行写入：AsParallelWriter

NativeParallelHashMap 和 NativeParallelMultiHashMap（注意 “Parallel” 前缀）提供线程安全的并行写入器：

并行写入 != 并行读写

ParallelWriter 只保证写入安全。写入同时读取同一容器，安全系统仍会报竞争。标准模式：写入 Job 完成后，再用依赖链接入读取 Job。

NativeParallelHashMap.AsReadOnly() 返回只读视图，可在多个 Job 间安全共享读取。

提取结果数组

NativeQueue

NativeQueue<T> 是 FIFO 队列，支持多生产者单消费者（MPSC）模式。

并行写入：AsParallelWriter

MPSC 语义

NativeQueue 是多生产者单消费者：ParallelWriter 允许多线程 Enqueue，但 Dequeue 只能在单线程执行。需要多消费者时改用 NativeStream 或拆分为多个队列。

NativeRingQueue<T> 是固定容量的环形缓冲区，容量满时 Enqueue 抛异常，适用于有界缓冲场景。

其他容器

NativeReference

NativeReference<T> 是指向单个值的 native 引用，功能等价于长度为 1 的 NativeArray<T>，但语义更清晰——常用于 Job 输出单个标量结果：

NativeText

可变长 UTF-8 编码字符串，可在 Burst 编译代码中使用，替代托管 string。配合 FixedString*Bytes（32/64/128/512/4096）使用：FixedString 不分配堆内存，容量固定，适合短标签和日志。

NativeBitArray

可变长位数组，用于标记集合、位图索引等场景。SetBits/IsSet 按位操作，构造时可指定 ClearMemory 全部清零。

NativeParallelHashSet

线程安全的唯一值集合，提供 AsParallelWriter() 支持多线程并发 Add，Contains() 查询。

NativeStream

一组 append-only 非类型化 buffer 集合，支持多 Job 并行写入可变长度数据。适用于”多个 Job 各自产出不定长结果”的场景，比预分配 NativeArray + 原子偏移更方便。

安全系统

NativeContainer 内建安全系统，在 Editor 和 Development Build 中自动检测并发错误。Release Build 中安全检查被移除，零运行时开销。

AtomicSafetyHandle

每个 NativeContainer 实例持有一个 AtomicSafetyHandle，跟踪当前容器的读写状态：

  • 主线程读/写：检查是否有未完成的 Job 也在读/写
  • Job 读/写：检查是否有其他 Job 或主线程也在写
  • 多个 Job 同时写同一个容器：调度时抛异常
  • 多个 Job 同时读同一个容器（需 [ReadOnly]）：允许

安全系统在调度时（Schedule() 调用）检查冲突，不是在运行时。不合法的访问模式在开发期就能暴露。

DisposeSentinel（已移除）

DisposeSentinel 曾是与 AtomicSafetyHandle 配套的内存泄漏检测机制——在编辑器模式下，如果容器被 GC 回收但从未被 Dispose()，其 finalizer 会打印警告。

Collections 1.0.0-pre.6 起已移除 DisposeSentinel

DisposeSentinel 在 com.unity.collections 1.0.0-pre.6 及之后版本中被移除。新版本使用 AtomicSafetyHandle 的版本号机制统一处理 use-after-free 和 double-dispose 检测，不再依赖 finalizer。如果你的项目使用较旧的 Collections 包版本，仍可见 DisposeSentinel 行为。

IsCreated 的局限性

IsCreated 仅在默认构造后或对同一个 struct 实例调用 Dispose() 后为 false。另一个 copy 的 IsCreated 可能仍为 true，但底层内存已释放。

IsCreated 不能跨 copy 判断生命周期

NativeContainer 是值类型，Dispose() 只标记当前 copy。不要依赖 IsCreated 作为跨 copy 的生命周期判据。

ENABLE_UNITY_COLLECTIONS_CHECKS

安全系统通过 #if ENABLE_UNITY_COLLECTIONS_CHECKS 编译开关控制。Editor 和 Development Build 默认开启，Release Build 关闭。这意味着 Release 中不会报错但行为未定义——必须在 Editor 中充分测试。

自定义 NativeContainer

当内置容器无法满足需求时（如特殊内存布局或自定义分配策略），可以实现自定义 NativeContainer。

核心要求

  1. 实现 IDisposable（或 INativeDisposable，支持 Dispose(JobHandle)）
  2. 是 unmanaged struct（不能含引用字段）
  3. 持有 AtomicSafetyHandle（参与安全系统；Collections 1.0.0-pre.6 起 DisposeSentinel 已移除，不再需要）
  4. 通过 AllocatorManager.Allocate 分配内存
  5. 用 [NativeContainer] 属性标记类型

关键注解

注解用途
[NativeContainer]标记为 NativeContainer，Job System 特殊处理
[NativeDisableUnsafePtrRestriction]允许 Job 内部使用指针字段
[NativeDisableContainerSafetyRestriction]禁用特定字段的容器安全检查（慎用）

Job 中的使用

[ReadOnly] 属性

Job 只读不写某个 NativeContainer 时必须加 [ReadOnly]。不加时安全系统默认容器可写，会阻止多个 Job 并行访问同一容器——即使你实际上只读：

[NativeDisableParallelForRestriction]

默认 IJobParallelFor 的安全系统要求每个 Worker 只写自己索引区间内的元素。需要写入其他索引位置（如直方图聚合）时，用此属性禁用索引范围限制：

NativeDisableParallelForRestriction 不保证线程安全

它只是禁用了安全系统的索引范围检查。如果写了有竞争的代码，安全系统不会再拦你，但运行时行为未定义。需要原子操作时应使用 UnsafeAtomicCounter32/64 或 Interlocked。

DeallocateOnJobCompletion

[DeallocateOnJobCompletion] 让容器在 Job 执行完毕后自动 Dispose：

仅限 IJob

此属性不适用于 IJobParallelFor——多个 Worker 无法协调谁负责释放。ParallelFor 场景应使用 Dispose(JobHandle)。

写入 struct 元素的正确方式

NativeContainer 索引器不返回 ref，对 struct 元素的修改不会写回：

静默无效的 struct 修改

nativeArray[0]++ 不会报错，但也不会更新数据。这是 C# 值类型语义导致的——索引器返回的是拷贝。此 Bug 极难定位，编译器和安全系统都不会报错。

反模式

忘记 Dispose

NativeContainer 没有终结器，忘记 Dispose() = native 内存泄漏。泄漏在 Profiler 的”Native Object”面板可追踪，但不如 GC 泄漏显眼。建议用 using 或 try/finally 保证释放路径。

Temp 分配器传入 Job

Allocator.Temp 创建的容器不能存入 Job struct 字段，调度时抛异常。Job 临时数据应使用 Allocator.TempJob。

4 帧内未释放 TempJob

常见原因：在 Update() 中创建但忘了在 LateUpdate() 中 Dispose，或 Job 依赖链过长导致 Complete 延迟超过 4 帧。

Schedule 后立刻 Dispose

Schedule() 推入队列但不立刻执行。Schedule 后立刻 Dispose 容器，Job 执行时访问已释放内存——安全系统抛异常，Release Build 中是 use-after-free 崩溃。正确做法：Dispose(JobHandle) 或先 Complete() 再 Dispose()。

静默无效的 struct 元素修改

nativeArray[i]++ 不会更新数据，编译期和运行期都不会报错，只能靠代码审查发现。

NativeList 在 ParallelFor 中直接 Add（非 AddNoResize）

NativeList 有 ParallelWriter，但只支持 AddNoResize（不能触发扩容）。使用前必须预分配足够容量：new NativeList<int>(expectedCount, Allocator.TempJob)，再通过 AsParallelWriter() 获取写入器。如果运行时可能超容量，应改用 NativeStream 或预分配 NativeArray + 原子计数器。

NativeHashMap 非 Parallel 版本用于并行写入

NativeHashMap 的 TryAdd 不是线程安全的。并行写入必须使用 NativeParallelHashMap + AsParallelWriter()。

Persistent 分配器在 hot loop 中频繁使用

Allocator.Persistent 等价 malloc，分配释放都慢。每帧循环中频繁 new + Dispose 会造成显著性能退化，应改用 TempJob 或预分配复用。

IsCreated 作为跨 copy 生命周期判据

Dispose() 只标记当前 struct copy。另一个 copy 的 IsCreated 可能仍为 true，但底层内存已释放。判断容器可用性应依赖自己的生命周期管理。
