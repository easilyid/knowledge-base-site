IJob 接口族（IJob Types）

是什么

Unity Job System 提供一组 IJob 接口族，每种接口对应一种并行模式。所有 Job 都是实现这些接口的 struct，通过 Schedule 提交给工作线程池执行。接口的选择决定了并行度、调度方式和数据访问模式——选错接口意味着要么浪费 CPU 核心，要么引入不必要的调度开销。

接口族按并行模式可分三档：

  • 单任务：IJob — 一个 Worker 跑一个 Execute()
  • 索引并行：IJobFor / IJobParallelFor / IJobParallelForBatch / IJobParallelForFilter — 按 index 切片，多个 Worker 各跑一片
  • ECS 并行：IJobChunk / IJobEntity — 按 Chunk 或 Entity 调度，与 ECS 架构深度耦合

加上专用于 Transform 层级的 IJobParallelForTransform，共 7 种接口。

继承/演进关系说明：

  • IJob 是最基础的单任务接口
  • IJobFor 在 IJob 基础上增加了索引循环，提供 Schedule（串行）和 ScheduleParallel（并行）两种调度
  • IJobParallelFor 是 IJobFor 的”强制并行版”，只提供 Schedule(arrayLength, batchSize) 并行调度
  • IJobParallelForBatch 和 IJobParallelForFilter 是 IJobParallelFor 的特化变体，分别优化 batch 内连续访问和过滤场景
  • IJobChunk 和 IJobEntity 属于 ECS 层，调度单位从 index 变成了 ArchetypeChunk / Entity

IJob — 单任务 Job

最简单的 Job 接口。Execute() 只被调用一次，在单个 Worker 线程上执行。

调度方式：

适用场景

  • 一次性计算（求和、归约、单次逻辑判断）
  • 必须串行执行的任务链中的一环
  • 工作量小、不值得并行的操作
  • 需要访问托管对象（非 Burst 编译的 IJob 可以持有 GameObject 引用）

性能特征

  • 只占一个 Worker，不会阻塞整个线程池
  • 调度开销最低（无需切 batch、无需 work stealing）
  • 适合作为依赖链中的”同步点”或”汇总节点”

IJob 也可以在主线程同步执行

调用 job.Run() 会在当前线程（通常是主线程）同步执行 Job，不经过线程池。适合极轻量操作或调试。

IJobFor / IJobParallelFor — 索引并行 Job

这两个接口是最常用的并行 Job 类型，区别在于调度的灵活性。

batchSize 的取舍

Schedule(arrayLength, batchSize) 中的 batchSize 决定每个 batch 包含多少次 Execute(i) 调用：

batchSize效果
小（如 1）任务粒度细，Worker 间负载均衡好；但调度开销大
大（如 64~256）调度开销小、缓存友好；负载不均时部分 Worker 提前闲置
等于 arrayLength退化为单线程

官方建议：从 1 开始测，逐步加大，直到性能不再提升。实际项目中 32~128 是常见区间。

Work Stealing 机制

完成快的 Worker 会从慢 Worker 队列尾偷一半剩余 batch。“偷一半”是为了保留缓存局部性——被偷的连续 batch 在内存上仍是局部的。

IJobParallelForBatch — 批量执行 Job

为什么 batching 对缓存局部性至关重要

CPU 缓存以 cache line（通常 64 字节）为单位加载内存。当 Worker 逐 index 执行 IJobParallelFor 时，如果单个 Execute(i) 内访问的内存跨度大（比如读 inputA[i]、inputB[i]、inputC[i] 分属不同数组），相邻 index 之间的 cache 复用率低。

IJobParallelForBatch 把连续 index 捆绑给同一个 Worker，使得：

  1. 同一 batch 内的连续内存访问集中在同一 Worker——L1/L2 cache 命中率高
  2. 减少跨 Worker 的 cache line 竞争——false sharing 风险降低
  3. 调度开销更低——batch 数量 = arrayLength / batchSize，远小于逐 index 的调度次数

典型受益场景：

  • 归约操作（求和、求最大值、前缀和的局部阶段）
  • 每个 index 需要访问多个相邻元素（如滑动窗口、卷积）
  • 单次 Execute 计算量小但内存访问模式跨步大

IJobParallelForBatch 是 IJobParallelFor 的缓存优化替代

当你的 IJobParallelFor 每个 Execute 计算量轻但内存访问密集时，换成 IJobParallelForBatch 并在 batch 内手动循环，往往能获得可测量的性能提升。

IJobParallelForFilter 已过时

在较新版本的 Collections 包中，IJobParallelForFilter 已被 IJobFilter 取代。IJobFilter 提供相同的过滤语义但 API 更简洁。如果你的包版本提供了 IJobFilter，建议迁移。

适用场景

  • 从大数组中筛选活跃对象（存活单位、可见物体、可交互目标）
  • 流式压缩（compact）——把稀疏数据压缩为密集数组
  • 替代 IJobParallelFor + 手动 atomic 计数的模式

性能特征

  • 内部使用 atomic 操作收集通过过滤的 index，输出数组紧凑排列
  • 相比手动用 Interlocked.Increment + 写输出数组，由运行时优化 atomic 策略
  • 输出 NativeList 的容量需要预分配（通常设为输入数组长度），实际写入数量通过 NativeList.Length 查询

  • 粒子、弹幕等大量 Transform 的逐帧更新

IJobParallelForTransform 的 Burst 编译有优化限制

IJobParallelForTransform 可以标记 [BurstCompile] 并被 Burst 编译，但由于 TransformAccess 内部封装了托管 Transform 引用，Burst 的部分优化（如 SIMD 自动向量化）受限。如果 Transform 操作是性能瓶颈，应迁移到 ECS 使用 IJobEntity + LocalTransform，后者可完全 Burst 优化。

ECS 专用 Job

ECS（Entities 包）提供两种与 Chunk 架构深度耦合的 Job 接口。它们不使用 NativeArray 作为数据源，而是从 EntityQuery 匹配的 ArchetypeChunk 中直接访问组件数据。

IJobChunk — 逐 Chunk 遍历

IJobChunk 的 Execute 以 ArchetypeChunk 为单位调用。每个 Chunk 包含同一 Archetype 的紧密排列的组件数据，是 ECS 数据布局的核心。

反模式

用 IJobParallelFor 处理元素间有顺序依赖的数据

IJobParallelFor 的 Execute(index) 在不同 Worker 上无序执行。如果 Execute(i) 依赖 Execute(i-1) 的结果，并行执行会产出错误数据。应改用 IJob.Schedule 串行执行，或用 依赖链 把顺序依赖拆成多个 Job。

IJobParallelForBatch 的 count 参数不是 batchSize

Execute(int startIndex, int count) 中的 count 是该 batch 的实际元素数，不一定等于 ScheduleBatch 时传入的 batch 大小——最后一个 batch 可能更短。在 batch 内循环时必须用 count 而非硬编码的 batch size。

对小数组使用并行 Job

数组长度 < 几百时，并行调度的开销（线程池分发、work stealing、安全系统检测）可能超过并行收益。用 Profiler 确认，小数组优先用 IJob 或 IJobFor.Schedule。

IJobFor 和 IJobParallelFor 的 Schedule 签名混淆

IJobFor.Schedule(arrayLength, dependsOn) 是串行调度，第二个参数是依赖；IJobParallelFor.Schedule(arrayLength, batchSize) 是并行调度，第二个参数是 batch 大小。两者签名不同，混用会导致编译错误或语义错误。

IJobParallelForTransform 的 Burst 优化受限

TransformAccess 内部封装了托管 Transform 引用，Burst 可以编译但部分优化被限制。如果 Transform 操作是性能瓶颈，应迁移到 ECS + IJobEntity + LocalTransform，后者完全支持 Burst 优化。

在 IJobChunk 中忘记刷新 TypeHandle

GetComponentTypeHandle<T>(isReadOnly) 返回的 handle 与当前帧的组件数据绑定。如果在上一帧缓存了 handle 并在下一帧使用，可能读到过时数据或触发安全系统异常。每帧的 OnUpdate 中必须重新获取 TypeHandle。

IJobEntity 的 Execute 参数决定查询，参数类型错误导致查询为空

IJobEntity 的 Execute 参数签名就是 EntityQuery：ref = ReadWrite，in = ReadOnly。如果本应 ref 的组件误写成 in，Job 无法写入该组件；如果方向相反（ref 但只读），Job System 会阻止其他 Job 并行读该组件。仔细检查每个参数的 ref/in 选择。

忽略 NativeContainer struct 元素的写回

NativeArray<T> 中 T 是 struct 时，array[i].member = value 不会写回——这是 C# 值类型语义。必须”取出 → 改 → 写回”：var temp = array[i]; temp.member = value; array[i] = temp;。详见 NativeContainer 的修改陷阱。

Unity 6 变更与注意事项

Unity 6 中 Job System 接口族本身没有重大 API 变更，但有以下值得注意的变化：

  • IJobFor 成为推荐的基础并行接口：官方文档和示例中 IJobFor 的出现频率增加，取代了部分原 IJobParallelFor 的推荐位置，因为它提供 Schedule / ScheduleParallel 双模式
  • IJobParallelForBatch 和 IJobParallelForFilter 在 Unity.Jobs 命名空间中正式可用：早期版本中这两个接口属于实验性 API
  • ECS Job 接口随 Entities 包版本演进：IJobEntity 在 Entities 1.0 正式引入，替代了已移除的 IJobForEach；IJobChunk 的调度方法签名在 Entities 1.3/1.4 中有微调
  • JobsUtility.JobWorkerCount 可用于动态计算 batchSize，避免硬编码导致某些平台上 Worker 数量与 batch 分配不匹配
  • Safety System 更严格：Unity 6 中对 [ReadOnly] 标记的检查更完善，之前版本中可能漏报的竞争现在会被捕获
