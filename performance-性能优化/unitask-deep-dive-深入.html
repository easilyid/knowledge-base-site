UniTask 深入（UniTask Deep Dive）

是什么

UniTask 是 Cysharp 为 Unity 设计的零分配 async/await 库。它把 Unity 的 AsyncOperation、UnityWebRequest、帧等待、PlayerLoop 时序、生命周期取消和并发组合封装成 struct-based 的 awaitable API，让 Unity 代码可以用 async/await 风格替代大量 Coroutine 和部分 Task 用法。

它解决的核心问题不是”多线程计算”，而是Unity 主循环里的异步流程编排，同时在运行时避免 GC 分配。

核心数据流：async UniTask 方法 → 编译器生成 struct-based AsyncUniTaskMethodBuilder → 产出 UniTask<T> struct（持有 IUniTaskSource + token）→ awaiter 判断是否完成 → 未完成时注册到 ContinuationQueue → PlayerLoopHelper 在指定 PlayerLoopTiming 阶段回调 continuation。

零分配原理

UniTask 是 struct，不是 class

UniTask 和 UniTask<T> 都是 [StructLayout(LayoutKind.Auto)] 的值类型。字段：

同步完成时 source 为 null、结果直接内联在 struct 中，无任何堆分配。异步完成时只持有 IUniTaskSource 的引用——这个引用指向的对象通常是对象池复用的，不是每次 new 出来的。

AsyncUniTaskMethodBuilder 也是 struct

C# 编译器为 async UniTask 方法生成的 builder 是 AsyncUniTaskMethodBuilder<T>，同样是 struct。相比标准 AsyncTaskMethodBuilder<T> 产生的 Task<T> class 对象，struct builder 在方法同步完成路径上零堆分配。

Debug vs Release 构建差异

Debug 构建下编译器可能把状态机生成成 class（产生堆分配），Release 构建下才是 struct。在 Unity 的 Project Settings → Player → Code Optimization 中选择 Release 或启用 C# Compiler Optimizations 可以避免此问题。Profiler 中如果看到 AsyncStateMachine 的分配，先检查构建配置。

IUniTaskSource 与对象池

IUniTaskSource 是 UniTask 的核心接口，所有异步操作源都实现它：

UniTask 内部大量使用对象池来复用实现此接口的对象。例如 AsyncOperationAwaiterSource、DelayFrameSource 等都是可池化的。当异步操作完成并消费后，对象归还池，下次复用。

跳过 ExecutionContext 和 SynchronizationContext

标准 .NET Task 在每次 continuation 时都会捕获和恢复 ExecutionContext，涉及 Thread-local 状态的复制，这是分配和性能开销的来源之一。UniTask 完全跳过 ExecutionContext 和 SynchronizationContext 的捕获，因为 Unity 主线程上的 async 流程不需要跨线程上下文传播。

与 ValueTask 的异同

UniTask 的设计哲学与 .NET 的 ValueTask<T> 一致（struct + 可池化 source），但 UniTask 走得更远：

UniTaskCompletionSource.Task 可以被多个调用方同时 await——所有等待者都会收到同一个结果。这是与普通 UniTask 的重要区别。

组合超时

PlayerLoop 集成

续延机制（Continuation without SynchronizationContext）

UniTask 不依赖 .NET SynchronizationContext。它通过 PlayerLoopHelper 把自定义 PlayerLoopSystem 节点注入到 Unity 的 PlayerLoop 中。当 await 操作需要续延时，注册回调到 ContinuationQueue，由 PlayerLoop 在指定阶段执行。

流程：

  1. await UniTask.Yield() → awaiter 发现未完成
  2. 向 ContinuationQueue 注册 continuation，关联一个 PlayerLoopTiming
  3. Unity PlayerLoop 运行到对应阶段 → PlayerLoopHelper 轮询队列
  4. 取出 continuation 并执行 → 状态机推进

Yield vs NextFrame 的区别

Yield 和 NextFrame 语义不同

UniTask.Yield() 在当前帧的后续阶段即可恢复——如果调用时机早于指定的 Timing，continuation 在同一帧执行。UniTask.NextFrame() 保证等到下一帧才恢复，语义等同 yield return null。

LoadSceneAsync.ToUniTask 的执行顺序问题

LoadSceneAsync.ToUniTask 可能导致 Start 和 continuation 顺序不一致

官方建议直接 await SceneManager.LoadSceneAsync("scene") 而不是 .ToUniTask()，因为后者可能改变场景中 Start() 方法和 await 后续代码的执行顺序。

UniTaskSynchronizationContext

UniTask 提供了 UniTaskSynchronizationContext 作为 Unity 默认 UnitySynchronizationContext 的高性能替代。它的作用是让非 UniTask 的 async 代码（如 async Task）的续延也能走 UniTask 的优化路径。

注入方式：

UniTaskSynchronizationContext 是可选的，不是必须注入的

async UniTask 本身完全不依赖 SynchronizationContext。注入它的唯一理由是改善 async Task 代码的性能。UniTaskSynchronizationContext 不保证与 UnitySynchronizationContext 行为完全一致，且性能仍不如 async UniTask。如果你的项目全部使用 async UniTask，则无需注入。

调试工具

UniTaskTracker

通过 Unity 菜单 Window > UniTask Tracker 打开。它可以：

  • 追踪当前活跃的 UniTask 实例
  • 检测泄漏的 UniTask（已完成但未被消费的）

UniTaskTracker 有显著性能开销

开启 Tracking 和 Stack Trace 捕获会导致性能大幅下降。仅在调试阶段使用，发布版本务必关闭。可通过 UniTaskTracker.EnableTracking 和 UniTaskTracker.EnableStackTrace 分别控制。

ValueTaskSupplement 的角色

ValueTaskSupplement 是 Cysharp 的另一个库，为 .NET Core 的 ValueTask 提供 WhenAll / WhenAny 等组合子。它存在的理由是：UniTask 的 .NET Core 版本是 Unity 版的子集（去掉了 PlayerLoop 依赖的 API），当共享代码需要在 .NET Core 上使用类似组合能力时，ValueTaskSupplement 填补了这个空缺。

IEnumerator 协程转 UniTask

IEnumerator.ToUniTask 不支持所有 yield 指令

WaitForEndOfFrame、WaitForFixedUpdate、嵌套 Coroutine 不能通过简单 .ToUniTask() 转换。需要完全兼容时使用 ToUniTask(MonoBehaviour coroutineRunner) 重载。

反模式

UniTask 不是并行计算框架

SwitchToThreadPool 只是把后续逻辑切到线程池，不等于把计算自动拆成多核任务。批量数据并行仍应使用 Job System + Burst。

忘记传递 CancellationToken

async 方法如果中间丢失 CancellationToken，GameObject 销毁后仍可能继续执行，访问失效 Unity 对象导致 MissingReferenceException。每个 await 调用都要传 token。

对同一个 UniTask await 两次

UniTask 是一次性的。第二次 await 抛 InvalidOperationException。需要多次消费时用 .Preserve()、UniTask.Lazy 或 UniTaskCompletionSource。

用 async void 代替 async UniTaskVoid

async void 不走 UniTask 系统，异常行为不可控。Fire-and-forget 应使用 async UniTaskVoid + .Forget()。

在后台线程直接访问 Unity API

SwitchToThreadPool 之后的所有代码都在后台线程。访问 Transform、GameObject 等 Unity API 会抛异常。必须先 await UniTask.SwitchToMainThread() 回主线程。

Yield 与 NextFrame 混淆

UniTask.Yield() 可能在同一帧恢复；UniTask.NextFrame() 保证等到下一帧。如果需要 yield return null 的等价语义，用 NextFrame()。

编辑器下 Delay 行为不一致

Editor 中 UniTask.Delay 的 DelayType.DeltaTime / UnscaledDeltaTime 不正确，会自动切换到 DelayType.Realtime。所有 PlayerLoopTiming 在编辑器中都在 EditorApplication.update 上运行，与运行时行为不同。编辑器扩展开发时需注意。

UniTask.Run 已废弃

应使用 UniTask.RunOnThreadPool。旧版 UniTask.Run 在语义上容易混淆（默认不在 ThreadPool 上执行），新 API 名字更明确。

LoadSceneAsync.ToUniTask 的执行顺序问题

await SceneManager.LoadSceneAsync("scene").ToUniTask() 可能导致新场景中 Start() 方法和 await 后续代码的执行顺序与直接 await 不一致。建议直接 await SceneManager.LoadSceneAsync("scene")。
