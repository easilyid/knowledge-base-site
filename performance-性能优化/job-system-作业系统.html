Unity Job System（作业系统）

是什么

Unity Job System 是一套让你以安全方式编写多线程代码的机制。它把工作单元封装成”Job”（作业），由 Unity 的工作线程池调度执行，让应用能利用 CPU 的所有核心，而不必直接处理原始 Thread 或锁。

它与传统多线程最大的区别是安全：Job System 在调度阶段就检测数据竞争（race condition），违规时直接抛异常，而不是让你在运行时遇到难复现的 Bug。

Job System 解决的是”并行计算的调度与安全”问题。至于每个 Job 的计算代码跑得多快，由 Burst Compiler 负责；跨线程传递数据用的容器，由 NativeContainer 负责。

核心组件

Job System 由三层组成：

  1. Job Scheduler（调度器）：Unity 内部的 native 层调度器，管理 Worker 线程池、任务队列和依赖图。调度器自动匹配 CPU 核心数创建 Worker 线程，你不需要也不应该自己控制线程数。

  2. Safety System（安全系统）：调度期的竞争检测层。它通过 AtomicSafetyHandle 追踪每个 NativeContainer 的读写状态，在调度时判断两个 Job 是否会冲突。冲突则抛异常，而不是让运行时出现未定义行为。

  3. Job 接口层：C# 侧的 IJob / IJobFor / IJobParallelFor / IJobParallelForTransform 等 接口族，是你编写 Job 的入口。

主线程与 Worker 线程的关系

主线程只做三件事：构造 Job 数据、调用 Schedule()、调用 Complete()。计算全部在 Worker 线程上完成。

Native Job 与 Managed Job

Job System 内部区分两种执行路径：

  • Native Job：被 Burst 编译的 Job，Execute() 直接作为 native 函数指针被调度器调用，零托管开销。这是绝大多数生产 Job 的路径。
  • Managed Job：未被 Burst 编译的 Job（如字段包含托管引用的 IJob），Execute() 通过委托回调进入托管层。调度器需要额外切换到托管执行环境，开销更大。

始终给 Job 加 [BurstCompile]

Managed Job 的调度和执行开销远高于 Native Job。如果一个 Job 没加 [BurstCompile]，它不仅没有 SIMD 优化，连调度本身也更慢。唯一的例外是需要访问托管对象的 Job（如 GameObject.GetComponent），但这种 Job 本身就是反模式——应该重构为纯数据 Job。

安全系统

安全系统是 Job System 最核心的设计决策之一。它的目标：在调度时检测竞争，而不是在运行时崩溃。

AtomicSafetyHandle

每个 NativeContainer 内部持有一个 AtomicSafetyHandle m_Safety 字段。这个句柄存储了当前容器被允许的操作标志：

  • 读标志：标记容器当前是否可被读取
  • 写标志：标记容器当前是否可被写入
  • 版本号：主版本号（容器被释放时递增）和次版本号（动态容器大小变化时递增）

调度 Job 时，Job System 自动遍历 Job 的所有 NativeContainer 字段，根据 [ReadOnly] 属性设置读写标志：

  • 带 [ReadOnly] 的容器：多个 Job 可同时读
  • 不带 [ReadOnly] 的容器：同一时间只允许一个 Job 写，且不允许其他 Job 读

读写追踪机制

安全系统在 Schedule() 调用时就做检查。这意味着你不需要等 Job 真正跑到一半才发现问题——错误在调度瞬间就被捕获。

版本号与 Use-After-Free 检测

AtomicSafetyHandle 内含版本号，当容器被 Dispose() 后版本号递增。如果此后还有 Job 试图访问该容器，版本号不匹配，安全系统抛异常。这就是 Use-After-Free 的检测机制。

次版本号用于动态容器（如 NativeList<T>）：当容器大小变化（如 Add 操作），次版本号递增，所有指向旧大小的 NativeSlice 视图自动失效。

DisposeSentinel（已移除）

DisposeSentinel 曾是与 AtomicSafetyHandle 配套的内存泄漏检测机制——在编辑器模式下，如果容器被 GC 回收但从未被 Dispose()，其 finalizer 会打印警告。

Collections 1.0.0-pre.6 起已移除 DisposeSentinel

DisposeSentinel 在 com.unity.collections 1.0.0-pre.6 及之后版本中被移除。新版本使用 AtomicSafetyHandle 的版本号机制统一处理 use-after-free 和 double-dispose 检测，不再依赖 finalizer。如果你的项目使用较旧的 Collections 包版本，仍可见 DisposeSentinel 行为。

static 字段在 Job 内既不会被复制也不会被检测。在 Job 里读写 static 数据会绕过所有安全机制，可能导致难以复现的崩溃、数据损坏或竞态条件。这是 Job System 中最危险的陷阱，因为安全系统对此完全无能为力。

Burst 集成

Job System 与 Burst Compiler 的集成是 Unity 性能栈的核心组合：Job System 负责”安全地分发到多核”，Burst 负责”让每个核心跑得更快”。

[BurstCompile] 在 Job 上的使用

关键要点：

  • [BurstCompile] 必须加在 Job struct 上，不是加在 Execute 方法上
  • Burst 会将整个 Job 的 Execute 编译成原生代码，包含 SIMD 自动向量化
  • 不加 [BurstCompile] 的 Job 走托管路径，调度和执行都更慢

[NoAlias] 属性

[NoAlias] 告诉 Burst 编译器：标记的指针或 NativeContainer 不会与其他指针/容器指向同一块内存。这让 Burst 能做更激进的优化（如重排读写、减少 load/store）。

的承诺必须由你保证

如果你标记了 [NoAlias] 但实际传入了别名（两个 NativeArray 指向重叠内存），Burst 编译器会基于错误假设做优化，导致静默的数据损坏。安全系统不检测别名，这是你自己的责任。最安全的做法：只在输入和输出完全分离的 Job 上使用 [NoAlias]。

[NativeDisableContainerSafetyRestriction]

完全禁用某个 NativeContainer 字段的安全检查。比 [NativeDisableParallelForRestriction] 更激进——后者只关闭并行写入检查，前者关闭所有检查：

是最后手段

此属性完全关闭安全检查，包括越界检测和读写冲突检测。它只应在性能剖析确认安全检查是瓶颈时使用，且你必须保证操作的绝对安全。

Burst 编译对调度的影响

Burst 编译的 Job 作为 native 函数指针被调度器直接调用。未编译的 Job 需要通过托管委托回调，调度器必须额外处理托管/非托管切换。这意味着：

  • Burst Job 的调度开销更低：函数指针调用 vs 委托 invoke + 托管切换
  • Burst Job 的执行开销更低：SIMD 向量化 + 寄存器优化 + 无 GC 压力
  • 混合调度时注意顺序：如果 Burst Job 依赖 Managed Job 的结果，Managed Job 的执行速度会成为瓶颈

FloatMode 与 FloatPrecision

在 Job 的 [BurstCompile] 中设置浮点策略：

  • FloatMode.Fast：允许非严格浮点语义（如 fused multiply-add、倒数替代除法），更快但不保证 IEEE 精确性
  • FloatMode.Strict：严格遵循 IEEE 754，适合需要确定性的物理/联网同步代码

FloatMode.Fast 破坏确定性

物理模拟回放、联网帧同步、录像系统等需要帧间确定性一致的场景，必须用 FloatMode.Strict。FloatMode.Fast 在不同 CPU 架构上可能产生不同结果。

与 ECS 集成

在 Unity DOTS / ECS 架构中，Job System 是 System 执行计算的核心方式。SystemBase 提供了 Dependency 属性，自动管理 JobHandle 链。

SystemBase.Dependency 属性

每个 SystemBase 子类都有一个 Dependency 属性（类型 JobHandle），它代表”当前 System 的所有前置依赖”。ECS 框架自动根据 System 的 Update 顺序和组件读写关系设置 Dependency。

性能调优

batchSize 调优

IJobParallelFor.Schedule(arrayLength, batchSize) 的 batchSize 直接影响调度效率和负载均衡。

batchSize调度开销缓存局部性负载均衡
1高（每个元素一个 batch）差极好
32-128中好好
arrayLength / workerCount低极好差（长尾效应）

调优步骤：

  1. 从 batchSize = 1 开始作为基线
  2. 逐步增大（32 → 64 → 128 → 256），每次用 Profiler 测量
  3. 当性能不再提升时停住——这就是你的最优 batchSize
  4. 如果数组长度变化很大，选一个在各长度下都表现稳定的值

IJobParallelForBatch 的 batchSize 含义不同

IJobParallelForBatch.ScheduleBatch(arrayLength, batchSize) 的 batchSize 决定了每个 batch 包含多少元素，Execute(startIndex, count) 中 count 就是 batchSize（最后一个 batch 可能更小）。选择更大的 batchSize 意味着每个 Worker 一次处理更多连续元素，对 Burst 向量化更友好。

Job Struct 布局优化

Job struct 的字段布局直接影响 memcpy 开销和缓存效率：

优化原则：

  • 减少 Job struct 的大小：每个字段在调度时被 memcpy，字段越多拷贝越慢
  • 用 [ReadOnly] / [WriteOnly] 标注：不仅帮助安全系统，也帮助 Burst 做读写优化
  • 标量字段紧随指针字段：减少缓存行跨越
  • 能用单个 NativeArray 就不要拆成多个：一个 NativeArray<float3> 比三个 NativeArray<float> 更缓存友好

缓存局部性

Job 的性能上限通常受内存带宽制约，而非计算能力。优化缓存局部性是突破内存墙的关键：

  1. 数据布局采用 SoA 而非 AoS：

SoA 让 Burst 自动向量化时能做连续内存加载，缓存命中率远高于 AoS。

  1. 避免跨 cache line 访问：一个 cache line = 64 bytes（主流 x86/ARM）。确保你的内层循环访问的数据落在尽量少的 cache line 中。

  2. 用 [NativeDisableParallelForRestriction] 做散射写入时格外注意：散射写入天然破坏空间局部性。如果散射目标地址不连续，每次写入都可能 miss cache。

调度开销与最小工作量

每个 Job 的调度有固定开销（入队、依赖检查、Worker 分配）。如果 Job 的实际工作量太小，调度开销占比会很高：

经验法则：单个 Job 的 Execute 工作量应该至少覆盖几微秒的计算。如果元素数量少于几十个，直接主线程跑可能更快。

反模式

Schedule 后立即 Complete

job.Schedule().Complete() 等价于同步执行，完全丧失并行优势。Complete() 不仅阻塞等待，还可能在调用线程上直接执行 Job（如果 Job 尚未开始），反而增加开销。正确做法：把 Schedule 和 Complete 分开放在不同位置（如 Update 中 Schedule，LateUpdate 中 Complete），给 Worker 最大的并行窗口。

在 Job 中访问托管对象

Job 的字段不能包含 string、List<T>、GameObject 等引用类型。这是编译期强制限制。但 IJob 可以在 Execute 中通过字段持有的 GameObject 引用调用 GetComponent——这走托管路径，不仅慢还可能引发主线程竞争。正确做法：把需要的数据提前提取到 NativeContainer 中，再传给 Job。

忘记 Dispose NativeContainer

NativeContainer 底层是 native 内存，不参与 GC。忘记 Dispose() 会导致内存泄漏。旧版 Collections 包的 DisposeSentinel 会在编辑器 GC 时打印警告（已在 Collections 1.0.0-pre.6 中移除），但发布构建中没有此检测。建议使用 using 或 try-finally 模式确保释放。

在 IJobParallelFor 中读写 static 变量

static 字段在 Job 中不受安全系统保护，也不会被 memcpy 复制。多个 Worker 同时读写同一个 static 变量会导致无声的数据竞争——不会抛异常，但结果不可预测。这是最难调试的 Job System Bug 之一。

过度依赖链降低并行度

依赖链条越长，并行度越低。A → B → C → D 意味着这四个 Job 只能串行执行。如果 B 和 C 不共享可写数据，应该让它们并行，只在 D 处合并依赖：A → B 和 A → C 并行，Combine(B, C) → D。

长时间 Job 霸占 Worker 池

单个执行时间长的 Job 会占用 Worker 线程，阻塞其他独立 Job 的调度。如果一个 Job 要跑 10ms，而帧预算只有 16ms，它就吃掉了超过一半的帧时间。解决方案：拆成多个小 Job，或调大 batchSize 让更少的 Worker 参与此 Job。

用 Allocator.Persistent 做 Per-Frame 临时容器

Allocator.Persistent 底层调用 malloc，分配/释放开销远大于 TempJob。如果容器的生命周期不超过几帧，用 Allocator.TempJob。Persistent 只用于初始化时分配、跨场景长期存在的容器。

在 ECS SystemBase.OnUpdate 中调用 Complete()

这会阻塞主线程等待 Job 完成，打破 ECS 框架的并行调度模型。正确做法：把 Job 的输出依赖传给下一个 Schedule，让框架自动管理同步点。
