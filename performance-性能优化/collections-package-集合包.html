Unity Collections 包（Unity Collections Package）

是什么

com.unity.collections 是 Unity 的高性能集合包，提供适合 job-system-作业系统 和 burst-compiler-Burst编译 的 unmanaged 数据结构。它扩展了 Unity 核心引擎中的 NativeContainer 概念，让 Job 不只局限于 NativeArray<T> / NativeSlice<T>，还可以使用可变长列表、哈希表、队列、位数组、UTF-8 文本和自定义 allocator。

它在 DOTS 性能栈里的位置是数据层：Job System 负责调度，Burst 负责编译计算，Collections 负责提供可被安全传入 Job / Burst 的数据结构。所有 Collections 类型都是 unmanaged 的，不产生 GC 分配，可以在 Burst 编译的代码中使用。

安全容器全景

Collections 包把集合分成安全容器（Native- 前缀）和非安全容器（Unsafe- 前缀）两大类。安全容器在开发期提供越界、use-after-free、数据竞争等检测；非安全容器完全不做检查，留给开发者手动保证正确性。

类型用途并发写入命名空间
NativeList<T>可变长列表是（ParallelWriter，AddNoResize）Unity.Collections
NativeHashMap<TKey,TValue>单线程 key-value 表否Unity.Collections
NativeParallelHashMap<TKey,TValue>多线程 key-value 表是（ParallelWriter）Unity.Collections
NativeParallelMultiHashMap<TKey,TValue>允许重复 key 的并行 map是（ParallelWriter）Unity.Collections

Parallel 前缀的含义

名称中带 Parallel 的类型内置了并发写入支持，通过 ParallelWriter 结构体让多个 Job 同时写入而不会产生数据竞争。不带 Parallel 的类型如果被多个 Job 同时写入，安全系统会抛异常。

NativeList

NativeList<T> 是 Collections 包中最常用的容器，相当于 unmanaged 版本的 List<T>。它在 NativeArray<T> 的基础上增加了动态扩容能力。

基本用法

容量管理

NativeList 内部维护 Length（实际元素数）和 Capacity（已分配空间能容纳的元素数）。Add 在 Length == Capacity 时触发扩容，新容量通常是当前的 2 倍。

AddNoResize 超出容量会静默越界

AddNoResize 不检查容量，在 Length >= Capacity 时写入会越界而不报错。只在已确认容量充足的 tight loop 中使用，开发期先用普通 Add 验证逻辑正确后再替换。

删除元素

RemoveAtSwapBack 是高频模式：当你不需要保持列表顺序时（如遍历后删除），它避免了数组搬移，性能远优于 RemoveAt。

NativeQueue

NativeQueue<T> 提供先进先出（FIFO）语义，支持并发入队操作。典型场景是生产者-消费者模式：多个 Job 往队列写结果，主线程或后续 Job 按序取出。

基本用法

并发入队

并发 Dequeue 不安全

NativeQueue 只支持并发 Enqueue。Dequeue 和 TryDequeue 不是线程安全的，只能在单线程中执行——通常是所有入队 Job 完成后，在主线程或后续串行 Job 中消费队列。

NativeText

NativeText 是可变长 UTF-8 文本容器，基于 UnsafeText 构建，用于在 Job / Burst 中替代托管 string。它支持动态扩容，适合运行时拼接、格式化等需要可变长文本的场景。

基本用法

NativeText vs FixedString

Collections 包提供了两套文本方案：

维度NativeTextFixedString*Bytes（如 FixedString64Bytes）
容量动态扩容，堆分配固定容量（32 / 64 / 128 / 512 / 4096 字节），栈上内联
分配需要 Allocator不需要 Allocator
适用场景长度不可预知的运行时文本短标签、日志 key、枚举名、asset path 片段
开销有 native 分配和 safety handle零分配，直接嵌入 struct
Burst 兼容完全兼容完全兼容
托管 string 互操作ToString() / Append(string)Append(string) 不兼容 Burst

FixedString 是 Job 内字符串首选

如果文本长度可预估且较短（如实体名、调试标签、路径片段），优先用 FixedString64Bytes 或 FixedString512Bytes——它无需 allocator，不产生任何 native 分配，且数据直接嵌入 struct 内存布局中，缓存友好性更好。

托管 string 在 Burst 中不可用

string 是托管类型，不能在 Burst 编译的代码中声明或操作。需要文本时必须使用 NativeText 或 FixedString*。NativeText.Append(string) 和 FixedString.Append(string) 重载因为依赖托管类型，也被排除在 Burst 兼容之外。

NativeBitArray

NativeBitArray 是可变长位数组，每个元素只占 1 bit，适合大量布尔标记、位掩码操作和集合位图。在 Job 中常用于标记”已处理”、“已访问”等状态。

基本用法

位掩码与批量标记

典型场景：

  • 寻路已访问标记：网格大小 1000x1000 = 1M 格，bool[] 需 1MB，NativeBitArray 只需 ~125KB
  • 碰撞层级过滤：32 位层级掩码，用 GetBits / SetBits 做批量检查
  • 实体活跃状态位图：与 ECS archetype 的 bitmask 配合

NativeBitArray 不支持并发写入

NativeBitArray 没有并行写入器。如果多个 Job 需要同时设置不同的位，需要用 UnsafeBitArray 自行保证不同位段不重叠，或者改用 NativeParallelHashSet<int> 存储已设置的索引。

Unsafe 容器

Unsafe- 前缀的容器位于 Unity.Collections.LowLevel.Unsafe 命名空间，不包含 AtomicSafetyHandle，因此没有越界、use-after-free、数据竞争检测。大多数 Native- 类型内部就是 Unsafe- 类型加一层安全句柄包装。

何时用 Unsafe

场景建议
正常 Job 开发用 Native-，安全检查在开发期帮你抓 bug
Native- 嵌套 Native- 不允许NativeList<NativeList<T>> 编译不通过，必须用 NativeList<UnsafeList<T>> 或 UnsafeList<UnsafeList<T>>
自定义容器内部实现用 Unsafe- 作底层存储，外层包装自己的安全逻辑
极致性能且已充分测试Release 构建中 safety checks 已关闭，Native- 和 Unsafe- 性能差距极小（约 10-20 条指令/访问），但 Unsafe- 少一次间接寻址
与 native 插件交互Unsafe- 可直接传递指针，免去 safety handle 管理负担

Unsafe 容器绕过安全系统后竞争难以重现

例如 UnsafeList alias 一个 NativeList，然后调度两个 Job 分别访问原对象和 alias。安全系统不一定能捕获这个冲突，因为其中一个路径绕过了 safety handle。这类 bug 只在特定调度时序下暴露，极难在开发期稳定重现。

与标准集合对比

System.Collections.Generic 中的 List<T>、Dictionary<TKey,TValue>、Queue<T> 等是托管集合，分配在托管堆上，受 GC 管理。Collections 包的 Native- / Unsafe- 类型是 unmanaged 的，分配在 native 内存上。

维度Collections 包System.Collections.Generic
内存位置Native 堆（不经过 GC）托管堆（受 GC 管理）
Burst 兼容全部兼容不兼容
Job 中使用可以不可以（托管类型不能出现在 Job struct 中）
安全检查Native- 有（开发期）无（依赖 CLR 边界检查）
并发写入Parallel 系列有原子写入支持无（ConcurrentDictionary 在 Burst 中不可用）
容量管理手动 Allocator + Dispose自动扩容 + GC 回收
嵌套受限（Native- 嵌 Native- 不允许）自由嵌套
泛型约束T : unmanagedT 无特殊约束

何时用哪个

  • Job / Burst 代码：必须用 Collections 包。标准集合是托管类型，无法放入 Job struct。
  • 主线程非 hot path：标准集合更简单、更安全、开发效率更高。不要为了”统一风格”在不需要的地方引入 Native- 类型。
  • 主线程 hot path 但需要避免 GC：如果某段主线程代码每帧执行且 GC 分配是瓶颈，可以考虑 Native- 类型 + Allocator.TempJob，但这增加了手动释放负担。
  • 与 DOTS / ECS 集成：Collections 包是 ECS 数据层的基础，SystemBase / ISystem 中天然使用 Native- 类型。

不要在 Job struct 中引用托管集合

List<T>、Dictionary<TKey,TValue> 等托管类型不能声明为 Job struct 的字段。编译器会阻止，但如果你通过 IntPtr 或其他方式间接传入 native 内存来绕过，就是未定义行为。

Burst 兼容性

所有 Native- 和 Unsafe- 集合类型都标注了 [BurstCompatible] 属性，可以在 [BurstCompile] 的代码中使用。以下是关键兼容性要点：

完全兼容的类型

NativeList<T>、NativeHashMap<TKey,TValue>、NativeParallelHashMap<TKey,TValue>、NativeParallelMultiHashMap<TKey,TValue>、NativeHashSet<T>、NativeParallelHashSet<T>、NativeQueue<T>、NativeBitArray、NativeText、NativeReference<T>、NativeStream 及其所有 Unsafe- 对应类型。

不兼容 Burst 的方法

部分方法因为依赖托管类型而不能在 Burst 编译的代码中调用：

方法原因
NativeText.ToString()返回托管 string
NativeText.Append(string)参数是托管 string
FixedString64Bytes.Append(string)参数是托管 string
FixedString* 的 Format(string, ...) 重载第一个参数是托管 string

Burst 中的格式化方案

在 Burst 中拼接文本，使用 FixedString 的 Append(ReadOnly) 或 Append(int/float) 重载，或使用 NativeText.AppendFormat 的非托管重载。避免一切接受 string 参数的方法。

Safety Checks 在 Release 中的行为

在 Release 构建（Player 构建）中，Burst 编译的代码会自动关闭 safety checks，此时 Native- 类型的开销与 Unsafe- 几乎没有区别——因为 Native- 本来就是 Unsafe- + safety handle，而 safety handle 检查只在开发期生效。因此性能不是选择 Unsafe- 的首要理由，嵌套需求才是。

反模式

在 Job 中使用 Allocator.Temp 主线程分配

Allocator.Temp 分配不能从主线程传入 Job。Job 临时数据应该用 Allocator.TempJob，并在 4 帧内释放。在 Job struct 字段中使用 Allocator.Temp 创建容器会导致运行时异常。

忘记延迟释放

如果容器被 Job 使用，主线程直接 Dispose() 会造成 use-after-free 风险。用 Dispose(JobHandle) 把释放挂到依赖链末端。如果容器还被多个 Job 共用，释放 handle 应该依赖所有使用该容器的 Job handle。

误以为 IsCreated 能判断所有 copy 的真实状态

Dispose() 只会把当前 struct copy 的 IsCreated 设为 false。如果另一个 copy 或 alias 释放了底层内存，当前 copy 的 IsCreated 可能仍然为 true。不要把 IsCreated 当成跨 copy 的绝对生命周期证明。

在 NativeHashMap 上并发写入

NativeHashMap 不支持并发写入。如果多个 Job 同时写入同一个 NativeHashMap，安全系统会抛异常。应该使用 NativeParallelHashMap 及其 ParallelWriter。这个规则同样适用于 NativeHashSet vs NativeParallelHashSet。

把二维数组照搬进 Job

Collections 没有多维数组类型。应把多维索引打包到一维数组，例如 (x, y) 映射为 index = y * width + x。如果需要多层嵌套列表，用 NativeList<UnsafeList<T>> 而非 NativeList<NativeList<T>>。

NativeList.AsArray() 的 alias 在 Dispose 后使用

AsArray() 返回的是共享原 allocation 的 alias，不是拷贝。原 NativeList 被 Dispose 后 alias 立即失效，对 alias 的任何访问都是 use-after-free。同样，AsDeferredJobArray() 返回的延迟数组也遵循此规则。

TempJob 超过 4 帧未释放

Allocator.TempJob 分配的容器必须在 4 帧内 Dispose()。Native- 类型会通过 safety checks 抛异常，但 Unsafe- 类型没有这层保护，内存泄漏不会被自动检测。

NativeText 托管 string 互操作在 Burst 中调用

NativeText.ToString() 和 NativeText.Append(string) 依赖托管类型，不能在 Burst 编译的代码中调用。在 Burst Job 中需要拼接文本时，用 Append(FixedString*) 或 Append(int/float) 重载。

权衡与选择

优先用 Collections package：

  • Job 需要可变长度结果，而 NativeArray<T> 容量固定
  • 多个 Job 需要并行写入 map / set
  • Burst 代码需要字符串替代类型
  • 临时数据结构很多，需要明确 allocator 生命周期
  • 想减少 GC 并改善缓存局部性
  • 需要在 Job 中做大量布尔标记（NativeBitArray）

不要急着用 Collections package：

  • 数据规模小，普通数组/List 已经足够
  • 逻辑必须频繁访问 UnityEngine 对象或托管引用
  • 团队还没建立 NativeContainer 生命周期管理习惯
  • 只是主线程一次性脚本，不在 hot path

在 Native- 和 Unsafe- 之间选择：

  • 默认用 Native-，除非有明确理由
  • 需要嵌套容器（如列表的列表）时用 Unsafe- 作内层
  • 构建自定义容器时用 Unsafe- 作底层
  • 不要为了”性能”盲目选 Unsafe-——Release 构建中两者性能差距可忽略
