ParallelFor Job 与批量调度

是什么

IJobParallelFor 是 Unity Job System 中对大数组做同质操作的标准模式。它把数组切成多个 batch，分配给多个 Worker 线程并行处理，是游戏开发中利用多核最常见的手段。

类比：普通 IJob 是一个 worker 跑完整循环，IJobParallelFor 是把循环切片，多个 worker 各自跑一片。

IJobParallelForBatch 是它的批量变体——Execute 收到的是一段起止区间而非单个索引，适合需要在 batch 内创建临时缓冲或做局部归约的场景。

核心接口对比：

接口Execute 签名并行保证典型用途
IJobParallelForExecute(int index)强制并行逐元素同质操作
IJobParallelForBatchExecute(int startIndex, int count)强制并行batch 内需临时变量、局部归约
IJobParallelForTransformExecute(int index, TransformAccess transform)强制并行批量操作 Transform

调度方式

Schedule — 逐索引调度

Schedule(arrayLength, innerloopBatchSize, dependsOn) 是 IJobParallelFor 的标准调度方法。Job System 把 arrayLength 次 Execute(i) 调用按 innerloopBatchSize 切成多个 batch，分发到 Worker 池。

调度参数含义：

  • arrayLength：Execute(i) 被调用的总次数，通常等于 NativeArray 的 Length
  • innerloopBatchSize：每个 batch 包含多少次连续调用
  • dependsOn：可选，前置依赖 JobHandle

ScheduleBatch — 逐区间调度

ScheduleBatch(arrayLength, minIndicesPerJobCount, dependsOn) 是 IJobParallelForBatch 的调度方法。与 Schedule 不同，它不会把工作切到 innerloopBatchSize 那么细，而是按 minIndicesPerJobCount 把总长度分成若干大块，每块交给一个 Worker 的 Execute(startIndex, count) 一次性处理。

何时选 Schedule vs ScheduleBatch

维度Schedule（IJobParallelFor）ScheduleBatch（IJobParallelForBatch）
粒度单元素 Execute(i)批区间 Execute(start, count)
负载均衡更细粒度，work-stealing 效率高块较大，负载不均风险更高
临时分配每次调用都创建 → 开销大batch 内创建一次 → 省分配
局部归约需要原子操作或 per-thread 缓冲天然支持 batch 内累加
代码复杂度简单需要手动循环 batch 内元素

选 Schedule 的场景：元素操作完全独立、无需 batch 内中间状态、负载可能不均匀。

选 ScheduleBatch 的场景：每个 batch 需要临时 NativeArray、要做 batch 内局部归约、元素操作极轻量而调度开销占比高。

ScheduleBatch 的 minIndicesPerJobCount 不宜过小

minIndicesPerJobCount 决定了每个 Job 处理的最少元素数。设太小会创建过多 Job，调度开销反超计算收益。通常从 arrayLength / JobsUtility.JobWorkerCount 开始调。

批大小调优

InnerloopBatchSize 的本质

innerloopBatchSize（旧称 batchCount）控制的是一个 Worker 连续执行多少次 Execute(i) 后才会让出执行权、允许 Job System 重新分配剩余 batch。它不是”创建多少个 Job”，而是”一个 batch 的粒度”。

总 batch 数 = arrayLength / innerloopBatchSize（向上取整）。

调优指南

batchSize优点缺点适合场景
1最细粒度负载均衡；work-stealing 几乎无损调度/同步开销大元素工作量差异极大
8~32均衡调度开销与负载均衡极端不均时仍有空转通用默认值
64~128缓存局部性好，调度开销极低负载不均时尾部空转明显元素工作量均匀、计算量轻
256+最大缓存局部性少数 Worker 长时间占满 batch元素操作极轻（几条指令）

调优流程：

  1. 从 innerloopBatchSize = 1 开始测量基准时间
  2. 依次测试 8、32、64、128、256
  3. 画出”batchSize vs 耗时”曲线，取拐点附近的值
  4. 目标平台（移动端/主机）CPU 核心数不同，需分别测

典型测量结果（10 万个 float 运算，8 核 PC）：

batchSize耗时（ms）相对提升
10.42基准
80.3126% 快
320.2540% 快
640.2443% 快
1280.2443% 快
2560.2540% 快（尾部空转抵消收益）

拐点在 32~64 之间。超过拐点后性能不再提升，甚至因尾部空转而回落。

batchSize 必须整除 arrayLength 是误区

innerloopBatchSize 不要求整除 arrayLength。最后一个 batch 会自动包含余数个元素。但整除时缓存对齐更好，对极端性能敏感的场景可以考虑对齐到 2 的幂。

Work Stealing 机制

完成快的 Worker 会从慢 Worker 队列尾偷一半剩余 batch。“偷一半”是为了保留缓存局部性——被偷的连续 batch 在内存上仍是局部的。

batchSize 越小，stealing 越频繁，均衡越好但同步开销越大。batchSize 越大，stealing 几乎不发生，均衡依赖初始分配。

并行访问模式

只读 vs 读写容器

并行 Job 中对 NativeContainer 的访问权限直接影响调度可行性：

访问模式标注多 Worker 并行安全系统行为
只读[ReadOnly]允许同时读多个 Job 可共享读权限
只写[WriteOnly]不允许同时写同一容器同一容器只能被一个 Job 写
读写无标注不允许同时写同一容器等同于写权限独占

会导致并行调度失败

两个 ParallelFor Job 同时读同一个 NativeArray 时，如果任一方未标注 [ReadOnly]，安全系统会认为存在写竞争并抛异常。即使你”知道”自己不会写，也必须标注。

NativeDisableParallelForRestriction — 绕过并行写限制

[NativeDisableParallelForRestriction] 告诉安全系统”我知道自己在做什么，允许这个 NativeContainer 在并行 Job 中被写入”。它绕过了”同一个 NativeContainer 不能被多个 Worker 同时写”的限制。

何时需要：

  • 每个 Worker 写入 NativeContainer 的不重叠区间（如 Worker 0 写 [0, N/4)，Worker 1 写 [N/4, N/2)）
  • 输出数组与输入数组不是同一容器，但索引映射后天然无冲突
  • 使用 NativeStream / NativeList.ParallelWriter 等已内建线程安全机制的写入器

NativeDisableParallelForRestriction 是 unsafe 操作

使用此属性时，你必须手动保证不同 Worker 写入的索引不会重叠。如果两个 Worker 写了同一个位置，结果是不确定的——不会有异常，只会静默产生错误数据。开发期应先用安全方式验证逻辑，确认无冲突后再加此属性。

NativeContainer 并行写入的安全替代方案

方案原理适用场景
[ReadOnly] + 独立输出数组每个 Job 写不同数组输出天然分离
NativeStream每个 Worker 分配独立 writer可变长输出
NativeList.ParallelWriter内建原子追加追加式写入
NativeCounter.Concurrent原子递增计数归约
[NativeDisableParallelForRestriction]手动保证索引不重叠散射写入

结果归约

ParallelFor 的经典难题：多个 Worker 各自计算了一部分结果，如何安全地汇总（归约）为一个最终值？三种主流方案：

原子归约

使用 Interlocked 或 Collections 包的原子类型，每个 Worker 直接对共享计数器做原子操作。

NativeCounter 是 EntityComponentSystemSamples 仓库中的示例类型（非 com.unity.collections 官方包 API）。其 NativeCounter.Concurrent 基于 Interlocked.Increment，适合整数计数。官方包中的替代为 UnsafeAtomicCounter32 / UnsafeAtomicCounter64（Unity.Collections.LowLevel.Unsafe 命名空间）。

优点：实现简单。缺点：原子操作在 Worker 数多时造成总线争用，Worker 越多越慢。

原子归约在 Worker > 4 时性能骤降

Interlocked 操作会锁定缓存行，多个 Worker 同时原子写同一位置时串行化严重。4 Worker 以下可接受，8 Worker 以上归约本身可能成为瓶颈。

NativeCounter 不是官方 API

NativeCounter 仅存在于 EntityComponentSystemSamples 示例仓库中，不是 com.unity.collections 包的一部分。官方替代是 UnsafeAtomicCounter32 / UnsafeAtomicCounter64。

Per-thread 归约

每个 Worker 各自累加到独立槽位，最后在主线程或单独的 IJob 中求和。这是高性能归约的标准做法。

ThreadIndex 不等于 Worker 编号

JobsUtility.ThreadIndex 在 Worker 空闲并切换执行不同 batch 时可能变化。同一 Worker 在执行两个 batch 之间可能被重新分配。如果 batch 内部做了局部累加，应在 batch 结束时写入，不能假设 ThreadIndex 在整个 Job 生命周期内不变。推荐用 IJobParallelForBatch 在 batch 级别做局部归约。

双缓冲归约

对结构性变化（而非标量归约）的场景，如粒子系统需要写回更新后的状态，可以用双缓冲模式：读上一帧的 buffer A，写当前帧的 buffer B，帧末交换。

调度端在帧间交换读写 buffer 引用即可。无需原子、无需 per-thread 汇总。

三种方案选择：

方案复杂度性能适用场景
原子归约低Worker 多时差计数、少量整数累加
Per-thread / batch 归约中高浮点求和、统计、方差
双缓冲中高结构性状态更新

游戏开发实战模式

1. Transform 批量更新

大量对象按速度移动，用 IJobParallelForTransform 避免逐个访问主线程 Transform。

2. 粒子系统位置更新

大量粒子各自按物理规则更新，天然逐元素独立。

3. AI 评估 — 评分并行，决策串行

对 N 个 AI agent 并行计算评分，再在主线程或单独 Job 中做最高分决策。

4. 网格顶点变形

逐顶点做形变计算，写回顶点缓冲。

5. 寻路代价估算

并行计算所有 agent 到目标的曼哈顿/欧几里得距离，作为寻路启发式或优先级排序依据。

6. 视锥体剔除批量判定

并行判定 N 个对象的包围球是否在相机视锥体内。6 个裁剪面需打包为 NativeArray<float4> 传入 Job。

兼容 Unity 2022 LTS 及以上。Unity 6 API 一致。IJobParallelForTransform 需要 TransformAccessArray，在 Unity.Jobs 命名空间。

与 Burst 协作

ParallelFor 的性能上限由 Burst 决定。不加 [BurstCompile] 的 ParallelFor Job 走 Mono/IL2CPP 虚拟机执行，调度开销可能比计算本身还大。

Burst 编译后的性能特征

维度无 Burst有 Burst典型倍率
单次 Execute 耗时基准3~10x 快向量化 + 寄存器优化
SIMD 向量化无自动（循环级）4~8x（float4/SOAA）
函数调用开销虚拟分发内联显著
首次调度无额外成本需编译（可异步）首次慢，后续无开销

Burst + ParallelFor 的性能陷阱

  • 首次调度延迟：Burst 首次编译一个 Job 类型需要几十毫秒。对实时场景，应在加载期预热（用 CompileSynchronously = true 跑一次空 Job）。
  • FloatMode.Fast 与确定性：并行 + Fast 浮点 = 不同 Worker 的累加顺序不可预测，结果逐帧微变。物理、网络同步需用 FloatMode.Default。
  • Burst 不支持捕获变量：Job 是 struct，所有数据必须通过字段传入，不能闭包捕获。

不加 Burst 的 ParallelFor 在移动端可能比主线程循环还慢

移动端 CPU 核心少（4~8 大核，甚至有能效核），调度开销 + 无优化的 IL2CPP 执行 = 并行收益为负。移动端 ParallelFor 必须搭配 Burst。

缓存与伪共享

缓存行基础

现代 CPU 的缓存行通常是 64 字节。当两个 Worker 线程各自修改同一缓存行中的不同变量时，缓存一致性协议（MESI）会强制使对方的缓存行失效——这就是伪共享（false sharing）。它让原本无逻辑冲突的写入变成实际串行。

ParallelFor 中的伪共享场景

NativeArray<float> 的逐元素写入通常不会伪共享，因为每个 float 只有 4 字节，同一 Worker 连续写一段区间。但以下模式会触发伪共享：

规避方案：缓存行对齐

每个 per-thread 槽位填充到 64 字节，确保不同 Worker 的写入落在不同缓存行。

NativeArray<T> 中 T 的布局决定了内存访问模式：

紧凑 struct（< 64B）低高优先

依赖与 Worker 占用的交互

长 ParallelFor 链会级联占满 Worker 池

每个 ParallelFor 默认尽量占用所有 Worker。如果链上有 3 个 ParallelFor，它们是串行执行的（因为依赖），不会同时抢 Worker——但每个阶段都会占满所有 Worker，阻塞同帧其他独立 Job。

缓解方法：手动调大 innerloopBatchSize，减少单个 ParallelFor 占用的 Worker 数，给其他 Job 留出并行空间。

反模式

元素数太少时调度 ParallelFor

数组长度 < 100 时，调度开销（线程同步、work-stealing 初始化）可能超过计算本身。直接用 IJobFor.Schedule() 跑单线程循环更快，或干脆主线程内联。

在 Execute 中分配内存

new NativeArray<T>(..., Allocator.Temp) 在 Execute 内部做会在每个元素上重复分配/释放。如果每个 Worker 都这样做，分配器争用严重。应改用 IJobParallelForBatch 在 batch 级别分配一次。

掩盖竞争

“先加上看看能不能跑”是危险做法。如果索引映射有重叠，结果静默错误且难以复现。应先用安全方式（独立输出数组 + [WriteOnly]）验证逻辑正确性，确认无冲突后再切换到此属性。

逐元素原子操作做浮点归约

Interlocked 不直接支持 float。自行用 Interlocked.CompareExchange 模拟 float 原子加，在高频 ParallelFor 中性能极差。应改用 per-thread/batch 局部归约 + 最终求和。

ParallelFor 中访问 static 字段

static 字段不会被 Job System 复制，也不受安全系统检测。多个 Worker 同时写同一个 static 字段 = 数据竞争，且无任何运行时保护。这是最难排查的 Job System Bug 来源之一。

在 Complete 之前读取 Job 写入的 NativeArray

JobHandle.Complete() 是主线程安全访问结果的唯一同步点。在 Complete 之前读取 Job 写入的 NativeArray，安全系统会抛异常；如果容器标注了 [NativeDisableContainerSafetyRestriction]，则静默读到未完成的数据。

忽略首次 Burst 编译延迟

首帧触发 Burst 编译会导致 30~100ms 卡顿。应在场景加载时用 CompileSynchronously = true 预热所有 Job 类型，或用 BurstCompiler.Compile 显式预热。

IJobParallelForTransform 的 TransformAccessArray 未同步

TransformAccessArray 中的 Transform 必须在主线程上设置，且在 Job 执行期间不能在主线程修改对应 Transform。否则结果不确定。
