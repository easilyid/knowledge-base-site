Burst 编译器（Burst Compiler）

是什么

Burst Compiler 是 Unity 的高性能 C# 编译器，基于 LLVM 后端，把符合约束的 C# 子集（Unity 称为 HPC#，High Performance C#）编译成高度优化的原生机器码。它解决的是 Job System 的”算得快不快”问题：Job System 负责把工作安全地分发到多核，Burst 负责把每个 Job 的计算代码优化到接近手写 SIMD 的性能。

Burst 与普通 C# 编译的关系是补充而非替代：Unity 项目仍然由 Mono 或 IL2CPP 作为主脚本后端，Burst 只编译被 [BurstCompile] 标记的 Job struct 和静态方法。编辑器中 JIT 模式用于快速迭代，发布构建使用 AOT 模式。

在 Unity 性能体系里，Burst 通常和 job-system-作业系统、native-container-Native容器、parallel-for-job-并行调度 一起出现：Job 定义并行任务，NativeContainer 传递数据，Burst 编译计算核心。

编译管线

Burst 的编译管线是一条从 C# IL 到平台原生代码的多阶段流水线：

flowchart LR
    A["C# 源码<br/>#91;BurstCompile#93;"] --> B["Roslyn 编译"]
    B --> C["IL 程序集"]
    C --> D["ILPostProcessing<br/>注入 $BurstDirectCall"]
    D --> E["Burst 前端<br/>IL → LLVM IR"]
    E --> F["LLVM 优化管线<br/>O1/O2/O3"]
    F --> G["平台代码生成<br/>x86-64 / ARM64 / Wasm"]
    G --> H["原生机器码"]

各阶段说明：

  1. ILPostProcessing：Unity 构建管线或 Domain Reload 时触发。为每个 [BurstCompile] 方法生成 $BurstDirectCall 嵌套类，注入 Invoke() 静态方法和 Constructor() 初始化方法，后者调用编译接口进行延迟编译。

  2. Burst 前端：将 .NET IL 转换为 LLVM IR。此阶段会执行 HPC# 子集检查，拒绝不支持的托管类型和语言特性。

  3. LLVM 优化管线：根据 OptimizeFor 选项选择优化级别。关键优化 pass 包括：

    • SimplifyCFG：控制流图简化
    • SROA：标量替换聚合值（消除不必要的 struct 拷贝）
    • EarlyCSE：公共子表达式消除
    • IPSCCP：跨过程常量传播
    • GlobalOpt：全局优化
    • Burst 自定义 DeadLoopRemoval pass：消除阻碍向量化的死循环
    • 自动向量化（SLP / Loop Vectorization）

  4. 平台代码生成：支持 x86-64（SSE2/AVX/AVX2）、ARM64（NEON）、WebAssembly 等目标架构。

编辑器使用 JIT，发布使用 AOT

编辑器中 Burst 首次调度时 JIT 编译，支持热重载迭代。Standalone Player 构建时切换为 AOT，所有 Burst 代码在构建期预编译完成，运行时不产生编译开销。

[BurstCompile] 属性可标注在 assembly、type（struct/class）或 method 级别，低级别覆盖高级别设置。

FloatMode 详解

FloatMode.Fast 允许的优化：

  • 假设参数和结果不含 NaN / +/-Infinity
  • 忽略零符号差异（+0 == -0）
  • 用倒数替代除法（1/x * y 替代 y/x）
  • 使用 fused 指令（如 FMA）

FloatMode.Fast 会破坏数值确定性

物理、回放、联网同步、确定性模拟等场景需要严格浮点语义。FloatMode.Fast 的性能收益必须和数值一致性风险一起评估。跨平台构建时 Fast 模式在不同 CPU 上的结果可能不同。

FloatPrecision 详解

FloatPrecision 直接影响 math.sin、math.cos、math.pow、math.log、math.exp 等内置函数的精度和性能。Low 精度在某些函数上使用查表近似，速度显著更快。

Debug 选项

启用 Debug = true 后，LLVM 禁用大部分优化（内联、向量化、常量折叠等），变量保留在栈上，支持源码级断点调试。仅用于排查问题，不要在生产代码中使用。

内存与指针属性

Burst 提供一组属性来向编译器传递别名和范围信息，帮助 LLVM 生成更优代码。

[NoAlias]

告诉编译器某个指针不与其它指针指向同一内存区域，允许更激进的加载/存储重排和向量化。

NoAlias 可用于参数、返回值和 struct 字段：

[AssumeRange]

标记整数参数或返回值的范围假设，让优化器利用此信息消除冗余分支和边界检查。

NativeArray.Length 和 NativeSlice.Length 已内置 AssumeRange(0, int.MaxValue) 标注，Burst 自动知道它们的值非负，从而消除循环中的负数检查。

[NativeDisableUnsafePtrRestriction]

默认情况下，Burst 限制在 Job 中直接使用原始指针（防止绕过安全检查）。此属性禁用该限制，允许在 Job struct 中持有 void* 或 T* 字段。

绕过安全检查意味着全靠你自己

使用 [NativeDisableUnsafePtrRestriction] 后，Burst 不再追踪指针生命周期和别名关系。悬空指针、use-after-free 等错误不会报异常，而是产生未定义行为。

常用数学函数示例

始终使用 Unity.Mathematics 而非 System.Math

函数指针

Burst 支持通过 FunctionPointer<T> 在 Burst 编译代码中调用其它 Burst 编译的静态方法，实现类似于 C 函数指针的间接调用。

基本用法

函数指针的限制

  • 目标方法必须是 static 且非泛型
  • 委托必须标注 [UnmanagedFunctionPointer(CallingConvention.Cdecl)]
  • 不支持多播委托
  • IL2CPP 构建需要 [MonoPInvokeCallback] 属性（Burst 自动添加）
  • 函数指针调用是间接调用，LLVM 无法跨调用边界内联，会阻碍部分优化

函数指针阻隔内联和向量化

函数指针是编译屏障——LLVM 无法跨间接调用做内联和向量化。如果 Job 内只有一个紧凑循环且需要极致性能，优先考虑直接内联代码而非函数指针。函数指针的价值在于运行时多态：同一个 Job 可以通过切换函数指针执行不同操作。

DisableDirectCall

默认情况下，Burst 将被标记的静态方法的调用转换为直接 native call。DisableDirectCall = true 禁用此转换，使调用走托管回退路径：

主要用于需要手动控制调用路径的场景（如仅通过 FunctionPointer<T> 间接调用）。

SIMD 自动向量化

Burst 的 LLVM 后端会自动尝试将适合的循环向量化。当向量化成功时，单条 SIMD 指令可同时处理多个数据元素（如 float4 在一条指令中处理 4 个 float）。

向量化成功的条件

  1. 循环体无分支或分支可预测：if/else 中的条件在迭代间一致时向量化效果最好
  2. 无函数指针调用：间接调用阻碍向量化
  3. 内存访问连续：array[i] 比 array[index[i]] 更容易向量化
  4. 数据类型对齐：float4 等对齐类型比标量更容易向量化
  5. 无数据依赖：循环迭代间无读写同一内存的冲突

验证向量化是否生效

Loop.ExpectNotVectorized() 用于标记故意不向量化的循环。

Loop intrinsics 是实验性功能

SharedStatic<T> 本身不提供原子操作或内存屏障。多线程并发读写同一个 SharedStatic 会产生数据竞争。如需原子操作，使用 Interlocked 或 NativeArray<int> 的 parallel writer。

左侧面板：Compile Targets 列表，显示项目中所有可被 Burst 编译的 Job 和函数指针（未标注 [BurstCompile] 的以灰色显示）。

  1. 选择左侧 Compile Target
  2. 点击 Refresh Disassembly
  3. 切换标签页查看不同阶段输出

关键诊断检查项

在 Burst Inspector 中应重点检查：

  • 向量化是否生效：Assembly 标签页中是否出现 xmm/ymm/zmm（x86）或 q/v 前缀指令（ARM NEON）
  • 循环是否展开：LLVM IR Diagnostics 中搜索 “unrolled”
  • 函数是否内联：Diagnostics 中搜索 “inlin” 查看内联决策
  • 别名假设是否正确：确认 ExpectNotAliased 验证通过

三者定位不同

Burst 不是 Unity 的主脚本后端，而是补充编译器——只编译被标记的代码。IL2CPP 是 Unity 主脚本后端，编译所有托管代码。.NET Native AOT 是 .NET 生态的 AOT 方案，Unity 6.8+ 可选 CoreCLR 模式时与之关联。性能上，Burst 在计算密集场景通常比 IL2CPP 快 10x-100x（主要因为 SIMD 向量化和 IL2CPP 本身不做激进优化），但 IL2CPP 覆盖完整 C# 语义。

反模式

把 Burst 当成"任何 C# 都能加速"

Burst 只支持 HPC# 子集。依赖托管对象、字符串、异常、虚调用、LINQ 的代码不适合 Burst。能放进 Burst 的通常是纯计算、值类型、NativeContainer、Unity.Mathematics 风格的数据处理。

用 FloatMode.Fast 破坏数值预期

物理、回放、联网同步、确定性模拟等场景需要严格浮点语义。跨平台构建时 FloatMode.Fast 在不同 CPU 上的结果可能不同。性能收益必须和数值一致性风险一起评估。

关闭安全检查来掩盖问题

DisableSafetyChecks = true 会移除一层保护。如果代码本身存在越界、竞争或生命周期错误，关闭检查只会让错误更难定位。开发期应保留安全检查，确认瓶颈后再针对性关闭。

函数指针过度使用导致向量化失败

函数指针是编译屏障，LLVM 无法跨间接调用做内联和向量化。如果 Job 内只有一个紧凑循环且需要极致性能，优先考虑直接内联代码。函数指针的真正价值在于运行时多态切换。

忽略首次编译成本

Burst 代码首次执行可能触发 JIT 编译（编辑器模式），benchmark 时要区分”编译成本”和”执行成本”。使用 CompileSynchronously = true 控制编译时机进行准确测量，但生产代码通常让 Burst 异步编译避免阻塞主线程。

在 Burst 代码中忘记优先用 math 替代 System.Math

System.Math 在 Burst 1.6+ 已被编译为 intrinsic，功能可用。但 Unity.Mathematics.math 提供更丰富的 SIMD 向量重载（float2/float3/float4），应优先使用以获得最佳向量化。

SharedStatic 委托引用泄漏或悬空

通过 Marshal.GetFunctionPointerForDelegate 获取的函数指针，底层委托如果被 GC 回收则指针悬空。必须将委托存入静态字段阻止 GC。反之，永远不释放的静态委托引用也是一种泄漏。

不用 Burst Inspector 验证就假设向量化生效

写了”看起来可以向量化”的循环并不等于 LLVM 真的做了向量化。一个条件分支、一次函数指针调用、一个非连续内存访问都可能让向量化失败。始终用 Burst Inspector 的 Assembly 和 Diagnostics 标签页验证。
