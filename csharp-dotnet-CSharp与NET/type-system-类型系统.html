C# 类型系统（C# Type System）

核心思想

C# 是强类型语言：每个变量、常量和表达式都有类型，编译器会在编译期检查操作是否合法。类型系统不仅决定语法可用性，也会影响内存语义、赋值行为、运行时派发和 Unity 中的性能表现。

C# 类型最终都处在统一的 System.Object 层级下；值类型派生自 System.ValueType，引用类型直接或间接派生自 object。这个统一层级属于 Common Type System（CTS）。

为什么重要

Unity 代码同时大量使用 C# 自定义类型和 UnityEngine 类型：MonoBehaviour、GameObject、Component 是引用语义；Vector3、Quaternion、Color 是值语义。分不清类型类别，很容易在复制、比较、传参、装箱、GC 分配和 Job/Burst 约束上踩坑。

类型系统的知识在以下场景尤其关键：

  • 选择 class 还是 struct 影响内存布局和 GC 压力
  • 泛型约束 where T : unmanaged 决定能否在 Job/Burst 中使用
  • [SerializeReference] 的多态需求受 Unity 序列化器类型限制
  • Nullable reference types 改变了 null 安全的编码约定
  • 模式匹配和类型转换影响代码可读性与运行时行为

工作原理

CTS 层次结构

所有 C# 类型都统一在 System.Object 下。值类型和引用类型在 CTS 中的派生路径不同：

Interface 不是类型层次的一部分

Interface 不参与继承链——class 和 struct 可以实现多个 interface，但 interface 不是 object 的”子类”。interface 变量引用的对象本身仍然从 object 派生。

装箱与拆箱在层次中的角色：当值类型被当作 object 或非泛型接口使用时，CLR 会在 managed heap 上创建一个”箱子”对象，把值复制进去——这就是装箱（boxing）。拆箱（unboxing）则从箱子中提取值。装箱是隐式的，拆箱是显式的：

Unity hot path 中的装箱

装箱会在 managed heap 分配对象，触发 GC 回收。在每帧执行的代码中（Update、FixedUpdate、Job 循环），应避免：

  • 把值类型传入 object 参数（如 Debug.Log 的字符串拼接）
  • 使用非泛型集合（ArrayList、Hashtable）
  • 把 enum 当作 IComparable 参数传递
  • 值类型调用虚方法（如 ToString()、Equals(object)）——用泛型版本替代

大小说明

值类型的大小是 sizeof(T) 的结果。引用类型变量本身在 64 位进程上占 8 字节（引用指针），对象在 heap 上的实际大小取决于字段布局。nint / nuint（C# 9+）是平台相关整数，32 位进程 4 字节，64 位进程 8 字节。

Unity 游戏开发中的内置类型选择

  • 坐标和角度用 float（与 Vector3、Quaternion 一致），不用 double
  • 金额、精确计数考虑 decimal，但 Unity 序列化器不支持——改用 long（分为单位）
  • string 是不可变引用类型，频繁拼接会产生 GC 压力；用 StringBuilder 或 Unity.Collections.NativeText
  • bool 在 Unity Inspector 中显示为勾选框，但 bool? 不被序列化

class — 行为与身份

适合：需要 Unity 生命周期、Inspector 挂载、场景对象身份、多态行为的场景。

struct — 轻量值数据

适合：小型、不可变、值语义的数据——数学值、事件数据、配置参数。详见 值类型 vs 引用类型。

record — 不可变数据与 with 表达式

详见下方”Records 在游戏开发中的应用”章节。

interface — 能力契约

适合：跨不相关类型表达能力、解耦依赖、测试替身。

enum — 具名常量

enum 滥用

enum 适合简单的有限状态标记。但以下情况应考虑替代方案：

  • 需要附加数据 → 用 record 或 类型对象 模式
  • 需要运行时扩展 → 用 interface 或策略模式
  • 需要组合标志 → 用 [Flags] enum，但注意序列化兼容性
  • 状态逻辑复杂 → 用 状态模式 或 FSM 库

delegate — 类型安全回调

适合：回调、事件订阅、策略模式。游戏开发中常用 System.Action<T> 和 System.Func<T> 代替自定义委托。

编译时类型与运行时类型

变量的编译时类型决定可调用成员、重载解析和隐式转换；运行时类型决定虚方法派发、is 模式匹配和 switch 表达式结果。

兼容 Unity 6.4 及以上。Unity 2022 LTS 同样适用，API 一致。

var vs object vs dynamic

关键字编译时类型运行时类型检查适用场景
var编译器推断，强类型编译时局部变量，类型显而易见时减少冗余
objectSystem.Object编译时 + 运行时 cast统一存储、泛型约束
dynamic编译时绕过运行时（DLR）COM 互操作、反射、脚本绑定

Unity 中避免使用 dynamic

dynamic 依赖 DLR（Dynamic Language Runtime），在 IL2CPP 和 AOT 构建中不受完整支持。Unity 游戏应使用 interface、泛型或模式匹配替代 dynamic。详见 .NET Native AOT。

模式匹配与类型检查

C# 7+ 的模式匹配让编译时/运行时类型的交互更简洁：

协变与逆变

泛型类型参数的**协变（covariance，out）和逆变（contravariance，in）**让编译时类型之间的赋值更具弹性：

Unity 中的协变/逆变

  • IEnumerable<out T> 的协变意味着 List<Enemy> 可以传给 IEnumerable<Component> 参数——只要元素类型有继承关系
  • IComparer<in T> 的逆变意味着 IComparer<object> 可以比较 string——比较器接受更宽泛的类型
  • List<T> 本身不支持协变（它是 class，不是 interface），只有 IEnumerable<out T>、IReadOnlyList<out T> 等接口支持

对 Unity 序列化与 Inspector 的影响

编译时类型决定 Unity Inspector 如何显示字段：

  • public int health — Inspector 显示数字输入框
  • public EnemyState state — Inspector 显示下拉菜单
  • public List<int> ids — Inspector 显示可展开列表
  • public object data — Inspector 不显示（object 不是可序列化类型）
  • public IDamageable target — Inspector 不显示（interface 不是可序列化类型），除非用 [SerializeReference]

详见下方”Unity 特定类型考量”章节。

值类型与引用类型

所有类型不是值类型就是引用类型。这个分界是 C# 性能模型的第一层，详见 值类型 vs 引用类型（Value Types vs Reference Types）。

Nullable 类型

Nullable 值类型（T?）

T?（Nullable<T>）让值类型可以表达”无值”状态：

Nullable 值类型的大小

T? 的大小是 sizeof(T) + 1（额外 1 字节存储 HasValue 标志）。在 Unity 序列化中，int? 不被直接支持——需拆成 int + bool 两个字段，或用自定义序列化。

Nullable 引用类型（C# 8+）

C# 8 引入可空引用类型（Nullable Reference Types，NRT），这是编译时静态分析特性，不是运行时特性：

null 状态分析：编译器追踪每个引用变量的 null 状态（not-null / maybe-null），在可能解引用 null 时发出警告。关键规则：

  • string 参数默认”非空”——传 null 会产生警告
  • string? 参数”可空”——使用前必须检查
  • 返回值同理：string 承诺非 null，string? 可能返回 null

Unity 与 Nullable Reference Types

  • Unity 2022.2+ 开始逐步在核心 API 上标注 NRT，但大量旧 API 仍缺少标注
  • [SerializeField] private string name; 在 NRT 启用时技术上应为 string?——Unity 序列化器可能赋 null，但编译器认为它非空
  • 建议在 .csproj 中启用 <Nullable>enable</Nullable>，对 MonoBehaviour 序列化字段使用 string? 或在 OnValidate 中断言非 null
  • T? 对值类型和引用类型的语义不同：int? 是 Nullable<int>（有额外 HasValue 字段），string? 仍是 string（仅编译时标注）

泛型与类型系统

泛型让类型成为参数，实现类型安全的代码复用。在游戏开发中，泛型是集合、工厂、对象池和组件系统的基础。

约束顺序规则

约束必须按以下顺序排列：主约束（class/struct/unmanaged/基类）→ 接口约束 → new()。 struct 已隐含无参构造函数，不需要再加 new()。

unmanaged 约束详解

unmanaged 约束要求 T 是不含任何引用类型字段的值类型——这对 Job/Burst 至关重要：

开放类型与封闭类型

  • 开放类型（open type）：包含未指定的类型参数，如 List<>、Dictionary<,>
  • 封闭类型（closed/constructed type）：所有类型参数已指定，如 List<int>

typeof 与反射

反射与 IL2CPP

Unity IL2CPP 构建对反射有限制。MakeGenericType 和 MakeGenericMethod 在 AOT 构建中可能失败，因为编译时必须已知所有封闭类型。使用 [Preserve] attribute 或 link.xml 防止类型被裁剪。详见 .NET Native AOT。

Record 与 Unity 序列化

Unity 序列化器不识别 record 关键字——[SerializeField] 对 record 字段的行为与普通 class/struct 一致，但：

  • with 表达式生成的 clone 方法不参与序列化
  • record 的主构造函数参数不会自动被序列化
  • record struct 可以标 [Serializable]，但 init 属性在反序列化时可能出问题
  • 建议：需要序列化的数据用普通 struct + [Serializable]，仅运行时不可变数据用 record

MonoBehaviour 字段必须是可序列化类型

一个 MonoBehaviour 的 [SerializeField] 字段如果不是可序列化类型，Unity 会静默忽略它——不会报错，但 Inspector 中不会显示，数据也不会保存。

[SerializeReference] 与多态

默认情况下，Unity 序列化器按值序列化 plain C# 对象（嵌入式），按引用序列化 UnityEngine.Object 派生类。这导致一个问题：

[SerializeReference]（Unity 2019.3+）解决此问题——它按引用序列化 plain C# 对象，并保存类型信息：

[SerializeReference] 的限制：

  • 类型必须有 [Serializable] attribute
  • 不支持 UnityEngine.Object 派生类（它们默认按引用序列化）
  • 不支持 Dictionary、多维数组等非可序列化容器
  • Unity 6+ 会验证类型层次中所有祖先都有 [Serializable]

unmanaged 约束的形式化定义：类型是值类型，且其所有字段（递归）都不是引用类型。

检查类型是否 unmanaged

NativeArray 的类型要求

NativeContainer 的泛型参数 T 必须满足 unmanaged 约束。这意味着：

  • 内置数值类型（int、float、double 等）✓
  • bool、char ✓
  • 仅包含值类型字段的自定义 struct ✓
  • enum ✓
  • string、class、接口 ✗
  • 包含引用类型字段（string、List<T> 等）的 struct ✗

权衡与选择

  • 需要 Unity 生命周期、Inspector 挂载、场景对象身份 → MonoBehaviour / class
  • 需要轻量不可变数据、数学值、事件数据 → struct 或 readonly struct
  • 需要不可变数据 + with 表达式 + 值相等 → record class 或 record struct
  • 需要跨不相关类型表达能力 → interface
  • 需要类型安全复用容器或算法 → generics
  • 需要在 Job/Burst 中传递数据 → unmanaged struct + NativeContainer
  • 需要序列化多态引用 → [SerializeReference] + [Serializable]
  • 高频路径避免不必要装箱、闭包和临时集合，相关见 .NET GC 与托管内存
