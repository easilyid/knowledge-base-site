值类型 vs 引用类型（Value Types vs Reference Types）

是什么

值类型变量直接包含数据，赋值、传参和返回结果时默认复制值本身。引用类型变量包含对象引用，赋值时复制引用，多个变量会指向同一个 managed heap 对象。

这不是语法细节，而是 C# 内存语义的核心分界。所有 C# 类型最终都处在 System.Object 层级下：值类型派生自 System.ValueType（enum 再派生自 System.Enum），引用类型直接或间接派生自 object。这个统一层级属于 Common Type System（CTS）。

内存布局

值类型的存储位置

值类型的存储位置取决于声明上下文，而非类型本身：

  • 方法内的局部变量 → 栈
  • 引用类型的实例字段 → 随对象在 managed heap
  • 值类型的实例字段 → 内联在包含类型中（无额外间接层）
  • NativeArray<T> / NativeList<T> 等容器元素 → native 内存
  • ref struct → 强制栈分配，不允许逃逸到堆

引用类型的内存开销

每个 managed heap 对象都有额外开销：

  • Sync Block（4 字节）：存储在对象偏移 -4/-8 处，用于锁、哈希码、AppDomain 索引
  • Method Table Pointer（4/8 字节）：指向类型的 MethodTable，用于虚方法派发、类型判断
  • 实例字段：按 LayoutKind.Auto 自动排列（编译器可重排以减少 padding）

因此一个空 class 实例在 x64 上至少占 24 字节（sync block + method table pointer + 最小对齐），而空 struct 占 1 字节。

值类型数组的连续性

值类型数组是内联的：数组元素就是实际数据，紧密排列。引用类型数组只存引用指针，实际对象分散在堆上。这直接影响缓存命中率——值类型数组的空间局部性远优于引用类型数组。

"值类型在栈上"是简化说法

准确地说，值类型实例存储在声明它的变量所在的上下文中。作为 class 字段时随对象在堆上，作为 struct 字段时内联在 struct 中。ref struct 是唯一强制栈分配的值类型。

enum

枚举是值类型，底层是整数。但 Enum.HasFlag() 会导致装箱——因为 HasFlag 接受 Enum 参数：

Enum.HasFlag() 在热代码路径中会装箱

nullable 值类型

int? 等价于 Nullable<int>，是值类型。它在底层是两个字的 struct（hasValue + value），不会装箱为引用类型。但将 int? 赋值给 object 时会按 Nullable 整体装箱（或拆箱为 null 时返回 null），行为与普通值类型装箱略有不同。

ValueTuple

(int, float) 等元组语法是 ValueTuple<int, float> 的语法糖，是值类型。但 ValueTuple 使用 LayoutKind.Auto，内存布局不可预测，不能用于 P/Invoke 或跨进程序列化。

Inline array 是 struct，分配在栈或内联在包含类型中，零堆分配。它不能与 record struct 同时使用。

引用类型深度

class

引用类型的主体。赋值复制引用，不复制对象：

每个 class 实例在 x64 上至少占 24 字节（sync block index 4B + method table pointer 8B + 最小对齐到 24B。仅 header 部分就占 16B，加上字段和对齐规则，CoreCLR 的最小托管对象大小为 24B）。

interface

interface 变量是引用。当值类型被赋给 interface 变量时会装箱：

泛型接口约束可避免此装箱：

delegate

delegate 是引用类型，持有方法引用和目标对象。在 Unity 中，delegate 常用于事件系统，但频繁创建 lambda 会产生闭包分配（captured variable 被包装为 class）。

array

数组是引用类型，但元素是内联的：int[] 的 int 值连续存储在数组对象内部，不是单独的 boxed int。struct[] 的 struct 也是内联的，这是值类型数组缓存友好的原因。

string 内部机制

string 是不可变引用类型，内部是 char[] 连续存储。字符串拼接会创建新 string 对象。C# 10 引入的 InterpolatedStringHandler 机制让 $"{x}" 可以避免中间 string 分配——DefaultInterpolatedStringHandler 是值类型，在栈上构建结果。

值类型中包含引用字段

struct 内部包含引用类型字段时，复制 struct 只复制引用字段的引用，不复制引用对象本身。两个 struct 副本共享内部对象：

这种”外层复制、内层共享”的混合语义是 bug 的温床。

值类型中的可变引用字段制造混合语义

struct 应该要么完全不包含引用字段（unmanaged struct），要么引用字段指向不可变对象（如 string）。包含可变引用的 struct 违背了值类型的”独立副本”语义。

在 Unity DOTS 中，IComponentData 要求 unmanaged struct（不含引用字段），这正是为了避免混合语义和保证 Burst 兼容。

装箱与拆箱

机制

当值类型被当作 object 或非泛型接口使用时，运行时会在堆上分配一个”盒子”对象，把值复制进去。拆箱是从盒子中提取值的操作：

分配分析

一次装箱操作的开销：

  1. 堆分配：至少 16 字节（x64 上 sync block + method table pointer）+ 值本身大小
  2. 复制：值从栈复制到堆
  3. GC 追踪：新对象纳入 GC 管理，增加 gen0 扫描成本
  4. 缓存失配：堆对象地址不可预测，访问时可能 cache miss

Unity 中的装箱影响

在 Mono 运行时中，装箱分配由 Boehm GC 管理；在 IL2CPP 中，装箱同样产生 managed heap 分配。IL2CPP 的装箱实现涉及额外的类型检查开销——Object::UnBox 需要读取 obj->klass->element_class 进行类型校验，可能造成 cache miss。

Vector3 复制与性能

Unity 的 Vector3、Quaternion、Color 等都是 12-16 字节的 struct。日常赋值和传参会复制，但因为体积小，复制成本可忽略。但在百万级粒子/实体的循环中，应考虑 ref 传递：

NativeArray 是 struct

NativeArray<T> 是 struct，但它的数据在 native 内存中。复制 NativeArray<T> 只复制”句柄”（指针 + 长度 + allocator），不复制底层数据。两个副本共享同一块 native 内存：

NativeArray 复制后共享底层内存

这是一种特殊的混合语义：struct 复制了句柄，但句柄指向同一块 native 内存。必须通过 Allocator 生命周期管理来避免 use-after-free。Dispose 一次后，所有副本都失效。

NativeSlice

NativeSlice<T> 也是 struct，是对 NativeArray<T> 某段的视图，不拥有内存。适合在 Job 中传递数组子范围，无需分配新容器。

FixedString 系列

FixedString32Bytes、FixedString64Bytes、FixedString128Bytes 等是 Unity Collections 包中的 fixed-size struct，用于替代 string 以避免 GC 分配。内部是固定大小的 byte 数组，UTF-8 编码，Burst 兼容：

BlobAssetReference

BlobAssetReference<T> 是 struct，指向不可变的 blob 数据。Blob 数据只含值类型（BlobArray、BlobPtr、BlobString），存放在连续 native 内存中，Burst 兼容，可安全并行读取：

Blob asset 的不可变性 + 纯值类型 + 连续内存，使其成为 DOTS 运行时只读数据的首选方案。

DOTS 中的值类型要求

IComponentData、ISharedComponentData、IBufferElementData 都要求 unmanaged struct：

  • 不含任何引用类型字段
  • 不含 ref struct 字段
  • 可通过 where T : unmanaged 约束验证

这确保了数据可被 Burst 编译、可在 Job 中安全传递、无需 GC 参与。

Span 在 Unity 中的使用

Burst 编译器支持 Span<T> 和 ReadOnlySpan<T>，但有限制：

  • 只能在 Burst job 或 function pointer 内部使用
  • 不能跨越 managed/Burst 边界传递（因为 Span 可能指向 managed 数组）
  • 启用 Safety Checks 时有越界检测，Release 构建无此开销

struct 布局与 Burst

Burst 对 struct 布局敏感。使用 StructLayout 控制字段排列可以提升 SIMD 向量化效果：

struct 布局优化建议

  • 默认使用 LayoutKind.Sequential，Burst 能更好地推理内存访问模式
  • 包含引用字段时布局会自动变为 LayoutKind.Auto，字段顺序不可控
  • DOTS 组件中保持 16/32/64 字节对齐，有助于 SIMD 和缓存行对齐
  • 用 Unsafe.SizeOf<T>() 验证实际大小

大 struct 性能分析

复制成本

值类型每次赋值、传参、返回都会复制。struct 越大，复制成本越高。16 字节以下的 struct 复制成本可忽略（2-3 条 CPU 指令）；64 字节以上应考虑 ref / in 传递；128 字节以上必须用引用语义。

缓存局部性

值类型数组的优势在于连续内存布局。一个 Particle[]（每个 32 字节），16 KB 缓存行可容纳 512 个粒子。等效的 Particle class 数组只有引用指针连续，实际对象分散在堆上。

容器类型缓存行命中率GC 压力
struct[]高（连续内存）无（元素无独立对象）
class[]低（指针间接）高（每个元素都是堆对象）
NativeArray<struct>最高（无对象头开销）无（native 内存）

反模式

反模式 1：可变 struct

可变 struct 在属性返回、集合元素访问、接口调用中会产生”改了副本”的 bug。readonly struct 或 record struct 可避免此问题。Unity 历史上的 Rect、Bounds 等可变 struct 就是典型陷阱。

反模式 2：过大的 struct

超过 64 字节的 struct 应优先考虑 class 或 ref / in 传递。盲目用 struct 替代 class 反而因复制成本降低性能。微软官方指南建议 struct 不超过 16 字节。

反模式 3：struct 中的可变引用字段

包含 List<T>、T[] 等可变引用的 struct 会产生”外层值语义、内层引用语义”的混合行为。两个副本修改同一个引用对象，导致难以追踪的共享状态 bug。

反模式 4：热路径中的装箱

Enum.HasFlag()、非泛型接口调用、params object[]、旧式 ArrayList 等场景在每帧调用时会产生大量 GC 分配。用泛型、位运算、Span<T> 替代。Unity Profiler 的 GC Alloc 列可快速定位装箱热点。

反模式 5：struct 作为字典键但不重写 GetHashCode

默认的 ValueType.GetHashCode() 使用反射，极慢。作为字典键的 struct 必须实现 IEquatable<T> 并重写 GetHashCode，或直接使用 record struct（编译器自动生成高效实现）。

反模式 6：struct 实现接口后通过接口调用

struct 实现接口后，通过接口变量调用方法会触发装箱。如果必须用接口抽象，应使用泛型约束 where T : IMyInterface 保持值类型调用路径。

反模式 7：struct 构造函数未初始化所有字段

C# 要求 struct 在使用前所有字段必须被赋值。构造函数中遗漏字段会导致编译错误或未定义行为。record struct 的主构造函数语法可避免此问题。

反模式 8：在 async 方法中使用 ref struct

Span<T> 等 ref struct 不能跨 await 使用。需要跨异步边界传递时，用 Memory<T>（非 ref struct，可装箱）替代 Span<T>，在异步回调内再转回 Span<T>。

权衡与选择

维度值类型 (struct)引用类型 (class)
赋值语义复制值复制引用
内存位置栈 / 内联managed heap
对象开销无16+ 字节 (x64)
数组局部性连续内存指针间接
GC 压力无（除非装箱）有
继承不支持支持
多态不支持（装箱后支持）支持
复制成本与大小成正比固定（一个指针）
线程安全天然隔离（独立副本）需要同步
Identity按值相等按引用相等

选择原则：

  • 小型（⇐ 16 字节）、不可变、无身份的数据 → 值类型
  • 需要共享身份、继承、多态、复杂生命周期 → 引用类型
  • 值类型过大时复制成本会上升，不适合盲目替代 class
  • 可变 struct 应谨慎，尤其在属性返回、集合元素访问和接口调用中
  • Unity DOTS 组件强制 unmanaged struct，确保 Burst 兼容和无 GC
