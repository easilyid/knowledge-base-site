.NET 托管执行流程（Managed Execution）

核心思想

.NET 托管执行通常经历：源代码由语言编译器编译为 CIL 和 metadata，运行前或运行时再把 CIL 转为目标平台 native code，最后由 CLR 提供 GC、安全、互操作、调试和版本管理等服务。

Unity C# 代码也绕不开”C# → IL/CIL → 执行后端”的链路，但执行后端可能是 Mono JIT、IL2CPP AOT、Burst LLVM 或即将引入的 CoreCLR——每一条路径都有不同的限制和性能特征。

为什么重要

理解托管执行流程，是理解以下问题的前提：

  • AOT 限制从何而来？为什么 IL2CPP 不支持 System.Reflection.Emit？
  • 泛型在 IL2CPP 下为什么膨胀？为什么引用类型参数可以共享实现，值类型参数不行？
  • JIT 优化了什么？为什么 Burst 编译的代码比 Mono JIT 快一个数量级？
  • Domain Reload 为什么慢？CoreCLR 迁移如何解决？
  • P/Invoke 的开销在哪里？什么是 blittable 类型？

Roslyn 编译阶段

C# 编译器（Roslyn）将源码编译为 Common Intermediate Language（CIL），同时生成 metadata。一个编译单元的输出是 assembly（.dll 或 .exe）。

PE 文件结构

.NET assembly 采用 PE/COFF（Portable Executable）格式，内部结构：

区域内容
PE HeaderCOFF 头 + 可选头，标识文件类型
CLI Header.NET 特有，指向 metadata 和 CIL
CIL 部分方法的 IL 指令流（方法体）
Metadata类型表、方法表、字段表、成员签名、引用表等
Manifest程序集级别信息：名称、版本、公钥、文化、文件列表、引用程序集
Resources嵌入资源（.resources）

Manifest 是程序集的”身份证”，包含：程序集名称、版本号（AssemblyVersion）、公钥令牌（强命名时）、文化信息、文件哈希列表、引用的其他程序集列表。

Metadata 表

Metadata 由一系列表组成，核心表包括：

表名内容
TypeDef当前程序集定义的类型
MethodDef方法定义（含 RVA 指向 CIL 体）
FieldDef字段定义
MemberRef引用其他程序集的成员
TypeRef引用其他程序集的类型
AssemblyRef引用的其他程序集
CustomAttribute自定义特性

Metadata 中的每个条目有一个 token（4 字节：高字节是表编号，低 3 字节是行号），CIL 指令通过 token 引用类型、方法、字段。

Unity 中的 assembly 结构

Unity 游戏的主代码编译为 Assembly-CSharp.dll，此外每个 package 和 assembly definition 生成独立的 .dll。Editor 状态下还有 Assembly-CSharp-Editor.dll。所有这些 DLL 最终在 Player build 中由 IL2CPP 或 Mono 处理。

2. CIL 指令集：基于栈的虚拟机

栈式计算模型

CIL 是基于评估栈（evaluation stack）的指令集：指令不从寄存器取操作数，而是从栈顶弹出、压入结果。每个方法头声明 .maxstack（最大栈深度），CLR 在 JIT 时据此分配栈帧空间。

常用 CIL 指令

类别指令作用
局部变量ldloc.n / stloc.n加载/存储局部变量
参数ldarg.n / starg.n加载/存储参数
对象模型newobj分配新对象并调用构造函数
方法调用call / callvirt直接调用 / 虚方法调用（含 null 检查）
字段ldfld / stfld / ldsfld / stsfld实例/静态字段读写
类型转换castclass / isinst强制转换 / as 运算符
分支br / brtrue / brfalse / beq无条件/条件跳转
返回ret返回

装箱与拆箱的 CIL 视角

  • box 指令：分配托管堆对象，复制值类型数据到堆，返回对象引用。
  • unbox 指令：返回指向堆对象中数据部分的托管指针（不复制）。
  • unbox.any 指令：返回值类型的副本（复制语义）。

拆箱后赋值的隐藏分配

unbox 本身不分配内存（只返回指针），但 unbox.any 会复制值。更重要的是，box 每次都会在托管堆分配一个新对象。这就是 值类型 vs 引用类型 中装箱分配的来源。

方法描述符表

CIL 中通过 metadata token 引用方法：callvirt 0x06000003 表示调用 MethodDef 表第 3 行。JIT 在编译时会将 token 解析为 MethodDesc（方法描述符），包含：方法槽位、入口点地址（JIT 编译后更新）、签名、所属类型。

3. JIT 编译详解

分层编译（Tiered Compilation）

.NET Core 2.1+ 默认启用分层编译，方法首次调用时快速编译，反复调用后重新优化编译：

关键阈值：方法被调用约 30 次后，Tier0 代码触发插桩；插桩收集足够数据后晋升为 Tier1。

Unity Mono 的 JIT

Unity 使用自定义 Mono fork，不支持 .NET 的分层编译和 Dynamic PGO。Mono JIT 只做单次编译，优化程度远低于 RyuJIT Tier1。这也是 Burst 性能远超 Mono JIT 的原因之一。

ReadyToRun（R2R）

ReadyToRun 是 .NET 的 AOT 预编译形式，在发布时用 crossgen2 工具将 IL 预编译为 native code，避免运行时 JIT 开销：

  • 预编译的方法在 PE 文件中标记 JIT_FLAG_AOT
  • 首次加载时跳过 JIT，直接使用预编译的 native code
  • 热方法仍可在运行时被 Tier1 JIT 代码替换（通过 patchpoint），获得更好的优化

RyuJIT 优化

RyuJIT 是 .NET 的主力 JIT 编译器（.NET Core 以来替代旧的 JIT32/JIT64），主要优化包括：

优化说明
内联（Inlining）小方法体直接嵌入调用点，消除调用开销。[MethodImpl(MethodImplOptions.AggressiveInlining)] 强制提示
守护式去虚化（GDV）对虚方法调用，JIT 生成类型检查 + 快速路径。若实际类型匹配 profile，走内联快速路径；否则回退虚调用
范围检查消除对 for (int i = 0; i < arr.Length; i++)，证明 i 在范围内后消除 arr[i] 的边界检查
循环提升（Loop Hoisting）将循环不变的计算移到循环外
常量折叠编译期计算常量表达式
SSA / 值编号静态单赋值形式上的全局优化

Burst vs RyuJIT 的优化差异

Burst 基于 LLVM，可以做跨过程优化、自动 SIMD 向量化、循环展开等更激进的变换。RyuJIT 的优化受限于 JIT 时间预算（编译越快，优化越少），且只优化单个方法。详见 Burst 编译器（Burst Compiler）。

4. CLR 运行时服务

类型系统：MethodTable 与 EEClass

CLR 内部用两个核心数据结构表示类型：

结构角色内容位置
MethodTable”热”数据虚方法调度表、实例大小、GC 信息、接口映射、静态字段指针GC 堆对象头部指向它
EEClass”冷”数据方法列表、字段列表、父类/接口链、类初始化状态、元数据 token仅 CLR 内部使用
  • 大多数类型 MethodTable 与 EEClass 是 1:1 的
  • 泛型实例化（如 List<int> 和 List<string>）共享同一个 EEClass，但各自有独立的 MethodTable（因为实例大小和 GC 布局不同）
  • TypeHandle 是对 MethodTable 指针的抽象，是 CLR 类型系统的核心句柄

GC 堆对象如何找到类型

每个 GC 堆上的对象头部（SyncBlock 之后的 4/8 字节）存储 MethodTable 指针。obj.GetType() 实际上就是读取这个指针，再包装为 System.RuntimeType。

线程池

.NET 线程池由 PortableThreadPool 实现，包含两类线程：

  • Worker 线程：执行 Task.Run、ThreadPool.QueueUserWorkItem 等工作项
  • I/O 完成端口线程：处理异步 I/O 完成通知

线程池根据 CPU 利用率动态调整线程数：当所有 worker 线程都在忙，且存在排队工作项时，会按约 1 秒间隔注入新线程（避免线程数暴增）。可配置上下限：

Unity 中不要手动调 ThreadPool

Unity 的主线程不是 ThreadPool 线程，async/await 的 continuation 通过 UnitySynchronizationContext 回到主线程，不走 ThreadPool。Burst Job 也不走 ThreadPool。手动调 SetMinThreads 可能干扰 Unity 内部调度。

异常处理

  • Windows 上基于 SEH（Structured Exception Handling）
  • Linux/macOS 上基于 DWARF 表格（零开销展开）
  • CLR 异常处理是两阶段过程：第一阶段搜索匹配的 catch 子句，第二阶段展开栈并执行 finally

5. Unity 执行后端

Unity 支持四种执行后端，它们在”C# → IL → 执行”链路的不同位置做了不同选择：

Unity 6.8 的 CoreCLR 迁移

根据 Unity 2025 Unite 大会公布的路线图，Unity 6.8（预计 2026 年）将用 CoreCLR 替换 Mono 作为默认运行时。核心变化：RyuJIT 替代 Mono JIT、分代精确 GC 替代 Boehm、AssemblyLoadContext 替代 Domain Reload。Unity 6.7 的桌面 Player 已实验性支持 CoreCLR。

6. IL2CPP 深入

AOT 管线

IL2CPP 的编译路径：

IL2CPP 不是解释器——它把 IL 转译为 C++ 代码，再由平台编译器编译为原生二进制。生成的 C++ 代码不是给人读的，但结构上与原始 IL 一一对应。

核心 C++ 结构

IL2CPP 运行时定义了以下核心结构（简化）：

Il2CppObject 头部开销

每个托管对象都有 klass + monitor 两个指针的开销（16 字节 / 64-bit）。这意味着即使一个空的 class Empty {} 实例也占 16 字节。这与 值类型 vs 引用类型 的内存布局直接相关。

泛型特化

IL2CPP 对泛型的处理方式取决于类型参数：

类型参数代码生成策略原因
引用类型（List<string>, List<Enemy>）共享同一份实现所有引用大小相同（IntPtr.Size），内存布局一致
值类型（List<int>, List<Vector3>）每个值类型生成特化版本大小和布局不同，无法共享

IL2CPP 泛型代码膨胀

使用大量不同值类型参数的泛型（如 List<int>、List<float>、List<Vector3>、List<Quaternion> …）会导致二进制体积膨胀。Unity 的 “Optimize for code size” 设置会生成一个”fully-sharable”版本（所有值类型参数共享），但运行时性能更差（需要间接访问和装箱）。

元数据注册

IL2CPP 运行时需要 metadata 来支持反射。构建时生成：

  • global-metadata.dat：包含所有 IL metadata 的序列化文件（类型、方法、字段、字符串等）
  • Il2CppMetadataRegistration：注册所有 metadata 使用点
  • Il2CppCodeRegistration：注册所有生成的函数指针

7. 程序集加载

AssemblyLoadContext

.NET Core 引入 AssemblyLoadContext（ALC）替代 .NET Framework 的 AppDomain，作为程序集的加载和隔离边界：

ALC 类型可卸载用途
Default否主应用域，加载核心程序集
Custom（collectible）是插件系统、热重载——卸载 ALC 可释放所有关联程序集
Custom（non-collectible）否隔离加载但不支持卸载

卸载过程分两阶段：

  1. 调用 Unload() 标记 ALC 为”待卸载”，阻止新加载
  2. 下一次 GC 时，扫描所有引用——若 ALC 中的所有对象都不可达，则回收内存

ALC 卸载泄漏

如果 ALC 外部的代码仍持有 ALC 内部对象的引用（如静态事件订阅、缓存引用），ALC 将无法卸载。常见于插件系统的静态事件忘记取消订阅。

Assembly.Load vs LoadFrom

方法加载上下文适用
Assembly.Load(name)Default ALC加载已知的强命名程序集
Assembly.LoadFrom(path)Default ALC + 路径跟踪从文件加载，自动解析依赖
ALC.LoadFromAssemblyPath(path)指定 ALC插件隔离加载

9. 安全与验证

类型安全验证（Verification）

CLR 在加载 CIL 时会对方法体执行验证（verification），确保代码不会违反类型安全。验证检查包括：

  • 局部变量和参数的类型与 CIL 指令的栈操作一致
  • 跳转目标不会绕过类型检查
  • 对 box / unbox 的使用与声明类型匹配
  • 数组访问的类型正确

验证通过的代码称为 verifiable（可验证的），可以在安全沙箱中执行。未通过验证但仍然合法的代码（如使用 unsafe 指针）称为 valid but not verifiable——CLR 允许执行，但需要完全信任（full trust）权限。

Unity 代码默认 full trust

Unity Player 运行在 full trust 环境下，不受验证限制。但 Editor 工具如果以沙箱模式加载第三方程序集，可能触发验证失败。

代码访问安全（CAS）的消亡

.NET Framework 曾经有代码访问安全（Code Access Security, CAS）机制，根据程序集的来源（本地 / 网络 / Internet）赋予不同权限。.NET Core / .NET 5+ 已完全移除 CAS：

  • SecurityException、PermissionSet、Deny / Assert / PermitOnly 等 API 标记为过时或直接移除
  • SecurityTransparent / SecurityCritical / SafeCritical 属性在 .NET Core 中被忽略
  • 沙箱场景改为使用操作系统级隔离（容器、AppContainer）而非 CLR 级权限

不要在 .NET 5+ / Unity 中使用 CAS API

[assembly: SecurityTransparent]、[SecurityCritical]、PermissionSet 等在 CoreCLR 中无效。如果代码依赖 CAS 做安全隔离，必须迁移到 OS 级隔离方案。

unsafe 代码与指针

C# 的 unsafe 上下文允许直接操作指针和内存，绕过 CLR 的类型安全保证：

unsafe 代码的限制与代价：

维度影响
类型安全绕过验证——方法体变为 valid but not verifiable
GC交互fixed 钉住对象，阻止 GC 移动，导致碎片化（详见 .NET GC 与托管内存）
可移植性指针大小和布局依赖平台（32-bit vs 64-bit）
安全性越界写入、野指针、use-after-free 可导致 native crash
IL2CPP 兼容unsafe 在 IL2CPP 中完全支持——生成的 C++ 本身就是 unsafe 的

unsafe 不等于高性能

unsafe 本身不加速代码——它只是绕过了安全检查。性能提升来源于消除了边界检查和间接访问，但如果安全代码已经足够快（如 JIT 消除了范围检查），unsafe 带来的提升可能微不足道。优先用 Span<T> / MemoryMarshal 等安全抽象，仅在 profiler 确认瓶颈后才考虑 unsafe。

Unity Burst 中优先用 unsafe 而非托管引用

Burst 编译的 Job 中，unsafe 指针操作是惯用模式——Burst 不会在运行时做边界检查，且指针操作可被 LLVM 充分优化。ref return 和 NativeArray 是更安全的选择，但在极端性能场景下 unsafe 指针无可替代。

Span 与 Memory：安全的不安全抽象

Span<T> 和 Memory<T> 提供了对连续内存的安全访问，无需 unsafe 关键字：

Span<T> 是 ref struct，只能存在于栈上——不能作为类字段、不能装箱、不能在 async 方法中跨 await 使用。Memory<T> 是其堆安全版本，可在需要跨栈帧时使用。

11. 反模式

假设 JIT 总是可用

IL2CPP / Native AOT 不支持运行时代码生成

System.Reflection.Emit、Expression.Compile()、dynamic 关键字在 AOT 后端不可用。如果依赖这些特性的库没有提供 AOT 兼容模式，它无法在 IL2CPP 构建中使用。

热路径使用重反射

反射在热路径中的成本

MethodInfo.Invoke 每次调用需要：参数装箱、访问检查、栈帧分配、间接调用。比直接调用慢 10-100 倍。如果必须在运行时分发，缓存委托或使用源码生成器代替。

AOT 构建中动态加载程序集

AOT 构建不支持运行时加载

IL2CPP 在构建时已经把所有 IL 编译为 C++ 并链接到 Player。运行时没有 JIT 编译器来处理新的 IL。需要动态加载内容的场景应使用 Addressables / AssetBundle（加载的是资源，不是代码）。

IL2CPP 泛型过度特化

值类型泛型组合爆炸

评估泛型类型参数的组合数。如果值类型参数种类多且泛型嵌套深，考虑：用引用类型包装、使用接口多态代替泛型、或开启 “Optimize for code size”（牺牲运行时性能）。

不处理 Domain Reload 的静态状态

关闭 Domain Reload 后必须手动管理静态状态

如果在 Project Settings 中关闭了 “Reload Domain”，静态变量和事件订阅在退出 Play Mode 后不会被重置。必须用 [RuntimeInitializeOnLoadMethod] 做手动清理。

混用 Mono / IL2CPP 假设

不要假设类型名和反射行为在所有后端上一致

IL2CPP 的 metadata 表示与 Mono 有差异。Type.GetType 的字符串格式、泛型类型名称、嵌套类型的命名可能不同。优先使用 typeof(T) 而非字符串查找。
