Dispose 模式（Dispose Pattern）

核心思想

IDisposable.Dispose 用来确定性释放 GC 不负责的资源，例如 unmanaged memory、文件句柄、管道、wait handle、native handle，或由对象拥有的其他 IDisposable 成员。

Dispose 不是”手动释放普通 C# 对象内存”；普通 managed object 的内存仍由 GC 回收。Dispose 的本质是把资源生命周期从 GC 的不确定性中抽离出来，让程序员决定何时释放。

为什么重要

Unity 中许多高性能资源都有明确生命周期：NativeArray、NativeList、Job 临时内存、文件流、网络流、编辑器资源句柄等。如果只依赖 GC，外部资源可能长时间不释放，甚至触发 leak 检测或运行时错误。更关键的是，Unity 的很多 native 资源（GPU buffer、render texture）没有 finalizer 兜底——忘了 Dispose 就是真泄漏。

Dispose(bool) 语义详解

Dispose(bool disposing) 是整个模式的核心分发点。理解 disposing 参数的含义是正确实现 Dispose 的关键。

场景disposing可安全操作的范围
用户代码调用 Dispose()true托管对象 + 非托管资源均可释放
Finalizer 调用 ~T()false仅非托管资源

为什么 finalizer 不能碰托管对象

  1. 执行顺序不确定：Finalizer 由 GC 的 finalizer 线程在不可预测的时间调用。此时对象引用的其他托管对象可能已经被 finalize 或正在被 finalize，访问它们的状态是未定义行为。

  2. 对象图失效：当 GC 决定回收一组对象时，它们变成”不可达”但可能同时进入 finalizer 队列。对象 A 的 finalizer 访问对象 B 的字段，而 B 的 finalizer 可能已经执行过、把字段设为 null——这就是”对象图失效”。

  3. 线程安全：Finalizer 在专用线程上执行，不在用户线程上。如果你的 Dispose(bool) 在 disposing == false 时访问托管对象，就引入了跨线程访问，而那些托管对象并没有按线程安全设计。

  4. GC.KeepAlive 的关联：在手写 finalizer 的时代，需要 GC.KeepAlive(this) 防止对象被过早回收。SafeHandle 从根本上消除了这个问题。

using 声明 vs using 语句 vs try-finally

C# 提供三种方式绑定 Dispose 到作用域，适用场景不同：

using 声明（C# 8+）

  • 作用域：从声明点到所在代码块末尾
  • 释放顺序：声明逆序（后声明的先释放）
  • 适合：短方法、资源贯穿整个方法体

using 语句（经典形式）

  • 作用域：using 块内部
  • 释放顺序：嵌套逆序（内层先释放）
  • 适合：需要精确控制释放时机的场景

try-finally（最底层形式）

  • 作用域：由 finally 块精确控制
  • 适合：需要自定义异常处理、日志、或 Dispose 前执行额外逻辑的场景

三种形式对比

维度using 声明using 语句try-finally
释放时机代码块末尾块右花括号finally 块
释放精度低（可能延迟）中高
代码简洁性最高中最低
自定义逻辑不支持不支持支持
适用场景资源贯穿方法精确作用域复杂清理逻辑

游戏开发推荐

Unity 热路径中，优先用 using 声明减少缩进层级；需要精确释放点（如帧内临时 NativeArray）用 using 语句；需要 Dispose 前记录 profiler 标记或完成 JobHandle 用 try-finally。

ref struct 的栈约束

Unity 中的 ref struct Dispose

Unity Collections 的 Unsafe 系列类型（如 UnsafeList、UnsafeHashMap）是 ref struct，需要手动调用 Dispose()。NativeArray 等类型虽然也实现 IDisposable，但它们是普通 struct（非 ref struct），可以用 using。

IAsyncDisposable

当资源释放需要异步操作（网络流关闭、数据库连接归还、大量缓冲异步刷写），使用 IAsyncDisposable。它提供 ValueTask DisposeAsync() 替代同步 Dispose()，配合 await using 在作用域末尾异步释放。Unity 游戏中绝大多数资源释放是同步的（内存、句柄），IAsyncDisposable 主要出现在网络服务、数据库交互等场景。

详细内容见：IAsyncDisposable 与异步释放，含基本模式、await using 用法、ConfigureAwait 陷阱、双接口实现（IDisposable + IAsyncDisposable）及选择建议。

Unity 专用可释放资源

Unity 中有大量资源不属于 .NET 的 IDisposable 体系，但同样需要确定性释放：

  • NativeArray / NativeList / NativeHashMap：实现 IDisposable，但必须先 JobHandle.Complete() 再 Dispose()；也可用 Dispose(JobHandle) 把释放调度为 Job 依赖。Allocator.TempJob 分配的内存必须在 4 帧内释放。
  • ComputeBuffer：不实现 IDisposable，必须手动 Release()，否则 standalone 必崩。
  • RenderTexture：临时 RT 用 ReleaseTemporary()，自建 RT 需 Release() + Destroy()。
  • AssetBundle：Unload(false) 保留已加载 asset，Unload(true) 同时销毁——不能部分卸载。
  • Object.Destroy vs IDisposable：两个完全不同的生命周期模型，不要混用。MonoBehaviour 持有资源应在 OnDestroy 中释放，不要让类实现 IDisposable。

详见 Unity 可释放资源与 SafeHandle，含完整代码示例和 SafeHandle 深入（CER、子类实现、P/Invoke 安全）。

共享资源的生命周期陷阱

如果两个 MonoBehaviour 引用同一个 NativeArray，一个 OnDestroy 中 Dispose 了，另一个还在用——这是 Unity 中经典的 use-after-free。解决方案：集中管理器 + 引用计数，或用 RewindableAllocator 统一释放。

为什么逆序释放

后获取的资源可能依赖先获取的资源（如 StreamReader 依赖 FileStream）。释放时先释放依赖方，再释放被依赖方，避免”被依赖方已释放但依赖方还试图使用”的问题。

权衡与选择

  • 拥有 disposable 成员 → 通常也应实现 IDisposable
  • 不拥有资源，只是借用引用 → 不应释放它
  • 直接持有 unmanaged handle → 优先 SafeHandle
  • 需要异步释放 → IAsyncDisposable（游戏代码中罕见）
  • Unity native container → 必须按 allocator 生命周期释放，详见 NativeContainer 与 Allocator
  • MonoBehaviour 持有资源 → 在 OnDestroy 中释放，不要让类实现 IDisposable
  • 需要精确释放时机 → using 语句或 try-finally
  • 资源贯穿方法 → using 声明
