.NET GC 与托管内存（.NET Garbage Collection）

核心思想

.NET GC 管理 managed heap 上对象的内存分配与释放。创建引用类型对象时，CLR 从 managed heap 分配内存；当可用空间不足或运行时判断合适时，GC 会查找应用不再使用的对象并回收其内存。

GC 解决的是普通托管对象内存的自动回收，不负责释放 unmanaged memory、文件句柄、native container 等外部资源——这些由 Dispose 模式（Dispose Pattern） 处理。

为什么重要

Unity 游戏对帧时间稳定性敏感。GC 暂停、临时对象、装箱、闭包和 LINQ 分配都会造成帧尖峰。理解 GC 能帮助判断哪些 C# 写法在编辑器工具里没问题，但不适合 gameplay hot path。

更重要的是：Unity 当前使用 Boehm GC（非分代、保守式、不移动对象），但正在迁移向 CoreCLR GC（分代、精确式、可移动）。两种 GC 的行为差异巨大，了解两者有助于为未来迁移做代码准备。

分代 GC 模型

三代结构

.NET CoreCLR GC 把 managed heap 分为三代：

世代定位内容分配预算
Gen 0最年轻，短命对象临时变量、函数局部引用、LINQ 中间结果动态预算（由 GC 根据存活率调整，无公开固定值；.NET 10+ DATAS 公式 (20 - 5) / sqrt(app_size_MB) 计算）
Gen 1缓冲层从 Gen 0 存活下来的短期对象与 Gen 0 共用 ephemeral segment
Gen 2长寿对象静态字段引用、缓存、单例、LOH 上的大数组无上限，仅受物理内存约束

Ephemeral Segment 大小（含 Gen 0 + Gen 1）

Workstation GC 64-bit = 256 MB / Server GC 64-bit = 4 GB / Server GC > 4 CPU = 2 GB / > 8 CPU = 1 GB（来自 Microsoft Learn · GC Fundamentals）。Gen 0 自身预算不等于 ephemeral segment 大小——前者是触发回收的阈值，后者是物理内存槽位。

设计依据是”弱代假说”（generational hypothesis）：大多数对象死得早。在典型服务器应用中，Gen 0 回收能释放绝大部分垃圾，无需扫描整堆。

分配与提升逻辑

  • 用户代码只能在 Gen 0（小对象）或 LOH（大对象）上分配。Gen 1 和 Gen 2 只通过提升填充。
  • 收集某代时，该代及所有更年轻的代一起回收。Gen 1 回收 = Gen 1 + Gen 0；Gen 2 回收 = 全堆（Full GC）。
  • GC 会根据各代存活率动态调整预算：存活率高 → 增大预算 → 下次回收更多空间。

Gen 0 “Arena” 分配速度

Gen 0 分配使用 bump pointer 机制：只需把指针向前移动对象大小即可，速度接近栈分配。这比 native heap 的 malloc/free（需遍历 free list）快得多。

Boehm GC 的分配速度

Boehm GC 同样使用 bump pointer 分配，但其回收不按代分离，每次都扫描全堆，导致回收代价远高于分代 GC。

短命代（Ephemeral Generations）

Gen 0 和 Gen 1 合称短命代（ephemeral generations），它们共享同一个内存段——短命段（ephemeral segment）。短命段的大小取决于 GC 模式和平台：

GC 模式32-bit64-bit
Workstation16 MB256 MB
Server64 MB4 GB
Server > 4 逻辑 CPU32 MB2 GB
Server > 8 逻辑 CPU16 MB1 GB

短命段的容量决定了单次 ephemeral GC 能释放多少内存。

LOH（Large Object Heap）

大对象判定

>= 85,000 字节的对象直接分配到 LOH，不经过 Gen 0。这个阈值是在性能调优中确定的，85,000 字节意味着 byte[85000] 或 double[10625] 都会进入 LOH。

典型大对象：大型数组（纹理数据、音频缓冲、序列化字节）、巨大的字符串。

LOH 是 Gen 2 的一部分

LOH 有时被称为”Gen 3”——这是物理上的独立区域，但逻辑上随 Gen 2 一起回收。这意味着：

  • 任何大对象的回收都伴随 Full GC（Gen 2 + Gen 1 + Gen 0 + LOH 全部扫描）。
  • 频繁创建和丢弃大对象会导致频繁 Full GC，这是性能杀手。

碎片问题

LOH 默认不压缩（移动大对象代价太高）。回收时只做 sweep：标记死对象，把相邻死对象合并到 free list，供后续大对象分配复用。但 free list 中的空闲块大小不一定匹配新的分配请求，导致碎片化：

临时大对象是 Full GC 和碎片化的双重来源

如果你的代码每帧创建 new byte[100000] 再丢弃，LOH 碎片会持续增长，Full GC 频率上升，帧率崩溃。

此外，当设置了 GCHeapHardLimit 或容器内存限制时，LOH 会自动压缩。

Unity 中的 LOH 风险

Unity 中大数组、纹理的 managed 副本、大型序列化缓冲都会进入 LOH。Boehm GC 对大对象的处理更粗糙——它是 conservative GC，无法精确识别大数组中的指针 vs 数据，扫描代价随数组长度线性增长。CoreCLR GC 对不含引用的纯值类型数组（如 byte[]）可以跳过引用扫描。

Unity 使用 Workstation GC

Unity 游戏是客户端应用，运行时使用 Workstation GC。Server GC 对游戏无意义——游戏不需要多堆并行分配，且 Server GC 的暂停时间更长。

Concurrent / Background GC

模式行为适用版本
Non-concurrentGC 时暂停所有托管线程（stop-the-world）早期 .NET
Concurrent GCGen 2 回收期间允许托管线程运行（1 个专用 GC 线程）.NET Framework 3.5 及之前
Background GCGen 2 回收期间允许托管线程运行 + 允许 Gen 0/1 foreground GC 插入.NET Framework 4+（默认开启）

Background GC 是当前默认模式。它在 Gen 2 回收期间使用专用线程执行标记和清扫，此时如果 Gen 0 预算耗尽，可以插入 foreground ephemeral GC（短暂暂停所有线程），然后 background GC 继续。

Unity Boehm GC 的增量模式

Unity Boehm GC 的 Incremental 模式不是 Background GC——它只是把一次 stop-the-world 回收分摊到多帧执行，每帧执行一部分。Project Settings > Player > “Use Incremental GC” 开启。这对减少单帧卡顿有效，但不减少总回收时间。

Boehm GC 的致命局限

Boehm 是 conservative GC——它无法区分栈/堆上的整数和托管引用。如果一个整数恰好值等于某个托管对象地址，该对象就无法被回收（false retention）。此外，不移动对象意味着碎片无法通过压缩修复。这是 Unity 迁移 CoreCLR GC 的核心动机。

GC 触发条件

.NET CoreCLR 触发条件

  1. Gen 0 预算耗尽：新对象分配时 Gen 0 空间不足 → 触发 ephemeral GC（最常见的触发原因）
  2. LOH 预算耗尽：大对象分配时 LOH 空间不足 → 触发 Full GC
  3. 系统低内存：OS 发出低内存通知，GC 判断 Full GC 有意义时触发
  4. 显式 GC.Collect：用户代码调用（应避免）
  5. GC.AddMemoryPressure / GC.RemoveMemoryPressure：告知 GC 存在 unmanaged 内存占用，影响 GC 决策

Unity Boehm GC 触发条件

Boehm GC 的触发更简单粗暴：当分配时堆上无足够连续空间，触发一次全堆扫描。没有分代预算、没有 LOH 独立触发。

Unity 在帧结束时会提供 collection hint：

Incremental GC 开启时，GC 在每帧最多执行 GarbageCollector.incrementalTimeSliceNanoseconds 纳秒的回收工作，未完成部分留到下一帧继续。

控制 Unity 增量 GC 时间片

时间片过小 → GC 永远追不上分配，堆持续增长；过大 → 单帧卡顿。2 ms 是常见起点。

碎片与钉住（Fragmentation and Pinning）

什么是钉住

钉住（pinning）阻止 GC 移动某个托管对象。在 GC 压缩阶段，被钉住的对象留在原位，导致其周围产生无法合并的空闲间隙。

钉住的三种来源

  1. GCHandle：显式钉住托管对象，用于 P/Invoke 传递托管引用给 native 代码
  1. fixed 语句：C# 语言级钉住，通常作用域很短
  1. P/Invoke 参数自动钉住：interop marshaller 在调用期间自动钉住 string 等类型

钉住对 Gen 0/1 的影响

钉住是 SOH 碎片的唯一用户来源

根据 .NET GC 团队的分析，钉住是 SOH 碎片化的唯一用户级原因。即使少量钉住对象，如果它们与短命代对象交错分布，也会阻止压缩，导致 Gen 0 可用空间碎片化。

最佳实践：钉住持续时间越短越好。如果 GC 不在钉住期间发生，钉住几乎无开销。理想情况是在钉住期间无分配（无 GC 触发）。

长期钉住的缓冲区应放在 Gen 2（先让它在几次 GC 中自然提升），再钉住——Gen 2 碎片对性能影响较小。

.NET 5+ Pinned Object Heap

.NET 5 引入了 Pinned Object Heap（POH），专门存放需要长期钉住的对象：

POH 上的对象从一开始就在独立堆段，不会碎片化 SOH 的短命代。

Unity 中 POH 不可用

Unity 当前运行时（Mono/IL2CPP + Boehm）不支持 POH。迁移 CoreCLR 后将可用。

DOTS 语境下的 GC

ECS 如何避免 GC

ECS 架构从根基上规避 GC：

  • Entity：轻量 ID（index + version），是值类型，不产生堆分配
  • IComponentData：unmanaged struct，纯数据，存储在 Archetype Chunk 的 SoA 布局中
  • ISystem：unmanaged，OnUpdate 可被 Burst 编译，整个系统无堆分配
  • Chunk：16 KiB 的 NativeArray-backed 内存块，数据紧密排列

Managed ComponentData 例外

IComponentData 也可以是 managed（class），但这会引入 GC 压力：

Managed Component 的代价

Managed Component 违背了 DOTS 的数据导向设计原则：无法被 Burst 编译，无法在 Chunk 中紧密排列，需要 GC 跟踪，访问时需要指针解引用。仅在确实需要托管引用（如 Unity Object 引用）时使用。

ECB 分配模式

EntityCommandBuffer（ECB）使用 native 内存队列，自身不产生托管堆分配：

ECB 的真正好处不是"无 GC"

ECB 的核心价值是延迟结构变更到安全点，避免遍历中修改导致异常。无 GC 是 native 内存的副产品，不是主要设计目标。

反模式

GC.Collect in Update

手动 GC.Collect 通常是错误优化

试图”控制 GC 时机”往往适得其反。GC 的预算调整算法依赖自然分配模式。手动 Collect 干扰算法学习，让后续 GC 更频繁。正确做法是减少分配。

单例事件订阅泄漏

事件订阅是最常见的泄漏源

+= 在委托中隐式捕获 this。如果 OnDisable / OnDestroy 不对称 -=，订阅者永远不会被 GC 回收。静态事件尤其危险——它们的生命周期等于进程生命周期。
