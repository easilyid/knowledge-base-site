LINQ 与延迟执行（LINQ and Deferred Execution）

核心思想

LINQ（Language Integrated Query）把查询能力直接集成到 C#，用统一的声明式语法对 IEnumerable<T> / IQueryable<T> 做筛选、映射、排序、分组、聚合等操作。它的底层模型是延迟执行：构建查询时不遍历数据，只在终端操作（foreach、ToList、Count 等）触发时才真正执行。

这个模型让链式组合成为可能——Where().Select().OrderBy() 不会产生中间集合，每条元素流过整个管道只被处理一次。但在 Unity 高频路径中，LINQ 的枚举器、闭包、lambda 和临时集合会带来 GC 分配和额外 CPU 开销，需要精确理解何时执行、何时分配。

为什么重要

  • 编辑器与加载期：LINQ 让配置转换、资源筛选、数据预处理非常简洁，可读性收益高
  • 高频 gameplay 路径：Update/FixedUpdate 中每帧执行 LINQ 会反复分配，引发 GC spike
  • 延迟执行的陷阱：查询对象被保存后底层集合变化，结果与预期不一致
  • DOTS 不兼容：Burst 编译的 Job 不能使用 LINQ，IJobEntity/IJobChunk 只接受 blittable 类型与 NativeContainer
  • 理解分配模型：知道哪个操作符分配、哪个不分配，才能在热路径上做出正确选择

LINQ 操作符按执行时机分为两类，Microsoft 官方还进一步将延迟操作符细分为流式（streaming）和非流式（non-streaming）：

延迟执行意味着每次遍历都会重新执行查询

将 LINQ 查询结果存入变量后多次 foreach，每次都会重新遍历源集合并重新计算。如果查询包含 OrderBy 等非流式操作，每次遍历都重排一次。需要快照时显式调用 ToList / ToArray。

内存与分配分析

LINQ 的 GC 分配主要来自三个来源：枚举器对象、闭包/lambda、终端操作分配的集合。

枚举器分配

foreach 对 IEnumerable<T> 调用 GetEnumerator()，返回 IEnumerator<T> 接口。即使 List<T>.Enumerator 是 struct，通过 IEnumerable<T> 接口调用时会装箱到堆上。

兼容 Unity 6.4 及以上。Unity 2022 LTS 同样适用，API 一致。

.NET 10 的改进

.NET 10 中 IEnumerable<T> 的 foreach 在很多场景下不再装箱。但 Unity 当前运行时（基于 CoreCLR 或旧版 Mono）尚未包含此优化，仍需假设有装箱分配。

ToList vs ToArray 的分配差异

ToArray() 在无法预知元素数量时（如 Select 后），会先分配小数组、倍增、最后修剪——可能分配多个中间数组。ToList() 内部同样用倍增数组，但最终无需修剪。若已知数量，两者分配量接近；若未知，ToArray() 可能额外分配一个修剪数组。对于大序列，中间数组可能进入 LOH（> 85 KB）。

查询语法 vs 方法语法

C# 提供两种 LINQ 语法：

维度查询语法方法语法
覆盖范围仅 where/orderby/select/group/join/let 等覆盖全部标准操作符
可读性SQL 风格，join/group 更直观链式调用，Where().Select() 更紧凑

性能编译后与方法语法等价同左
推荐场景复杂 join/group/let日常绝大多数场景

实际开发中方法语法更常用

查询语法不支持 Take、Skip、First、DistinctBy、Chunk 等操作符，必须混用方法语法。Unity 社区几乎统一使用方法语法。

常用操作符深度

Where — 筛选

延迟-流式。逐元素测试谓词，不分配中间集合。

避免对 IEnumerable<T> 多次 Where 链接后多次遍历

Where 本身不缓存结果，每次 foreach 都重新遍历源。如果需要多次使用结果，在筛选后 ToList() 存为快照。

Select — 映射

延迟-流式。对每个元素应用投影函数。

Select 改变元素类型后无法使用源集合的 ICollection 优化

ToArray() 对 ICollection<T> 源可直接取 Count 一次性分配数组；但 Select 返回的 IEnumerable<T> 不实现 ICollection，导致 ToArray() 必须倍增分配。若已知元素数量，可用 new T[count] + CopyTo() 手动优化。

OrderBy / OrderByDescending — 排序

延迟-非流式。首次遍历时必须消费全部元素并分配内部 buffer 进行排序（基于 QuickSort 变体）。

OrderBy 每次遍历都重新排序

因为是延迟-非流式，OrderBy 在首次 MoveNext 时才执行排序。如果对同一个查询对象多次 foreach，每次都会重排。排序后应立即 ToList() 或 ToArray() 固定结果。

使用 MinBy / MaxBy 替代排序取极值

.NET 6+ 提供 MinBy / MaxBy，只需一次遍历 O(n)，而 OrderBy(...).First() 是 O(n log n)。

GroupBy — 分组

延迟-非流式。首次遍历时分配 Dictionary<TKey, List<TElement>> 结构，每个分组是一个 IGrouping<TKey, TElement> 实现，背后持有 List<TElement>。

GroupBy 是 LINQ 中分配最重的操作符之一

它为每个 key 分配一个 List<TElement>，再加上外层 Dictionary 的 entries 数组和 bucket 数组。在 Unity 热路径中使用 GroupBy 几乎必定造成 GC spike。

Join — 内连接

延迟-流式。基于 hash lookup 实现，内部会分配 Dictionary<TKey, List<TElement>> 对右序列建索引。

Zip — 合并序列

延迟-流式（.NET 6+ 支持三序列 Zip）。逐位置合并多个序列为元组。

Chunk — 分块

.NET 6+ 新增，延迟-非流式。将序列按指定大小切分为数组块。

Chunk 返回 int[] 数组

每个 chunk 本身是一个新数组，因此有分配。适合分批处理（如分帧加载），不适合热路径高频调用。

DistinctBy — 按属性去重

.NET 6+ 新增，延迟-非流式。与 Distinct 不同，它接受 key selector，保留完整对象。

同理，MinBy、MaxBy、ExceptBy、IntersectBy、UnionBy 都是 .NET 6+ 引入的 By 系列操作符。

游戏开发中的表达式树

表达式树在 Unity gameplay 中几乎不使用

IQueryable 和表达式树主要用于数据库查询（EF Core）。Unity 中的 IEnumerable<T> LINQ 使用委托路径，不涉及表达式树。在 Unity 中手动构建表达式树只有极少数场景（如动态查询构建、规则引擎），且 Expression.Compile() 在 IL2CPP 下有限制。

PLINQ 并行查询

PLINQ（Parallel LINQ）是 LINQ 的并行实现，通过 AsParallel() 将查询转为并行执行，自动分区并利用多核。

基本用法

关键 API

API作用
AsParallel()将 IEnumerable<T> 转为 ParallelQuery<T>，后续操作符使用并行实现
WithDegreeOfParallelism(n)限制最多使用 n 个并发线程（默认使用所有逻辑核心，上限 64）
AsOrdered()保持原始顺序（有性能开销，需追踪原始索引）
AsSequential()退回顺序执行
WithMergeOptions()控制结果缓冲策略：NotBuffered / AutoBuffered（默认）/ FullyBuffered
WithCancellation(token)传入 CancellationToken 支持取消
ForAll(action)并行执行 action，不保留顺序，不合并回主序列

顺序保证

默认 PLINQ 不保证顺序。需要顺序时：

AsOrdered 有额外性能开销

PLINQ 必须追踪每个元素的原始位置，合并时按索引排序。对大量元素，这个开销可能抵消并行收益。如果不需要顺序，不要加 AsOrdered()。

何时使用 PLINQ

适合不适合
CPU 密集型操作（数学计算、图像处理）I/O 密集型操作（文件/网络）
元素数量大（> 10,000）小集合（并行开销 > 计算收益）
每个元素的委托计算耗时较长每个元素只是简单属性访问
可容忍无序结果需要严格顺序且集合大

PLINQ 不适合 Unity 的 per-frame 路径

PLINQ 使用 ThreadPool 线程，与 Unity 的 Job System 线程池竞争。在 Unity 中应优先使用 Job System + Burst 做并行，而非 PLINQ。PLINQ 适合编辑器工具、离线数据处理。

Unity 游戏开发深度

热路径避坑

Unity 官方文档明确建议：避免在性能关键路径使用 LINQ。原因：

  1. 枚举器装箱：foreach 对 IEnumerable<T> 装箱 ~24-40 B
  2. 闭包分配：lambda 捕获局部变量生成闭包类 ~24-64 B
  3. 终端操作分配：ToList/ToArray/ToDictionary 分配 O(n) 集合
  4. 排序/分组分配：OrderBy/GroupBy 分配内部缓冲区
  5. CPU 开销：虚方法调用、委托间接调用比直接循环慢 2-10x

兼容 Unity 6.4 及以上。Unity 2022 LTS 同样适用，API 一致。

DOTS 不兼容性

Unity DOTS（Data-Oriented Technology Stack）基于 Burst + Job System + NativeContainer + ECS，对 LINQ 有根本性限制：

限制原因
Job 内无法使用 LINQLINQ 操作符返回 IEnumerable<T>，不是 blittable 类型
Burst 不支持委托/LambdaBurst 使用 C# 子集，不支持 Func<T, bool> 等
NativeArray/NativeList 不实现 IEnumerable<T>有意为之：避免意外使用 LINQ 导致 GC 分配
IJobEntity/IJobChunk 只接受 blittable 字段闭包/委托是引用类型

Collections Package 提供 LINQ 风格的 NativeArray 扩展

Unity.Collections 包为 NativeArray<T> / NativeList<T> 提供了 IndexOf、Contains、Sort 等方法，虽不是完整 LINQ，但覆盖了常见需求且零 GC。详见 Unity Collections 包。

闭包分配详解

捕获 this 的闭包在 Unity 中特别常见

e => Vector3.Distance(transform.position, e.Position) 捕获了 this（MonoBehaviour 实例），每次调用分配闭包。热路径应将 transform.position 预先存入局部变量，然后将捕获改为 struct 缓存或手动循环。

foreach 在 Unity 中的分配行为

遍历方式是否分配说明
foreach (T x in List<T>)无编译器直接调用 List<T>.GetEnumerator()（struct），不走接口
foreach (T x in T[])无数组有特殊的 IL 指令
foreach (T x in IEnumerable<T>)有 (~24-40 B)接口调用导致枚举器装箱
foreach (T x in IList<T>)有 (~24-40 B)IList<T> 继承 IEnumerable<T>，走接口路径
for (int i = 0; ...)无索引访问，无枚举器

替代方案

1. 手动循环 — 最可靠的零 GC 方案

使用 List<T>.Clear() 复用集合，而非重新 new List<T>()

Clear() 只重置 count 不释放内部数组，避免重复分配。

2. Span-based 查询 — SpanLinq

SpanLinq 在 Span<T> / ReadOnlySpan<T> 上实现零分配 LINQ 操作符。C# 13 的 allows ref struct 泛型约束使其可自然集成 Span<T>。

SpanLinq 在 Unity 2022.2+ 可用

需要 .NET Standard 2.1 兼容级别。可通过 NuGetForUnity 安装。Span<T> 在 Unity 2021.2+ 可用。

3. ZLinq — 零分配全功能 LINQ 替代

Cysharp/ZLinq 是 Cysharp（UniRx/R3/ZString 作者）开发的零分配 LINQ 实现，关键特性：

  • 所有操作符使用 struct 枚举器，零托管堆分配
  • 通过 9000+ 测试（dotnet/runtime 的 System.Linq.Tests），API 兼容标准 LINQ
  • 支持 Span<T> 查询（LINQ to Span）
  • 支持 SIMD 加速聚合（LINQ to SIMD）
  • 支持 Tree 遍历（FileSystem/JSON/GameObject）
  • Unity + Godot 均可使用

兼容 Unity 6.4 及以上。Unity 2022 LTS 同样适用。

反模式

反模式 1：热路径中使用 LINQ

Update/FixedUpdate/LateUpdate 中的 LINQ 每帧分配，累积造成 GC spike。移动端尤为严重。

反模式 2：对延迟查询多次遍历

var q = src.Where(...); q.Count(); q.First(); q.Last(); 三次遍历源，每次都重新计算。应先 ToList() 再操作。

反模式 3：OrderBy().First() 取极值

排序 O(n log n) 只为取一个元素。应用 MinBy() / MaxBy()（.NET 6+），O(n) 一次遍历。

反模式 4：在 Job/Burst 中尝试使用 LINQ

IJobParallelFor 内无法调用 LINQ，编译直接报错。用 NativeArray + 手动循环替代。

反模式 5：GroupBy 后立即 ToList 但不需要分组结构

GroupBy 分配大量中间 Dictionary 和 List。如果只需按 key 查第一个元素，DistinctBy 更高效且分配更少。

反模式 6：foreach 遍历 IEnumerable 接口类型

当变量类型是 IEnumerable<T>（而非具体 List<T>），foreach 必然装箱枚举器。保持具体类型或用 for 循环。

反模式 7：闭包捕获 this 导致意外分配

e => e.Name == this.targetName 捕获了整个 this。将 targetName 预存到局部变量可消除闭包分配：var name = targetName; e => e.Name == name。

反模式 8：在 Unity 中使用 PLINQ 做帧内并行

PLINQ 使用 ThreadPool 线程，与 Unity 主线程 + Job System 线程池冲突。Unity 的并行方案是 Job System，而非 PLINQ。

反模式 9：对大序列调用 ToArray() 时未预分配

当源非 ICollection<T> 时（如 Select 后），ToArray() 倍增分配 + 修剪。对 > 85KB 的数组会进入 LOH。若已知数量，手动分配 new T[count] + CopyTo()。
