C# 泛型集合（Generic Collections）

核心思想

System.Collections.Generic 提供强类型集合，让同一套容器和算法可复用于不同元素类型，同时避免非泛型集合常见的 cast 和值类型装箱。

泛型集合是普通 Unity gameplay 代码最常用的数据结构层；进入 Job/Burst 后，则常迁移到 Unity Collections 包（Unity Collections Package）。

为什么重要

游戏逻辑充满动态集合：敌人列表、状态表、对象注册表、事件队列、路径节点、缓存池。选错集合会让代码复杂度、查找成本、GC 分配和帧时间稳定性都变差。理解集合内部实现，才能在容量预分配、枚举安全、GC 敏感路径上做出正确选择。

List<T> 内部机制

动态数组结构

List<T> 内部持有一个 T[] 数组。Capacity 是数组长度，Count 是实际元素数。Count <= Capacity 始终成立。

兼容 Unity 6.4 及以上。Unity 2022 LTS 同样适用，API 一致。

扩容策略

当 Count == Capacity 时再调用 Add，内部分配一个更大的数组并把旧元素拷贝过去。.NET 的扩容策略是至少翻倍（实际上 Grow 方法选择 2 * Capacity 与所需容量的较大值），然后取素数对齐（部分版本）。扩容涉及一次 Array.Copy，代价为 O(n)。

预分配容量

如果大致知道元素数量，在构造时指定 capacity，避免扩容产生的中间数组分配和拷贝。这对 Unity hot path 尤其重要——每次扩容都是一次 managed heap 分配，增加 GC 压力。

摊销 O(1) 追加

单次 Add 的最坏情况是 O(n)（扩容），但连续 n 次 Add 的总代价为 O(n)，摊销到每次为 O(1)。这是动态数组”翻倍扩容”的经典性质。

中间插入与删除

Insert(index, item) 和 RemoveAt(index) 需要将 index 之后的元素整体移动，代价 O(n)。频繁在头部或中间插入/删除是 List<T> 的弱点——此时应考虑 LinkedList<T>（但见下方反模式关于缓存局部性的警告）或其他数据结构。

ForEach vs foreach

List<T>.ForEach(Action<T>) 是 List 特有的实例方法，不接受 break/return 控制。foreach 生成标准枚举器代码，支持 break/return/异常。

List.ForEach 在 .NET Core 中被标记 [Obsolete]（诊断级别，非编译错误），不建议新代码使用。

Dictionary<TKey, TValue> 内部机制

哈希表结构

Dictionary<TKey,TValue> 内部维护两个数组：

  • bucket 数组：长度为素数，每个槽位存储链头索引（-1 表示空桶）
  • entry 数组：连续存储所有键值对，每个 entry 包含 hashCode、next（链指针）、key、value

冲突解决采用链地址法（separate chaining）：hash 到同一桶的 entry 通过 next 字段串成链表。

扩容策略

当 Count / Capacity 超过负载因子时（默认约 0.72–1.0，随 .NET 版本调整），字典扩容：选择下一个素数作为新容量，重新分配两个数组，所有 entry 重哈希。

GetHashCode 的重要性

Dictionary 在插入时缓存 key 的 GetHashCode() 结果到 entry 的 hashCode 字段，后续查找和 rehash 不再重复调用 GetHashCode。但如果 GetHashCode 实现质量差（高碰撞率），同一桶的链会变长，查找退化为 O(n)。

自定义 IEqualityComparer

TryGetValue vs 索引器

避免先 ContainsKey 再索引器

ContainsKey + dict[key] 等于两次哈希查找。TryGetValue 只查一次，性能更优。

ContainsKey vs ContainsValue

ContainsKey 是 O(1)（哈希查找）。ContainsValue 是 O(n)（必须遍历所有 entry，因为值没有索引结构）。游戏逻辑中不应在高频路径上调用 ContainsValue。

容量预分配

构造函数的 capacity 参数让字典一次性分配足够大的 bucket + entry 数组，避免后续反复扩容。

Dictionary 的 capacity 参数表示"预期元素数"，内部实际分配的 bucket 大小会取 >= capacity 的下一个素数。

与 Dictionary 的关系

HashSet<T> 的内部结构与 Dictionary<TKey, TValue> 几乎相同，只是 entry 没有 value 字段。bucket 数组 + entry 数组 + 链地址法冲突解决，完全一致。

Queue<T> 与 Stack<T>

Queue<T> — 环形缓冲区

Queue<T> 内部不是简单的数组前移，而是环形缓冲区（circular buffer）。维护 head 和 tail 两个指针：

  • Enqueue：在 tail 位置写入，tail = (tail + 1) % Capacity
  • Dequeue：读取 head 位置，head = (head + 1) % Capacity

当 Count == Capacity 时自动扩容（分配新数组、按顺序复制、重置 head=0）。环形缓冲区让 Enqueue/Dequeue 均为 O(1)（摊销），且不需要每次 Dequeue 后移动元素。

Stack<T> — 简单数组 + 栈顶指针

Stack<T> 更简单：内部就是一个 T[] + int size（栈顶指针）。Push 在 size 位置写入并递增；Pop 递减并返回。两者均为 O(1)（摊销）。扩容时同样翻倍分配。

集合典型游戏用途

内存与 GC 影响

扩容分配

List<T>、Dictionary<TKey,TValue>、HashSet<T> 等在扩容时分配新的内部数组，旧数组成为垃圾。在 Unity hot path 中，不可预测的扩容会导致帧尖峰。

闭包捕获在 Find/Predicate 中的分配

List<T>.Find(Predicate<T>) 和 List<T>.FindAll(Predicate<T>) 的 lambda 如果捕获局部变量，会产生闭包分配：

Unity hot path 中避免用 Find/FindAll/Exists 等 Predicate 方法，改用显式 for 循环。不仅避免闭包分配，for 循环比枚举器更易被 JIT 内联。

IEnumerable 分配

foreach 在 List<T> 上不产生分配（因为 List<T>.Enumerator 是 struct）。但对 IEnumerable<T> 接口变量使用 foreach 会装箱枚举器 struct：

在 Unity Profiler 中观察到 IEnumerable<T> 相关分配时，检查是否通过接口而非具体类型枚举。详见 .NET GC 与托管内存。

IReadOnlyList vs List 协变

IReadOnlyList<Enemy> 不与 IReadOnlyList<Component> 协变——C# 泛型不支持值类型和 class 的声明式协变。但 List<Enemy> 可以隐式转为 IReadOnlyList<Enemy>，因为 List<T> 实现了 IReadOnlyList<T>：

IReadOnlyList<T> 阻止调用者调用 Add/Remove，但不阻止对元素本身的修改（如果 Enemy 是引用类型）。这是"只读集合"与"不可变集合"的关键区别。

struct vs class 元素性能

当 T 是值类型时，List<T> 内部数组是连续的值，缓存局部性极佳。当 T 是引用类型时，数组存储引用，实际对象分散在堆上，缓存局部性差——这正是 DOTS 使用 IComponentData（struct）+ 连续 Archetype Chunk 的设计动机，见 ECS 和 数据局部性。

预容量模式

Clear() 不释放内部数组，只重置 Count/head/tail 等指针，让集合回到空但保留 Capacity 的状态——这是帧间复用集合的核心模式。

Span 与 CollectionsMarshal

CollectionsMarshal.AsSpan

System.Runtime.InteropServices.CollectionsMarshal.AsSpan<T>(List<T>) 返回 Span<T>，直接覆盖 List<T> 内部数组，零拷贝、零分配。适合在已知不修改 List 结构（不 Add/Remove）的前提下进行高性能批量读写：

AsSpan 返回的 Span 在 List 发生任何结构变更（Add/Remove/扩容）后立即失效。使用 Span 期间绝对不能修改 List 结构。这是 ref struct 生命周期的根本约束。

Span 排序与搜索

Span 上的 Sort/BinarySearch 使用 MemoryExtensions 方法，不经过 IComparer 接口，性能优于 List.Sort 的接口版本。

何时 Span 有帮助 vs 何时不帮助

场景Span 帮助原因
批量读写 List 元素有帮助避免逐个索引器的边界检查
对 List 内容排序/搜索有帮助直接操作内存、无接口分发
只读取一两个元素帮助不大索引器本身已足够快
需要 Add/Remove不适用Span 无法改变 List 结构
List 可能扩容危险Span 悬垂引用

Frozen 集合（.NET 8+）

FrozenDictionary 与 FrozenSet

System.Collections.Frozen 命名空间提供 FrozenDictionary<TKey, TValue> 和 FrozenSet<T>。构造后不可修改，作为交换，读取性能比 Dictionary/HashSet 更优。

优化策略

FrozenDictionary 在构造时根据 key 类型选择最优内部布局：

  • 字符串 key：使用长度前缀 + 字符逐级哈希的特化布局
  • 整数 key：使用直接映射或紧凑哈希
  • 其他 key：回退到标准哈希

这种”构造时决策、运行时无分支”的模式让 TryGetValue 的热路径比普通 Dictionary 更快（少一次分支、更紧凑的内存布局）。

适用场景

  • 启动时构建的只读配置表（物品 ID、技能定义、本地化文本）
  • 网络协议的消息类型注册表
  • AI 的行为树节点索引

AOT 友好

Frozen 集合不依赖运行时反射或动态代码生成，对 Native AOT 编译友好。Unity IL2CPP 的 AOT 环境同样兼容。

Unity 兼容性

Frozen 集合需要 .NET 8+。Unity 2022 LTS 使用 .NET Standard 2.1 / .NET Framework， 无法直接使用。Unity 6（基于 .NET 8 核心 API 子集）的兼容性需查看具体 Unity 版本的 API 支持列表。在 Unity 中如果不可用，可用 IReadOnlyDictionary 暴露只读视图作为降级方案。

用 LinkedList<T> 做缓存敏感数据

LinkedList<T> 的每个节点是独立的堆对象，遍历时指针追踪导致缓存未命中。对于游戏中的大集合顺序遍历，List<T> 的连续数组布局通常更快，即使中间删除需要 O(n) 移动。

LinkedList<T> 仅在频繁从已知节点位置插入/删除（已有 LinkedListNode<T> 引用）时有优势。游戏开发中这种情况很少。

只读接口

许多集合实现 IReadOnlyCollection<T> 或 IReadOnlyDictionary<TKey,TValue>，适合 API 暴露”可读视图”，避免调用者直接修改内部集合。

并发集合

.NET 提供 ConcurrentDictionary<TKey,TValue>、ConcurrentQueue<T>、ConcurrentStack<T> 等线程安全集合，但 Unity gameplay 多数 API 仍要求主线程访问。并发集合不能绕过 UnityEngine API 的主线程限制。
