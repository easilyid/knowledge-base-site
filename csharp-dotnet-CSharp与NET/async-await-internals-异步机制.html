async/await 内部机制（Async Await Internals）

核心思想

C# 编译器会把 async 方法重写成状态机。每个 await 是一个可能挂起的位置；awaited operation 完成后，awaiter 注册的 continuation 会驱动状态机从对应位置继续执行。整个机制由三层协作完成：编译器生成的状态机（控制流拆分）、AsyncMethodBuilder（创建/完成返回类型）、Awaiter（检查完成/注册 continuation）。

这解释了为什么 async/await 看起来像同步代码，实际执行顺序却由任务完成时机和调度上下文决定——也解释了 Unity Awaitable、UniTask 为什么能无缝接入同一语法：只要提供正确的 Builder + Awaiter。

为什么重要

Unity 开发中，async/await 常被误解为”开线程”或”下一帧继续”。实际并非如此。状态机模型能帮助判断：是否分配、异常如何传播、为什么 async void 危险、为什么 await 后可能不在原线程、为什么 Unity Awaitable / UniTask 能接入同一语法、为什么库代码应该用 ConfigureAwait(false) 和 UnsafeOnCompleted、什么时候 ValueTask 值得引入。

工作原理

1. 状态机生成（完整编译流程）

编译器对 async 方法的重写分为四个步骤：

第一步：生成入口方法

编译器移除 async 修饰符，把方法体替换为状态机创建和启动代码：

关键点：入口方法只负责创建状态机、初始化为 -1 状态、调用 Start() 启动、返回 Builder 管理的 Task。如果方法同步完成，Start() 内部直接跑完 MoveNext() 不会挂起。

第二步：生成状态机 struct

第三步：MoveNext() 状态跳转

MoveNext 是状态机的核心，用 switch/if + goto 实现状态跳转：

状态编号规则：

状态值含义
-1初始状态，从方法开头开始执行
0从第一个 await 恢复
1从第二个 await 恢复
…依此类推
-2方法已完成（成功或异常）

每个 await 对应一个状态号；状态机保存该号后 return，恢复时通过 goto 跳到对应位置继续执行。

第四步：局部变量提升与 this 捕获

跨 await 边界使用的局部变量被”提升”（hoist）为状态机字段。仅在一个 await 段内使用且完毕的局部变量可以留在栈上（编译器优化）。实例方法的 this 也被捕获为字段，以便恢复后访问实例成员。

Debug vs Release 的区别

Debug 构建中状态机是 class（始终堆分配，方便调试器检查）；Release 构建中状态机是 struct（栈上分配，只有在需要挂起时才 box 到堆上）。这对 Unity Editor（Debug 构建）vs 构建后（Release 构建）的性能差异有直接影响。

2. AsyncTaskMethodBuilder

AsyncTaskMethodBuilder<TResult> 是 async Task<TResult> 方法的默认 builder。它负责创建 Task、驱动状态机、处理结果和异常。

核心 API 流程：

同步完成优化（Fast Path）：

当 async 方法在第一个 await 之前就已完成（或 await 的对象已经 IsCompleted），整个状态机不会挂起。此时：

  • Start() 内部同步跑完 MoveNext()
  • SetResult() 被直接调用
  • Task 属性返回 Task.FromResult(result)，使用运行时缓存的已完成 Task 对象

这意味着同步完成的 async 方法几乎零分配——struct 状态机始终在栈上，不需要 box，Builder 也不需要创建新的 Task 对象。

已完成 Task 的缓存

Task.FromResult(0)、Task.FromResult(false)、Task.CompletedTask 等常用值会使用运行时内部缓存，避免重复分配。自定义 builder 可以模仿这一模式。

3. AsyncVoidMethodBuilder

async void 方法使用 AsyncVoidMethodBuilder，API 形状与 AsyncTaskMethodBuilder 类似，但有两个关键差异：

差异一：异常路由

ThrowAsync 的行为：

  1. 如果当前有 SynchronizationContext（如 UI 线程、Unity 主线程）→ context.Post(throwAction) 在该上下文上抛出
  2. 否则 → ThreadPool.QueueUserWorkItem(throwAction) 在线程池上抛出

这意味着 async void 的异常不会回到调用者的 try-catch，而是被抛到 SynchronizationContext 或线程池——通常导致未观察异常崩溃。

差异二：无 Task 返回

Builder 没有 Task 属性，调用者无法 await、无法检查完成、无法组合。

为什么 Unity 有时用它：

Unity 的 Start()、OnEnable() 等事件方法签名是 void，且由引擎从 native 侧调用。在这些入口点写 async void 是合理的——但必须自己 catch 所有异常并记录日志：

async void 的三大危险

  1. 异常不回调用者 → 容易崩溃且难以追踪
  2. 无法 await → 无法组合、无法等待完成
  3. 无法取消 → 没有 Task 可以注册 cancellation

原则：仅用于事件处理器入口；业务逻辑方法一律返回 Task / ValueTask / Awaitable / UniTask。

4. 自定义 Async Method Builder

C# 允许通过 [AsyncMethodBuilder] 属性将自定义 builder 关联到返回类型，使 async 方法返回非 Task 类型。

Builder 必须实现的 API：

UniTask 的 AsyncMethodBuilder：

UniTask 通过 [AsyncMethodBuilder(typeof(AsyncUniTaskMethodBuilder<>))] 将 builder 关联到 UniTask<T> struct。与 AsyncTaskMethodBuilder 的关键差异：

维度AsyncTaskMethodBuilderUniTask Builder
返回类型Task<T>（class）UniTask<T>（struct）
状态机装箱每次 suspend 都 box使用 IUniTaskSource 池化对象
SynchronizationContext默认捕获并 Post 回不走 SynchronizationContext，直接 PlayerLoop
同步完成返回缓存 Task直接存 result 到 struct 字段
池化无TaskPool<> 池化 promise 对象

UniTask 的 builder 在 AwaitUnsafeOnCompleted 中不是把 continuation 注册到 TaskAwaiter.UnsafeOnCompleted，而是通过 IUniTaskSource.OnCompleted 注册到 UniTask 自己的 PlayerLoop 调度系统。

Unity Awaitable 的 Builder：

Unity Awaitable 同样使用 [AsyncMethodBuilder] 关联自定义 builder。Awaitable builder 的关键设计：

  • 使用对象池复用 Awaitable 实例，降低 GC
  • 同步完成时不分配，直接在 struct 中携带结果
  • continuation 在完成时同步运行（而非 Post 到队列），减少延迟

C# 10+ 方法级 Builder 覆盖

从 C# 10 开始，[AsyncMethodBuilder] 可以标注在方法上（而非仅类型上），允许同一类型在不同方法上使用不同 builder：

5. Awaiter Pattern 深入

await 不是只认识 Task。编译器对 await expr 的处理遵循固定的模式调用链：

模式要求：

INotifyCompletion vs ICriticalNotifyCompletion：

编译器优先检查 awaiter 是否实现 ICriticalNotifyCompletion；如果是，调用 UnsafeOnCompleted（跳过 ExecutionContext 流动）；否则回退到 OnCompleted。

为什么 ICriticalNotifyCompletion 跳过 ExecutionContext：

流动 ExecutionContext 需要捕获当前线程的 AsyncLocal<T> 等环境状态，并在 continuation 执行时恢复——每次 await 都要一次 capture + restore，有可观开销。库代码通常不需要 AsyncLocal 传播，因此 UnsafeOnCompleted 是性能优先选择。BCL 的 TaskAwaiter 内部正是在 UnsafeOnCompleted 中传 flowExecutionContext: false。

Awaiter struct vs class 的性能：

TaskAwaiter、ValueTaskAwaiter、UniTask 的 Awaiter 都是 struct。这意味着 GetAwaiter() 不分配——awaiter 在栈上创建，用完即弃。如果 awaiter 是 class，每次 await 都会堆分配一个 awaiter 对象，在高频 await 路径（如每帧 await）上造成 GC 压力。

Unity 场景：

UniTask 为 Unity 的 AsyncOperation、UnityWebRequestAsyncOperation 等 20+ 类型提供了 struct awaiter，避免每次 await 产生分配。自定义 awaiter 时也应优先用 struct。

6. ExecutionContext 流动

ExecutionContext 是环境状态的容器——AsyncLocal<T> 的值、安全上下文、逻辑调用上下文等都存在其中。

async/await 中的流动机制：

  1. 方法在 await 处挂起时，Builder 捕获当前 ExecutionContext
  2. Continuation 被调度执行时，通过 ExecutionContext.Run(capturedContext, callback) 恢复
  3. 整个 async 方法的所有 await 点共享同一份 captured context（由 MoveNextRunner 持有）

流动的成本：

  • 每次 suspend 都要 ExecutionContext.Capture()（复制 AsyncLocal 字典等）
  • 每次 resume 都要 ExecutionContext.Run()（设置/恢复线程状态）
  • 高频 await 路径（如每帧 await NextFrameAsync）上，这个开销不可忽视

抑制流动（UnsafeOnCompleted）：

当 awaiter 实现 ICriticalNotifyCompletion 时，Builder 调用 UnsafeOnCompleted 而非 OnCompleted。此时 ExecutionContext 不会被 capture/restore，但 Builder 自身通过 MoveNextRunner 单独管理了一次 capture（整个方法共享一份），避免每个 await 点重复捕获。

为什么库代码应该用 UnsafeOnCompleted：

库内部不需要也不应该依赖调用者的 AsyncLocal<T> 传播。使用 UnsafeOnCompleted 可以避免每次 await 的 capture/restore 开销。这也是 TaskAwaiter.UnsafeOnCompleted 的设计意图。

Unity 中的 AsyncLocal：

Unity 主线程的 AsyncLocal<T> 在跨 await 时能正确流动（因为 UnitySynchronizationContext 保证回到主线程）。但 Awaitable.BackgroundThreadAsync() 切到后台线程后，AsyncLocal<T> 仍然流动（通过 ExecutionContext），不会丢失。

7. SynchronizationContext 捕获

SynchronizationContext 是调度目标的抽象——“continuation 应该在哪里运行”。

await 中的捕获机制：

  1. await 遇到未完成的 Task 时，TaskAwaiter 检查 SynchronizationContext.Current
  2. 如果存在非默认 SynchronizationContext → 捕获它
  3. Task 完成时，continuation 被投递到捕获的 context（通过 Post）

ConfigureAwait(false) 的作用：

告诉 TaskAwaiter 不要捕获 SynchronizationContext——continuation 直接在线程池或完成线程上执行，省去 Post 的开销和线程切换。

自定义 SynchronizationContext 实现：

实现Post 行为典型场景
默认（基类）ThreadPool.QueueUserWorkItem控制台、ASP.NET Core
DispatcherSynchronizationContextDispatcher.BeginInvokeWPF
WindowsFormsSynchronizationContextControl.BeginInvokeWinForms
UnitySynchronizationContextPlayerLoop 队列Unity

UnitySynchronizationContext：

Unity 的自定义实现把 continuation 排入 PlayerLoop 队列，在下一帧的特定阶段执行。这意味着：

  • 主线程上 await Task.Delay(100) 后，continuation 不一定在 100ms 后立即执行——要等到下一个 PlayerLoop 周期
  • 这是 UniTask 选择不走 SynchronizationContext 的核心原因：直接注册到 PlayerLoopTiming 更精确、更少延迟

单线程 SynchronizationContext 的死锁陷阱：

Unity 中永远不要在主线程上同步阻塞等待 async 方法

Task.Wait()、Task.Result、GetAwaiter().GetResult() 在单线程 SynchronizationContext 上都会死锁。Unity 主线程尤其如此。

8. IValueTaskSource

ValueTask 可以包装两种后端：一个已完成的 TResult（零分配）或一个 Task（堆分配）。.NET Core 2.1 引入第三种：IValueTaskSource——自定义的可池化后端对象。

接口定义：

三个方法的角色：

方法调用时机作用
GetStatusawait 时检查状态返回 Pending / Succeeded / Faulted / Canceled
OnCompletedawait 时 awaiter.IsCompleted 为 false注册 continuation；如果已完成则立即调用
GetResultcontinuation 执行后获取结果或抛出异常；仅调用一次

池化模式：

何时值得使用：

  • 高频 async 操作（如网络 socket 每秒数千次读取）且大部分异步完成
  • 需要消除 async ValueTask<T> 挂起时的 Task 分配
  • 可以复用同一池化对象（同一方法的不同调用轮流使用池中对象）

ValueTask 的使用约束同样适用于 IValueTaskSource

  • 每个 ValueTask 只能 await 一次
  • 不能存储 ValueTask 供后续多次 await
  • 需要多次 await 时用 .Preserve()（UniTask）或转为 Task

ManualResetValueTaskSourceCore：

.NET 提供了 ManualResetValueTaskSourceCore<T> 结构体，封装了 IValueTaskSource 的核心逻辑（版本号管理、continuation 管理、ExecutionContext/SynchronizationContext 处理），避免从零实现。ASP.NET Core 和 .NET 网络栈内部大量使用此辅助类型。

.NET 5+ 的自动池化：

设置环境变量 DOTNET_SYSTEM_THREADING_POOLASYNCVALUETASKS=1 后，AsyncValueTaskMethodBuilder 自动使用池化 IValueTaskSource 对象替代 Task，使 async ValueTask<T> 的异步路径也几乎零分配。Unity 运行时中此特性不可用——UniTask 通过自己的 TaskPool<> 实现了等价效果。

10. 反模式

理解状态机但仍然写阻塞代码

task.Result、task.Wait()、task.GetAwaiter().GetResult() 在有 SynchronizationContext 的线程上会死锁。即使没有 SynchronizationContext，同步阻塞也浪费线程资源。Unity 主线程上尤其危险——这是最常见的 async 反模式。

假设 async 保留线程亲和性

async 不保证 await 之后回到原线程。回到哪个线程取决于 SynchronizationContext 和 awaitable 类型。Unity 主线程上 await Task.Run(...) 之后，continuation 可能回到主线程（有 UnitySynchronizationContext），也可能不回（ConfigureAwait(false)）。用 Awaitable.MainThreadAsync() 或 UniTask.SwitchToMainThread() 显式控制。

async 方法从不 await（CS1998）

编译器警告 CS1998 表示方法标记了 async 但没有 await。这样的方法仍会生成完整状态机——不必要的开销。要么去掉 async 直接返回 Task.FromResult()，要么确实需要 async 就加上 await。

状态机装箱为接口

Release 构建中状态机是 struct。当它需要被存储为 IAsyncStateMachine 引用时（suspend 时 box 到堆上），会发生装箱。这是 async 方法挂起时唯一的必要分配。UniTask 通过池化 IUniTaskSource 对象来复用这些装箱，避免每次 suspend 分配新对象。

库代码忘记 ConfigureAwait(false)

库代码中不加 ConfigureAwait(false) 意味着每个 await 都可能捕获 SynchronizationContext 并 Post 回去——不必要地依赖调用者的上下文、增加线程切换和延迟。.NET 库开发规范：库代码一律 ConfigureAwait(false)。Unity 中如果后续需要访问 UnityEngine API，则不能加 ConfigureAwait(false)——必须回到主线程。

自定义 awaiter 泄漏内存

实现 ICriticalNotifyCompletion.UnsafeOnCompleted 时，如果 continuation 被存储但从未被调用（如底层操作完成但忘记触发 continuation），注册的 delegate 和它捕获的闭包会永远无法被 GC。自定义 awaiter 必须保证：要么最终调用 continuation，要么提供取消/超时机制释放引用。

ValueTask 被多次 await

ValueTask 不是 Task——它可能包装池化对象，await 后对象被归还到池。再次 await 同一个 ValueTask 实例是未定义行为。需要存储或多次 await 时，先 .AsTask() 转为 Task，或使用 UniTask 的 .Preserve()。

权衡与选择

  • Task 适合通用 .NET 异步；Unity 高频/跨帧场景考虑 ValueTask、Awaitable 或 UniTask
  • ValueTask 在同步路径零分配，但使用约束严格；需要池化时实现 IValueTaskSource
  • 自定义 builder 接入 async/await 的门槛不高，但正确处理 ExecutionContext/SynchronizationContext/boxing 需要深入理解
  • 状态机让异常传播比 Coroutine 更自然，但未 await 的 Task 仍容易丢失错误
  • Unity Editor（Debug 构建）的 async 额外开销在生产构建中不存在——不要以 Editor 表现评判 async 性能
