.NET Native AOT

核心思想

Native AOT 在 publish 阶段把 IL ahead-of-time 编译成平台原生的 machine code，生成自包含应用。运行时完全不依赖 JIT 编译器，因此启动更快、内存占用更小，也能部署在不允许 JIT 的受限环境（如 iOS、某些云沙箱）。

核心权衡可以概括为一句话：提前编译换取部署可预测性和平台合规性，同时牺牲运行时动态能力。理解这个权衡，是理解所有 AOT 限制（反射、裁剪、泛型膨胀、序列化兼容）的钥匙。

虽然 Unity IL2CPP 与 .NET Native AOT 不是同一个工具链，但它们都体现了 AOT 的同一套核心约束。理解 Native AOT，有助于理解游戏构建中常见的反射限制、裁剪警告、泛型膨胀和代码生成替代方案。

编译管线

Native AOT 的编译管线是一条从托管 IL 到原生二进制的单向流水线：

flowchart LR
    A["C# 源码"] --> B["Roslyn 编译"]
    B --> C["IL 程序集"]
    C --> D["静态分析<br/>(数据流 + 反射追踪)"]
    D --> E["裁剪<br/>(Trimmer)"]
    E --> F["泛型特化<br/>(值类型实例化)"]
    F --> G["ILC 编译器<br/>(IL → native)"]
    G --> H["原生二进制<br/>(.exe / .so / .dll)"]

关键阶段说明：

  1. Roslyn 编译：C# 源码编译为标准 IL 程序集，这一步与普通 .NET 构建完全一致
  2. 静态分析：ILC（IL Compiler）对整个应用及其依赖做数据流分析，追踪反射调用、动态类型访问等，生成裁剪决策
  3. 裁剪：基于分析结果，移除未被静态可达的代码和数据
  4. 泛型特化：为每个值类型泛型实例化生成专门的 native code（引用类型可共享实现）
  5. ILC 编译：将分析后的 IL 编译为目标平台的 native code，使用 RyuJIT 的代码生成后端

与 JIT 管线的关键差异

JIT 管线是”运行时按需编译”——只有实际执行到的代码才被编译，反射和动态加载自然得到支持。AOT 管线是”构建时全量分析”——编译器必须在 publish 时确定所有需要保留的代码，任何运行时才揭晓的类型访问都会导致问题。

裁剪系统

裁剪（Trimming）是 Native AOT 的前置步骤——移除静态分析认为”不可达”的代码。裁剪不是可选的，它是 AOT 编译的前提。

裁剪级别

TrimMode行为适用场景
full（默认）裁剪器积极移除所有未被静态可达的成员发布生产二进制
partial仅裁剪标记为 IsTrimmable 的程序集，其余保留渐进式迁移，兼容性测试

full 模式可能"过度裁剪"

full 模式下，如果代码通过反射访问的成员没有正确标注，裁剪器会误删这些成员，导致运行时 MissingMethodException 或 NullReferenceException。必须确保所有反射访问都有对应的裁剪标注。

DynamicallyAccessedMembers 标注

这是让裁剪器理解反射意图的核心机制。它创建一个”契约”：告诉裁剪器某个 Type 上需要保留哪些成员。

常用 DynamicallyAccessedMemberTypes 值：

值保留的成员
All所有成员（慎用，会膨胀体积）
PublicMethods公共方法
PublicProperties公共属性
PublicConstructors公共构造函数
NonPublicMethods非公共方法
Interfaces实现的接口

标注必须贯穿整个调用链

DynamicallyAccessedMembers 的要求从反射调用点逆向传播到 Type 值的来源。如果调用链中间某一层没有标注，警告仍然会出现。必须确保从反射使用处回溯到 typeof() 入口的每一步参数都标注了相同或更宽的要求。

泛型特化

值类型实例化生成独立代码

.NET 的泛型在运行时对值类型和引用类型采取不同策略：

  • 引用类型：共享一份 native code（因为引用都是指针大小，内存布局一致）
  • 值类型：每个不同的泛型实参组合生成一份专门的 native code（因为内存布局不同）

这意味着：

在 JIT 模式下这不是大问题——运行时按需编译，只编译实际用到的实例化。但在 Native AOT 中，编译器必须在 publish 时确定所有需要编译的实例化，否则运行时会因为找不到对应代码而崩溃。

传递闭包膨胀

一个看似简单的泛型类型，其传递闭包可能涉及大量类型。例如 List<T> 的传递闭包包含约 28 个类型——包括枚举器、比较器、集合调试视图等。每个值类型实例化都会复制整条链。

值类型泛型是 AOT 体积膨胀的主要来源

在 Native AOT 中，每个值类型泛型实例化都会生成独立的 native code。大量使用值类型泛型（尤其是嵌套泛型，如 Dictionary<int, List<float>>）会导致二进制体积显著膨胀。这是 AOT 的固有特性，不是 bug。

反射创建泛型实例化的问题

MakeGenericType 要求运行时存在对应值类型实例化的 native code，但 AOT 编译器无法从静态分析中确定需要编译哪些实例化。即使对引用类型使用 MakeGenericType，也可能因为静态抽象接口方法等特性而失败。

基于反射的插件系统（如扫描程序集查找实现某接口的类型）在 AOT 下完全不可行。替代方案：编译时代码生成、显式注册表模式、或预定义插件清单。

核心差异：IL2CPP 的”C++ 转译”策略让它在跨平台构建上更灵活（C++ 编译器遍地都是），但牺牲了代码优化质量和调试体验。Native AOT 直接从 IL 到 native，优化路径更短更可控，但要求目标平台的构建工具链。

核心差异：Burst 是一个”计算编译器”——它只编译一个小子集的 C#，但在这个子集内做到极致优化（SIMD、向量化）。Native AOT 是一个”应用编译器”——它编译完整的 C#，但优化目标是通用场景。两者解决的是完全不同的问题。

理解 AOT 的统一视角

Native AOT / IL2CPP / Burst 三者虽然工具链完全不同，但都受同一套 AOT 约束：编译时必须确定所有代码路径、反射受限、值类型泛型膨胀。理解这套约束，就能在 Unity 项目中更快定位”为什么这个库在 Player 构建中不工作”。

游戏开发启示

虽然 Unity 当前使用 IL2CPP 而非 .NET Native AOT，但理解 Native AOT 的约束体系对游戏开发者有直接价值：

  1. 理解 IL2CPP 的限制来源：IL2CPP 的反射限制、link.xml 需求、泛型膨胀，与 Native AOT 面对的是同一套问题。理解裁剪标注体系，就能理解为什么 Unity 需要 [Preserve] 和 link.xml。

  2. 库选型的 AOT 意识：在 Unity 项目中使用 NuGet 包时，AOT 兼容性是重要考量。依赖反射的库在 IL2CPP 构建中同样会出问题。

  3. 序列化架构设计：游戏存档、配置系统、网络协议——这些序列化场景在 AOT 环境下必须用 Source Generator 或显式注册模式，不能依赖反射。

  4. 泛型使用策略：在 Burst Job 中大量使用值类型泛型是合理的（Burst 会优化），但在托管代码中过度使用值类型泛型组合会导致构建体积膨胀。

  5. Unity CoreCLR 迁移的前瞻：Unity 计划在 6.7 提供实验性 CoreCLR 桌面 Player，6.8 将 CoreCLR 设为唯一运行时。届时 .NET 生态中 AOT 兼容库的成熟度将直接影响 Unity 项目的可用库范围。

  6. Source Generator 思维：养成”编译时生成而非运行时反射”的编程习惯。这不仅对 AOT 友好，也对启动性能有利。

反模式

在 AOT 中使用 Assembly.LoadFile 动态加载程序集

Native AOT 编译产生单一原生二进制，不存在独立的程序集文件可供运行时加载。所有代码必须在 publish 时静态可达。如果需要插件系统，改用编译时代码生成或预定义注册表。

使用 System.Reflection.Emit 在运行时生成 IL

Native AOT 没有 JIT 编译器，无法将运行时生成的 IL 编译为机器码。DynamicMethod、AssemblyBuilder 等类型在 AOT 下不可用。替代方案：Source Generator、表达式树（有限支持）、手写代码生成器。

通过 Type.GetType(string) 从字符串加载类型

裁剪器无法从字符串推断目标类型，对应的类型元数据可能已被移除。AOT 发布时会生成 IL2057 警告。替代方案：使用 typeof() 显式引用，或用 DynamicallyAccessedMembers 标注。

忽略裁剪警告直接发布

裁剪警告（IL2xxx / IL3xxx）不是”建议”，是”运行时必然出错的前兆”。一个没有裁剪警告的 AOT 应用，其行为保证与 JIT 模式一致。有警告则可能在运行时抛出 MissingMethodException 等异常。必须在发布前清零所有裁剪警告。

在 AOT 项目中继续使用 Newtonsoft.Json

Json.NET 的核心架构依赖运行时反射遍历属性树，没有 Source Generator 模式，无法在 AOT 下工作。即使你的项目不是 Native AOT，如果未来可能迁移到 Unity CoreCLR + AOT，现在就应规划向 System.Text.Json 的迁移。

大量嵌套值类型泛型组合

Dictionary<int, List<Vector3>> 这种嵌套泛型在值类型上的组合，每个实例化都会生成独立的 native code。在游戏代码中，对值类型泛型保持克制：热路径手写特化，非热路径可接受，但要避免大量排列组合（如 ECS 中每个组件类型 x 每个查询组合都生成独立代码）。

在泛型方法中使用未约束的反射

在泛型上下文中，编译器不知道 T 的具体类型，无法确定需要保留哪些属性。解决方案：对 T 添加 DynamicallyAccessedMembers 约束，或在调用方显式传递类型信息。

假设 AOT 编译的代码比 JIT 更快

AOT 的优势是启动速度和部署形态，而非峰值吞吐量。JIT 可以根据运行时 CPU 特性进行针对性优化（如利用 AVX2/AVX-512），AOT 编译时只能针对通用指令集。长时间运行的服务端应用，JIT 的峰值性能往往优于 AOT。
