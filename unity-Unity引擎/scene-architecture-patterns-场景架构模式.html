场景架构模式

核心思想

场景不只是”关卡的容器”——它是 Unity 中组织子系统、管理生命周期、控制内存和实现团队协作的架构单元。场景架构模式决定了（1）如何拆分功能到独立场景（2）场景之间如何通信（3）何时加载/卸载哪个场景。正确的场景架构可以让大型项目保持可维护性，错误的架构会导致耦合、内存泄漏和难以调试的生命周期问题。

为什么重要

在游戏开发中，场景架构直接影响：

  • 性能：场景加载/卸载的时序和粒度决定内存峰值和帧率卡顿
  • 团队协作：不同团队能否并行编辑不同场景而减少 Git 冲突
  • 可维护性：子系统是否独立、可测试、可替换
  • 热更新：能否通过 Addressables 远程更新部分场景内容

DontDestroyOnLoad 与 Addressables 的冲突

从 Addressable 场景中 DontDestroyOnLoad 的对象会导致 AssetBundle 引用问题：

  • Addressables 通过 AssetBundle 管理资源生命周期
  • DontDestroyOnLoad 把对象移到持久场景，脱离了 AssetBundle 的管理
  • 如果 AssetBundle 被卸载（引用计数归零），DontDestroyOnLoad 对象引用的材质、贴图等会丢失

解决方案：

  1. 将 DontDestroyOnLoad 对象作为独立 Addressable 加载，与场景 AssetBundle 分离
  2. 使用 ResourceManager.Acquire 增加引用计数，防止 AssetBundle 过早卸载
  3. 避免在 Addressable 场景中使用 DontDestroyOnLoad，改用 PersistentManagers 场景模式

项目规模选择

小型项目用 SceneManager + Build Settings 足够。中大型项目，尤其是需要内容更新或远程加载的场景，应迁移到 Addressables。两者可以共存——主流程用 Addressables，启动场景用 SceneManager。

跨场景引用

问题

Unity 默认禁止跨场景引用（EditorSceneManager.preventCrossSceneReferences = true）。场景 A 中的对象不能在 Inspector 中拖拽引用场景 B 中的对象——这种引用无法序列化到场景文件中。

运行时 additive 加载后，代码中可以通过 Find/GetComponent 获取其他场景的对象，但当场景 B 卸载后，场景 A 持有的引用会指向已销毁对象——这是最常见的运行时 null 引用来源之一。

解决方案

方案原理优点缺点
ScriptableObject 事件通道通过 SO 作为中间层解耦，不直接引用零耦合、可 Inspector 配置需要为每种事件定义 SO
字符串/GUID 运行时查找存储标识符而非直接引用，运行时查找灵活、支持跨场景查找有性能开销、字符串易错
依赖注入框架Zenject/VContainer 注入跨场景依赖类型安全、可测试引入框架复杂度
注册模式目标对象在 Start 中将自己注册到管理器简单直接管理器成为耦合点
场景查询Find/GetComponent/Interface 查找无额外架构性能差、时序不可靠

ScriptableObject 事件通道

ScriptableObject 作为资产独立于场景存在，可被任何场景的对象引用，天然解决跨场景通信问题。

注册模式

跨场景引用在运行时断裂

场景 A 中的对象引用场景 B 中的对象——当场景 B 卸载后，引用指向已销毁对象（Unity 假 null）。Unity 不提供跨场景引用的自动保护。additive 架构中应通过事件/接口解耦，或使用 ScriptableObject 作为中介。

ECS SubScene

DOTS/ECS 使用 SubScene 组件将 GameObject 场景烘焙为 ECS 实体数据：

  • Authoring Scene：包含 GameObject 的场景，用于编辑和烘焙
  • Entity Scene：烘焙后的 ECS 数据，运行时加载
  • SceneSection：实体场景的分段，支持流式加载
  • SceneSystem.LoadSceneAsync：ECS 运行时场景加载 API（非 SceneManager）
  • EntitySceneReference：推荐使用，替代 GUID 引用场景

SubScene 与 SceneManager 的关系

SubScene 在编辑器中使用 EditorSceneManager 管理场景文件，运行时通过 ECS 的 SceneSystem 加载实体场景数据——不经过 SceneManager。SubScene 内的对象在烘焙后变成 ECS Entity，不再是 MonoBehaviour/GameObject。详见 ECS。

常见陷阱

跨场景引用在运行时断裂

场景 A 中的对象引用场景 B 中的对象——当场景 B 卸载后，引用指向已销毁对象（Unity 假 null）。Unity 不提供跨场景引用的自动保护。additive 架构中应通过事件/接口解耦，或使用 ScriptableObject 作为中介。

DontDestroyOnLoad 与 Addressables 的冲突

从 Addressable 场景中 DontDestroyOnLoad 的对象，其引用的材质、贴图等资源可能因 AssetBundle 被卸载而丢失。应使用 PersistentManagers 场景模式替代，或将对象作为独立 Addressable 加载。

additive 加载后忘记设置 Active Scene

Additive 加载新场景后，active scene 仍然是原来的。新创建的 GameObject 会进入旧场景而非新场景。加载后应显式 SetActiveScene。
