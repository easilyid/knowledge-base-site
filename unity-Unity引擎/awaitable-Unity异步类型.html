Unity Awaitable

是什么

Awaitable 是 Unity 官方提供的 async/await 友好类型（UnityEngine.Awaitable），用来在 Unity 的 PlayerLoop 系统（PlayerLoop System） 中表达下一帧、帧末、固定更新、时间等待、主线程/后台线程切换等操作。

它与 .NET Task 一样可被 await，但设计目标更偏 Unity：低 GC（池化实例）、PlayerLoop 感知、continuation 同步执行、主线程语义明确。Awaitable<T> 是其泛型版本，支持返回类型化结果。

兼容 Unity 2023.1 及以上（Awaitable 首次引入）。Unity 6+ 为推荐版本，API 稳定且文档完整。

Awaiter 模式的核心

任何类型只要提供 GetAwaiter() 方法（实例方法或扩展方法），返回的对象实现 INotifyCompletion + IsCompleted + GetResult()，就能被 await。Unity 2023+ 的 AsyncOperation 已内置 awaiter 支持，此模式主要用于旧版本兼容。

自定义 Awaiter 不走 UnitySynchronizationContext

此 awaiter 的 continuation 在 completed 回调线程上执行（通常是主线程），但不会经过 UnitySynchronizationContext.Post。与 Awaitable 的同步 continuation 语义一致，但缺少 CancellationToken 支持。

池化机制与 Continuation 语义

Awaitable 采用**内部对象池**管理实例：工厂方法从池中取出实例，await 完成后立即归还，帧循环中零分配。重要约束：同一 Awaitable 实例只能被 await 一次，完成后实例已归还池，再次 await 会导致 NullReferenceException 或死锁。

Continuation 语义与 Task 根本不同：completion 触发时，continuation 同步执行，不经过 SynchronizationContext.Post，代码在同帧立即恢复。长链路中若每步都同步完成，调用栈深度 = 链长度，极端情况可能 StackOverflowException——可定期插入 await Awaitable.NextFrameAsync() 打断。

线程切换：MainThreadAsync() 从后台切回主线程（至少一帧延迟），BackgroundThreadAsync() 切到 ThreadPool。线程切换指令只影响当前方法，不影响调用方。

详见 Awaitable 池化与 Continuation 语义，含池化 vs Task 对比表、重复 await 危险示例、线程安全一览。

Awaitable + Job System 集成

官方推荐的”帧末调度、下帧完成”模式：在 EndOfFrameAsync 后调度 Job（此时主渲染、物理已完成），NextFrameAsync 后完成并读取结果，不阻塞主线程。BackgroundThreadAsync 不能替代 Job System——它是单线程、不支持 Burst、无内存安全保障。

详见 Awaitable + Job System 集成，含骨骼动画后处理完整示例和 Job System vs BackgroundThreadAsync 对比表。

Awaitable vs UniTask 对比

Awaitable 是官方内置方案（零依赖，适合公共库和简单场景），UniTask 功能更全（WhenAll/异步流/细粒度 PlayerLoopTiming）。Awaitable 不等于 UniTask 替代品，而是 Coroutine 的 async/await 等价物。详细对比见 Awaitable 与 UniTask 对比。

Cancellation 详解

Unity Awaitable 使用 .NET CancellationToken 实现协作式取消，通过 destroyCancellationToken 绑定对象生命周期、CreateLinkedTokenSource 组合多取消源。finally 块保证资源清理，比 StopCoroutine 更安全。Awaitable.Cancel() 因池化风险不推荐使用。详细说明见 Awaitable Cancellation 详解。
