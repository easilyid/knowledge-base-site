MonoBehaviour

是什么

MonoBehaviour 是 Unity 经典脚本的基类。它总是作为 Component 挂在某个 GameObject 上，通过 Unity 发送的生命周期消息接入引擎主循环。几乎所有 Unity 项目的游戏逻辑都从 MonoBehaviour 派生开始——它是 GameObject 组件体系中”行为”的标准载体。

MonoBehaviour 不用 new 创建，而是通过挂载脚本、Prefab 实例化或 AddComponent<T>() 创建：

关键细节

生命周期消息

MonoBehaviour 接收的生命周期消息分为以下几类，完整执行顺序详见 MonoBehaviour 生命周期：

分类方法说明
初始化Awake / OnEnable / Start对象创建和首次启用
更新Update / FixedUpdate / LateUpdate每帧/每物理步回调
禁用销毁OnDisable / OnDestroy组件或对象停用/销毁
物理OnCollisionEnter / OnCollisionStay / OnCollisionExit碰撞回调
物理（触发器）OnTriggerEnter / OnTriggerStay / OnTriggerExit触发器回调
渲染OnPreRender / OnPostRender / OnRenderObject渲染管线回调
应用OnApplicationPause / OnApplicationFocus / OnApplicationQuit应用生命周期
编辑器OnValidate / ResetInspector 变更回调

enabled 与 active

enabled = false 时：Update/FixedUpdate/LateUpdate 不再调用，但 Awake/Start/OnEnable/OnDisable/OnDestroy 等生命周期消息仍会触发。

Unity 假 null 与 C# null 语义不一致

obj == null 走 Unity 重载（检查 native 对象是否销毁），但 obj?. 和 obj ?? 走 C# 默认语义（只检查引用是否为 null）。销毁后未 GC 的对象上用 ?. 会跳过 null 检查直接访问，导致 MissingReferenceException。在协程和回调中尤其常见——对象可能已 Destroy 但协程仍在运行。

runInEditMode 与 ExecuteInEditMode

Edit 模式脚本的副作用

ExecuteInEditMode 的 Update 在编辑器中每帧都会调用（Inspector 变化、场景视图重绘等）。不要在其中放重计算或修改场景状态的代码——这些修改在退出 Play 模式时不会被自动还原。

游戏开发深度

MonoBehaviour 的虚调用成本

Unity 内部通过 native→managed 桥接调用 Update/FixedUpdate/LateUpdate——每次调用涉及：

  1. 查找托管方法指针
  2. 从 native 上下文切换到 managed 上下文
  3. 虚方法分派

单个调用的开销很小（~微秒级），但场景中有 1000+ 个活跃 MonoBehaviour 时累积不可忽视。集中式 Update Manager（参见 GameObject 与 Component）通过接口列表遍历消除虚调用。

MonoBehaviour.enabled = false 不停止协程

enabled = false 时协程不会自动停止

很多开发者以为禁用脚本就停掉协程，实际上只有 GameObject.SetActive(false) 才会停止协程。enabled = false 只停止 Update 等回调。必须在 OnDisable 中显式 StopAllCoroutines() 或 StopCoroutine(coroutineRef)。

MonoBehaviour 中使用 async/await

async void 的异常会直接抛到 SyncContext

async void 方法中未捕获的异常会导致应用崩溃（不像 async Task 会被放到 Task 的异常中）。务必在 async void 中 try-catch，或改用 async Awaitable（Unity 6+）。

Reset 与 OnValidate 的编辑器工作流

Reset 是给设计器设默认值的最佳位置——比字段初始化器更可靠（字段初始化器在序列化后被覆盖）。

反模式

不要用构造函数做 Unity 初始化

Unity 序列化字段在构造阶段未必处于可用状态。初始化引用和状态通常用 Awake / Start。构造函数在 Unity 的序列化/反序列化流程中也会被调用（编辑器中），可能产生意外行为。

async void 生命周期不自动绑定 MonoBehaviour

async 任务不会因为宿主销毁自动停止，除非显式使用 CancellationToken 或 Unity 6 的 destroyCancellationToken。协程则自动随宿主停用/销毁而停止——这是协程相对 async/await 的一个便利优势。

空的 OnGUI 也会引入 IMGUI 处理开销

Unity Manual 明确提示：即使空 OnGUI 也会把 IMGUI processing 加入帧处理过程。除非需要 IMGUI，否则不要声明此方法。

在 Update 中用 Invoke/InvokeRepeating 重复注册

InvokeRepeating 是全局注册，不需要每帧调用。在 Update 中反复注册会导致同一方法被多次调度，产生指数级调用。

依赖不同 GameObject 间同名回调的执行顺序

Unity 不保证不同 GameObject 上 Awake/Start/Update 的调用顺序。如果 A 必须在 B 之前初始化，用 [DefaultExecutionOrder] 或在 Start 中显式调用 A 的初始化方法——不要依赖隐式顺序。

MonoBehaviour 上用 ?. 和 ?? 操作符

销毁后的 Unity Object 的 ?. 和 ?? 不走 Unity 的 null 重载，可能跳过检查导致 MissingReferenceException。在协程回调和延迟逻辑中务必用 if (this != null) 显式检查。
