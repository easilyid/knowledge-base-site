ScriptableObject 深入（ScriptableObject Deep Dive）

本页是 ScriptableObject 实体页的扩展，聚焦生命周期、持久化语义、架构模式与生产级陷阱。基础定义参见主页面。

核心思想

ScriptableObject 的核心价值是”共享引用而非复制数据”的享元模式——但它同时也是 Unity 中最容易因生命周期和持久化语义被误用的类型。理解它在 Editor 和 Player 中的不同行为，是避免生产 Bug 的前提。

1. 生命周期回调

ScriptableObject 提供的回调比 MonoBehaviour 少得多：没有 Start、Update、FixedUpdate，只有四个生命周期消息。

回调总览

回调触发时机典型用途
Awake()实例首次创建时一次性初始化（只在 CreateInstance 或首次加载时触发）
OnEnable()对象被加载到内存时订阅事件、重置运行时状态
OnDisable()对象离开作用域时取消事件订阅
OnDestroy()对象即将被销毁时释放非托管资源

OnEnable 触发场景（官方文档完整列表）

  • Editor 启动时，所有在打开场景中被引用的 ScriptableObject
  • 通过 CreateAssetMenu 在 Editor 中创建新资产时
  • 运行时通过 ScriptableObject.CreateInstance<T>() 实例化时
  • 运行时加载包含该 ScriptableObject 引用的资产时
  • Domain Reload 时，所有已加载的 ScriptableObject（先 OnDisable 再 OnEnable）
  • 首次加载包含该 ScriptableObject 引用的场景时
  • 在 Project 窗口首次选中该资产时（如果之前被 GC 回收了）

OnDisable 触发场景

  • 加载新场景时，当前加载但新场景未引用的 ScriptableObject
  • Resources.UnloadUnusedAssets 被调用时
  • Domain Reload 时（所有已加载的 ScriptableObject）

关键区别：Awake vs OnEnable

Awake 不在进入 Play Mode 时重新触发

作为资产保存的 ScriptableObject，Awake 只在首次创建时调用。进入 Play Mode 时，OnEnable 会触发（因为有 Domain Reload），但 Awake 不会。运行时初始化逻辑应放在 OnEnable 而非 Awake 中。

Domain Reload 关闭时的影响

当 Project Settings 中关闭 “Enter Play Mode Options → Reload Domain” 时：

  • OnEnable / OnDisable 不会在进入/退出 Play Mode 时触发
  • ScriptableObject 的运行时状态不会自动重置
  • 必须使用 EditorApplication.playModeStateChanged 手动处理重置

2. 运行时 vs Editor 持久化

这是 ScriptableObject 被误用最频繁的领域。理解”什么活下来、什么不活”是核心。

持久化矩阵

操作Editor Play ModeEditor 退出 Play ModeBuild 重启
修改序列化字段内存中保留，写入磁盘（直接修改 .asset）变更保留（因为已写入 .asset）变更丢失（build 中无 AssetDatabase，数据来自编译时的序列化快照）
修改非序列化字段 ([NonSerialized])内存中保留变更丢失变更丢失
CreateInstance<T>() 创建的运行时实例内存中保留实例销毁实例销毁
Domain Reload 关闭 + 运行时修改保留（无 Reload）取决于是否退出 Play Mode丢失

关键原则

Build 中 ScriptableObject 是不可变配置

在编译出的 Player 中，ScriptableObject 被序列化进游戏数据文件，运行时无法写回磁盘。修改只存在于当前会话的内存中，应用重启后恢复为构建时的原始值。

因此：

  • 不可变配置（武器属性、关卡参数）→ ScriptableObject 天然适合
  • 可变运行时状态（当前血量、已解锁关卡）→ 不应存放在 ScriptableObject 上，应使用 PlayerPrefs、JSON 序列化到 Application.persistentDataPath、或内存中的 plain C# 对象

运行时可变副本模式

当需要运行时修改 ScriptableObject 数据又不想污染原始资产时：

Ryan Hipple 的建议

为运行时变量 SO 添加 HideFlags.DontUnloadUnusedAsset，防止无引用时被意外卸载。

4. ScriptableObject 作为运行时数据容器

不可变配置 vs 可变状态

数据类别存放位置原因
武器基础伤害、移动速度等设计参数ScriptableObject 序列化字段只读、共享、Inspector 可编辑
运行时当前血量、Buff 修正值MonoBehaviour 或 plain C# 对象的 [NonSerialized] 字段每个实例独立、不应污染共享资产
全局游戏状态（分数、关卡进度）ScriptableObject 的 [NonSerialized] 字段 + 外部持久化运行时可变但 Build 中需保存到磁盘

线程安全

ScriptableObject 不是线程安全的

Unity 的核心运行时是单线程的，ScriptableObject 继承自 UnityEngine.Object，其所有 API（包括字段访问和序列化）只能在主线程上执行。在 Job System 或 Task 中直接访问 ScriptableObject 字段会导致错误或未定义行为。

正确做法：

  • 在主线程上将 ScriptableObject 的配置数据拷贝到 NativeContainer（如 NativeArray、NativeHashMap）
  • 将 NativeContainer 传入 Job
  • Job 完成后在主线程读取结果

5. ScriptableObject vs MonoBehaviour 共享数据

内存对比

维度MonoBehaviour（每实例独立数据）ScriptableObject（共享引用）
1000 个敌人各带 10 个 float 字段1000 份数据拷贝1 份数据 + 1000 个引用
每实例额外开销~320 bytes（UnityEngine.Object 头） + Transform + GameObject仅引用（8 bytes 64位）
ScriptableObject 自身开销—~320 bytes (Player) / ~424 bytes (Editor)
场景文件膨胀每个实例序列化完整数据仅序列化引用

何时 ScriptableObject 才有内存优势

只有当共享数据被多个实例引用且数据量有一定规模时，ScriptableObject 才比每实例复制更省内存。如果只有一个消费者，ScriptableObject 反而多了 ~320 bytes 的 UnityEngine.Object 头部开销。

GC 影响

  • ScriptableObject 字段本身：作为 UnityEngine.Object 派生类，实例在 native 侧分配，不受 C# GC 管理。Destroy 后 native 资源释放，C# 侧包装对象等 GC 回收。
  • ScriptableObject 内部的引用类型字段（List<T>、string[] 等）：分配在 managed heap 上，与 MonoBehaviour 中的同类字段 GC 行为一致。
  • 访问模式：从 ScriptableObject 读取值没有额外 GC 分配（直接字段访问），但如果通过 UnityEvent.Invoke() 触发事件通道，会产生每次调用的 delegate 分配。

6. 序列化边界情况

[SerializeReference] 与多态序列化

ScriptableObject 的字段默认不支持多态——如果字段类型是基类，序列化后只会保留基类字段，派生类新增字段会丢失。

方案 1：[SerializeReference]（Unity 2019.3+）

方案 2：ScriptableObject 子类资产

SerializeReference 的局限性

  • 不能用于 struct（只支持 reference type）
  • Prefab 中 SerializeReference 字段有已知的边缘 Bug
  • 类型丢失（类被删除/重命名）会导致 Managed references with missing types 警告，数据无法恢复
  • 直接自引用循环会被忽略，间接循环限制 10 层递归
  • 同一对象被多个 SerializeReference 字段引用时，Inspector 中添加元素可能共享引用而非复制

ISerializationCallbackReceiver

ScriptableObject 可实现 ISerializationCallbackReceiver，用于序列化前/反序列化后的数据变换：

OnAfterDeserialize 在非主线程执行

OnAfterDeserialize 在 Unity 的序列化线程上执行，不能调用任何 Unity 主线程 API（如 GameObject.Find、Debug.Log 在某些版本中等）。只应处理字段级别的数据变换。

OnAfterDeserialize 对 ScriptableObject 的触发频率

ScriptableObject 作为资产，OnAfterDeserialize 只在首次加载到内存时触发，不像 MonoBehaviour 每次场景加载都触发。它不适合用于”每次进入 Play Mode 重置运行时值”——那个场景应该用 OnEnable。

7. Addressables + ScriptableObject

实例重复问题

内置场景 + Addressables 加载会导致 ScriptableObject 出现两个实例

当 ScriptableObject 同时被内置场景引用和 Addressables 加载的资源引用时，会创建两个内存实例（可通过 GetInstanceID() 验证）。所有引用指向的不是同一个对象。

最佳实践：

  1. 项目只保留一个内置场景（Loader Scene），其唯一职责是通过 Addressables 加载后续场景
  2. 后续场景及其依赖的 ScriptableObject 全部标记为 Addressable
  3. 同一 AssetGroup 内的 ScriptableObject 会在加载时共享同一实例

内存管理

Addressables 基于引用计数管理内存：

关键规则：

  • 每次 LoadAssetAsync 引用计数 +1，Release 引用计数 -1
  • 引用计数归零时，资产及其所在 AssetBundle 才被卸载
  • 一个 AssetBundle 中只要有一个资产的引用计数不为零，整个 Bundle 就留在内存中
  • Instantiate 创建的实例需用 Addressables.ReleaseInstance 销毁（而非 Object.Destroy），否则引用计数泄漏

PreferBinarySerialization

当 ScriptableObject 包含大数组时，标记 [PreferBinarySerialization] 可跳过 YAML 序列化，在 Addressables 打包时直接使用二进制格式，显著减小包体和加载时间。

8. ScriptableObject 与 DOTS / ECS

核心问题

ScriptableObject 是 UnityEngine.Object 派生类，分配在堆上、有 native 头部、不连续存储。ECS 的性能优势来自线性内存访问（IComponentData 是 struct）。ScriptableObject 与 ECS 的数据布局直接矛盾。

正确的数据流：Authoring → Baking → ECS

替代方案：BlobAsset

不要在 ECS System 中直接引用 ScriptableObject

在 SystemBase.OnUpdate 中访问 ScriptableObject 会破坏 ECS 的数据局部性优化。应在 Baker 中把数据一次性拷贝到 IComponentData / IBufferElementData / BlobAssetReference。

9. OnAfterDeserialize 与序列化回调细节

回调执行顺序

对于使用 [SerializeReference] 的对象：

  • OnBeforeSerialize：先调用宿主对象，再调用其 managed reference
  • OnAfterDeserialize：先调用宿主对象，再调用其 managed reference

常见错误：在 OnAfterDeserialize 中调用主线程 API

安全操作： 纯数据变换（字段赋值、集合重建）。不安全操作： 任何 UnityEngine.Object 查询、场景访问、Debug.Log（部分版本中）。

OnValidate（Editor Only）

OnValidate 在以下时机触发：

  • 脚本加载时
  • Inspector 中值变更时
  • 不在运行时触发

10. 生产级反模式

反模式 1：God Object ScriptableObject

一个 ScriptableObject 包含几十个字段、跨多个系统被引用、既有配置数据又有运行时状态。

症状：

  • 修改任何字段都需要重新测试所有引用系统
  • 无法并行编辑（多人同时改同一资产产生版本冲突）
  • 任何修改都可能导致看似无关的 Bug

修复： 按”单一职责”拆分。一个 SO 只负责一类配置（如 WeaponStatsSO、WeaponVfxSO、WeaponAudioSO 分开），通过组合引用。

反模式 2：运行时修改共享 ScriptableObject 导致 Bug

两个敌人引用同一 EnemyData ScriptableObject，一个敌人的 Buff 修改了 moveSpeed，另一个敌人也受影响。

修复：

反模式 3：ScriptableObject 循环引用

WeaponDataSO 引用 AbilityDataSO，AbilityDataSO 又引用回 WeaponDataSO。

后果：

  • Unity 序列化对直接自引用循环会忽略该字段
  • 间接循环限制 10 层递归，超出部分数据丢失
  • Inspector 中出现数据异常

修复：

  • 用接口或事件解耦
  • 将共享部分提取为第三个独立 SO
  • 用 string/Hash ID 替代直接引用，运行时查找

反模式 4：ScriptableObject 不能引用场景对象

ScriptableObject 是项目级资产，不能持有对场景内 GameObject 或 MonoBehaviour 的引用（场景对象的生命周期与场景绑定）。

反模式 5：忘记处理 Domain Reload 关闭的情况

当 “Enter Play Mode Options” 关闭了 Reload Domain 时，ScriptableObject 的运行时状态不会重置，导致”第一次 Play 正常、第二次 Play 状态残留”的 Bug。

修复： 在 OnEnable 中重置运行时状态，或使用 EditorApplication.playModeStateChanged 事件。

反模式 6：用 ScriptableObject 做存档

Build 中 ScriptableObject 变更不持久

在编译后的 Player 中，ScriptableObject 运行时修改仅存在于内存中。应用关闭后，所有修改丢失。绝对不能用 ScriptableObject 代替存档系统。

正确做法： 将需要持久化的数据序列化为 JSON/binary，写入 Application.persistentDataPath。

权衡与选择

场景ScriptableObject 合适？推荐替代
编辑期配置数据（武器属性、关卡参数）非常合适—
跨场景共享的只读数据非常合适—
事件通道 / 解耦通信合适（Inspector 友好）静态事件总线（更轻量）
运行时可变状态（血量、分数）不合适MonoBehaviour 字段 / plain C# class
存档数据不合适JSON + persistentDataPath
ECS 配置仅作 Authoring 层BlobAsset / IComponentData
大规模动态数据（10000+ 条目）边界情况ScriptableObject + PreferBinarySerialization 或外部 DB
