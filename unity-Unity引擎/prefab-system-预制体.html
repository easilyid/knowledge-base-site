Prefab 系统深入（Prefab System Deep Dive）

核心思想

Prefab 系统是 Unity 内容复用的基础架构。一个 Prefab asset 是一组序列化的 GameObject + Component 数据，场景中的 Prefab instance 通过”源引用 + 修改列表”模型与 asset 保持连接——instance 并非 asset 的完整拷贝，而是 asset 的增量描述。理解这个内部模型是避免 override 累积、深层嵌套、变体链过长等失控局面的前提。

为什么重要

中大型 Unity 项目的 Prefab 数量可达数千。Override 累积、深层嵌套、变体链过长、运行时误用 Editor API 等问题都会导致”改 Prefab 不知道哪些 instance 会变”的失控局面。Prefab 是 Unity 内容生产的核心单位——角色、敌人、子弹、特效、UI 面板、道具、机关通常都通过 Prefab 复用和实例化。没有 Prefab，项目会迅速陷入复制粘贴和配置漂移。

1. Prefab Instance Override 系统

1.1 Override 的三种类型

Unity 在 Prefab instance 上识别以下 override：

Override 类型含义Inspector 标记
属性修改（Modified Property）实例上某属性值与 asset 不同属性值加粗 + 蓝色左划线
添加组件（Added Component）实例上有 asset 中不存在的 Component组件图标叠加 + 徽章
移除组件（Removed Component）实例上移除了 asset 中存在的 Component组件图标叠加 - 徽章
添加子 GameObject（Added GameObject）实例下新增了 asset 中不存在的子对象层级中绿色 + 图标
移除子 GameObject—只能 Deactivate（视为属性修改），不能真正删除

Transform 位置与旋转不算 Override

Prefab instance 根的 Position 和 Rotation 默认就与 asset 不同，Unity 不把它们视为显式 override——因为几乎所有 instance 都需要放在不同位置。

1.2 Override 优先级规则

Override 永远优先于 asset 值：如果一个属性在 instance 上被 override 了，那么修改 asset 上的同一属性不会影响该 instance。这是最常见的”改了 Prefab 但某个 instance 没变”的原因。

1.3 Apply 与 Revert

  • Apply：将 instance 上的 override 写回 Prefab asset，override 消失，asset 获得新值，所有其他 instance 也会受影响。
  • Revert：丢弃 instance 上的 override，恢复为 asset 原值。

1.4 Editor vs Runtime 的根本区别

维度EditorRuntime（Built Player）
Prefab 概念存在——instance 与 asset 有连接不存在——所有 Prefab/Nested Prefab/Variant 在 build 时被”预烘焙”为扁平独立对象
Override 解析实时从 asset + modification list 合成无需解析——build 时已将 override 烘焙进实例数据
Apply/Revert可用不可用（PrefabUtility 是 Editor 命名空间）
CPU 开销有（需要 diff 合成）零——所有内容已预烘焙

Runtime 没有 Prefab 连接

在 built player 中，Nested Prefab、Variant、override 等概念完全不存在。Build 过程把所有 instance 烘焙成完全独立的 GameObject 副本。这意味着运行时没有任何 CPU 开销花在解析嵌套或应用 override 上——但也意味着每个实例的 GameObject 和 Component 数据在磁盘和内存中是完全独立的拷贝，不存在共享。

1.5 Unused Override 数据

当声明 override 的脚本被修改或删除时，override 可能变成”unused”。Unity 提供了清理入口：

  • Overrides 下拉窗口中会显示”Remove Unused Overrides”选项
  • PrefabUtility 提供了相关 API

2. Prefab Variant vs Nested Prefab

2.1 定义差异

Prefab VariantNested Prefab
本质根级别的 Prefab，以另一个 Prefab 为 base，根表现为一个 Prefab instance子级别的 Prefab instance，嵌入在另一个 Prefab 内部
存储位置项目中的独立 .prefab 文件作为外层 Prefab 的 override 记录在 m_Modification 中
Override 可复用性Override 保存在项目文件中，可被多场景多 instance 共享Override 保存在场景或外层 Prefab 中，只有该场景/外层 Prefab 的 instance 受影响
继承链可以层层嵌套 variant（Variant of Variant），形成继承链保持与源 Prefab 的连接，但不在项目级形成独立资产

2.2 何时使用

用 Prefab Variant 的场景：

  • 同一类敌人有多个配置版本（如 Enemy_Goblin → Enemy_Goblin_Elite、Enemy_Goblin_Archer）
  • 需要在一处修改影响所有使用该 Variant 的 instance
  • Variant 本身是项目级资产，可以被多个场景引用

用 Nested Prefab 的场景：

  • 复合对象包含可独立修改的子部件（如 Car 包含嵌套的 Wheel Prefab）
  • 子部件需要独立于父 Prefab 演化——修改 Wheel asset 会反映到所有包含它的父 Prefab
  • 不需要把子部件的 override 提升为独立资产

Variant vs Nested 的关键区别：Override 的宿主

Variant 的 override 存在 .prefab 文件中，是项目级资产，所有引用该 Variant 的 instance 都共享这些 override。Nested Prefab 的 override 存在外层 Prefab 或场景中——如果你在场景中修改了一个 Nested Prefab instance，这个 override 仅存在于该场景，不会影响其他场景的同名 instance。如果同一 override 需要复用，应先创建 Variant。

2.3 Override 传播规则

多层 Prefab 结构中，override 传播遵循以下规则：

  1. Apply All 按钮总是 Apply 到最外层 Prefab

  2. 单个 override 的 Apply 可以选择目标：

    • Apply to inner Prefab Asset → 修改内层 Prefab，所有使用该内层 Prefab 的 instance 受影响
    • Apply as Override in outer Prefab → 在外层 Prefab 内创建 override，不影响内层 asset

  3. 当选择 Apply to inner Prefab Asset 时，如果外层 Prefab 已有同一属性的 override，外层的 override 会被自动 Revert，以确保 instance 上的值不变

2.4 Source 与 Original Source

Prefab 类型Source（直接源）Original Source（原始源）
普通 instance原 Prefab asset同 Source
Prefab VariantVariant 自身Variant 链根部的原始 Prefab asset
Nested Prefab嵌套的那个 Prefab asset同 Source（嵌套 asset 自身就是原始源）

3. Object.Instantiate vs PrefabUtility.InstantiatePrefab

3.1 核心差异

维度Object.InstantiatePrefabUtility.InstantiatePrefab
命名空间UnityEngine（运行时可用）UnityEditor（仅 Editor 可用）
Prefab 连接不保留——产生普通克隆，与源 Prefab 无连接保留——创建的 instance 保持与 Prefab asset 的连接
位置/旋转参数支持（Instantiate(prefab, pos, rot)）不支持（需实例化后手动设置 transform.position）
父对象参数支持不支持（需实例化后 SetParent）
适用场景运行时实例化、游戏逻辑Editor 工具、自定义 Inspector、编辑器脚本

3.2 Editor 中的影响

在 Editor 中使用 Object.Instantiate 实例化 Prefab asset 时：

  • 产生的对象丢失 Prefab 连接——在 Hierarchy 中不显示蓝色 Prefab 标记
  • 修改源 Prefab asset 不会影响这些克隆对象
  • Overrides 下拉窗口不可用

使用 PrefabUtility.InstantiatePrefab 时：

  • 产生的对象保留 Prefab 连接——显示蓝色 Prefab 标记
  • 修改源 Prefab asset 会反映到这些 instance
  • Overrides 下拉窗口可用，可以 Apply/Revert

Editor 脚本误用 Object.Instantiate

如果在 Editor 工具代码中使用 Object.Instantiate 而非 PrefabUtility.InstantiatePrefab，生成的对象会丢失 Prefab 连接。这在大型项目中非常危险——修改 Prefab asset 后，这些”断联”的 instance 不会更新，导致配置漂移。

3.3 实例化过程内部流程

Object.Instantiate 在 Editor 和 Runtime 都遵循相同的三步序列化流程：

  1. 序列化源对象（包括所有 UnityEngine.Object 派生类数据）
  2. 创建新 GameObject 并反序列化数据到新对象
  3. 修补引用：运行序列化代码的另一变体来报告所有引用的 UnityEngine.Object——外部引用（如 Texture）保持不变，内部引用（如子 GameObject）修补到对应副本

这意味着 Instantiate 本质上是序列化 → 反序列化，而非简单的内存拷贝。

4.4 Instantiate 时什么被复制

数据类型Instantiate 时是否复制说明
GameObject + Component 数据全部复制每个 instance 是完全独立的 C++ 对象
内部引用（子对象引用）修补到副本序列化第 3 步自动修补
外部引用（Texture、Material 等）共享，不复制所有 instance 指向同一 Texture/Material
Prefab 连接（Editor）取决于 APIObject.Instantiate 丢失，PrefabUtility.InstantiatePrefab 保留
Override 列表不复制Override 是 instance 与 asset 的 diff，克隆产生独立对象

Material 共享与独立

Instantiate 后，所有 instance 默认共享同一个 sharedMaterial。修改 sharedMaterial 会影响所有 instance。若需要独立材质，使用 renderer.material（自动创建实例副本）或手动 Instantiate(material)。前者每次访问都会分配，应缓存结果。

4.5 Built Player 中的内存

Build 时 Unity 将所有 Prefab instance 烘焙为扁平独立数据：

  • 不存在 Prefab/Nested Prefab/Variant 概念
  • 每个 instance 的 GameObject + Component 数据是完全独立的拷贝
  • 共享的只有外部引用（Texture、Material、Mesh 等）
  • PersistentManager.Remapper 在 AssetBundle 加载场景中可能占用可观内存——对含非常大 Prefab（深对象层级）的 AssetBundle 尤其明显，且一旦分配不会缩小

5. Addressables 与 Prefab

5.1 两种实例化路径

路径API说明
直接实例化Addressables.InstantiateAsync(key)Addressables 自动解析位置、下载依赖、实例化。实例化本身是同步的，异步部分是加载。
分步实例化Addressables.LoadAssetAsync → Object.Instantiate先加载 asset，再手动 Instantiate。可缓存 load handle，多次实例化无额外加载开销。

5.2 关键差异与陷阱

LoadAssetAsync + Object.Instantiate 的引用计数陷阱

如果先 LoadAssetAsync 加载 Prefab，再 Object.Instantiate 实例化，然后过早 Release 了 load handle，AssetBundle 会被卸载，所有正在使用该 Prefab 的 instance 的 Material/Texture 数据会被从底层抽走，导致粉色（missing material）或崩溃。必须确保所有 instance 销毁后才 Release。

5.3 Addressables.InstantiateAsync 的开销

相比直接 Object.Instantiate，Addressables.InstantiateAsync 有额外开销：

  • 位置解析：如果是 key 版本 API，需要遍历 ResourceLocators 查找 IResourceLocation
  • 依赖下载：自动下载所有依赖的 AssetBundle
  • 引用计数管理：每个 InstantiateAsync 调用增加引用计数

性能数据参考（社区实测）：

  • 直接 AssetBundle.Load + Instantiate 可比 Addressables 快 3-4 倍（PC 端）
  • iOS 端 Async 加载可能比 Scene 加载慢数倍
  • 如果预加载（LoadAssetAsync 完成），后续 Instantiate 是同步的，开销与普通 Object.Instantiate 一致

6. Prefab 编辑模式

6.1 Isolation Mode（隔离模式）

  • Prefab 显示在默认 Skybox 环境中
  • 场景中其他对象不可见
  • 可以编辑 Transform 值
  • 可以配置编辑环境场景（Editor Settings → Prefab Mode → Editing Environments）

适用场景：编辑独立的、与场景上下文无关的 Prefab（如角色、道具）

6.2 In Context Mode（上下文模式）

  • Prefab 显示在实例所在的场景位置
  • 场景中其他对象灰化显示，但可见
  • 不能直接编辑 Transform 值——因为 instance 的位置可能与 asset 不同
  • 可以使用 Snapping 对齐到场景中的其他对象

Context 模式的三种灰化程度：Normal（正常显示）、Gray（灰化，默认）、Hidden（完全隐藏）

适用场景：编辑需要与场景环境配合的 Prefab（如嵌入墙面的开关、地面的陷阱）

6.3 Auto Save

Prefab 编辑模式默认开启 Auto Save——每次修改都会立即写入 Prefab asset。可以在 Inspector 顶部关闭 Auto Save，改为手动保存。

关闭 Auto Save 的场景

对大型 Prefab 做实验性修改时，关闭 Auto Save 可以避免误操作影响所有 instance。完成后再手动 Apply 或 Revert。

7. Prefab 运行时修改

7.1 Instantiate 后的 Override 状态

运行时 Object.Instantiate 产生的克隆：

  • 完全独立——与源 Prefab asset 无连接
  • 所有值（包括 asset 中的默认值）都被”烘焙”进克隆对象
  • 修改克隆对象的属性不会影响源 Prefab 或其他 instance
  • 无法使用 PrefabUtility API（Editor Only）

7.2 运行时修改克隆实例的模式

7.3 运行时”恢复出厂”的困难

Unity 运行时没有内置的”恢复到 Prefab 默认值”机制（因为 Prefab 连接在 build 中不存在）：

方案优点缺点
销毁 + 重新 Instantiate完全干净开销大，需要转移状态
JsonUtility 序列化/反序列化轻量不处理添加/删除的 Component，需逐 Component 操作
自定义 Reset 方法完全可控需手动维护 reset 逻辑与 Prefab 同步
对象池 + Return 时 Reset复用 + 可控Reset 逻辑可能遗漏状态

对象池中 Reset 不完整

从池中取出的对象可能携带上次使用的状态（粒子进度、动画状态、变量值等）。这是对象池最常见的 bug 来源。Reset 逻辑必须覆盖所有运行时可能修改的状态。有效的策略是：actionOnGet 中重置，actionOnRelease 中关闭。

8.1 Unity 内置 ObjectPool

8.2 Prefab + 对象池的关键考量

考量说明
首次 Instantiate 开销池的 createFunc 在首次 Get 时调用，如果同时请求大量对象会造成帧尖峰。应在加载时预热。

8.3 Addressables + 对象池的注意事项

  • 预热时 LoadAssetAsync 加载 Prefab，然后多次 Instantiate 填充池
  • actionOnDestroy 使用 Destroy（不是 Addressables.ReleaseInstance，因为实例是通过 Object.Instantiate 创建的）
  • 池销毁时：先 Destroy 所有池化对象，再 Addressables.Release load handle
  • Addressables.InstantiateAsync 有自己的引用计数——如果用 InstantiateAsync 创建对象，必须用 Addressables.ReleaseInstance 归还

9. 常见 Prefab 反模式

9.1 深层嵌套

问题：

  • 嵌套层级越深，override 传播路径越长，debug 难度指数增长
  • Editor 中每次修改都需要递归解析所有嵌套层
  • 团队协作时，不同成员修改不同层级的 Prefab 容易产生 merge conflict
  • 建议嵌套控制在 3 层以内

9.2 Override 累积

场景中某个 Prefab instance 有大量 override 时：

  • 无法判断最终值来源
  • 修改 Prefab asset 后哪些 instance 受影响完全不可预测
  • 大量 override 应提升为 Prefab Variant

检测方法：

  • Inspector 的 Overrides 下拉窗口显示 override 数量
  • PrefabUtility.GetPropertyOverrides、GetAddedComponents、GetRemovedComponents 可编程检查

定期清理 Override

项目迭代中很多 override 可能已经不需要了。定期检查并 Apply 或 Revert 无用 override，保持 instance 干净。

9.3 Missing Prefab Reference

常见原因：

  1. .meta 文件丢失或 GUID 变更（如 Git merge 冲突处理不当）
  2. Prefab 文件被删除但场景中仍有 instance 引用
  3. Prefab Variant 链中间环节断裂

预防措施：

  • 版本控制中永远不要忽略 .meta 文件
  • 删除 Prefab asset 前搜索所有引用
  • 使用 PrefabUtility.GetCorrespondingObjectFromSource 检查引用有效性

Variant 的 fileID 不稳定问题

在旧版本 Unity（2018-2019）中，编辑 Prefab Variant 可能导致内部 fileID 变更，使外部引用失效。表现为 ScriptableObject 中引用的 Variant 突然变为 null。此问题在较新版本中已修复，但仍需注意跨版本升级时的验证。

9.4 场景中放置而非 Prefab 化

在场景中直接构建复杂对象而不创建 Prefab——无法复用到其他场景、无法通过代码实例化、修改需要逐场景手动同步。即使只用一次，也推荐 Prefab 化。

9.5 m_Modifications 序列化顺序不稳定

PrefabInstance 的 m_Modifications 块在版本控制中经常出现顺序变更（即使实际内容未改变），导致无意义的 diff 噪声。这是 Unity 已知的序列化行为，替换源 Prefab 后可能产生过时 override 条目，加剧问题。

9.6 Prefab 与场景耦合

Prefab 中引用场景内的特定对象（如 FindWithTag("Player")）会使 Prefab 丧失独立性——换到另一个场景就无法工作。Prefab 应通过外部注入引用（Instantiate 后由调用方设置），而非内部硬编码查找。

9.7 Instantiate 空引用

Instantiate(null) 不抛异常，而是返回 null——后续访问导致 NullReferenceException。在 Instantiate 前检查 prefab 是否为 null。

在 DOTS 项目中，Prefab 的”模板复用”价值仍然存在——Entity Prefab 可以通过 EntityManager.Instantiate 高效实例化。但 Override、Variant、Nested Prefab 等 Editor 级概念没有 ECS 对应物。如果需要”同一基础 Entity 的多个配置版本”，应在 Baking 阶段通过不同 Authoring 配置 + Baker 逻辑实现，而非依赖 Prefab Variant。
