MonoBehaviour 生命周期（MonoBehaviour Lifecycle）

核心思想

Unity 通过一组预定义 event functions 调用 MonoBehaviour 脚本，让脚本接入对象初始化、启用/禁用、每帧更新、物理更新、渲染、碰撞和销毁等阶段。

生命周期不是单个脚本内部的孤立顺序，而是 PlayerLoop 系统 中各阶段调度出来的结果——理解 PlayerLoop 就理解了为什么 Awake 先于 Start、为什么 FixedUpdate 可能一帧执行多次。

为什么重要

绝大多数 Unity bug 都能归到”对象何时存在、引用何时初始化、Update 何时执行、销毁何时发生”。正确使用生命周期能避免初始化竞态、物理帧错位、摄像机跟随抖动和对象池状态泄漏。

工作原理

完整生命周期流程

stateDiagram-v2
    [*] --> Awake : 脚本实例加载
    Awake --> OnEnable : GameObject active<br/>且组件 enabled
    OnEnable --> Start : 首次 Update 前
    Start --> Update : 每帧

    state 每帧循环 {
        Update --> LateUpdate : 所有 Update 完成
    }

    state 物理步 {
        [*] --> FixedUpdate : 固定时间步
    }

    LateUpdate --> OnDisable : 组件禁用/对象停用
    OnDisable --> OnEnable : 重新启用
    OnDisable --> OnDestroy : 对象销毁
    OnDestroy --> [*]

初始化阶段

方法调用时机典型用途注意事项
Awake脚本实例加载时（场景加载 / Instantiate / AddComponent）初始化自身字段、缓存 GetComponent 引用所有 Awake 完成后才开始任何 Start
OnEnable组件启用且 GameObject active 时注册事件、启动协程每次 enabled 变 true 都调用
Start脚本第一次 Update 前依赖其他对象 Awake 结果的初始化只调用一次，即使后续 OnEnable/OnDisable

Unity 保证：场景中所有 Awake 都完成后，才开始调用任何 Start。但不同 GameObject 之间的 Awake 顺序不可靠。

更新阶段

方法调用时机PlayerLoop 阶段典型用途deltaTime
FixedUpdate固定时间步（默认 0.02s）FixedUpdate物理、Rigidbody 操作Time.fixedDeltaTime
Update每帧一次，渲染前Update输入、逻辑、动画Time.deltaTime
LateUpdate每帧一次，所有 Update 后PostLateUpdate相机跟随、后处理Time.deltaTime

关键时序事实：

  • FixedUpdate 可能在同一帧执行多次（追赶物理步），也可能不执行
  • Update 每帧恰好执行一次
  • LateUpdate 在所有 Update 之后执行，适合读取其他对象本帧最终状态

物理回调

方法触发条件说明
OnCollisionEnter碰撞体首次接触两个非 trigger Collider 接触
OnCollisionStay碰撞体持续接触每物理步调用
OnCollisionExit碰撞体分离不再接触
OnTriggerEnter触发器首次进入一方是 trigger
OnTriggerStay触发器内持续每物理步调用
OnTriggerExit触发器离开退出 trigger 范围
OnCollisionEnter2D 等2D 物理版本Physics2D 系统

物理回调在 FixedUpdate 阶段触发

碰撞和触发器回调发生在物理步内——它们在 FixedUpdate 的时间步中调用，不在 Update 中。如果一帧执行多次 FixedUpdate，物理回调也会被多次调用。

禁用与销毁

OnDisable 与 OnDestroy 的区别

OnDisable 可能被多次调用（每次禁用都触发），OnDestroy 只调用一次（对象真正销毁时）。对象池中对象归还时触发 OnDisable 但不触发 OnDestroy——应在 OnDisable 中清理状态。

应用生命周期回调

方法触发条件典型用途
OnApplicationPause应用暂停（切后台、来电）保存游戏状态、暂停音乐
OnApplicationFocus应用获得/失去焦点显示/隐藏光标
OnApplicationQuit应用退出前保存持久数据

方法调用时机用途

生命周期是 PlayerLoop 调度的结果

Update/FixedUpdate/LateUpdate 的调用时机完全由 PlayerLoop 系统 决定：

PlayerLoop 阶段MonoBehaviour 回调
FixedUpdateFixedUpdate、物理回调
UpdateUpdate、协程 yield null 恢复
PostLateUpdateLateUpdate、WaitForEndOfFrame

理解 PlayerLoop 就能理解为什么物理回调一帧可能触发多次、为什么 LateUpdate 适合相机跟随。

Awake/Start 与依赖注入

Awake → Start 的两阶段初始化本质上是一种手动依赖注入：

但如果 A 的 Start 需要 B 的 Start 结果呢？这种情况下应改用事件/接口或显式初始化方法——不要试图用 Script Execution Order 强制排序所有依赖。

协程与生命周期的交互

Coroutine 的执行受宿主 MonoBehaviour 生命周期影响：

  • OnDisable → 所有协程停止
  • OnEnable → 需要手动重启协程（不会自动恢复）
  • OnDestroy → 协程销毁
  • GameObject inactive → 协程中断

这是对象池场景中协程的常见陷阱——归还对象时 SetActive(false) 会停掉所有协程，下次租借必须重启。

反模式

在 Awake 中访问其他对象的初始化结果

不同 GameObject 的 Awake 调用顺序不确定。如果 A 的 Awake 需要 B 的 Awake 结果，可能时序不对。把 A 的依赖初始化移到 Start——所有 Awake 完成后才调用 Start。

在 Start 中做每帧都会失效的注册

Start 只调用一次。如果对象可能被禁用再启用，事件注册应放在 OnEnable（对应地在 OnDisable 注销），而非 Start。否则对象重新启用后事件监听丢失。

依赖不同 GameObject 间同名回调的顺序

Unity 不保证不同 GameObject 上 Update/FixedUpdate 的调用顺序。如果 A 必须在 B 之前执行，用 [DefaultExecutionOrder] 或重构为事件驱动。但这种依赖通常意味着架构需要解耦。

在 FixedUpdate 中放非物理逻辑

FixedUpdate 一帧可能执行 0 次或多次。非物理逻辑（输入处理、UI 更新、音效播放）放这里会导致行为不一致。只有物理和 Rigidbody 操作才应该放在 FixedUpdate。

对象池中 OnDestroy vs OnDisable 混淆

对象池回收对象时 SetActive(false) 触发 OnDisable 而非 OnDestroy。如果清理逻辑放在 OnDestroy，池化对象的状态不会被重置。对象池兼容的组件应在 OnDisable 中清理状态。

OnApplicationQuit 与 OnDestroy 的时序

OnApplicationQuit 在应用退出时调用，但此时场景中的对象仍在——OnDestroy 在之后才调用。如果在 OnApplicationQuit 中引用其他对象是安全的，但 OnDestroy 中可能部分对象已销毁。
