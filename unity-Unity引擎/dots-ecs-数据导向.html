DOTS / ECS（数据导向技术栈）

核心思想

DOTS（Data-Oriented Technology Stack）是 Unity 的数据导向技术栈；Entities package 提供 ECS（Entity Component System）实现。ECS 把对象拆成”实体 ID + 组件数据 + 系统逻辑”：数据集中存放，系统批量查询并处理匹配组件的实体。

它与 GameObject/MonoBehaviour 的核心差异是：运行时逻辑围绕数据布局和批处理组织，而不是围绕对象层级和组件回调组织。

为什么重要

Job System、Burst 编译器、Collections 包 是性能栈的执行、编译和数据结构层；Entities/ECS 是把这些能力组织成大规模 gameplay 数据模型的上层架构。

当游戏需要处理大量相似对象（单位、粒子、弹幕、交通、群体 AI、海量可见实体）时，ECS 的数据布局和批处理方式能比传统每对象 MonoBehaviour 更新更适合 CPU cache 和多线程。

工作原理

三大核心概念

Entity

Entity 通常可以理解为一个轻量 ID（包含 index 和 version），不直接保存行为。它通过挂载组件数据获得”状态”。

Component

IComponentData 标记 ECS 组件数据。每个 entity 同一类型的 IComponentData 只能有一个；需要多个同类值时使用 buffer component。

兼容 Entities 1.4 官方文档。Unity 版本与 Entities 包版本需以项目 Package Manager 为准。

Archetype 与 Chunk

Entities 共享相同组件类型集合的 Entity 属于同一 Archetype。ECS 把同一 Archetype 的实体数据存储在 16 KiB 的内存块（Chunk）中：

关键特征：

  • Chunk 大小固定 16 KiB，每个 Archetype 的 Chunk 容量取决于组件大小
  • 数据紧密排列（SoA 布局），遍历时 cache 友好
  • 同一 Chunk 中的实体在内存中连续——System 遍历时顺序预取

Archetype 变更是昂贵操作

给 Entity 添加或删除组件会改变其 Archetype，导致 Entity 从一个 Chunk 移到另一个 Chunk（即”结构变更”）。这涉及内存拷贝和 Chunk 碎片整理，且产生同步点（sync point），阻塞所有正在运行的 Job。高频结构变更会严重影响性能。

Chunk 碎片化

Entity 被销毁或搬走后，Chunk 中出现空洞。碎片化意味着：

  • 遍历时访问未使用的内存
  • 整体内存占用比实际需要更多

通过 Archetypes 窗口（Window > Analysis > Archetypes）可诊断碎片化：

  • 查看 Allocated Chunks vs 实际 Entity 数量
  • 关注 unused space 指标
  • 每个 Chunk 最多 128 个 Entity——接近此上限说明 Archetype 组件过大

减少碎片化的核心策略

  • 减少 Archetype 变更频率（用 IEnableableComponent 代替增删组件）
  • 大 Entity（组件多）每 Chunk 容纳的 Entity 少，cache 命中率低——考虑按系统拆成多个小 Entity
  • 批量创建/销毁而非逐帧零散操作
  • 用 Profiler 的 Structural Changes 模块追踪哪个系统触发了结构变更

EntityCommandBuffer

EntityCommandBuffer（ECB）允许延迟执行结构变更，避免在 System 遍历中直接修改 Entity 导致的同步点：

ECB 的关键优势：

  • 遍历中不直接修改 Entity，避免”遍历时修改集合”的问题
  • 所有结构变更在 Playback 时批量执行，减少同步点
  • 支持 Burst 编译（EntityCommandBuffer 是 unmanaged 的）

Baking

Baking 把 Editor 中的 GameObject authoring data 转换为运行时 entity/component 数据。Authoring 仍可用 MonoBehaviour 暴露 Inspector 字段，Baker 负责转换。

TransformUsageFlags说明
Dynamic会移动的对象（生成 LocalTransform + LocalToWorld）
Renderable静态渲染对象（只生成 LocalToWorld）
Manual手动控制变换组件

Baker vs BakingSystem

Baker<T> 处理单个 Authoring 组件的转换；BakingSystem 处理跨 Authoring 的转换后逻辑（如根据多个组件生成派生数据）。Baker 是逐对象转换，BakingSystem 是全局后处理。

Baking 管线细节

Baker 的核心规则：

  • 使用 Baker.GetComponent<T>() 而非 GameObject.GetComponent<T>()——前者让管线追踪依赖，后者不追踪
  • 使用 DependsOn() 显式声明外部引用依赖（GameObject、Mesh、Material 等）
  • Baker 在每次 baking pass 中重新运行

SubScene

ECS 使用 SubScene 管理内容——因为 Unity 核心场景系统与 ECS 不兼容。Baking 期间，SubScene 中的 GameObject 和 MonoBehaviour 会转换为 entities 和 ECS components。

SubScene 的关键行为：

  • 编辑器中修改 Authoring → 自动增量 baking
  • 构建时 baking 结果序列化为二进制——运行时直接加载，无需 baking
  • SubScene 支持按 SceneSection 流式加载——适合开放世界

ECS 层级 vs Transform 层级

ECS 的 Parent 组件与 GameObject 的 transform.parent 概念相似但实现不同：ECS 用 LocalToWorldSystem 批量计算世界矩阵，而非逐对象传播脏标记。深层级在 ECS 中也是 O(depth) 但可以并行。

Job 与 System 的协作

ISystem 内部可以调度 Job System 的 Job。核心机制是 state.Dependency（JobHandle 依赖链）：

  • OnUpdate 执行前，Dependency 包含前置系统留下的 JobHandle
  • 调度新 Job 时，以 Dependency 作为输入依赖
  • 调度完成后，将返回的 JobHandle 赋回 Dependency

渐进式采用

DOTS 和 GameObject 可以在同一项目中共存。常见模式：核心 gameplay 用 MonoBehaviour，特定高性能子系统（弹幕、群体 AI、大规模粒子）用 ECS。通过 SubScene 将两者隔离。

DOTS 性能栈全景

各层关系：

  • Entities 用 Collections 的 NativeArray/NativeList 存储组件数据
  • System 调度 Job 来并行处理组件数据
  • Job 被 Burst 编译为高度优化的 native 代码
  • 四层协同才能发挥 DOTS 全部性能优势

反模式

ECS 不是 MonoBehaviour 的语法替换

ECS 改变的是数据组织方式和执行模型，不是把 Update() 换成 OnUpdate() 就结束。核心差异是”数据布局优先”——如果只是换个 API 写法但仍然逐对象访问，性能不会提升。

Authoring 与 runtime data 是两套世界

Editor 中的 GameObject/MonoBehaviour authoring data 通过 baking 转成 runtime entity data；运行时不直接使用 authoring component。在 runtime 代码中引用 MonoBehaviour 类型是常见错误。

高频结构变更

添加/删除组件导致 archetype 变更 → entity 在 chunk 间移动 → 同步点阻塞所有 Job。每帧添加/移除大量组件会严重拖慢帧率。用 IEnableableComponent 或 tag buffer 代替频繁的结构变更。

过度碎片化组件

把数据拆成太多小组件会增加 archetype 组合数——每种组合一个 archetype，导致 chunk 碎片化（每个 chunk 只有少量 entity）。组件拆分应基于”System 同时访问的数据”而非”语义最小化”。

在 System 遍历中直接修改 Entity 结构

foreach 遍历中调用 EntityManager.AddComponent 会立即触发同步点，且可能使遍历迭代器失效。应使用 EntityCommandBuffer 记录变更，在遍历结束后批量回放。

Managed System 的性能陷阱

SystemBase（managed）不支持 Burst 编译，且每个 managed system 调用都有托管↔非托管切换开销。即使是少量 managed system 也会在 System 列表中引入”burst 中断”。应尽量用 ISystem + [BurstCompile]。

Package 版本很关键

Entities API 演进较快，示例和项目实际版本必须对齐。Entities 1.0/1.1/1.3/1.4 之间的 API 有不兼容变更（如 IJobForEach 已移除、EntityQuery 用法变化等）。升级 Entities 包时务必查阅 changelog。

忽略 sync point

ECB Playback、EntityManager.AddComponent、EntityManager.DestroyEntity 等操作都会产生同步点——等待所有运行中 Job 完成后才执行。同步点越多，多线程利用率越低。项目中应审计同步点数量，尽量把结构变更集中到 ECBSystem 回放点。

DynamicBuffer 溢出

InternalBufferCapacity 设为 0 或过小，所有 buffer 元素都在 Chunk 外分配，遍历时 cache miss 严重。应根据实际数据分布设置合理的 InternalBufferCapacity，让大多数 Entity 的 buffer 留在 Chunk 内。

忽略依赖链

在 ISystem.OnUpdate 中调度 Job 但不正确传递 state.Dependency，导致竞态或 Job 未等待前置完成。始终将 state.Dependency 作为 Job 调度的输入依赖，将返回的 JobHandle 赋回 state.Dependency。
