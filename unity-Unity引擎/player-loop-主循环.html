PlayerLoop 系统（PlayerLoop System）

主线脉络

PlayerLoop 是 Unity runtime application 的主循环：每次循环中，Unity 按既定顺序更新输入、物理、脚本、动画、渲染、音频、异步任务和帧末回调等系统。Update、FixedUpdate、LateUpdate 只是 PlayerLoop 中脚本相关阶段暴露给 MonoBehaviour 的入口。

理解 PlayerLoop，可以把 MonoBehaviour 生命周期、Coroutine、Unity Awaitable、await continuation、Job System 完成点放到同一张时间轴上。

节点 2：MonoBehaviour 回调在 PlayerLoop 中的位置

sequenceDiagram
    participant PL as PlayerLoop

    PL->>FI: ScriptRunBehaviourFixedUpdate

    Note over FI: 一帧可能执行 0~N 次

    PL->>UP: ScriptRunBehaviourUpdate
    UP->>UP: MonoBehaviour.Update()
    UP->>UP: yield return null 协程恢复
    UP->>UP: async/await continuation

    PL->>LA: ScriptRunBehaviourLateUpdate
    LA->>LA: MonoBehaviour.LateUpdate()
    LA->>LA: WaitForEndOfFrame 协程恢复

关键时序事实：

  • FixedUpdate 可能在同一帧执行多次（追赶物理步），也可能不执行
  • Update 每帧恰好执行一次
  • LateUpdate 在所有 Update 之后执行，适合相机跟随
  • 协程的恢复时机取决于 yield 指令

节点 3：延迟任务与异步恢复

不同异步机制的恢复点：

机制恢复时机（PlayerLoop 阶段）说明
yield return null下一帧 Update 阶段最常用的协程恢复点
yield return WaitForFixedUpdate()下一 FixedUpdate 阶段末等下一个物理步
yield return WaitForEndOfFrame()PostLateUpdate 末尾所有渲染之后
yield return WaitForSeconds(t)等待时间到达后的下一 Update基于 Time.time
await Awaitable.NextFrameAsync()下一帧 Update 阶段awaitable 版 yield null
await Awaitable.FixedUpdateAsync()下一 FixedUpdate 阶段awaitable 版 WaitForFixedUpdate
await Task.Yield()Update 阶段（SynchronizationContext 调度）.NET Task 恢复
Job System JobHandle.Complete()调用线程阻塞等待不依赖 PlayerLoop

协程和 awaitable 的恢复顺序不确定

Unity 文档明确指出：同一帧内多个协程和 awaitable 的恢复顺序不保证。它们按组执行（协程组、awaitable 组），但组内顺序未定义。

PlayerLoop 是”等下一帧”和”每帧更新”的共同底座

Coroutine 的 yield return null、Unity Awaitable.NextFrameAsync()、Update、LateUpdate 解决的都是”在 PlayerLoop 的哪个时机继续”。它们不是多线程计算机制，而是主循环调度机制。

从这个视角看：

  • Update() = 每帧自动注册并执行的”回调”
  • yield return null = “把后续逻辑挂起，下一帧 Update 阶段恢复”
  • await NextFrameAsync() = awaitable 版本的 yield return null
  • 三者本质相同——都是 PlayerLoop 时序调度

PlayerLoop 与 Job System 是 when / how 的分工

Job System 负责多线程并行计算（how）；PlayerLoop 决定什么时候 schedule、什么时候 complete、什么时候把结果应用回主线程（when）。

自定义 Update Manager 是 PlayerLoop 层优化

GameObject 上成千上万个 MonoBehaviour.Update 的虚调用开销累积后不可忽视。集中式 update manager（向 PlayerLoop 插入自定义系统）可以消除虚调用，改用接口列表遍历——这是 update-method-更新方法 模式在 Unity 中的工程优化。

PlayerLoop 与游戏循环模式的关系

PlayerLoop 是 game-loop-游戏循环 模式的引擎级实现——它解决了 GoF 未触及的帧驱动问题：每帧必须按时交付、帧率波动时时间步适配、帧边界原子性。Unity 的半固定方案（FixedUpdate 物理用固定步长 + Update 逻辑用可变步长）是游戏循环模式中”固定+可变混合”策略的工程范例。

结论与权衡

  • 普通项目应先理解默认 PlayerLoop，不要急着修改它
  • 插入自定义系统比替换默认系统安全——替换会移除 Unity 默认功能
  • PlayerLoop 是理解 Coroutine / Awaitable / Update / Job 协同的核心底图
  • 集中式 Update Manager 是中大型项目的常见优化手段
  • ECS 的 ComponentSystemGroup 已内置声明式调度，DOTS 项目通常不需要手动修改 PlayerLoop
  • SetPlayerLoop 是全局覆盖操作，任何遗漏都会导致对应系统停摆——修改前必须打印完整 PlayerLoop 树确认

反模式

在 PlayerLoop.SetPlayerLoop 中丢失默认系统

SetPlayerLoop 是覆盖式设置——传入的 loop 完全替换当前 PlayerLoop。如果漏掉了某个默认子系统（如物理、音频、输入），这些系统将停止工作。始终在默认 PlayerLoop 基础上修改，而非从零构建。

协程恢复顺序假设

不要假设同一帧内多个协程或 awaitable 的恢复顺序——Unity 不保证此顺序。如果两个异步操作有因果关系（先 A 后 B），必须显式同步（如 await A 完成后再启动 B）。

FixedUpdate 频率假设

FixedUpdate 的执行频率由 Time.fixedDeltaTime 决定（默认 0.02s = 50Hz），但一帧内可能执行 0 次或多次。不要假设 FixedUpdate 和 Update 是 1:1 关系。

在错误的阶段做操作

  • 在 Update 中修改物理状态 → 物理已经在 FixedUpdate 中算完了，改了也要等下一物理步
  • 在 FixedUpdate 中播放音效 → 一帧内多次 FixedUpdate 会重复播放
  • 在 LateUpdate 中修改其他对象位置 → 相机跟随是对的，但改其他游戏逻辑会被跳过一帧

编辑器中 PlayerLoop 与构建后的差异

编辑器模式下 PlayerLoop 包含额外的编辑器子系统（EditorUpdate、Inspector 刷新等），运行时构建不包含这些。PlayerLoop.GetDefaultPlayerLoop() 在编辑器和构建中返回不同结果——在编辑器中测试自定义 PlayerLoop 时要注意这一点。

Domain Reload 对自定义 PlayerLoop 的影响

Enter Play Mode 时如果启用了 Domain Reload，自定义的 PlayerLoop 会被重置回默认值。必须在 [RuntimeInitializeOnLoadMethod] 或 InitializeOnLoadMethod 中重新注册。如果禁用了 Domain Reload（Configurable Enter Play Mode），自定义 PlayerLoop 会保留——但这可能导致多次进入 Play Mode 时重复插入自定义系统。
