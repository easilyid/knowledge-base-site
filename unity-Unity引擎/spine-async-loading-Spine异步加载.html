Spine 异步加载（Spine Async Loading）

是什么

将 Spine 动画组件的 Initialize 过程从主线程同步执行改为异步线程创建，避免复杂 Spine 动画在实例化时阻塞主线程 1-2 秒导致 UI 卡顿。

核心用法

问题根因

Spine 组件绑定在预制体上时，实例化会自动调用 Initialize 解析动画数据——这是同步的。复杂动画解析耗时直接阻塞主线程。

解决思路

  1. 使用二进制格式（.skel）而非 JSON 格式——解析速度快 80%-95%
  2. 不绑定 Spine 组件到预制体，改用代码手动创建
  3. 将 Initialize 拆为异步版本 InitializeAsync，在异步线程中解析数据，需要 Unity API 的部分通过 MainThread 调度器抛回主线程

关键细节

  • InitializeAsync 是将 SkeletonGraphic.Initialize 的实现拷贝出来，把其中调用 Unity API 的部分用 MainThread.RunTask 包裹
  • 主要修改集中在 SkeletonDataAsset 类中——该类中涉及 Unity Object 的操作需要切回主线程
  • Editor 下测不出阻塞——Spine 在非 PlayMode 时就已经把数据解析好了，必须在真机测试
  • ManualResetEventSlim 的 SpinCount 默认 10，适合毫秒级短等待。Spine 初始化中主线程任务通常极轻（LoadImage、Create），自旋等待 < 1ms 即可完成——这恰好是 ManualResetEventSlim 的最佳场景

Spine 版本兼容

  • 原始方案基于 spine-unity 3.6 + Unity 2019.4.x。更新版本（spine-unity 4.0+）的 SkeletonGraphic.Initialize 实现可能已变化，需重新确认异步改造点
  • Spine 4.0+ 引入了新的 SkeletonDataAsset 后处理 API（AtlasUtilities），可能减少主线程依赖——在投入异步改造前先评估新版是否已优化同步性能

真机验证

小程序/移动端上 Spine 解析耗时与 PC Editor 差异显著——Editor 在非 PlayMode 已预解析数据。验证必须：

  1. Development Build + 真机：确认卡顿确实在 Spine 初始化段
  2. Profiler.BeginSample/EndSample 包裹 Initialize 调用，量化精确耗时
  3. 优先尝试 .skel 二进制格式——实测可减少 80%-95%，可能不需要异步方案

常见陷阱

不要在异步线程中直接调用 Unity API

Texture2D.LoadImage、Sprite.Create 等 Unity API 只能在主线程调用。必须通过 MainThread 调度器将任务抛回主线程执行，否则会崩溃。

ManualResetEventSlim 适合短等待

InitializeAsync 中主线程和异步线程的切换等待时间通常很短（毫秒级），适合用 ManualResetEventSlim（自旋等待）。如果等待时间可能超过 300ms，应改用 ManualResetEvent。参见 concurrency-models-synthesis-并发全景。

二进制格式应优先尝试

在做异步初始化之前，先尝试将 Spine 导出格式从 JSON 改为二进制（.skel），可能就能解决问题，不需要引入异步方案的复杂度。
