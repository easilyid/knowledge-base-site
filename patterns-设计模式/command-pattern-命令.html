命令（Command）

核心思想

将请求封装为独立对象，包含与请求相关的所有信息。支持参数化、延迟执行、队列和撤销操作。

GPP（Game Programming Patterns）关键洞察：命令模式本质上是”回调的面向对象实现”——将函数调用提升为一等公民，使其可存储、传递、排队和撤回。GoF 低估了这个模式，在游戏中它的用途远比教科书描述的广泛。

结构图

classDiagram
    class Invoker {
        -history: Stack~ICommand~
        +ExecuteCommand(cmd)
        +UndoLast()
    }
    class ICommand {
        <<interface>>
        +Execute()
        +Undo()
    }
    class MoveCommand {
        -transform: Transform
        -direction: Vector3
        -previousPos: Vector3
        +Execute()
        +Undo()
    }
    class HealCommand {
        -target: Health
        -amount: float
        +Execute()
        +Undo()
    }
    class Receiver {
        真正执行操作的对象
    }

    Invoker --> ICommand : 存储/调用
    MoveCommand ..|> ICommand
    HealCommand ..|> ICommand
    MoveCommand --> Receiver : 委托执行
    HealCommand --> Receiver : 委托执行

sequenceDiagram
    participant Input as 输入处理器(Invoker)
    participant Cmd as MoveCommand
    participant Receiver as 角色(Receiver)

    Input->>Cmd: 创建（绑定参数）
    Input->>Cmd: Execute()
    Cmd->>Cmd: 保存 previousPos
    Cmd->>Receiver: position += direction
    Input->>Input: history.Push(cmd)

    Note over Input: 撤销时
    Input->>Input: history.Pop()
    Input->>Cmd: Undo()
    Cmd->>Receiver: position = previousPos

问题动机

没有命令模式时，输入处理直接耦合行为：

这种写法的问题：

  • 不可重映射：按键和行为硬绑死，玩家无法自定义键位
  • 不可撤销：行为执行后没有记录，无法回退
  • 不可复用：AI 触发移动需要另写一套逻辑
  • 不可组合：无法实现队列、宏、回放等高级功能

命令模式的核心动机：将”发起请求”和”执行请求”解耦，让请求本身成为可操控的一等对象。

按键重映射零成本

因为按键只负责选择命令对象，修改按键映射不需要改任何命令逻辑。只需在 Input Action Asset 中重新绑定，或运行时切换 Action Map。

游戏开发深度

GPP 独有见解

Robert Nystrom 在 GPP 中提出命令模式在游戏中的五大用途，远超 GoF 原书描述：

  1. 配置输入：按键到命令对象的映射。这是最基础也最被忽视的应用——没有命令模式的输入系统，键位重映射几乎不可能优雅实现
  2. 撤销/重做：命令保存反向执行所需信息。编辑器工具和回合制游戏的核心能力
  3. 回放系统：记录每帧输入命令序列，重放时按序执行。格斗游戏的回放、RTS 的录像功能都基于此
  4. AI 决策：AI 选择命令对象而非直接执行行为——决策层和执行层解耦后，AI 可复用玩家的全部命令集
  5. 宏命令：将多个命令组合为一个原子操作，一键连招就是宏命令

Unity 特有踩坑

命令持有 MonoBehaviour 引用

命令对象常持有 Transform、Rigidbody 等引用。场景切换时这些引用会随 GameObject 销毁变为 null，但命令历史栈可能仍持有它们。撤销操作会触发 MissingReferenceException。解决方案：命令保存 Entity ID 或引用容器，撤销时重新查找。

命令与 player-loop-主循环 的时序

命令的 Execute() 在哪一帧执行？在 Update 中入队的命令，实际效果可能要到下一帧的 player-loop-主循环 FixedUpdate 阶段才生效。物理相关命令应显式标记为”延迟到 FixedUpdate 执行”。

交叉引用

  • player-loop-主循环 — 命令在 PlayerLoop 中的调度时序
  • state-pattern-状态 — 命令触发状态转换时，状态机应作为 Receiver 而非 Invoker
  • memento-pattern-备忘录 — 复杂撤销（如编辑器操作）需要命令+备忘录配合：命令记住”做了什么”，备忘录记住”之前的状态”
  • observer-pattern-观察者 — 命令执行后可触发观察者通知（如技能命中后广播伤害事件）
  • strategy-pattern-策略 — 意图差异：策略是”可替换算法”，命令是”可存储请求”。策略关注”怎么做”，命令关注”做什么”
  • chain-of-responsibility-责任链 — 责任链是”请求沿链传播直到被处理”，命令是”请求被封装后交给唯一执行者”

实践示例

  • 输入绑定：按键映射到命令对象，实现可重映射的输入系统
  • 撤销/重做：关卡编辑器操作、回合制游戏走棋回退
  • 技能队列：MOBA/RPG 技能排队执行，命令带优先级和冷却
  • 回放系统：录制每帧命令序列并重放（格斗游戏、RTS 录像）
  • AI 行为：AI 决策层选择命令对象，执行层统一处理

回放系统示例

确定性回放的要求

回放系统要求数值计算完全确定性。Unity 的 Time.deltaTime 每帧不同，物理模拟也有浮点误差。格斗游戏通常使用固定时间步（FixedUpdate）+ 整数化坐标来保证确定性。

反模式

命令对象变成"上帝方法"

如果一个命令的 Execute() 内部做了太多事情（移动+攻击+播放特效+掉落道具），说明粒度太粗。应拆分为多个独立命令，用宏命令组合。

忽略命令的不可变性

命令对象在 Execute() 后被存入历史栈。如果外部代码修改了命令的内部状态（如通过引用修改了 direction），撤销行为会出错。命令入队后应视为不可变。

过度使用命令模式

不是所有操作都需要命令模式。简单的同步调用、无需撤销/排队/重放的操作，直接调用方法即可。命令模式引入了额外的类和间接层，只为”将来可能需要”而提前使用属于过度设计。

权衡与选择

  • 用命令：需要撤销、队列、延迟执行、回放或 AI 复用时
  • 用策略：只需可替换算法、无需存储/撤销时
  • 用责任链：请求需要经过多个处理阶段、可被中间环节拦截时
  • 用事件：需要一对多广播、发送方不关心接收方时

常见陷阱

命令对象的生命周期

存储命令历史时，命令可能持有大对象的引用，导致内存泄漏。撤销历史应有容量限制或快照压缩。

命令执行顺序依赖

多个命令之间可能存在隐式的顺序依赖（如”移动”必须在”攻击”之前），如果队列执行器不处理优先级，会产生逻辑错误。
