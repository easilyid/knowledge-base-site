优化模式（Optimization Patterns）

核心思想

游戏有硬性性能约束——60fps 意味着每帧只有 16.6ms，包含输入、逻辑、物理、渲染、音频在内的所有工作必须在此时限内完成。优化模式不是”让代码更快”的技巧集，而是为达到性能约束的工程手段：用结构化的设计取舍换取确定性性能。

GoF 将性能视为可选，优化模式将性能视为第一等公民。四种模式分别解决四种性能瓶颈：内存墙（缓存未命中）、计算浪费（重复重算）、分配墙（GC/分配延迟）、查询墙（暴力遍历）。理解瓶颈才能选对模式——不是所有代码都需要优化，但热路径必须优化。

问题动机

四种写法分别对应四种性能瓶颈：

四种模式覆盖四种性能瓶颈，组合使用覆盖全部性能热点：

  • 数据局部性让 CPU 预取命中——消除内存墙
  • 脏标识只在需要时计算——消除计算浪费
  • 对象池消除运行时分配——消除分配墙
  • 空间分区缩小搜索范围——消除查询墙

理解优化模式是理解 performance 分支的前提

NativeArray 的设计不是随意选择——它是数据局部性模式的工程落地。ObjectPool<T> 的存在不是因为 C# 缺少 GC——它是对象池模式的标准化实现。知道模式才能理解为什么这些 API 长这样。

四种模式详解

数据局部性（Data Locality）

核心意图：将频繁一起访问的数据在内存中连续排列，最大化 CPU 缓存命中率。现代 CPU 访问主内存比访问 L1 缓存慢 100-200 倍——算法时间复杂度再好，每次访问都 Cache Miss 性能照样崩溃。

经典场景：大量实体遍历（1000+ 敌人位置更新）、DOTS/ECS 全部 System、粒子系统。

Unity 映射：DOTS 的整个设计就是数据局部性模式的系统级实现——Archetype 保证同类 Component 内存连续，Chunk 是 CPU 缓存行友好的 16KB 块，Burst 编译器利用连续数据布局生成 SIMD 指令。

数据局部性是 DOTS 存在的理由

ECS Archetype = 自动 SoA 分组，NativeArray = 连续 unmanaged 内存，Burst = 利用连续布局生成 SIMD 指令，Job System = 按数据批次并行处理。四个组件全部服务于数据局部性。

详见 data-locality-数据局部性。

脏标识（Dirty Flag）

核心意图：用一位标记追踪导出数据是否与原始数据一致，只在结果被请求时才重新计算。将工作延期至结果被需要的时刻——如果中间多次修改原始数据但最终没人读取，计算工作就完全省掉了。

经典场景：场景图 Transform 矩阵（父节点移动 → 子节点世界变换重算）、UI 布局（元素尺寸变化 → 重排）、材质属性（修改后统一提交 GPU）。

Unity 映射：Transform.hasChanged 是 Unity 暴露的脏标识。UGUI Layout 系统是脏标识的教科书级实现——修改布局属性时标记脏，下一帧 Layout 阶段统一重建。

脏标识的核心不是"缓存"，而是"延期"

缓存是副产品。GPP 的关键洞察：脏标识把不必要的工作推迟，直到确认它真的需要做。场景图中父节点移动导致子节点世界变换重算，是脏标识最经典的应用场景。

详见 dirty-flag-脏标识。

对象池（Object Pool）

核心意图：从固定池中重用对象，避免频繁分配/释放。预分配一批对象循环使用——“租借-归还”而非”新建-销毁”。核心收益：消除 GC Spike 和内存碎片，保证帧时间稳定。

经典场景：子弹、特效、敌人实例——频繁创建销毁的短生命周期对象。

Unity 映射：Unity 2021+ 内置 UnityEngine.Pool.ObjectPool<T>，是对象池模式的标准化实现。

对象池的前提是"对象可复用"

归还到池中的对象必须被彻底重置，否则下一个租借者会拿到脏数据。池化不是简单的”不 Destroy”，而是”Destroy 改成 Reset + 回收”。

详见 object-pool-对象池。

空间分区（Spatial Partition）

核心意图：根据空间位置组织对象到数据结构中，高效查询”某处附近有什么”。将 O(n²) 的暴力配对检测降至 O(n log n) 甚至 O(n)。

经典场景：碰撞检测、视野裁剪、AOI（Area of Interest）、战争迷雾、寻敌。

Unity 映射：PhysX 内部使用 BVH + Sweep and Prune 做碰撞 Broadphase，开发者通常用 Physics.OverlapSphere 等内建 API 即可，无需自实现。DOTS Physics 使用动态 AABB 树。

选择空间分区结构的关键因素

对象数量（少则暴力够用）、移动频率（静则 k-d 树，动则网格/松散 QuadTree）、分布均匀度（均匀则网格，不均则树）、查询类型（点查询、范围查询、最近邻）。

详见 spatial-partition-空间分区。

反模式

过早优化——先 Profile 再优化

优化模式会牺牲代码可读性和灵活性。不要在项目早期就对所有数据做 SoA、对所有对象做池化——先用自然的方式写代码，用 Profiler 确认瓶颈后再针对性优化。Nystrom 的建议：“先让它跑起来，再让它跑得快，最后让它跑得优雅。”

忽视 Profiler 数据——凭感觉优化

“我觉得这里慢”是最危险的优化起点。必须用 Profiler 确认瓶颈在哪——可能是 CPU、可能是 GPU、可能是 GC、可能是 IO。优化模式解决的是 CPU 侧的性能问题，如果瓶颈在 GPU 渲染，优化 CPU 侧毫无意义。参见 garbage-collection-GC与内存。

数据局部性的过度优化

不是所有数据都需要连续布局。只有”每帧遍历大量实例”的热路径才值得重组内存。冷数据用经典 OOP 就好——过度 SoA 导致代码可读性急剧下降，20 个字段拆成 20 个并行数组，每个操作都要同步维护 20 个索引。

对象池的内存常驻

池化对象即使不用也占内存。如果峰值 1000 个子弹但平均只用 50 个，池化让 950 个子弹的内存始终占用。需根据实际峰值调池大小，或实现动态缩容。ObjectPool<T> 的 maxSize 参数控制池的最大容量——超过时 Release 会直接销毁。

脏标识忘记设标记 = 缓存不一致

最常见也最难调试的 bug：修改了原始数据但忘记标记 dirty，导致导出数据返回过时的缓存值。防范：用属性封装所有对原始数据的修改，在 setter 中自动标记。绝不能绕过属性直接改字段。

空间分区的维护开销超过查询收益

对象频繁移动时，空间分区的更新开销可能抵消查询收益。四叉树在动态场景中频繁分裂/合并，均匀网格在高密度区域退化。选择结构要看对象数量和移动频率。对象少于 100 个时，暴力 O(n²) 可能比空间分区更快。
