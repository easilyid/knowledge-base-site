创建型模式（Creational Patterns）

核心思想

创建型模式封装了对象创建的细节，让客户端代码无需关心”如何构造”，只需关心”我要什么”。它们将实例化逻辑从使用逻辑中解耦，使系统更灵活、更易扩展。

为什么重要

在游戏开发中，对象创建频繁且多变——敌人类型、道具掉落、UI 面板、关卡配置等都需要灵活的创建机制。直接 new 导致客户端与具体类耦合，难以应对变化。

五种模式概览

模式核心意图典型 Unity 场景使用频率
factory-method-工厂方法子类决定创建哪个对象敌人工厂：不同关卡产出不同敌人高频
abstract-factory-抽象工厂创建一族相关对象主题工厂：同一主题的 UI、音效、特效中频
builder-pattern-生成器分步骤构造复杂对象角色构建器：种族→职业→装备→属性中频
prototype-pattern-原型克隆已有对象子弹预制体克隆、技能模板复制高频
singleton-pattern-单例全局唯一实例GameManager、AudioManager极高频（但需警惕）

模式间关系

  • 工厂方法 vs 抽象工厂：工厂方法通过继承解决”创建哪个”，抽象工厂通过组合解决”创建哪一族”
  • 原型 vs 工厂方法：原型通过克隆绕过构造过程，工厂方法通过子类多态创建
  • 生成器 vs 抽象工厂：生成器关注分步构建一个复杂产品，抽象工厂关注一次创建一族产品
  • 单例：最简单的创建型模式，也是最易滥用的——Unity 中常见替代方案见 singleton-pattern-单例

Unity 中的创建型模式全景

Unity 引擎在多个层面内置了创建型模式的支持，日常开发应优先使用引擎机制：

引擎机制对应模式替代自建方案
Instantiate(prefab)原型模式自建克隆工厂——引擎的 Prefab 系统本身就是原型
ScriptableObject 配置表工厂变体 / 策略配置硬编码工厂——用 SO 数据驱动替代代码分支
Addressables 加载延迟加载工厂同步工厂——按需异步加载，减少初始内存
ObjectPool<T> (2021+)对象池（原型变体）手动池——引擎池处理租借/归还/清空
Resources.Load<T>()代理 / 延迟加载直接引用——适合编辑期绑定，运行时用 Addressables

Prefab 就是原型模式的引擎级实现

Unity 的 Prefab 系统：设计期定义模板 → 运行期 Instantiate 克隆 → 修改克隆体不影响模板。这完全符合原型模式的意图。大多数情况下不需要自己写原型克隆代码。

创建与 GC：创建型模式的内存代价

创建型模式在游戏中的隐藏成本是 GC 压力。频繁创建/销毁对象是 Unity 中 GC Spike 的主因之一：

模式GC 风险缓解策略
原型（Instantiate）高 — 每次克隆分配新内存用 对象池 复用；或用 DOTS 的 native-container-Native容器
工厂方法中 — 创建逻辑可控，但产物仍是 new返回值用对象池包装
抽象工厂中 — 创建一族对象，一次性分配整族入池，整族归还
生成器低 — 逐步构建，可控分配时机复用 Builder 实例，避免每次 new Builder()
单例极低 — 只创建一次全局唯一 = 零后续 GC，但要注意单例持有的大量引用

Instantiate / Destroy 是 GC Spike 的常见元凶

每帧创建子弹、特效等短命对象 → 频繁触发 GC。解决方案：享元共享不变数据 + 对象池复用可变对象。详见 garbage-collection-GC与内存。

常见陷阱

不要为了"灵活"而过度使用创建型模式

如果对象类型稳定、创建逻辑简单，直接构造即可。引入工厂/抽象工厂的前提是：类型会扩展、创建逻辑会变化。

单例不是全局变量的合法外衣

单例在 Unity 中极高频，但也是最易滥用的模式。常见问题：测试困难、隐式依赖、生命周期混乱。替代方案见 singleton-pattern-单例。
