工厂方法（Factory Method）

核心思想

在父类中定义创建对象的接口，让子类决定实例化哪个具体类。将”创建哪个对象”的决策延迟到子类。

问题动机

不用工厂方法会怎样？

  • 客户端直接 new 具体类，导致与具体类强耦合——换一种敌人类型就要改调用方代码
  • 创建逻辑散落在各处，无法统一管理（初始化、对象池、日志等）
  • 单元测试无法替换为 mock 对象，因为 new 写死在业务代码中

工厂方法的核心价值：把”创建什么”的决策从”使用什么”中解耦出来，让系统对扩展开放、对修改关闭。

Unity 中工厂的常见形态

Unity 中工厂方法不止”子类 override”一种形态，以下三种更常见：

1. ScriptableObject 工厂——数据驱动创建

SO 工厂 vs 子类工厂

SO 工厂用配置代替继承——不同敌人用不同 SO 实例而非不同子类。策划在 Inspector 里配 prefab，不需要程序员写新类。这是 Unity 中更实用的工厂形态。

2. Addressable 资源工厂——异步创建

异步工厂改变了调用方结构

InstantiateAsync 返回 AsyncOperationHandle，调用方必须用 async/await 或协程。这意味着工厂方法不再是简单的同步调用——调用链上游都要适配异步。可参考 unitask-deep-dive-深入 中的异步模式。

3. GameObject 工厂——统一 Instantiate 的入口

参数化工厂：消灭子类爆炸

GoF 原始工厂方法每新增一个产品就要新增一个 Creator 子类。参数化工厂用参数代替子类：

参数化工厂是开闭原则的更好实现

新增敌人类型只需 Register，不需要新建子类、不需要改工厂代码。注册甚至可以在运行时完成（如 Mod 系统加载新敌人）。

泛型工厂：Factory<T> 的 C# 实现

工厂 + 对象池：创建即入池

工厂创建的对象如果能复用，应直接与对象池集成，避免 GC 压力：

工厂负责创建，池负责复用

职责分离：工厂知道”怎么建”，池知道”怎么存”。工厂的 Create 是池 Get 内部在池空时的回调。Unity ObjectPool<T> 构造函数接受 Func<T> 正是这个意图。

与 ECS/DOTS 的关系：EntityArchetype 作为数据驱动工厂

在 DOTS 中，EntityArchetype 扮演了”数据驱动的工厂模板”角色：

Archetype = 组件配方 = 工厂模板

传统工厂用代码决定创建什么类；DOTS 用 Archetype 决定 Entity 有哪些 Component。Archetype 可在运行时动态组合，是比类继承更灵活的”工厂”。详见 dots-ecs-数据导向。

ScriptableObject 配置表 + 工厂

策划用 SO 定义”创建什么”，工厂负责”怎么创建”——这是 Unity 中最实用的工厂组合模式：

变体与演进

变体说明适用场景
参数化工厂用 enum/Type/Func 代替子类产品类型多，不想子类爆炸
泛型工厂Factory<T> where T : new()产品构造简单、类型在编译期已知
SO 工厂ScriptableObject 持有 prefab + 配置Unity 项目，策划可配
异步工厂返回 Task<T> / AwaitableAddressable 加载
池化工厂工厂 + 对象池集成频繁创建销毁，需避免 GC
注册式工厂Dictionary<Key, Func<Product>>运行时动态注册产品类型（Mod 系统）
数据驱动工厂配置表定义”创建什么”，工厂定义”怎么创建”配置与逻辑分离

反模式

万能工厂：一个工厂类创建所有东西

GameFactory.CreateEnemy()、GameFactory.CreateWeapon()、GameFactory.CreateUI() 全挤在一个类里——这违反了单一职责。每个产品族应该有自己的工厂。

工厂返回具体类型而非接口

public Zombie CreateZombie() ——调用方又绑回了具体类，工厂的解耦价值归零。工厂方法应返回接口或基类：public IEnemy CreateZombie()。

工厂里塞业务逻辑

工厂只负责”创建”，不应包含产品的使用逻辑。如果在工厂里看到 enemy.Attack(player) 这样的调用，说明职责混乱。

忽略异步工厂的异常传播

Addressable 异步工厂中，InstantiateAsync 可能失败（资源未加载、key 不存在）。必须处理 AsyncOperationHandle 的异常状态，否则异常会被吞掉。

实践示例

  • 不同关卡使用不同 EnemySpawner 子类
  • Addressables 加载中，根据 key 创建不同资源
  • Unity 的 ScriptableObject 配合工厂方法做道具掉落表
  • GameObject.Instantiate 的统一入口（日志、池化、初始化）
  • DOTS 中按 Archetype 批量创建 Entity
  • Mod 系统：运行时注册新的产品类型到工厂

权衡与选择

  • 用工厂方法：创建逻辑因类型而异、且需要基类统一流程时
  • 用抽象工厂：需要创建一族相关对象时——abstract-factory-抽象工厂 保证产品族一致性
  • 用原型：已有模板实例，通过克隆创建更方便——prototype-pattern-原型 适合 Unity prefab
  • 用生成器：对象构造步骤多、需要分步配置——builder-pattern-生成器 解决参数爆炸
  • 直接 new：类型固定、不会扩展时——不要过度设计

常见陷阱

每新增一个产品就要新增一个创建者子类

如果产品类型很多且频繁新增，工厂方法会导致子类爆炸。此时考虑用参数化工厂或抽象工厂替代。

工厂创建的对象无人释放

工厂只管创建不管回收。如果产品是 MonoBehaviour 或持有非托管资源，必须有对应的销毁/回收机制（对象池、Dispose 模式）。参见 garbage-collection-GC与内存。
