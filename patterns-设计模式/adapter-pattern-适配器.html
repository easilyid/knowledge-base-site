适配器（Adapter）

核心思想

让接口不兼容的对象能够合作。适配器包装已有对象，将其接口转换为目标接口。

GoF 定义：将一个类的接口转换成客户期望的另一个接口。适配器让原本接口不兼容的类可以合作。

结构图

classDiagram
    class ITarget {
        <<interface>>
        +Request() string
    }
    class Adapter {
        -_adaptee: Adaptee
        +Adapter(adaptee: Adaptee)
        +Request() string
    }
    class Adaptee {
        +SpecificRequest() string
    }
    class Client {
        -_target: ITarget
        +DoWork()
    }

    Client --> ITarget : 依赖
    Adapter ..|> ITarget : 实现
    Adapter --> Adaptee : 委托

调用流程：Client 调用 ITarget.Request() → Adapter 接收调用 → 委托给 Adaptee 的 SpecificRequest() → 将返回值转换为目标格式 → 返回给 Client。

问题动机

不用适配器会怎样？

这种写法的问题：

  • 接口不兼容：Firebase 用枚举+字符串，Umeng 用字符串+字典，调用方式完全不同
  • 切换成本高：换一个分析 SDK 就要改客户端所有调用点
  • 无法测试：无法用 mock 替换真实 SDK，测试时必须连真 SDK
  • 违反依赖倒置：高层模块依赖底层具体实现

适配器的核心动机：在不修改已有代码的情况下，让不兼容的接口能够协作。它是”事后补救”的结构型工具——当接口已成事实无法更改时，适配器是唯一的桥梁。

角色职责Unity/C# 对应

工作原理

对象适配器（组合方式）

类适配器（继承方式——C# 的限制）

C# 中类适配器受限

C# 只允许单继承，所以类适配器只能”继承 Adaptee + 实现 Target 接口”（Target 必须是接口而非抽象类）。如果 Target 也需要是类，则只能用对象适配器。实际项目中对象适配器更常用，因为组合比继承灵活。

游戏开发深度

第三方插件适配（核心场景）

游戏项目通常需要对接多个第三方 SDK，每个 SDK 的接口完全不同。适配器模式是 SDK 集成的标准手段：

用适配器隔离 SDK 依赖

所有第三方 SDK 的引用只在 Adapter 类内部出现。游戏其余代码只依赖 IIapService 等接口。更换 SDK 时，只需写新适配器并替换注入——零改动业务代码。参见 strategy-pattern-策略 的依赖注入方式。

旧系统接口包装

项目迭代中经常遇到”新系统已上线，但旧代码还在用旧接口”的情况：

适配器是迁移期的安全网

不要一次性改掉所有旧代码——用适配器桥接新旧系统，逐步迁移调用方。等所有调用方都迁移到新接口后，再删除适配器。这与 facade-pattern-外观 的”简化入口”有本质区别：适配器是”接口转换”，外观是”接口简化”。

类适配器 vs 对象适配器的选择

维度对象适配器（组合）类适配器（继承）
C# 支持完全支持仅支持”继承 Adaptee + 实现 Target 接口”
灵活性可运行时替换 AdapteeAdaptee 编译期固定
覆盖行为无法覆盖 Adaptee 方法可 override Adaptee 虚方法
接口泄露只暴露 ITarget 接口Adaptee 的公共方法也暴露
推荐度首选仅当需要 override Adaptee 行为时

C# 接口默认方法

C# 8.0+ 支持接口默认实现（default 方法），一定程度上替代了缺省适配器。但 Unity 的 Mono 运行时对 C# 8.0 特性支持有限，IL2CPP 后端下默认接口方法可能有问题。目前仍建议用抽象基类做缺省适配器。

变体对比

变体说明适用场景
对象适配器组合持有 Adaptee，委托调用通用场景，首选
类适配器继承 Adaptee + 实现 Target 接口需要 override Adaptee 行为、且 C# 允许时
双向适配器同时实现两个接口，双向转换新旧系统互操作、双向桥接
缺省适配器空实现基类，选择性 override接口方法多、只需实现少数几个

反模式

适配器堆积：多层适配器嵌套

A → B → C → D，三个适配器层层包装。每层都做一次接口转换，调用栈极深，调试困难。正确做法：如果 A 和 D 的接口差距大，写一个直接适配器 A → D，而不是串联多个中间适配器。当适配器超过两层时，考虑重构接口设计。

适配器变成新接口

适配器中不断添加”方便方法”，最终适配器自身成了一个更复杂的接口，比原始 Adaptee 还臃肿。适配器应该只做接口转换，不做功能扩展——那是 decorator-pattern-装饰 的事。

适配器隐藏了 Adaptee 的异常

Adaptee 抛出的异常类型与 ITarget 期望的异常类型不同。适配器吞掉原始异常或转为通用异常，导致调试时丢失关键信息。正确做法：适配器应包装原始异常（throw new TargetException("message", innerException)），保留异常链。

权衡与选择

  • 用适配器：已有类无法修改但接口不匹配时——事后补救
  • 用桥接：设计初期就想分离抽象与实现时——事前设计
  • 用装饰：接口匹配但想增强行为时——不改接口加功能
  • 用外观：接口太复杂想简化时——子系统简化入口

常见陷阱

适配器是事后补救，不是设计目标

如果能在设计时统一接口，就不要用适配器。过多适配器层会导致调用栈加深。当系统中适配器数量超过核心类的数量时，说明接口设计需要反思。

忽略性能开销

适配器每次调用都多一层间接委托。在每帧调用数千次的热路径上（如物理碰撞回调），适配器的开销可能不可忽略。热路径应直接调用而非通过适配器。
