状态（State）

核心思想

让对象在其内部状态变化时改变行为，看上去就像改变了所属类。将每个状态的行为封装到独立类中，状态转换由状态对象自身或转换表驱动，而非宿主的 switch 语句。

问题动机

没有状态模式会怎样？用枚举 + switch 管理状态：

问题：每个新状态都要改所有 switch 分支；状态越多，代码越膨胀；转换逻辑分散在多个方法中，难以维护。状态模式把每个状态的行为和转换逻辑封装到独立类中。

工作原理

基本实现

入口行为与出口行为（GPP 关键洞察）

Enter()/Exit() 是状态模式的核心价值

GPP 指出：没有入口/出口行为的状态模式只是策略模式的别名。Enter() 让状态自己管理”进入时做什么”（播放动画、启用碰撞体），Exit() 让状态管理”离开时做什么”（停止粒子、清除计时器）。这比依赖前一个状态来清理更安全——前一个状态不知道下一个状态是什么。

静态状态 vs 实例化状态

无数据的状态用享元，有数据的状态用实例

GPP 区分两种风格：静态状态（所有字段在编译期确定，可共享单一实例，是 flyweight-pattern-享元 的应用）和实例化状态（状态持有运行时数据如计时器、计数器，每次转换需 new）。

选择原则

状态只有行为无数据 → 静态实例。状态需要计时器/计数器等运行时数据 → 实例化。频繁转换的状态（如 AI 每帧切换）可考虑对象池复用实例化状态，避免 GC。

并发状态机：避免笛卡尔积爆炸

一个角色有”动作”（站立/跑/跳）和”装备”（空手/持枪/持剑），如果合并成一个 FSM，状态数 = 3 x 3 = 9。再加一个”生命状态”（存活/濒死/死亡），就是 27 个状态。并发状态机用多个独立 FSM 避免这个问题：

并发状态机之间的交互

两个 FSM 独立运行时，如果需要跨 FSM 通信（如”持枪时不能跳跃”），需要额外的协调机制。不要在状态内部直接访问另一个 FSM——用观察者或消息通知。参见 observer-pattern-观察者。

层次状态机（HFSM）

子状态继承父状态的转换，避免在每个子状态重复相同逻辑：

HFSM 实现

Unity 社区常用 HFSM 库：Stateless（.NET 标准，支持 DOT 图导出）、Sirenix Odin State Machine（Inspector 可视化）。简单项目手写 HFSM 即可，复杂 AI 考虑行为树。

状态栈过深

如果栈深度不受控（如下推自动机循环压栈），内存会持续增长。加深度上限或改用显式目标状态。

Burst 编译器对 switch 有专门的优化（跳转表），而接口虚调用在 Burst 中不被支持。在 Job System 热路径中，枚举 + switch 比状态模式更快。状态模式适合主线程复杂逻辑，Burst 路径用数据驱动。参见 job-system-作业系统 和 burst-compiler-Burst编译。

变体与演进

转换表（Transition Table）

将转换逻辑从状态类中抽出，集中管理：

转换表 vs 状态内部转换

转换表集中了”哪些转换合法”，方便审查和可视化，但每次加状态要改表。状态内部转换分散但自包含。GPP 建议：状态少用内部转换，状态多用转换表。

字符串键转换表 FSM（实用示例）

跑酷游戏角色有 3 种状态（跑动、一段跳、二段跳），用字符串常量标识状态和事件，转换表注册合法转换和回调：

字符串键 FSM 的权衡

字符串键缺少编译期检查（拼错只在运行时暴露），但对快速原型和小型项目足够用。生产代码建议用枚举或泛型 FSM 库（如 Stateless）替代字符串键，获得编译期安全和重构支持。

状态模式 → 行为树 → 规划系统

graph LR
    A["状态模式/FSM<br>确定性的状态转换"] --> B["行为树<br>条件驱动的决策树"]
    B --> C["GOAP/规划系统<br>目标驱动的自动规划"]

状态模式不是图灵完全的

GPP 明确指出：FSM/状态模式只能表达有限个状态和预定义转换。复杂 AI 需要行为树（条件驱动的树结构决策）或 GOAP（目标驱动的自动规划，搜索从当前状态到目标状态的行动序列）。状态模式是 AI 的起点，不是终点。

反模式

状态转换散落在各状态类中

每个状态类决定自己转到哪个状态，转换逻辑分散。如果状态 A 不知道状态 B 的存在（解耦），却要转到 B，耦合就通过状态类本身泄露了。可用转换表（Transition Table）集中管理转换规则。

在 Enter/Exit 中执行耗时操作

Enter() 和 Exit() 是同步调用。在其中加载资源、等待异步操作会阻塞状态转换。耗时初始化应拆为”进入中”过渡状态，完成后才正式进入。

状态类持有 MonoBehaviour 引用并直接操作

状态类如果直接调用 GetComponent<>() 或访问大量 MonoBehaviour 字段，会变成”披着状态模式外衣的 god class”。状态类应通过 Context 接口访问数据，保持职责单一。

忽略 Unity 的帧率波动

状态的 Update() 依赖 Time.deltaTime，但某些帧 deltaTime 可能异常大（如加载卡顿、切后台回来）。状态计时器应加 Mathf.Min(deltaTime, maxDelta) 上限保护。

把所有逻辑塞进一个状态

如果某个状态的 Update() 超过 100 行，通常意味着这个状态应该拆分为子状态或并发状态机。参见”层次状态机”章节。

权衡与选择

  • 用状态模式：状态少（3-8个）、转换逻辑简单时
  • 用 FSM 库：状态多、转换复杂、需要可视化编辑时（如 Stateless、Sirenix Odin State Machine）
  • 用策略：行为可替换但由客户端选择时（状态是自动切换，策略是外部选择——结构相似，意图不同）
  • 用行为树：AI 决策需要条件组合、优先级、并行执行时
  • 用 GOAP：AI 需要动态规划行动序列时

参见 strategy-pattern-策略 了解策略与状态的意图差异。
