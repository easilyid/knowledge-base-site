备忘录（Memento）

核心思想

在不暴露对象实现细节的情况下保存和恢复对象之前的状态。将状态的快照封装为独立对象——原发器的内部状态被备忘录”冻结”，外部只能传递不能读取细节。

结构图

classDiagram
    class Originator {
        -_state: State
        +Save() Memento
        +Restore(memento: Memento)
        +DoSomething()
    }
    class Memento {
        -_state: State
        -_timestamp: DateTime
        +GetState() State
        +GetName() string
    }
    class Caretaker {
        -_history: Stack~Memento~
        -_maxHistory: int
        +Push(memento: Memento)
        +Pop() Memento
        +Clear()
    }

    Originator --> Memento : 创建/消费
    Caretaker --> Memento : 存储（不读取内容）
    note for Caretaker "只负责存储和传递备忘录，不读取其内部状态"

    Note over Originator: 状态已恢复

问题动机

没有备忘录时，保存/恢复对象状态要么暴露内部实现，要么违反封装：

这种写法的问题：

  • 封装破裂：为了保存状态，把所有字段暴露为 public
  • 保存逻辑散落：每个修改状态的地方都要手动保存前一个值
  • 深拷贝陷阱：引用类型（List<Buff>）容易忘记深拷贝，恢复后指向同一对象
  • 多步撤销困难：手动管理 _lastXxx 变量，字段越多越混乱

备忘录的核心动机：让对象自己负责保存/恢复状态，外部只传递备忘录不解读其内容——既保存了完整状态，又不违反封装。

参与者

角色职责Unity/C# 对应
Originator（原发器）创建备忘录（保存状态）和用备忘录恢复状态Player、LevelEditor、GameState
Memento（备忘录）封装 Originator 的内部状态快照PlayerMemento、SaveData 序列化对象
Caretaker（负责人）存储备忘录历史，不读取其内容SaveManager、UndoHistory、CheckPointManager

Caretaker 的"不读取"原则

GoF 强调 Caretaker 只负责存储和传递备忘录，不读取或操作备忘录的内部状态。在 C# 中这个约束靠约定（而非语言强制），备忘录类可以把状态字段设为 internal 或 private，只对 Originator 所在程序集可见。

关卡编辑器撤销系统（与 Command 配合）

关卡编辑器中，撤销需要同时记录”做了什么”（命令）和”之前的状态”（备忘录）：

命令 vs 备忘录：谁负责撤销

command-pattern-命令 记录”做了什么”，用逆操作撤销（如”移动”的反操作是”移回”）。备忘录记录”之前的状态”，直接恢复。选择依据：逆操作简单用命令，状态复杂或逆操作困难用备忘录。复杂编辑器通常两者配合使用。

游戏存档/读档

游戏存档是备忘录模式的最大规模应用——整个游戏世界状态被冻结为可序列化的快照：

序列化陷阱（JSON/二进制选择）

序列化方式优点缺点适用场景
JsonUtility轻量、Unity 内置、可读不支持 Dictionary、多态简单存档、配置
Newtonsoft.Json功能完整、支持多态较重、GC 压力复杂存档
二进制（BinaryWriter）快速、紧凑不可读、版本迁移困难网络快照、回放
ScriptableObjectInspector 可编辑运行时修改不持久配置数据（非存档）

JsonUtility 的限制

JsonUtility.ToJson() 不支持 Dictionary、不支持多态（子类字段丢失）、不支持 null 数组元素。复杂存档建议用 Newtonsoft.Json（Unity 2020+ 已内置 com.unity.nuget.newtonsoft-json）。

检查点系统

检查点是有限深度的备忘录栈——只保留关键节点的快照：

变体与演进

变体特点适用场景内存开销
完整快照每次保存全部状态状态小、保存频率低高
增量备忘录只记录与前一个快照的差异状态大、保存频繁低
命令 + 备忘录命令记录操作，备忘录记录关键节点状态编辑器撤销中
序列化备忘录用 JSON/二进制序列化替代手写备忘录类存档系统视格式

增量备忘录

增量备忘录的权衡

增量快照节省内存，但恢复时需要从最近完整快照开始依次应用差异——恢复速度较慢。适合”保存频繁、恢复较少”的场景（如自动存档）。

反模式

备忘录泄漏内存（Caretaker 无限保留历史）

每个备忘录持有完整状态快照，如果 Caretaker 的栈没有深度限制，长时间运行会持续消耗内存。必须设置历史深度上限，超出时丢弃最旧的快照或改用增量备忘录。编辑器工具中尤其容易忽视——用户可能连续撤销 1000 次。

备忘录暴露内部实现

如果备忘录类用 public 字段，任何代码都能读取或修改备忘录内容——这违反了备忘录的封装意图。备忘录的状态应设为 internal 或 private，仅 Originator 能访问。在 C# 中可用 internal 访问修饰符 + [InternalsVisibleTo] 控制。

引用类型的浅拷贝陷阱

备忘录中的引用类型（List<T>、自定义类）如果只拷贝引用而非深拷贝，恢复时两个备忘录会指向同一个对象——修改一个会影响所有快照：

对嵌套引用类型需要递归深拷贝，或使用序列化（JsonUtility.ToJson → FromJson）实现深拷贝。

权衡与选择

  • 用备忘录：需要完整状态快照、撤销时直接恢复时
  • 用命令：只需撤销操作（而非完整回滚状态）时——参见 command-pattern-命令
  • 用序列化：存档系统通常直接用 JsonUtility/BinaryFormatter，本质是备忘录的特化
  • 用原型：需要克隆对象整体（而非仅状态快照）时——参见 prototype-pattern-原型
  • 备忘录 + 命令：编辑器撤销——命令记录”做了什么”，备忘录记录”之前的状态”
