原型（Prototype）

核心思想

通过克隆已有对象来创建新对象，而不依赖其具体类。将”如何创建”委托给对象自身。

问题动机

不用原型会怎样？

  • 创建成本高：有些对象初始化复杂（读取配置、计算默认值、加载资源），直接 new + 初始化很慢
  • 类型在运行时才确定：客户端不知道要创建什么具体类——只知道”我要一个跟这个一样的”
  • 子类爆炸：每种可创建对象配一个工厂类——当对象种类多且频繁变化时，工厂类数量失控

原型的核心价值：把”创建什么”的决策从”类名”变成”已有实例”——用对象代替类作为创建的锚点。

反面教材——不用原型时的创建困境：

原型模式用”克隆”替代”new + 初始化”：一次创建成本高的实例作为原型，后续直接克隆——快且不依赖具体类名。

参与者说明：

角色职责Unity/C# 对应
IPrototype（原型接口）声明 Clone() 方法C# ICloneable，或自定义接口
Skill / EnemyData（具体原型）实现 Clone()，定义如何克隆自己纯 C# 类、ScriptableObject、MonoBehaviour

Client（客户端）通过注册表获取克隆，不直接 new关卡系统、技能系统、敌人生成器

PrototypeRegistry 是可选的

简单场景直接持有原型引用即可，不需要注册表。注册表的价值在于”用字符串 key 动态查找原型”——适合配置驱动、Mod 系统等场景。

游戏开发深度

Unity Prefab 就是引擎级原型

Unity 的 Instantiate() 是原型模式最直接的体现——Prefab 是原型，Instantiate 是 Clone：

Prefab Variant 是"原型 + 微调"

Unity 的 Prefab Variant（预制体变体）本质上是原型模式的变体——基础 Prefab 是原型，Variant 是”克隆后微调”的结果。这与 Builder + Prototype 组合的思路一致（见 builder-pattern-生成器 的”模板化构建”章节）。

深拷贝 vs 浅拷贝陷阱

这是原型模式在 Unity/C# 中最常踩的坑。MemberwiseClone() 是浅拷贝——引用类型字段只复制引用，不复制对象本身：

Unity 中 Instantiate 的深拷贝边界

Instantiate(prefab) 会深拷贝 GameObject 及其所有组件，但组件内的引用类型字段（如 List<T>、自定义类实例）仍然是浅拷贝——克隆体的组件与原型的组件可能共享同一个 C# 对象引用。对于 MonoBehaviour 组件的字段，务必在 Awake / Start 中重新初始化引用类型。

ICloneable 在 C# 中的争议

System.ICloneable 接口在 .NET 社区有争议：

  • 问题：ICloneable.Clone() 返回 object，调用方必须强制转换；且接口没有约定是深拷贝还是浅拷贝
  • 微软官方建议：不要在公共 API 中使用 ICloneable——改为自定义泛型接口

内部代码可用 ICloneable，公共 API 用自定义接口

团队内部代码如果约定了 ICloneable 是深拷贝，用起来没问题。但给外部团队或发布 SDK 时，ICloneable 的歧义会成为坑。自定义接口能明确语义。

原型 + 对象池的天然配合

原型模式与 object-pool-对象池 是天然搭档——原型负责”第一次怎么创建”，池负责”后续怎么复用”：

原型是池的"种子"

对象池首次创建对象时需要知道”怎么建”——原型提供了这个”种子”。池空时从原型克隆，池满时直接复用。这是 factory-method-工厂方法 与 object-pool-对象池 配合的通用模式，但用原型替代工厂方法，创建逻辑由对象自身承担。

ScriptableObject 作为原型注册表

ScriptableObject 天然适合做原型注册表——策划在 Inspector 里配好所有技能/敌人/道具原型，运行时按 key 克隆：

SO 引用 vs 运行时数据

vfxPrefab 和 sfx 是 Unity 资产引用，不需要深拷贝——所有克隆体共享同一个 prefab/clip 是正确的（享元思想）。只有运行时会修改的数据（damage、cooldown）才需要独立副本。这正是 flyweight-pattern-享元 的应用——不可变的共享部分与可变的私有部分分离。

与工厂方法的对比

维度factory-method-工厂方法prototype-pattern-原型
创建方式new 具体类克隆已有实例
知道”创建什么”的方式类名 / enum / Type已有实例
新增产品新增一个工厂子类注册一个新原型实例
初始化成本每次都要完整初始化首次初始化原型，后续克隆更快
深拷贝问题无必须处理深浅拷贝
Unity 对应ScriptableObject 工厂Instantiate(prefab)
适合场景创建逻辑简单、无模板实例创建成本高、有模板实例

简单判断法

已有 Prefab/SO 实例可以作为模板 → 原型；从零创建、没有模板 → 工厂方法。Unity 中两者常组合使用：用原型克隆 GameObject，用工厂方法初始化组件数据。

序列化深拷贝——最通用的深拷贝方式：

序列化深拷贝的代价

序列化/反序列化比 MemberwiseClone + 手动拷贝慢 10-100 倍，且产生大量中间字符串 GC。只在对象图极其复杂、手动深拷贝不可行时使用。性能敏感路径（如每帧创建子弹）应避免。参见 garbage-collection-GC与内存 的 GC 规避策略。

MemberwiseClone——C# 内置的浅拷贝机制：

MemberwiseClone 的效率

MemberwiseClone 是 CLR 内置的内存块拷贝，比手动赋值快，比序列化快几十倍。它的局限是只能浅拷贝——引用类型字段需要手动补深拷贝。最佳实践：先用 MemberwiseClone 做浅拷贝（拿速度），再逐个深拷贝引用类型字段（拿正确性）。

反模式

浅拷贝导致共享引用被意外修改

这是最常见的原型陷阱。MemberwiseClone() 只复制引用，两个克隆体共享同一个 List<T>、Dictionary<K,V> 或自定义类实例。一方修改，另一方被影响——Bug 隐蔽且难追踪。

防御：所有引用类型字段在 Clone() 中都要手动深拷贝，或使用自定义 IDeepCloneable<T> 接口明确语义。

原型注册表无限制增长

如果注册表只增不删，运行时间越长占内存越多——尤其是 Mod 系统或动态内容加载场景。

防御：注册表提供 Unregister(key) 方法，Mod 卸载时清理对应原型。或用 IDisposable + 引用计数管理原型生命周期。

循环引用导致深拷贝无限递归

循环引用的深拷贝需要”引用映射表”（Dictionary<object, object> 记录已拷贝对象），或使用序列化方案（大多数序列化库能处理循环引用）。

实践示例

  • Instantiate(prefab) — Unity 内置的原型模式，最常用的应用
  • 技能模板：从 ScriptableObject 配置克隆运行时实例
  • 子弹/特效：从对象池取出或克隆原型
  • 关卡配置：从模板关卡克隆后微调敌人布局
  • Mod 系统：运行时注册新原型到注册表，克隆创建
  • AI 行为树：从模板行为树克隆后根据角色微调参数
  • 网络同步：服务器状态对象克隆后序列化发送给客户端

权衡与选择

  • 用原型：对象类型多、创建成本高（如复杂预制体），且已有模板实例时
  • 用工厂方法：创建逻辑简单、不需要已有实例时——factory-method-工厂方法
  • 用抽象工厂：需要创建一族一致产品时——abstract-factory-抽象工厂 保证族一致性
  • 用享元：对象无状态、可共享时——flyweight-pattern-享元 共享而非克隆
  • 用生成器：从零分步构建复杂对象时——builder-pattern-生成器 不需要模板

常见陷阱

循环引用导致深拷贝复杂

对象图中存在循环引用时，手动深拷贝容易出错。可考虑序列化/反序列化（如 JsonUtility）作为深拷贝手段。

Unity Instantiate 不拷贝 C# 堆上的引用类型

Instantiate 拷贝的是 Unity 原生对象（GameObject、Component），不是 C# 堆上的对象。如果 MonoBehaviour 的字段持有 List<T> 或自定义类，克隆体的组件与原组件共享这些引用。必须在 Awake / OnEnable 中重新初始化。

原型克隆产生 GC 压力

每次克隆都创建新对象——如果每帧克隆大量对象（如子弹），GC 压力会很大。高频场景应与 object-pool-对象池 配合，克隆一次后反复复用。参见 garbage-collection-GC与内存。
