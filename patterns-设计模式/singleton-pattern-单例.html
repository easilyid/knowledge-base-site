单例（Singleton）

核心思想

保证一个类只有一个实例，并提供全局访问点。

GPP（Game Programming Patterns）关键洞察：Robert Nystrom 在书中明确指出：“尽管出于良好意图，GoF 描述的 Singleton 模式通常弊大于利”，“单例就是封装在类中的全局状态”。他自己坦言：“在游戏开发中我从未用过完整的 GoF Singleton 实现——要保证唯一实例，我通常用静态类；如果需要运行时检查，就在构造函数里加一个 static flag。” 单例解决的两个问题（唯一实例 + 全局访问），几乎都有更好的替代方案（Dependency Injection、Service Locator、Subclass Sandbox）。但理解它为什么有害，比简单回避更重要。

出处：Game Programming Patterns · Singleton（开源在线版，可对原文）。

问题动机

游戏开发中确实存在”全局唯一”的需求： GameManager、AudioManager、配置系统。但单例模式同时引入了五个严重问题：

问题 1：全局状态

任何代码都能访问和修改单例状态，导致：

  • Bug 难以追踪：谁改了 GameManager.Score？不知道，因为任何地方都能改
  • 隐式耦合：两个看似无关的系统通过单例暗中通信
  • 并发隐患：多线程下全局状态竞争

问题 2：紧耦合

这段代码同时依赖三个单例，无法单独测试、无法替换实现。

问题 3：延迟初始化的陷阱

问题 4：多场景切换时的问题

DontDestroyOnLoad 让单例跨场景存活，但这带来新的陷阱：

  • 场景 A 创建了单例，切到场景 B 再切回 A，又会创建一个——需要重复实例检测
  • 单例身上可能挂载了场景 A 的引用，切到场景 B 后引用失效

问题 5：不支持多个实例

如果某天需要两个 GameManager（如分屏双人、本地联机测试），单例的 static Instance 设计直接阻止了这个需求。

参与者

角色职责问题
Singleton 类持有唯一实例 + 全局访问点构造器私有，禁止外部创建
Instance 属性全局唯一的访问入口所有客户端硬编码依赖此属性
Client通过 Instance 访问功能与 Singleton 形成紧耦合

单例与简单工厂的区分

单例的重点不是”如何创建”，而是”全局唯一+全局访问”。如果只需要控制实例数量，用工厂或 DI 容器更合适。

工作原理

MonoBehaviour 单例（Unity 常见形式）

MonoBehaviour 单例的 Awake 时序 问题

Unity 不保证多个 MonoBehaviour 之间 Awake 的执行顺序。如果脚本 B 在 Awake 中访问 GameManager.Instance，而 GameManager 的 Awake 还没执行，就会得到 null。解决方案：用 [DefaultExecutionOrder(-100)] 属性标记单例脚本，确保它先初始化；或在访问时加 null 检查 + 延迟初始化。

C# 纯类单例（线程安全懒加载）

Lazy<T> 是 C# 中最简洁的线程安全单例写法

它保证首次访问时才初始化、线程安全、无需显式锁。比”双重检查锁定”写法更简单且正确。

ScriptableObject 单例

ScriptableObject 单例适合配置型数据

不需要 MonoBehaviour 生命周期（无 Update、无协程）、需要在 Inspector 中配置的数据，用 ScriptableObject 比 MonoBehaviour 单例更轻量。但注意 Resources.Load 有性能开销，不应在热路径中反复调用。

游戏开发深度

GPP 独有见解

Nystrom 列出了单例的替代方案，按场景选择：

替代方案解决的问题适用场景
静态类全局访问无状态工具类（Mathf、Input）
服务定位器全局访问+可替换需要运行时切换实现
依赖注入解耦+可测试中大型项目
将实例作为参数传递显式依赖调用链较短时
将实例存储在拥有者上减少全局性实例的生命周期与某个对象绑定

Unity 特有踩坑

单例持有引用导致 GC 无法回收

单例的生命周期贯穿整个应用，如果它持有对场景对象的引用（如 List<Enemy> enemies），切换场景后这些对象无法被 GC 回收。必须主动在 OnDestroy 或场景切换事件中清空引用。

DontDestroyOnLoad 与场景切换的交互

DontDestroyOnLoad 的 GameObject 会被移到特殊的”持久化场景”中。如果用 SceneManager.LoadScene 的 LoadSceneMode.Single，这个持久化场景不会被卸载，但其他场景中的引用全部失效。用 LoadSceneMode.Additive 可以更好地控制生命周期。

MonoBehaviour 单例的 组件 陷阱

单例 MonoBehaviour 通常挂在空 GameObject 上，但其他人可能误删这个 GameObject、修改组件顺序、或在同一对象上添加冲突组件。建议将单例放在专用 GameObject 上，并用 [DisallowMultipleComponent] 保护。

依赖注入替代单例

DI 的核心优势

依赖注入让依赖关系显式化（构造函数参数一目了然）、可替换（测试时注入 Mock）、可控制生命周期（由容器决定何时创建和销毁）。这是解决单例紧耦合问题的结构性方案。

服务定位器替代单例

服务定位器 vs 依赖注入

服务定位器仍是”主动拉取”模式（调用方知道自己需要什么），但至少将”从哪获取”从硬编码的 Instance 变为可配置的注册表。依赖注入是”被动推送”模式，解耦更彻底。两者都优于裸单例。

变体与演进

泛型单例基类

泛型单例基类的隐患

多个泛型单例之间仍然没有初始化顺序保证。如果 AudioManager.Awake 访问 GameManager.Instance，而后者还没初始化，仍然会 null。泛型基类只是减少样板代码，不解决架构问题。

可持久化单例（支持多实例场景）

显式初始化/清理

这种变体将”何时创建”和”何时销毁”的控制权还给调用方，而非被动等待首次访问。配合场景加载器，可以在场景切换时可控地重建单例。

ECS 单例组件的优势

不依赖静态变量、不引用 MonoBehaviour、由 EntityManager 管理生命周期、天然支持多 World（每个 World 可以有自己的”单例”）。这是 DOTS 架构下最”正确”的全局状态方案。

反模式

"万能 Manager"单例

GameManager 既管分数、又管场景切换、又管玩家状态、又管 UI——这不是单例的问题，是职责不清的问题。单例让”往一个大类里塞功能”变得太容易。每个 Manager 应只做一件事。

单例之间互相引用

AudioManager.Instance 引用 GameManager.Instance，GameManager.Instance 又引用 UIManager.Instance……形成隐式的依赖网，初始化顺序成为噩梦。如果必须互相通信，用事件/中介者解耦。

测试中无法替换单例

单元测试需要隔离被测系统。如果被测代码直接调用 GameManager.Instance，测试时无法注入 Mock 对象。这是单例最大的架构伤害——让代码变得不可测试。

单例不是"全局变量"的语法糖

如果你发现单例的所有字段都是 public 的、任何代码都能随意修改，那它本质上就是一个全局变量，只是穿了一件面向对象的外衣。这种用法比裸全局变量更危险，因为修改点分散在各处但表面上看起来”有组织”。

权衡与选择

替代方案适用场景
依赖注入（VContainer/Zenject）中大型项目，需要解耦和测试
静态类无状态的工具类（如 Mathf、Input）
ScriptableObject 单例配置型数据，不需要 MonoBehaviour 生命周期
服务定位器需要运行时切换实现，但不想引入 DI 框架
显式参数传递调用链短，依赖关系简单

优先考虑依赖注入

单例是”全局状态的合法化”，容易导致隐式依赖。中大型项目用 VContainer 等 DI 框架替代手动单例。小型项目/原型阶段，单例的简洁性仍有价值——但应标记为技术债，在项目规模化时重构。

常见陷阱

单例是最易滥用的模式

  1. 全局状态难以测试
  2. 隐式依赖，修改时牵一发动全身
  3. 多场景单例重复实例问题（需要 DontDestroyOnLoad）
  4. 不是线程安全的（除非用 Lazy<T>）
  5. 持有引用导致 GC 无法回收

滥用 DontDestroyOnLoad

DontDestroyOnLoad 应只用于真正需要跨场景存活的对象（如音频播放器、网络连接）。场景级的管理器（如该场景的 BossController）不应标记为持久化，否则场景卸载后它们仍在内存中。
