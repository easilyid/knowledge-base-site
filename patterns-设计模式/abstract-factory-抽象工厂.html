抽象工厂（Abstract Factory）

核心思想

提供创建一系列相关对象的接口，而无需指定具体类。保证同一族的产品总是一起使用。

问题动机

不用抽象工厂会怎样？

  • 客户端手动组合不同族产品，导致”火焰武器 + 冰霜护甲”这种不一致搭配混入系统
  • 产品族约束散落在各处，每新增一个族就要搜遍代码库加 if-else
  • 单元测试中无法一次性替换整族产品（想测”火焰族”就要逐个 mock）

抽象工厂的核心价值：把”产品族一致性”的约束从散落式 if 检查，收束为类型系统保证。

Unity 中最实用的抽象工厂形态——用 ScriptableObject 承载一整族配置，策划在 Inspector 里配完一个”主题包”即可使用：

策划创建两个 SO 实例 FireTheme 和 IceTheme，各自配不同 prefab / 音效 / 特效。代码只依赖 EnemyThemeFactorySO，运行时注入不同实例即切换整族。

SO 工厂族 vs 纯代码工厂

SO 工厂族的优势是”配置与代码分离”——策划改主题不需要改代码、不需要重编译。纯代码工厂适合产品创建逻辑复杂（需要计算、依赖注入）的场景。两者可组合：SO 持有配置，代码工厂持有创建逻辑，SO 作为代码工厂的参数。

Addressable 标签分组加载：异步工厂族

当产品是 Addressable 资源时，可用标签（Label）定义”族”，一次性加载整族资源：

异步工厂改变了抽象工厂的接口

GoF 的抽象工厂是同步的，但 Addressable 加载是异步的。两种处理方式：(1) 工厂加 LoadAsync() 初始化方法，创建方法仍是同步的（如上）；(2) 创建方法本身返回 Task<T>。前者对客户端更友好，后者更灵活。详见 unitask-deep-dive-深入 的异步工厂模式。

简单判断法

只有一个产品接口 → 工厂方法；有两个以上产品接口且需要族一致性 → 抽象工厂。如果工厂接口只有一个方法，那它本质上就是工厂方法——抽象工厂是工厂方法的”族化”推广。

装饰器风格的池化

PooledThemeFactory 装饰了内部工厂——这是 decorator-pattern-装饰 的应用。池化逻辑与创建逻辑分离，任意工厂都可按需加池化层。与 object-pool-对象池 和 garbage-collection-GC与内存 的 GC 规避策略一致。

抽象工厂 + ECS/DOTS：Archetype 作为产品族

在 DOTS 中，EntityArchetype 天然定义了一族 Component 的组合——相当于抽象工厂的”产品配方”：

Archetype = 编译期检查的抽象工厂

传统抽象工厂靠接口约束”族一致性”；DOTS 靠 Archetype 的 Component 集合约束。Archetype 是 struct 级别的”工厂配方”，比接口更轻量、零 GC。详见 dots-ecs-数据导向。

反模式

产品族膨胀：产品类型持续增长

抽象工厂接口每加一个产品方法（如从 CreateWeapon/CreateArmor 扩展到 CreateWeapon/CreateArmor/CreateMount/CreateSkill/CreateEffect），所有具体工厂都要实现。如果产品类型频繁变化，抽象工厂会变成维护噩梦。产品类型稳定时用抽象工厂，产品类型频繁变化时改用 builder-pattern-生成器 或独立的 factory-method-工厂方法。

工厂嵌套工厂：AbstractFactory 内部 new 具体工厂

正确做法是通过构造函数注入子工厂，或让具体工厂直接创建产品（不需要内部再嵌套工厂）。嵌套工厂增加了无意义的间接层，也破坏了依赖注入。

忽略异步创建：Addressable 工厂假装是同步的

Addressable 加载是异步的，不能在同步方法中直接 .Result。要么加 LoadAsync() 初始化阶段，要么让创建方法返回 Task<IWeapon>。参见 unitask-deep-dive-深入 的异步模式。

实践示例

  • RPG 不同种族（人类/精灵/矮人）各有武器、护甲、坐骑——族一致性
  • UI 主题系统：Dark/Light 工厂产出 Button、Panel、Font——视觉一致性
  • 关卡主题：森林/沙漠/地牢各产出敌人、地形、BGM——氛围一致性
  • 多平台适配：Mobile/Desktop 工厂产出不同输入方案、分辨率策略、UI 布局
  • 本地化工厂：各语言工厂产出字体、文本方向、文化适配的 UI 元素

权衡与选择

  • 用抽象工厂：需要创建一族一致产品、且产品类型稳定时
  • 用工厂方法：只需创建一个产品、产品类型频繁变化时——factory-method-工厂方法
  • 用生成器：产品构造步骤多、不需要族一致性时——builder-pattern-生成器
  • 用原型：已有模板实例、克隆比创建更方便时——prototype-pattern-原型
  • 用享元：产品无状态、可共享时——flyweight-pattern-享元 避免重复创建

常见陷阱

新增产品类型困难

抽象工厂接口每加一个产品方法，所有具体工厂都要实现。产品族稳定时用抽象工厂，产品类型频繁变化时不适合。

工厂创建的对象无人释放

工厂只管创建不管回收。如果产品是 MonoBehaviour 或持有非托管资源，必须有对应的销毁/回收机制（对象池、Dispose 模式）。参见 garbage-collection-GC与内存。

过度设计：只有一种族时用抽象工厂

如果当前只有一个主题/种族，且近期不会新增，用抽象工厂是过早抽象——直接用工厂方法或简单 new 即可。
