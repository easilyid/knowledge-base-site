对象池（Object Pool）

核心思想

预创建一组对象并重复使用，避免频繁的实例化和销毁。取用时从池中获取，用完归还池中——对象被循环利用而非创建后丢弃。本质是用空间换时间：常驻内存避免 GC 开销，在”内存常驻”与”分配/回收代价”之间取舍。

GPP 关键洞察：对象池解决了游戏开发中最常见的性能陷阱——频繁 new 和 destroy 导致 GC Spike。Nystrom 的核心论点：如果你的对象”用完即弃”但类型固定、大小固定，就不应该真的”丢弃”——复用才是正解。

对象池 vs 享元模式——关键区分

两者都涉及”复用”，但本质不同——对象池复用实例（同一对象在不同时间被不同调用者使用），享元复用数据（多个对象共享同一份不可变数据）。子弹池是对象池（每颗子弹有独立的位置/方向），材质共享是享元（多个渲染器共享同一个 Material）。参见 flyweight-pattern-享元。

何时用 SimpleObjectPool vs Unity ObjectPool<T>

SimpleObjectPool 适合快速原型或极简项目。生产代码建议用 Unity 官方 ObjectPool<T>——它提供 collectionCheck（防重复释放）、maxSize（防内存膨胀）、onGet/onRelease/onDestroy 回调。

对象池与 GC 的关系

对象池对 GC 的影响是根本性的——参见 garbage-collection-GC与内存：

池化对象对 GC 的影响

池化对象常驻内存，最终会升到 Gen2。这对 GC 来说是好事——Gen2 对象不会被频繁扫描。但池化太多对象会增大 Gen2 体积，Gen2 GC 触发时扫描更慢。平衡点：只池化真正高频使用的对象。

反模式

忘记归还对象——池泄漏

从池中取出对象后忘记归还，池逐渐枯竭，最后被迫不断创建新对象，等于没有池化。解决：使用 using 模式或自动回收机制。

池中对象状态未重置

归还对象时不重置状态，下次取出的对象带着上次的数据——位置错误、碰撞残留、UI 文字残留。每次归还必须完整重置。

池大小设置不当

  • 太小：频繁扩容，峰值性能下降
  • 太大：浪费内存，GC 扫描更多对象
  • 经验法则：池大小 = 预估峰值 * 1.2（留 20% 余量），用 Profiler 确认实际峰值
