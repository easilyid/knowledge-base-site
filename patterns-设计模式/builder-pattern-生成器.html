生成器（Builder）

核心思想

将复杂对象的构造过程分步骤进行，使得同样的构建流程可以产出不同表示。将”怎么建”与”建什么”分离。

问题动机

不用生成器会怎样？

  • Telescoping Constructor（望远镜构造函数）：参数越来越多，构造函数重载爆炸
  • 客户端必须知道正确的参数顺序和组合，传错一个就创建出无效对象
  • 不可变对象的分步构建无法实现（构造函数必须一次传完所有参数）

生成器的核心价值：把”构造复杂对象”从一步到位变成可控的分步流程，让客户端只关心自己需要的步骤。

参与者说明：

角色职责Unity/C# 对应
Director（指挥者）定义构建步骤的顺序和流程，不关心具体实现关卡配置脚本、角色创建流程控制器
IBuilder（生成器接口）声明各步骤的抽象方法C# interface，常与 ScriptableObject 配合
CharacterBuilder（具体生成器）实现各步骤，逐步组装产品纯 C# 类或持有 SO 配置的构建器
Character（产品）最终构建结果，不关心自己是怎么被组装的游戏实体、配置对象、ScriptableObject 实例

Director 不是必须的

流畅接口（Fluent Builder）模式中，客户端直接链式调用 Builder 方法，不需要 Director。Director 的价值在于”复用构建流程”——如果多个地方需要相同的构建步骤顺序，Director 才有意义。

Unity 中 Builder 的一大应用场景：用 ScriptableObject 定义”构建步骤的配置”，策划在 Inspector 里配每个步骤用什么资源：

SO Builder vs 纯代码 Builder

SO Builder 的步骤是策划可配的——新增一种”初始装备”步骤不需要写代码，只需在 Inspector 里加一个 ApplyEquipmentStep SO。纯代码 Builder 适合有复杂逻辑判断的构建步骤（如”如果种族是精灵则自动加 MP”）。

Addressable 链式加载：步骤化异步 Builder

当构建步骤涉及异步资源加载时，Builder 每一步都可以是异步的：

异步 Builder 的 Build 阶段是"汇聚点"

同步 Builder 的每一步都是立即执行的；异步 Builder 的步骤只记录参数，BuildAsync 时统一加载。这种”延迟到 Build 时执行”的设计使得步骤间可以做优化（如并行加载）。详见 unitask-deep-dive-深入 的异步构建模式。

简单判断法

对象只有 2-3 个必填参数 → 构造函数或工厂方法；对象有大量可选参数或构建步骤有顺序约束 → Builder。Builder 的本质是用代码表达”先做什么、后做什么”。

Builder + Prototype：模板化构建

Builder 与 prototype-pattern-原型 组合：从模板克隆后，再用 Builder 微调：

原型提供"起点"，Builder 提供"微调"

单独用原型只能做完整克隆；单独用 Builder 每次都从零开始。两者组合：原型给出 80% 的初始状态，Builder 覆盖 20% 的差异。这比纯 Builder 从零构建效率更高。

Builder 创建不可变对象

C# 中用 Builder 创建 record 或只读对象，保证构建完成后不可修改：

record + with 表达式是 C# 10+ 的轻量替代

如果不需要 Director 复用构建流程，C# 10 的 record + with 表达式可以替代 Builder：

但 with 只能覆盖已有属性，无法表达”步骤顺序约束”或”校验逻辑”。需要这两者时仍用 Builder。

反模式

Builder 过度抽象：简单对象不需要 Builder

只有 2-3 个参数且没有步骤顺序约束的对象，用 Builder 是过度设计——用命名参数、可选参数或 record + with 即可。Builder 的价值在于”步骤多、有约束、需复用流程”，不是”每个类都配一个 Builder”。

Builder 内部状态不一致：未调用必要步骤就 Build

Builder 没有”强制调用顺序”的机制——客户端可能忘了设必填字段就调用 Build()。防御方式：

  • Build() 中校验必填字段，缺失时抛异常
  • 用”阶段性 Builder”在类型系统层面强制顺序（见下方示例）

Builder 复用导致状态泄漏

Builder 设计有两种选择：(1) 每次 Build() 后 Builder 不可复用（抛异常或重置）；(2) Build() 内部深拷贝 product，Builder 可复用。明确选择一种并在文档中标注。

实践示例

  • 角色创建流程：种族 → 职业 → 初始装备 → 属性
  • 关卡构建：地形 → 敌人 → 道具 → 触发器
  • Unity Inspector 本质上就是一个 Builder UI——每个字段就是一个构建步骤
  • 网络协议消息构建：Header → Body → Checksum
  • 技能效果链构建：主效果 → Buff → Debuff → 特效
  • 配置对象构建：从 JSON/ScriptableObject 读取参数，Builder 校验后构建不可变配置

权衡与选择

  • 用生成器：对象有很多可选参数、构建步骤有顺序要求时
  • 用工厂方法：对象简单、创建逻辑一步完成时——factory-method-工厂方法
  • 用抽象工厂：需要创建一族相关对象时——abstract-factory-抽象工厂 保证族一致性
  • 用原型：已有模板实例、克隆更方便时——prototype-pattern-原型 适合 Prefab 克隆
  • 直接 new / record with：参数少且无步骤约束时——不要过度设计
  • 用组合模式：Builder 构建的对象本身是树形结构时——composite-pattern-组合

常见陷阱

Builder 需要维护一个与产品平行的 Builder 类

产品字段变化时 Builder 也要同步修改。如果产品很简单（3 个以下参数），Builder 是过度设计——用命名参数或 record 即可。

Director 与 Builder 强耦合

Director 如果依赖具体 Builder 而非 IBuilder 接口，就失去了”同样流程不同表示”的能力。Director 应只依赖 IBuilder 接口。

异步 Builder 的异常处理

BuildAsync() 中任何一步异步操作都可能失败。必须在 await 处加 try-catch，或在 Builder 层面提供回退逻辑（如资源加载失败时使用默认资源）。
