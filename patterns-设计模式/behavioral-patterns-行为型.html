行为型模式（Behavioral Patterns）

核心思想

行为型模式关注对象间的通信与职责分配——谁做什么、谁通知谁、谁处理什么。它们解决的不是”创建什么”或”如何组合”，而是”如何协作”。

为什么重要

游戏系统交互密集：输入响应、AI 决策、事件通知、状态切换、回合流程。行为型模式帮助解耦交互逻辑，让系统更容易扩展和维护。行为型模式是游戏开发中使用频率最高的模式类别。

十种模式概览

模式核心意图典型 Unity 场景使用频率
chain-of-responsibility-责任链请求沿处理链传递伤害计算管线、输入事件分发、日志处理器中频
command-pattern-命令请求封装为对象输入绑定、撤销/重做、回放系统、技能队列高频
iterator-pattern-迭代器统一遍历集合自定义集合遍历、Inventory 道具遍历中频
mediator-pattern-中介者对象通过中介者通信UI 面板间通信、ChatMediator、EventBus中频
memento-pattern-备忘录保存/恢复对象状态存档系统、撤销/重做（与命令模式配合）中频
observer-pattern-观察者发布-订阅通知UnityEvent、Action、UniRx、成就系统极高频
state-pattern-状态状态变化改变行为AI 状态机、角色状态（站立/跑/跳）、UI 状态极高频
strategy-pattern-策略算法族可互换AI 行为策略、伤害计算、武器系统高频
template-method-pattern-模板方法超类定义算法骨架关卡流程、Boss 行为模板、角色初始化流程中频
visitor-pattern-访问者算法与对象结构分离序列化、AST 解析、伤害类型分发低频

模式间关系

  • 命令 vs 策略：命令封装请求，策略封装算法；命令强调”做什么”，策略强调”怎么做”
  • 命令 vs 备忘录：命令+备忘录实现撤销——命令执行操作，备忘录保存状态快照
  • 观察者 vs 中介者：观察者是一对多通知，中介者是多对多协调；观察者更轻量，中介者更集中
  • 状态 vs 策略：结构相似但意图不同——状态对象随上下文自动切换，策略由客户端选择
  • 责任链 vs 中介者：责任链是链式传递，中介者是集中调度
  • 模板方法 vs 策略：模板方法用继承重写步骤，策略用组合替换算法

Unity 中的行为型模式全景

Unity 在行为层面提供了大量内置实现，日常开发应优先使用：

引擎机制对应模式说明
UnityEvent / Action<T>观察者模式一等公民级支持，编辑器可配置
UniRx / R3观察者模式（响应式）响应式扩展，流式事件处理
Animator / AnimatorController状态模式可视化状态机编辑器，驱动动画切换
Input System (新)命令模式输入动作封装为 InputAction，可运行时重绑定
Coroutine / IEnumerator迭代器模式Unity 特化的帧驱动迭代器
ScriptableObject 事件通道观察者 + 中介者无需单例的跨对象通信方案
PlayerLoop 子系统模板方法变体固定帧循环骨架，子系统注册回调

UnityEvent 就是观察者的引擎级实现

UnityEvent 在 Inspector 可视化绑定，运行时自动通知所有监听者。日常开发优先用 UnityEvent 或 Action<T>，不必手写观察者基础设施。

行为模式与调度

Unity 的 player-loop-主循环 定义了每帧的执行顺序，行为型模式的时序必须与帧循环对齐：

  1. Input 阶段 — 收集输入，封装为命令对象
  2. Update 阶段 — 命令执行，触发观察者通知，可能引发状态切换
  3. Coroutine 继续 — yield return null 后在此阶段恢复
  4. LateUpdate — 状态稳定后可安全查询
时序关切涉及模式建议
观察者通知顺序观察者不依赖通知顺序；有顺序需求改用责任链
状态切换的副作用状态避免在 OnDisable/OnDestroy 中切换状态
Coroutine 时序迭代器yield null = 下帧 Update 后；WaitForFixedUpdate = 物理帧后

观察者通知中修改集合会抛异常

回调中添加/移除监听者会导致集合修改异常。方案：用待处理队列缓冲变更，通知完成后统一处理。

GPP 中额外收录的行为模式

GoF 的 10 种行为型模式源自企业软件，游戏开发还有三种高频行为模式未被收录，由 GPP（Game Programming Patterns）补充：

GPP 模式核心意图与 GoF 行为模式的关系Unity 映射
字节码数据驱动的行为定义，非程序员可编写逻辑解释器的轻量游戏版——不做完整 AST，只做指令集Mod 系统、技能脚本、可视化编程
子类沙箱基类提供操作集，子类只组合调用模板方法的逆方向——模板方法是”基类定骨架、子类填细节”，子类沙箱是”基类提供积木、子类自由组合”MonoBehaviour 虚方法体系
类型对象数据定义类型而非继承，运行时可增删类型策略 + 原型的结合——策略选行为，原型克隆模板ScriptableObject 作为类型定义

子类沙箱 vs 模板方法

两者都涉及基类与子类协作，但方向相反：

  • 模板方法：基类定义算法骨架（控制权在基类），子类只能重写特定步骤
  • 子类沙箱：基类提供操作工具箱（控制权在子类），子类自由组合调用

Unity 的 MonoBehaviour 是子类沙箱的典型：引擎提供 transform、gameObject、Start()、Update() 等操作集，子类自由组合使用。

游戏开发中的高频行为型模式

  1. 观察者 — 几乎无处不在（UnityEvent 本身就是观察者）
  2. 状态 — AI、角色、UI 的核心模式
  3. 命令 — 输入系统、撤销、技能队列
  4. 策略 — AI 行为切换、伤害计算

常见陷阱

状态模式 ≠ 状态机库

状态模式是一种设计模式（每个状态一个类），FSM 是一种架构工具。小规模用状态模式就够，复杂 AI 用 FSM 库（如 Stateless、Sirenix）更合适。

命令不是万能解耦器

命令模式解耦的是”发起者”和”执行者”，但引入命令对象本身会增加 GC 压力（每个命令是一次分配）。高频路径（如每帧输入）建议用结构体命令 + 对象池，避免 GC Spike。详见 garbage-collection-GC与内存。
