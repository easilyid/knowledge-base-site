外观（Facade）

核心思想

为复杂子系统提供简化的统一接口。外观不封装子系统，只是提供一个更高层的便利入口，让客户端无需了解子系统内部的交互细节。

GPP 关键洞察：外观模式是游戏开发中最常被使用却最不被意识到的结构型模式。几乎每个 GameManager 都是外观——只是很多人没意识到它是一个模式，也没有意识地控制它的边界。

问题动机

没有外观时，客户端直接与多个子系统交互，导致强耦合和脆弱的初始化代码：

这种写法的问题：

  • 耦合子系统的初始化顺序：任何子系统的增删改都要改调用方
  • 逻辑散落：同样的初始化序列出现在多个地方，复制粘贴维护
  • 无法替换实现：子系统换了一个，所有调用方都要改
  • 难以测试：无法用一个简化的接口 mock 整个子系统群

外观模式的核心动机：将”与多个子系统交互的协作逻辑”集中到一个地方，让客户端只跟一个对象打交道。

参与者

角色职责Unity/C# 对应
Facade提供简化的高层接口，将客户端请求委托给适当子系统GameManager、AudioManager、AssetLoadingService
Subsystem实现专业功能，不知道 Facade 的存在各个独立 Manager/System（AudioSystem、ParticleSystem、SpawnSystem）
Client通过 Facade 与子系统交互，不直接引用子系统关卡脚本、UI 控制器、GameLoop

子系统不知道 Facade 的存在

这是外观与中介者的关键区别。子系统不知道自己被外观包装了，它们仍然可以独立使用。外观是单向依赖——外观依赖子系统，子系统不依赖外观。

1. GameManager 作为游戏初始化外观

这是 Unity 项目中最常见的外观——但很多人没意识到它是个外观模式，也没有意识地控制它的边界：

GameManager 容易从"外观"变成"上帝类"

外观只封装子系统协作，不添加业务逻辑。如果 GameManager 里出现了 CalculateDamage()、CheckWinCondition() 等方法，说明它已经越界。见下方反模式章节。

2. 资源加载外观：封装 Addressables + 缓存 + 对象池

资源加载是外观模式在 Unity 中最实用的场景——底层涉及 Addressables、缓存策略、对象池、引用计数等复杂逻辑，上层只需要”给我这个资源”：

资源加载外观的价值

上层代码不需要知道资源是从 Addressables、AssetBundle 还是 Resources 加载的。切换底层策略时只改外观内部实现，调用方无感知。

外观与中介者的区分

两者结构相似但意图不同，这是最常见的混淆点：

维度外观（Facade）中介者（Mediator）
意图简化接口，让客户端更容易使用消除子系统间的直接耦合
依赖方向单向：外观依赖子系统双向：子系统依赖中介者
子系统是否知道子系统不知道外观的存在子系统知道中介者的存在
通信方向客户端 → 外观 → 子系统子系统 ↔ 中介者 ↔ 子系统
典型场景游戏初始化、资源加载UI 控件间通信、战斗系统
变化影响子系统换实现，只改外观加新子系统交互，改中介者

选择标准

如果只需要”调用多个子系统完成一件事”，用外观。如果子系统之间需要”互相通知、协调行为”，用 mediator-pattern-中介者。

交叉引用

  • mediator-pattern-中介者 — 中介者：子系统间双向通信，与外观的核心区分
  • adapter-pattern-适配器 — 适配器：转换接口，外观是简化接口
  • singleton-pattern-单例 — 单例：Unity 中外观常与单例组合
  • decorator-pattern-装饰 — 装饰器：添加行为，外观是简化访问
  • unitask-deep-dive-深入 — 异步外观的 UniTask 实现

变体与演进

变体说明适用场景
外观 + 单例全局唯一的外观入口Unity 中最常见的组合，GameManager 单例
子外观对子系统子集再封装一个更窄的接口大系统中分层简化，如 AudioFacade 是 GameFacade 的子外观
外观 + 依赖注入外观通过 DI 容器获取子系统可测试、可替换子系统实现
异步外观外观方法返回 UniTask/Awaitable子系统含异步操作（Addressables、网络请求）
外观 + 事件总线外观发布事件通知结果调用方需要异步获知操作结果，又不希望直接耦合

外观 + 单例（Unity 中最常见的组合）

外观不等于单例

外观是结构型模式，关注”简化接口”；单例是创建型模式，关注”唯一实例”。两者经常组合但不应混为一谈。外观完全可以不是单例——每个关卡可以有自己的 LevelFacade 实例。

反模式

外观变成"上帝类"

外观只应封装子系统协作，不应包含业务逻辑。如果外观里出现 CalculateDamage()、CheckWinCondition()、ProcessInventory() 等方法，说明它已经从”简化入口”变成了”什么都管”的上帝类。正确做法：外观调用子系统，业务逻辑留在子系统内部。

把所有子系统方法都暴露在外观上

外观的价值在于”提供比子系统更简单的高层接口”，而不是把子系统所有方法原样搬过来。如果外观的方法签名和子系统一一对应（PlayBGM() → _audio.PlayBGM()、PlaySFX() → _audio.PlaySFX()、SetVolume() → _audio.SetVolume()），那外观只是多了一层无意义的间接——客户端直接用 AudioSystem 更简单。正确做法：外观提供”用例级”方法（如 StartBossFight()），而不是”操作级”方法。

外观添加业务逻辑

外观中不应出现 if/else 业务分支。如果外观的 StartBossFight() 里有 if (player.Level > 10) { ... } else { ... }，这是业务逻辑——应该移入专门的 BossFightService。外观只编排调用顺序，不做决策。

权衡与选择

  • 用外观：需要简化多个子系统的访问接口时
  • 用中介者：子系统之间需要互相通信、协调行为时——mediator-pattern-中介者
  • 用适配器：需要转换已有接口以匹配期望接口时——adapter-pattern-适配器
  • 用装饰器：需要动态添加行为时——decorator-pattern-装饰

常见陷阱

外观不是万能胶

外观只简化接口，不改变子系统行为。如果子系统之间需要复杂交互，应用 mediator-pattern-中介者 而非外观。

外观持有子系统引用导致生命周期问题

外观通常持有子系统的引用。在 Unity 中，如果子系统是 MonoBehaviour 且外观也是 MonoBehaviour，场景切换时子系统的引用可能失效。解决方案：外观在 OnEnable/OnDisable 中重新获取引用，或使用依赖注入容器管理生命周期。

实践示例

  • GameManager 作为各子系统的外观入口
  • 资源加载门面：统一 Addressables / Resources / AssetBundle 加载
  • 关卡初始化门面：一键启动场景加载+敌人生成+BGM+特效
  • AudioManager 外观：封装 BGM 淡入淡出、SFX 池化、3D 音效定位
  • 网络层外观：封装连接、认证、心跳、重连逻辑为 Connect() / Disconnect() 接口
  • 存档外观：封装序列化、加密、云存储同步为 Save() / Load() 接口
