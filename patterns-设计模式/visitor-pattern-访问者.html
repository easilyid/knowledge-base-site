访问者（Visitor）

核心思想

将算法与对象结构分离。在不修改对象类的前提下，通过访问者为对象结构中的各类型元素定义新操作。核心机制是双重分派（Double Dispatch）——运行时根据访问者和元素的实际类型选择正确的方法。

问题动机

没有访问者时，对不同类型对象添加操作需要在每个对象类中加方法——违反开闭原则：

这种写法的问题：

  • 操作侵入元素类：每新增一种操作，所有元素类都要加方法
  • 类型判断散落：if-else / switch 类型判断遍布代码，新增类型要改所有判断点
  • 无法统一遍历：不同类型的操作逻辑分散，无法统一管理
  • 编译期无保障：if-else 链漏掉一种类型不会有编译错误

访问者的核心动机：让操作独立于对象结构变化——新增操作只需添加一个 Visitor 类，不修改任何元素类。

双重分派的工作原理

C# 的方法重载在编译期根据声明类型选择重载版本。visitor.Visit((IElement)element) 永远调用 Visit(IElement)，而非 Visit(Treasure)。双重分派绕过这个限制：

  1. 第一重分派：element.Accept(visitor) —— 运行时按 element 的实际类型选择 Treasure.Accept()
  2. 第二重分派：visitor.Visit(this) —— 此时 this 的编译期类型是 Treasure，所以选择 Visit(Treasure) 重载

变体与演进

用 C# dynamic 实现动态分派

用 dynamic 关键字绕过双重分派的样板代码——运行时根据实际类型选择方法重载：

dynamic 的代价

dynamic 使用 DLR（Dynamic Language Runtime），每次调用有反射开销。热路径中不适用。此外，编译期无法检查类型安全——新增元素类型不会触发编译错误，只有运行时兜底。

用 pattern matching 替代 Visitor（C# 8+）

C# 8.0+ 的 switch expression 提供了更简洁的类型分派：

dynamic无样板代码、元素类不需要改反射开销、运行时错误运行时

选择建议

元素类型稳定、操作频繁新增 → 经典 Visitor。元素和操作都频繁变化 → pattern matching（更灵活）。原型/工具代码 → dynamic（最快实现）。

反模式

元素类型频繁变化时使用 Visitor

Visitor 的最大限制：每新增一种元素类型，所有 Visitor 接口和具体 Visitor 都要修改。如果元素类型频繁变化（如每周新增一种地图对象），维护成本会急剧上升。判断标准：元素类型是否比操作更稳定？如果是，用 Visitor；如果否，用 pattern matching 或策略模式。

Visitor 破坏封装

Visitor 需要访问元素的内部数据（如 Treasure.Gold、Enemy.Hp），这意味着元素必须暴露足够的数据供 Visitor 操作。如果元素本应隐藏内部实现，Visitor 会迫使你打破封装。解决方案：元素提供”足够但不过度”的接口——暴露”访问者需要的数据”，隐藏”内部实现细节”。

循环引用导致 Visitor 与元素紧耦合

如果 Visitor 在 Visit 方法中回调元素的公共方法修改其状态，而元素又在 Accept 中依赖 Visitor 的特定类型，循环依赖会让两者都无法独立变化。Visitor 应该是”只读遍历+外部计算”，尽量避免在 Visit 中修改元素状态。

权衡与选择

  • 用访问者：对象结构稳定、需要频繁添加新操作时
  • 用策略：操作可替换但不需要按类型分派时
  • 用命令：操作需要撤销/队列时
  • 用 pattern matching：元素类型和操作都频繁变化、需要灵活组合时
  • 用 ECS 查询：在 DOTS 架构中，System 查询天然替代 Visitor
