游戏编程模式（Game Programming Patterns）

核心思想

《Game Programming Patterns》是 Robert Nystrom（EA 8 年工作经验）从游戏开发实战出发归纳的设计模式体系。全书覆盖 19 种模式，其中 6 种复访 GoF（命令、享元、观察者、原型、单例、状态），13 种是 GoF 未收录的游戏特有模式。

GPP 与 GoF 的根本区分：GoF 解决”对象间关系”，GPP 解决”游戏独有关切”——帧驱动（游戏循环/更新方法）、性能约束（数据局部性/对象池/空间分区）、数据驱动（类型对象/字节码/脏标识）。理解这条脉络，就知道为什么有些 GoF 模式在游戏中低频（如访问者），而 GPP 模式反而天天用。

架构哲学：长期速度、运行速度与短期速度的角力

GPP 序言提出了一个被多数设计模式书籍忽略的宏观视角：软件架构的核心目标是降低”理解代码”的认知开销。

评价架构设计就是评价它应对变化有多么轻松。没有了变化，它就是永远不会离开起跑线的运动员。 —— Robert Nystrom, Game Programming Patterns

整个开发周期中，三大要素始终在角力：

要素含义与其他要素的冲突
长期开发速度好架构长期来看提高了生产力——改动局部化，理解成本低但维护每个变化都需要更多努力让代码保持整洁
游戏运行速度高度优化的代码消除帧预算超标但优化后代码不灵活、难改动，还污染架构
短期开发速度尽可能快地实现特性，尽早得到反馈但快速堆代码会积累黑魔法，阻碍未来产出

这三点都是”速度”——长期开发的速度、游戏运行的速度、短期开发的速度。它们至少部分对立，没有银弹，只有具体问题具体分析的动态平衡。

解耦的真实含义

两种理解方式：

  1. 学习阶段视角：如果两块代码是耦合的，就无法只理解其中一个而不了解另一个。解耦后可以独立理解——最小化进入大脑的知识量。
  2. 变化传播视角：一块代码变化时，不必修改另一块代码。耦合程度越小，变化波及范围越小。

YAGNI 与过度设计

每添加一层抽象或扩展点，就是在赌”这部分功能以后用得上”。赌对了，功夫不负有心人；赌错了，有害——你得花时间去实现和维护无人使用的代码。社区用 YAGNI（You Aren’t Gonna Need It）对抗”面向未来编程”的冲动。

无数开发者听着加强可扩展性的"警世名言"，花费多年时间制作"引擎"，却没有搞清楚做引擎是为了什么。

烂代码在原型阶段的合理性

原型阶段的代码不必、也不应该是好架构的代码。关键约束：

  • 原型代码的目标是尽快验证想法，如果想法不对，花在优雅设计上的时间全部白费
  • 但必须让所有人清楚：可抛弃的代码即使看上去能工作，也不能被维护，必须重写
  • 一个保证原型代码不会变成正式代码的技巧：使用和正式游戏不同的编程语言

保持灵活直到设计定型

GPP 给出的折中策略：

  1. 保持代码灵活直到设计定下来——用接口、用模式、用解耦
  2. 设计定下来后，抽出抽象层来提高性能——这时牺牲灵活性换运行速度是值得的
  3. C++ 模板是一个有趣的中间地带——编译时决定调用哪些类，既有抽象的灵活性，又没有虚调度的运行时开销

这种写法的问题：

  • 帧驱动盲区：GoF 没有”每帧执行”的概念——观察者是”事件来了通知”，但游戏需要”每帧主动推进”
  • 性能盲区：GoF 模式（策略、状态、命令）大量使用虚调用和堆分配，在每帧执行 1000 次时性能不可接受
  • 数据驱动盲区：GoF 用继承和多态定义行为差异，游戏中行为种类爆炸（100 种技能、200 种怪物），继承体系无法承载

三大演进方向：

  1. 帧驱动层：GoF 没有时序概念 → GPP 增加了”每帧执行”和”帧边界原子性”
  2. 解耦层：GoF 的解耦是”接口隔离” → GPP 进一步要求”运行时可替换”和”时序解耦”
  3. 优化层：GoF 将性能视为可选 → GPP 将性能视为第一等公民

与 GoF 重叠的 6 种模式

GPP 复访了 GoF 的 6 种模式，但对每种都给出了游戏特化解读——不是简单复述，而是指出”游戏中怎么用”和”游戏中的坑”。理解这 6 种模式的 GoF→GPP 演化，是掌握 GPP 体系的关键桥梁。

命令（Command）

GoF 说：将请求封装为对象。GPP 说：这是被 GoF 低估的模式——输入重映射、撤销/重做、回放系统的基石。游戏中命令模式的使用频率远高于企业软件。

GPP 额外贡献的 5 种游戏用法：(1) 输入重映射、(2) 撤销/重做（IUndoableCommand）、(3) 回放系统（录制命令序列逐帧重放）、(4) AI 代理（AI 产生命令而非直接操作对象）、(5) 异步命令（IAsyncCommand + UniTask）。详见 command-pattern-命令。

享元（Flyweight）

GoF 说：共享内在状态以节省内存。GPP 重点区分了享元与对象池——享元共享的是数据（同一把剑的模型纹理），对象池复用的是实例（同一个子弹对象的内存槽位）。两者常组合使用：享元定义”共享什么”，对象池管理”复用谁”。

游戏中享元的典型场景：(1) 共享纹理/模型/Mesh——1000 把同类型剑共享 1 个 Mesh、(2) 共享 Tile/Block 数据——Minecraft 的方块类型、(3) 共享动画状态——AnimatorController 在同类型角色间共享。详见 flyweight-pattern-享元。

观察者（Observer）

GoF 说：一对多依赖关系，状态变化自动通知。GPP 重点讨论了失效监听者问题（Lapsed Listener）——观察者已销毁但未取消订阅，导致空引用或幽灵回调。Unity 中 OnEnable/OnDisable 配对是标准解法。

GPP 的进一步贡献：观察者 → 事件队列的演进脉络。观察者是同步直接调用（生产者等消费者），事件队列是异步缓冲解耦（生产者入队即返）。当观察者链中有慢消费者（如音效加载、网络请求），必须升级为事件队列。详见 observer-pattern-观察者、event-queue-事件队列。

原型（Prototype）

GoF 说：通过克隆已有对象创建新对象。GPP 指出 Unity 的 Instantiate() 就是原型模式——克隆 Prefab 实例。GPP 还讨论了深拷贝 vs 浅拷贝的陷阱：Instantiate 是浅拷贝，子物体引用的共享资源不会被复制。

游戏中原型的核心价值：策划配置一个”模板”实体，运行时通过克隆快速产出大量实例。这与 type-object-类型对象 天然组合——类型对象定义”克隆什么”，原型模式执行”如何克隆”。详见 prototype-pattern-原型。

单例（Singleton）

GoF 说：保证全局唯一实例。GPP 的态度是被过度使用的模式——Nystrom 专门用一章来”批判”单例，指出三大问题：

  1. 隐藏依赖：类的构造函数看不出它依赖了哪些单例，耦合隐式散落在方法体中
  2. 初始化顺序不可控：单例之间可能有依赖关系，Awake 执行顺序不确定
  3. 与具体实现绑定：GameManager.Instance 直接绑死了具体类，无法替换为 Mock 测试

替代方案的演进路径：单例 → service-locator-服务定位（全局但接口解耦）→ 依赖注入（VContainer，推模式，依赖显式化）→ ECS 单例组件（DOTS 中用 SystemAPI.GetSingleton<T>()）。详见 singleton-pattern-单例。

状态（State）

GoF 说：内部状态变化改变行为。GPP 展示了从枚举 + switch → 状态模式 → 并发状态机 → 层次状态机 → 下推自动机的完整演进路径。游戏中角色状态比企业软件复杂得多：

GPP 最有价值的洞察：游戏角色的状态不是互斥的——角色可以同时处于”移动”和”攻击”状态，这需要并发状态机而非 GoF 的单状态切换。详见 state-pattern-状态。

GPP 模式选择决策

选择 GPP 模式的关键不是”哪个模式好”，而是”你的问题属于哪一层关切”：

你的问题属于哪层先看再看
”每帧执行顺序/时序有问题”帧驱动层game-loop-游戏循环double-buffer-双缓冲、update-method-更新方法
”行为硬编码，策划改数值要改代码”行为定义层type-object-类型对象bytecode-字节码、subclass-sandbox-子类沙箱
”模块间耦合，改一个崩一片”解耦层component-组件模式event-queue-事件队列、service-locator-服务定位

诊断优先级：帧驱动 > 解耦 > 优化 > 行为定义

帧驱动是游戏运行的前提（不跑起来什么都没用），解耦是架构可持续演化的基础，优化在 Profiler 确认瓶颈后做，行为定义模式（字节码/类型对象）通常在项目成熟期引入。不要一上来就搞字节码 VM——先让游戏跑起来再说。

反模式

拿 GoF 模式生搬硬套到游戏中

不考虑帧驱动和性能约束，直接在 Update 中使用 GoF 的虚调用链——1000 个敌人每个持有 3 个策略接口，每帧 3000 次虚调用 + Cache Miss。GoF 模式本身没错，但在热路径上必须考虑数据局部性和批量处理。

忽视 GPP 的"游戏特化解读"

命令模式不只是”封装请求”——它还是输入重映射和回放系统的基石。观察者模式不只是”通知”——还要处理失效监听者。单例不只是”全局唯一”——更要警惕隐藏依赖。读 GPP 的价值在于这些游戏特化洞察，而非模式的通用定义。

13 种模式全上

不是每个游戏都需要字节码或空间分区。按频率分层选择：极高频模式（组件、对象池、游戏循环）几乎必用，中低频模式按需引入。过早引入不需要的模式徒增复杂度。

混淆 GoF 策略与 GPP 类型对象

两者都能让对象行为可替换，但机制完全不同：GoF 策略用接口多态（每个策略一个类，虚调用分发），GPP 类型对象用数据驱动（一个类读配置表，行为由数据决定）。100 种技能用策略 = 100 个子类 + 100 次虚调用；用类型对象 = 1 个类 + 100 条配置。在行为种类爆炸时，类型对象远优于策略。
