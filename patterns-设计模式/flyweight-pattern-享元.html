享元（Flyweight）

核心思想

通过共享多个对象共有的相同状态（内在状态），减少内存占用。将共享状态与独有状态（外在状态）分离——内在状态存储在享元对象中被所有引用者共享，外在状态由客户端自行维护。

GPP 关键洞察：享元模式的本质是”数据与上下文的分离”。在游戏中，大量相似对象（树、子弹、Tile）只有极少量数据是独有的一般来说只是位置/朝向。共享不变的数据不是优化技巧，而是正确的数据建模方式。

问题动机

没有享元时，大量相似对象各自持有完整数据，造成严重的内存浪费：

这种写法的问题：

  • 内存膨胀：相同数据被重复存储 N 次，内存占用可能是必要量的 N 倍
  • 缓存不友好：相同数据分散在不同内存位置，CPU 缓存命中率低
  • 修改影响面不可控：如果错误地修改了某个实例的”共享”数据，其他实例不受影响——看似是隔离的，但意味着无法批量更新
  • 加载时间增加：相同资源被重复加载或创建

享元模式的核心动机：识别并分离内在状态与外在状态，让共享数据只存一份。

    Client --> IFlyweight : 使用
    FlyweightFactory --> IFlyweight : 缓存/创建
    IFlyweight <|.. ConcreteFlyweight : 共享
    IFlyweight <|.. UnsharedConcreteFlyweight : 不共享

    participant F as FlyweightFactory
    participant P as Pool (缓存)
    participant FW as ConcreteFlyweight

    F->>P: 查找 "OakTree"
    alt 缓存命中
        P-->>F: 返回已缓存的享元
    else 缓存未命中
        F->>FW: new ConcreteFlyweight("OakTree")
        FW-->>F: 创建完成
        F->>P: 缓存享元
    end
    F-->>C: 返回享元
    C->>FW: Operation(position) // 传入外在状态

Tile 地图共享地形数据

Tile 地图是享元模式的经典场景——同类型 Tile 共享纹理、碰撞形状、移动消耗等数据，每个 Tile 实例只存坐标：

用 struct 存外在状态

Tile 地图中格子的外在状态（坐标+享元引用）非常小，用 struct 而非 class 可以进一步减少内存——没有对象头开销，数组连续存储对 CPU 缓存友好。这与 native-container-Native容器 中 NativeArray 的设计理念一致。

ScriptableObject 作为享元载体

Unity 中 ScriptableObject 天然适合充当享元——它是独立于场景的数据容器，多个 MonoBehaviour 可以引用同一个 SO 实例，实现数据共享：

SO 享元 vs 纯 C# 享元

SO 享元的优势：Inspector 可视化编辑、运行时热重载、资源引用自动管理。劣势：加载依赖 Unity 资源管线，无法在非 MonoBehaviour 上下文中使用。纯 C# 享元更轻量，适合 DOTS/Burst 编译环境。

DOTS Archetype 与享元思想的对应

DOTS 中的 EntityArchetype 体现了享元思想——Archetype 定义了 Entity 的”组件配方”（内在结构），同 Archetype 的 Entity 在内存中连续排列：

Archetype = 结构共享 + 数据分离

Archetype 不是经典的享元模式——它共享的是”结构”而非”数据”。但核心思想一致：识别共性、分离差异。详见 dots-ecs-数据导向。

享元与对象池的区分（关键！）

两者经常被混淆，但本质完全不同：

维度享元（Flyweight）对象池（Object Pool）
核心目的减少内存占用（共享同一份数据）减少 GC 压力（复用实例避免分配销毁）
对象身份多个客户端持有同一个对象引用池中对象是独立实例，每次 Rent 返回不同实例
状态特征内在状态不可变池对象的状态每次 Rent 后重置
生命周期享元一旦创建通常不销毁池对象频繁 Rent/Return
数量关系1 个享元 → N 个客户端共享N 个池对象 → 同一时刻最多 N 个客户端使用
典型场景同类型 Tile 数据、弹丸配置子弹实例、特效粒子、敌人实例

混淆享元与对象池是最常见的错误

享元共享同一对象（1 个对象被 N 处引用），对象池复用独立实例（N 个对象轮流使用）。享元解决内存问题，对象池解决 GC 问题。两者经常组合使用，但绝不能混为一谈。

享元解决”1 万发子弹共享 1 份配置”的内存问题，对象池解决”1 万发子弹频繁创建销毁”的 GC 问题。两者互补而非替代。

不可变享元

强制不可变是享元安全的前提——C# 中用 readonly / init 保证：

为什么不可变是必须的

如果享元可变，任何一个客户端修改享元都会影响所有共享者——这是灾难性的副作用。readonly / init 在编译期阻止这种错误。

反模式

混淆享元与对象池

享元共享同一对象（1 个对象 → N 个引用），对象池复用独立实例（N 个对象 → 轮流使用）。享元解决内存问题，对象池解决 GC 问题。混淆二者会导致：用享元的地方误用对象池（内存浪费）、用对象池的地方误用享元（状态污染）。

享元中存储了外在状态

享元对象只应包含内在状态（所有共享者相同的部分）。如果享元中出现了 Position、CurrentHealth、Owner 等字段——这些是外在状态，应移到客户端/上下文对象中。外在状态混入享元会导致共享者之间互相干扰。

享元工厂无限增长

享元工厂的缓存如果没有释放机制，会随着游戏进行持续增长。尤其在动态加载场景中（关卡切换、Mod 系统），不用的享元应被释放。解决方案：引用计数、LRU 缓存、或场景切换时批量释放。

权衡与选择

  • 用享元：大量对象共享大部分状态、内存是瓶颈时
  • 用对象池：对象生命周期短、频繁创建销毁时——object-pool-对象池
  • 用原型：需要克隆已有实例创建新对象时——prototype-pattern-原型
  • 享元 + 对象池组合：既需要共享数据，又需要复用实例时（弹幕、粒子）

常见陷阱

共享状态必须是不可变的

如果享元对象的状态被某个实例修改，会影响所有共享该对象的实例。内在状态必须只读。C# 中用 readonly、init 或 get-only 属性强制约束。

享元的线程安全

如果享元工厂在多线程环境中使用（如 DOTS 的并行 Job），缓存字典需要同步。ConcurrentDictionary 或在主线程预加载所有享元是常见解决方案。参见 concurrency-models-synthesis-并发全景。

外在状态的传递开销

享元模式将外在状态从对象中移出，每次操作都需要传入外在状态参数。如果外在状态很多（10+ 个字段），方法签名会膨胀。此时可考虑将外在状态封装为一个 Context 对象，或重新审视是否真的需要享元。
