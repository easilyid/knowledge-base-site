GPP 行为模式（GPP Behavioral Patterns）

核心思想

让行为可由数据定义而非硬编码。GoF 行为型模式关注”对象间如何通信”，GPP 行为模式关注”行为本身如何定义”——从编译时绑定走向运行时可配置，从继承体系走向数据驱动。

这是游戏与普通软件的关键区别之一：行为必须频繁变化。新角色、新技能、新敌人、新关卡——每次更新都要加行为。如果行为硬编码在 C# 类中，每次改动都要重新编译、重启；设计师无法自主调整，必须等程序员；Mod 社区无法扩展。

GPP 行为模式的共同目标：把行为从代码中解放出来，交给数据。

问题动机

这些写法的问题：

  • 硬编码：行为与代码绑定，无法运行时修改或扩展
  • 继承爆炸：每种行为一个子类，100 种行为 = 100 个子类
  • 上帝基类：试图用继承解决所有行为差异，基类操作集无限膨胀

GPP 行为模式的演进方向：硬编码 → 子类沙箱（基类约束行为） → 类型对象（数据定义类型） → 字节码（数据定义行为）。

三种模式构成复杂度光谱：

  • 子类沙箱最简单——适用于行为变化有限、程序员可控的场景
  • 类型对象居中——用数据表替代继承，适合种类多但每种行为较简单的情况
  • 字节码最强大——完全可编程，适合需要用户生成内容（UGC）或复杂行为逻辑的场景

三种模式详解

子类沙箱（Subclass Sandbox）

核心意图：基类提供一组”安全操作”，子类只组合调用这些操作来定义行为——不允许子类直接操作底层系统。

经典场景：技能基类、敌人 AI 基类、效果基类——子类只”拼装”操作，不”新建”操作。

Unity 映射：MonoBehaviour 就是子类沙箱的经典实现——引擎提供 GetComponent、SendMessage、Instantiate 等操作，开发者只组合调用。

子类沙箱 vs GoF 模板方法

方向相反——模板方法是”基类定义算法骨架，子类填充步骤”，子类沙箱是”基类提供工具箱，子类组合使用”。前者约束流程，后者约束能力边界。详见 template-method-pattern-模板方法。

详见 subclass-sandbox-子类沙箱（待建）。

类型对象（Type Object）

核心意图：用数据定义”类型”，而非用继承体系。100 种怪物不需要 100 个子类，只需一个 Monster 类 + 100 行配置表。

经典场景：怪物种类、道具类型、角色职业、装备品质——种类多但每种行为较简单。

Unity 映射：ScriptableObject 天然支持类型对象模式——用 SO 配置表替代继承体系。

类型对象 vs 继承体系

10 种怪物 → 继承体系还行。100 种怪物 → 继承爆炸。类型对象让策划用配置表定义怪物种类，程序员只写一个 Monster 类。这本质上是 strategy-pattern-策略 的数据驱动版——策略由数据选择而非代码选择。

详见 type-object-类型对象（待建）。

字节码（Bytecode）

核心意图：将行为编码为指令序列，由虚拟机解释执行。让行为可由数据定义而非代码定义——新增行为只需新增指令组合，无需修改宿主程序。

经典场景：技能系统、Mod/脚本系统、AI 行为树——行为极其复杂且需要策划/用户定义。

Unity 映射：Unity Visual Scripting 的核心就是字节码 VM——策划在可视化编辑器中连接节点，编辑器编译为指令序列，运行时 VM 解释执行。

字节码代价最高

需要实现虚拟机、编译器、调试工具链。大多数游戏用子类沙箱或类型对象就够了。字节码适合需要 Mod 支持、可视化编程或行为极其复杂的系统（如 MOBA 技能系统）。

详见 bytecode-字节码。

字节码在技能系统中的实际应用

在 MOBA / ARPG 等技能系统极复杂的游戏中，技能效果被编译成字节码由虚拟机执行。Unity 生态中类似思路的实现：

  • 可视化技能编辑器（如 Abilties / Game Creator）— 节点图 → 字节码
  • Lua / MoonSharp 嵌入 — 用现成脚本语言替代自研字节码
  • Unity Visual Scripting — 官方可视化脚本系统，底层是字节码 VM

反模式

硬编码行为——最常见的问题

行为直接写死在代码中，策划改数值必须找程序员改代码、重编译、重部署。应该用类型对象将数值外化到配置表，或用字节码将整个行为数据化。

过度继承——子类爆炸

每种行为差异都新建子类，100 种技能 = 100 个 Spell 子类。应该用类型对象替代继承——通用类 + 配置表。过度继承的信号：子类之间只有数值差异、子类数量超过 20 个、策划频繁要求加”只是数值不同”的新子类。

子类沙箱的操作集膨胀

基类操作集随需求增长而膨胀，最终变成”上帝基类”。控制操作集规模的关键：按领域拆分多个基类，或引入类型对象替代。操作集超过 15 个方法 → 考虑拆分或切换到类型对象。

类型对象的"类型"逃逸

类型对象本应完全由数据定义，但如果代码中出现 if (type.name == "Boss") 这样的硬编码分支，类型对象就退化成了枚举 + switch。正确做法是把所有差异都编码进类型对象的数据字段。

字节码的调试黑洞

自研虚拟机的最大痛点：没有调试器、没有断点、没有堆栈跟踪。一旦出 Bug，几乎无法定位。如果选择字节码，必须同时实现调试工具：指令反汇编器、执行日志、可视化编辑器中的单步调试。否则后期维护成本会吞噬前期开发效率。

一上来就选字节码

字节码强大但代价极高。大多数游戏用子类沙箱或类型对象就够了。选择标准：需要 Mod 支持 → 字节码；策划需要可视化编辑 → 字节码 + 节点图；只是数值多行为简单 → 类型对象；行为有限且程序员可控 → 子类沙箱。
