字节码（Bytecode）

核心思想

将行为编码为数据（指令流），由虚拟机解释执行——实现数据驱动的可扩展行为。新增行为只需新增指令组合，无需修改宿主程序。字节码是”数据驱动行为”的终极实现：策划/设计师可以在不碰代码的情况下定义新的技能、AI 行为和对话逻辑。

GPP 关键洞察：字节码在”性能”和”灵活性”之间找到了最佳平衡——比硬编码灵活，比嵌入脚本语言轻量。硬编码 → 子类爆炸 → 嵌入脚本语言 → 字节码 VM，这是一条从僵硬到灵活的演进路径。

问题动机

硬编码技能逻辑导致每加一个技能就要改代码重新编译：

这种写法的问题：

  • 子类爆炸：每种行为一个子类，100 种技能 = 100 个类
  • 策划无法自主：修改数值/组合需要程序员改代码、重编译
  • 冗余代码：大量子类只有微小差异（伤害值不同、特效不同）
  • 无法运行时扩展：新增行为必须重新编译部署

字节码的核心动机：让”行为”成为数据而非代码，使行为的定义与宿主程序解耦。

Mod 系统：Lua/Python 嵌入 vs 自定义字节码

字节码是 Mod 系统的基础——Mod 作者用 DSL 或可视化编辑器编写行为，编译为指令序列，由 VM 安全执行：

安全沙箱

字节码 VM 天然是沙箱——指令只能执行 VM 预定义的操作，无法访问文件系统、网络或任意内存。这使得 Mod 系统比嵌入 Lua/Python 更安全。但仍需注意：DEAL_DAMAGE 等指令如果允许任意大的操作数，可能导致数值溢出。应对操作数范围做校验。

与 Unity Visual Scripting 的关系

Unity Visual Scripting（原 Bolt）的核心就是字节码 VM：

  1. 策划在可视化编辑器中连接节点
  2. 编辑器将节点图编译为指令序列
  3. 运行时 VM 解释执行指令序列

Visual Scripting 的性能

Visual Scripting 的 VM 解释执行比原生 C# 慢 10-100 倍。对于高频逻辑（每帧执行的 AI、移动），应使用 C# 脚本。Visual Scripting 适合低频逻辑（技能触发、对话分支、关卡事件）。

性能：解释执行 vs JIT vs AOT

执行方式速度安全性复杂度游戏中的典型用法
解释执行慢（1×）最高（完全沙箱）低自定义技能 VM
JIT（即时编译）快（10-100×）低（可执行原生代码）高LuaJIT、嵌入脚本
AOT（预先编译）最快（与 C# 相当）中（编译期检查）中Burst 编译的 Job

游戏中推荐：简单系统用解释执行，复杂系统用嵌入 LuaJIT，性能关键路径用 AOT。参见 burst-compiler-Burst编译。

变体与演进

变体说明适用场景
栈式 VM操作数通过栈传递，指令短小游戏脚本、简单 DSL
寄存器式 VM操作数通过寄存器传递，指令较长但执行快高性能脚本（Lua 5.0+）
树遍历解释器直接遍历 AST 执行，不编译为字节码简单规则引擎
字节码编译到原生将字节码进一步编译为机器码性能关键路径

栈式 VM vs 寄存器式 VM

维度栈式 VM寄存器式 VM
指令长度短（只有操作码）长（操作码 + 寄存器号）
指令数量多（需要 PUSH/POP）少（直接操作寄存器）
实现复杂度低中
分发开销高（指令多 = switch 分支多）低（指令少）
典型代表JVM、PostScriptLua 5.0+、Dalvik

游戏中推荐栈式 VM

栈式 VM 实现简单、代码紧凑、易于序列化——这些对游戏更重要。寄存器式的性能优势在游戏中通常不显著（游戏 VM 的瓶颈是宿主调用而非指令分发）。

反模式

VM 指令集设计过度复杂

设计 VM 时容易过度工程化——加入函数调用、闭包、面向对象等高级特性。游戏 VM 的核心价值是”简单 + 安全”，不是”图灵完备”。如果需要图灵完备，直接嵌入 Lua/MoonSharp 更合理。自研 VM 应保持指令集最小化：算术 + 游戏操作 + 基本控制流。

字节码与游戏逻辑紧耦合

VM 的指令应该是对游戏操作的抽象（如 DEAL_DAMAGE、PLAY_EFFECT），而不是对游戏系统的暴露（如 GET_RIGIDBODY、SET_TRANSFORM）。指令越接近游戏语义，策划越好用；越接近引擎实现，耦合越紧。参见 subclass-sandbox-子类沙箱 的”基类提供操作集”思想。

字节码性能不如原生代码

VM 解释执行比原生 C# 慢 10-100 倍。对于高频逻辑（每帧执行的 AI、物理、移动），不应使用字节码。字节码适合低频触发的逻辑（技能释放、对话分支、关卡事件）。热路径仍应用原生 C# 或 burst-compiler-Burst编译 编译的 Job。

调试困难

字节码是数据不是代码——无法在 IDE 中设断点、无法单步执行、堆栈跟踪显示的是 VM 内部而非技能逻辑。必须自己实现调试工具：指令反汇编器、执行日志、可视化编辑器中的单步调试。这是字节码模式最大的工程成本。

权衡与选择

  • 用字节码：行为需要数据驱动、策划可编辑、运行时扩展时
  • 用子类沙箱：行为由代码定义但需要隔离时——subclass-sandbox-子类沙箱
  • 用类型对象：只需数据差异不需要行为差异时——type-object-类型对象
  • 用命令模式：行为需要撤销/排队/回放时——command-pattern-命令
