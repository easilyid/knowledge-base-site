解耦模式（Decoupling Patterns）

核心思想

游戏系统天然耦合——AI 决策后驱动物理，物理结果触发渲染，碰撞事件播放音效，UI 需要监听所有状态变化。解耦模式不追求”消除耦合”（不可能），而是控制耦合的方向和范围：谁依赖谁、依赖多深、变化传播多远。

GoF 解耦关注通信方式（中介者集中协调、观察者发布订阅），GPP 解耦关注架构结构——组件改变实体与行为的关系，事件队列改变系统间的时间耦合，服务定位器改变依赖的绑定时机。这是 GPP 解耦与 GoF 解耦的根本区分。

问题动机

这些写法的问题：

  • God Class：所有系统耦合在一个巨型类中，改一处牵动全局
  • 硬引用：FindObjectOfType / 直接 new → 与具体实现绑定，无法替换、无法测试
  • 同步阻塞：观察者直接调用 → 生产者被消费者阻塞，时序耦合

解耦模式的演进方向：God Class → 组件拆分（纵向解耦）；硬引用 → 服务定位器（点对点解耦）；同步阻塞 → 事件队列（横向解耦）。

三种模式覆盖解耦的三个维度：

  • 组件解耦”是什么”——从”我是 X 类型实体”到”我有这些能力”
  • 事件队列解耦”谁先谁后”——从”我直接调你”到”我发事件，你什么时候处理随你”
  • 服务定位器解耦”从哪拿”——从”我 import 你的类”到”我通过 key 找你的实现”

三种模式详解

组件模式（Component）

核心意图：用组合替代继承，将实体的行为拆分为独立组件，实体通过组合组件获得行为。每个组件封装一个方面的能力，实体本身只是组件的容器。

经典场景：游戏角色（移动 + 血量 + 攻击 + 动画等能力自由组合）、UI 控件（布局 + 交互 + 渲染分离）。

Unity 映射：GameObject + MonoBehaviour 就是组件模式的工业化实现——Unity 从第一天就将组件模式作为核心架构。GameObject 本身几乎无行为，所有功能通过挂载 MonoBehaviour 子类实现。

组件模式的 ECS 演进

Unity 经典组件模式（MonoBehaviour）的问题是组件仍是 class、有引用、产生 GC。DOTS/ECS 把组件推向极致——组件变成纯数据 struct，逻辑移到 System。参见 dots-ecs-数据导向。

详见 component-组件模式。

事件队列（Event Queue）

核心意图：将事件入队而非立即通知，解耦生产者与消费者的时序。生产者只管把事件丢进队列，消费者按自己的节奏取出来处理——两者不再同步执行。

经典场景：音效播放（不能阻塞战斗）、成就检测（可延迟处理）、网络消息（跨帧通信）、跨线程通信（Job System 回到主线程）。

Unity 映射：UnityEvent 是同步观察者，加一层队列就变成事件队列。主线程调度器（MainThreadDispatcher）是事件队列在跨线程场景的典型应用。

事件队列 vs 观察者

观察者是”发送方直接调用接收方”——同步、紧时间耦合。事件队列是”发送方写入队列，接收方稍后取出”——异步、松时间耦合。游戏中大量场景需要后者：战斗结算不能卡住输入、音效播放不能阻塞物理。

详见 event-queue-事件队列。

服务定位器（Service Locator）

核心意图：提供服务的全局接入点，避免使用者和实现服务的具体类耦合。使用者通过定位器请求服务接口，不关心具体实现——是单例模式的解耦版。

经典场景：音效系统、日志系统、输入管理器——全局唯一且需要跨场景访问的基础设施服务。

Unity 映射：GetComponent<T>() 本质上是”在 Entity 范围内的服务定位”。VContainer / Zenject 提供依赖注入容器，是服务定位器的”推”模式替代。

服务定位器 vs 依赖注入

服务定位器是”拉”模式（消费者主动查找），依赖注入是”推”模式（容器自动注入）。Unity 生态中两者都在用——小型项目用服务定位器够用，大型项目用 VContainer 做依赖注入。

详见 service-locator-服务定位。

反模式

God Class——解耦的反面

把所有系统塞进一个 GameManager 类（玩家、敌人、UI、音效、物理、存档全管），等于用类的壳包了一坨全局变量。每个系统都能看到其他所有系统的状态，改一个系统可能意外破坏另一个系统。God Class 的信号：单类超过 500 行、Update 方法超过 50 行、字段数超过 20 个。

组件间网状耦合

组件 A 持有组件 B 的引用，组件 B 又持有组件 A 的引用，形成循环依赖网。正确做法：组件之间通过 observer-pattern-观察者 事件或 event-queue-事件队列 通信，或引入中介者（如 Entity 本身）中转。参见 component-组件模式 的反模式章节。

事件队列的时序不确定性

异步解耦的代价：事件处理顺序不再确定。如果两个事件有因果关系（先 A 后 B），队列可能乱序。解决方案：给事件加优先级，或用有序队列。

服务定位器的隐式依赖

服务定位器让依赖在代码中不可见——读构造函数看不出来这个类需要什么服务。编译时不检查服务是否存在，运行时才发现 KeyNotFoundException。依赖注入（DI）通过构造函数参数让依赖显式化。

事件队列无限制增长

如果消费者处理速度赶不上生产速度，队列会无限增长导致内存泄漏。必须设置容量上限或反压机制。

过度解耦

不是所有通信都需要事件队列——同一实体内紧密协作的组件用 GetComponent + 直接调用更简单高效。过度解耦的信号：简单功能需要经过 3 层以上间接调用、事件队列中 90% 的事件只有一个消费者、开发者需要画架构图才能理解调用链。
