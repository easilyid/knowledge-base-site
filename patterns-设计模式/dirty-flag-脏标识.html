脏标识（Dirty Flag）

核心思想

只在数据变化时将状态标记为”脏”，在真正需要结果时才重新计算——避免每帧无意义的重算。这是一种延迟计算策略，用 O(1) 的标记操作替代 O(n) 的无谓重算。核心洞察：如果数据没有变化，计算结果不变，标记为”干净”直接复用上次结果。

GPP 关键洞察：很多游戏系统存在”重算远多于变化”的模式——世界矩阵每帧重算但 Transform 很少变化、UI 每帧重排但布局很少变化。脏标识把”每次都算”变成”变了才算”，在计算密集与变化稀疏之间取得巨大收益。

脏标识与缓存的关系

脏标识是缓存的”失效策略”——缓存的问题是”何时过期”，脏标识给出精确答案：“源数据变化时过期”。相比 TTL 过期（时间驱动）或 LRU 淘汰（空间驱动），脏标识是语义驱动的精确失效。

游戏开发深度

Unity Transform 的 hasChanged

Unity 的 Transform 有一个内置的脏标识 hasChanged，用于检测 Transform 是否发生了变化：

hasChanged 不会自动清除

Transform.hasChanged 在任何属性变化后保持 true，直到你手动设为 false。如果不清除，后续帧都会误判为”变化了”。这实际上是 Unity 的设计选择——脏标识由消费者负责清除，而非系统自动清除。

UI 布局的脏标识

Unity UI（UGUI）系统大量使用脏标识来避免每帧重排布局：

UGUI 性能关键

UI 布局计算是脏标识的经典应用场景。避免在 Update 中直接修改 UI 属性再立刻读取布局结果——先修改（标脏），等下一帧的布局重建阶段统一处理。如果需要立即得到结果，调用 LayoutRebuilder.ForceRebuildLayoutImmediate。

网络同步的脏标识

Shader 材质脏标识

GPU 材质属性变化时，需要重新上传到 GPU。Unity 内部用脏标识跟踪哪些属性变了：

MaterialPropertyBlock 与脏标识

MaterialPropertyBlock 是 Unity 提供的优化 API——不修改共享材质，而是为每个渲染器设置独立的属性覆盖。它内部使用脏标识来跟踪哪些属性需要重新上传到 GPU。使用 MaterialPropertyBlock 可以避免材质实例化，减少 draw call 的分裂。

与观察者模式的配合

脏标识与 observer-pattern-观察者 经常组合使用：数据变化时通过观察者通知”需要重新获取结果”，但实际重算延迟到消费者真正读取时：

通知与计算分离

观察者通知”数据变了”（轻量），脏标识负责”要不要重算”（延迟到读取时）。两者配合：观察者保证不遗漏变化，脏标识保证不浪费计算。

时间戳脏标识

版本号 vs bool 的优势

版本号可以判断”谁比谁新”——多个消费者各自记录上次看到的版本号，互不影响。bool 只能”是/否”，不支持多消费者独立追踪。网络同步中版本号特别有用：客户端说”我上次看到的是 v42”，服务器返回”当前是 v45，这是 diff”。

反模式

忘记清除脏标识——每次都重算

忘记在计算完成后清除脏标识，等于脏标识完全失效——每次读取结果都触发重算，比不用脏标识还糟（多了标志判断的开销）。

脏传播粒度过粗——一个小改动触发大面积重算

用一个 bool 管整个 UI 面板的布局，结果改一个按钮的文字就重排整个面板。正确做法：细粒度脏标识，只重排受影响的部分。

脏标识与多消费者的竞争

多个消费者在不同时机读取同一脏数据：第一个消费者读取后清除了脏标识，第二个消费者来了看不到脏标识，但缓存结果是第一个消费者触发的重算，可能不是第二个消费者想要的。解决：每个消费者维护自己的”上次读取版本号”。
