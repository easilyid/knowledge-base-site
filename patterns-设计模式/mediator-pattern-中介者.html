中介者（Mediator）

核心思想

减少对象之间混乱的直接依赖，迫使它们通过一个中介者对象通信。将多对多（M:N）的网状交互变为星形——所有对象只与中介者通信，互不引用。

问题动机

没有中介者时，有交互需求的对象之间形成网状依赖：

这种写法的问题：

  • 网状依赖：N 个对象互相引用，依赖数量 = O(N^2)
  • 修改扩散：新增一个面板，所有相关面板都要加引用和调用
  • 循环引用：A 引用 B，B 引用 A，生命周期管理困难
  • 无法独立测试：测试一个面板必须实例化所有相关面板

中介者的核心动机：将 M:N 的网状交互集中到一个协调者，每个同事对象只与中介者通信。

与 observer-pattern-观察者 的关系

维度观察者中介者
通信方向一对多（主题→观察者）多对多（同事↔中介者↔同事）
谁知道谁主题知道观察者（但不知道具体类型）同事只知道中介者
协调逻辑无（主题只管通知）有（中介者决定如何协调）
典型场景事件广播系统间联动

中介者 = 观察者 + 协调逻辑

中介者内部通常用观察者机制实现通信，但增加了”收到事件后该怎么协调”的逻辑。观察者是”发通知”，中介者是”收通知并协调”。

变体与演进

变体特点适用场景复杂度
集中式中介者一个类知道所有同事，协调逻辑集中同事少、交互逻辑明确低
EventBus全局事件路由，发布者/订阅者互不知道跨系统通信、同事多中
C# event 作为轻量中介者用静态事件替代中介者类简单通信、不需要协调逻辑极低
消息队列异步解耦，事件入队后延迟处理时序敏感、需要回放高

反模式

中介者变成"上帝对象"

所有交互逻辑集中到一个中介者，它变得比原来的网状依赖更难维护。判断标准：如果中介者超过 300 行或引用了超过 5 个同事，考虑拆分。按职责域拆分多个中介者（如 CombatMediator、UIMediator、ProgressionMediator）。

中介者知道太多同事细节

如果中介者直接调用同事的内部方法（如 _inventory._scrollRect.verticalNormalizedPosition = 0），说明中介者和同事的耦合度太高。同事应提供高层接口（如 _inventory.ResetScroll()），中介者只调用高层接口。

用 EventBus 替代所有通信

“所有事件都走 EventBus”会导致：事件名冲突、调试时无法追踪事件来源和去向、隐式依赖遍布代码。EventBus 适合跨层级通信（如 UI 与游戏逻辑），同层通信用直接调用或观察者更清晰。参见 observer-pattern-观察者。

权衡与选择

  • 用中介者：多个对象之间有复杂交互、需要集中协调时
  • 用观察者：只需一对多通知、不需要协调逻辑时（更轻量）
  • 用外观：只需简化接口、不需要对象间双向通信时
  • 用责任链：请求需要沿链顺序处理时
  • 用命令：通信内容需要被封装、排队或撤销时
