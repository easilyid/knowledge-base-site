类型对象（Type Object）

核心思想

用数据对象定义”类型”，而非用继承——不同”种类”的对象共享同一类，通过数据区分行为。类型对象让”种类”成为可配置的数据，而非硬编码的类层次结构。新增种类只需新增一条数据记录，无需编写新类。

GPP 关键洞察：类型对象把”种类”从代码世界搬到了数据世界。继承体系里，每种怪物是一个类；类型对象里，每种怪物是一条配置记录。这是从”代码驱动”到”数据驱动”的关键转折。

问题动机

每新增一种怪物就要写一个子类——导致类爆炸：

这种写法的问题：

  • 类爆炸：100 种怪物 = 100 个子类，大部分只有数值差异
  • 策划无法自主：新增怪物种类需要程序员写类、编译、部署
  • 冗余代码：大量子类只是覆写几个数值，逻辑完全相同
  • 运行时不可扩展：无法在游戏运行中新增怪物种类

类型对象的核心动机：用数据对象替代继承体系定义”种类”，让种类成为可配置的数据而非硬编码的类。

类型继承 vs 代码继承

类型继承是数据层面的——“子类型”只覆写需要差异化的字段，其余从父类型读取。这比代码继承灵活得多：新增子类型不需要编译，策划在编辑器中拖拽赋值即可。

变体与演进

变体说明适用场景
只读类型对象类型数据不可变，实例不可覆盖配置表驱动的怪物/道具系统
可变类型对象实例可覆盖类型默认值RPG 装备系统（每个实例可强化）
类型继承链类型对象之间有”父类型”关系共享基础配置的怪物族群
类型对象 + 策略数据差异用类型对象，行为差异用策略近战/远程等行为不同的怪物

只读 vs 可变类型对象

只读是默认选择

类型对象的核心价值是”数据定义类型”。如果实例经常覆盖类型默认值，说明类型对象的抽象不够——可能需要更细粒度的类型，或引入 prototype-pattern-原型 做实例级定制。

反模式

类型对象变成"伪继承"

如果类型对象的数据中出现了 if (type.name == "Boss") 这样的硬编码分支，类型对象就退化成了枚举 + switch——跟继承体系没有本质区别。正确做法是把所有差异都编码进类型对象的数据字段和策略对象，让代码对类型名无感知。参见 strategy-pattern-策略。

类型对象过度通用化

类型对象是”数据定义种类”，不是”数据定义一切”。有些场景需要的是 bytecode-字节码（行为可编程）或 subclass-sandbox-子类沙箱（行为由代码定义但需隔离），强行用类型对象表达会导致数据字段膨胀、逻辑散落在各处。类型对象适合”种类多但行为差异小”的场景。

忽略类型继承的循环引用

类型继承链如果出现 A → B → A 的循环，解析属性时会导致无限递归。必须在设置 parentType 时校验无循环，或在解析时加深度上限。

类型对象与实例状态混淆

类型对象存储的是”类型的默认值”，不应存储实例的运行时状态。常见错误：在 SO 中存储 currentHp，导致所有同类型怪物共享血量。正确做法：类型对象存 baseHp，实例存 _currentHp。

权衡与选择

  • 用类型对象：种类多但行为差异小，数据定义种类时
  • 用子类沙箱：行为差异大且由代码定义时——subclass-sandbox-子类沙箱
  • 用字节码：行为需要运行时可编程、策划可编辑时——bytecode-字节码
  • 用策略模式：行为差异需要独立封装和替换时——strategy-pattern-策略
  • 用原型模式：需要克隆已有实例创建新实例时——prototype-pattern-原型
