装饰（Decorator）

核心思想

动态地为对象添加行为，不改变其接口。通过将对象放入特殊封装对象中来绑定新行为，支持递归组合。

GoF 定义：动态地给一个对象增加一些额外的职责。就增加功能来说，装饰模式比生成子类更为灵活。

GPP 关键洞察：装饰模式在游戏中的核心应用是 Buff/Debuff 叠加——这是继承无法优雅解决的问题。5 种 Buff 的任意组合需要 2^5 = 32 个子类，而装饰模式只需 5 个装饰器类。

结构图

classDiagram
    class IComponent {
        <<interface>>
        +Operation() string
    }
    class ConcreteComponent {
        +Operation() string
    }
    class BaseDecorator {
        #_wrapped: IComponent
        +BaseDecorator(component: IComponent)
        +Operation() string
    }
    class ConcreteDecoratorA {
        -_addedState: string
        +Operation() string
        +AddedBehavior()
    }
    class ConcreteDecoratorB {
        +Operation() string
        +AddedBehavior()
    }

    IComponent <|.. ConcreteComponent
    IComponent <|.. BaseDecorator
    BaseDecorator <|-- ConcreteDecoratorA
    BaseDecorator <|-- ConcreteDecoratorB
    BaseDecorator o--> IComponent : 包装

调用流程：Client 调用 Operation() → 最外层装饰器处理 → 调用 _wrapped.Operation() → 下一层装饰器处理 → … → 最终到达 ConcreteComponent.Operation()。每一层装饰器都可以在调用前后添加行为。

问题动机

不用装饰模式会怎样？——继承爆炸。

这种写法的问题：

  • 继承爆炸：n 种修饰需要 2^n - 1 个子类
  • 静态组合：编译期就确定行为组合，无法运行时动态增减
  • 无法撤销：装备脱下后无法去掉对应子类的行为
  • 代码重复：不同组合子类中大量重复的 override 逻辑

装饰模式的核心动机：用组合代替继承，让行为可以动态叠加和撤销。每个装饰器只负责一种修饰，通过链式包装实现任意组合。

角色职责Unity/C# 对应

装饰链重建的代价

装饰器构造时绑定了 _inner 引用，移除中间层装饰器需要重建整条链。这是装饰模式的固有代价。替代方案：用不可变装饰链（每次增减都创建新链），或用委托链（见下方变体章节）。

装备属性修饰

与 Unity Component 模型的关系

Unity 的 Component 模型与装饰模式在”动态添加行为”这个目标上是一致的，但实现方式不同：

维度装饰模式Unity Component
结构链式包装（线性）扁平列表（组合）
接口装饰者和被装饰者共用同一接口每个 Component 有自己的接口
调用方式自动传播——调用外层自动链式传播到内层手动查找——GetComponent<T>()
顺序敏感是——装饰顺序影响结果否——Component 之间平等
适用场景管道式处理（伤害计算、属性修饰）扁平功能扩展（Rigidbody、Collider）

不要用 Component 模拟装饰器

有人尝试用 AddComponent<ArmorBuff>() 来模拟装饰器，但 Component 之间是扁平关系，不像装饰器那样自动链式传播。每次计算伤害都需要手动遍历所有 Buff Component 并聚合——这不是装饰模式，更接近 chain-of-responsibility-责任链 或简单的事件聚合。

伤害计算管道

装饰顺序很重要

先算抗性再算护盾，与先算护盾再算抗性，结果不同。装饰模式的管道构建应明确文档化顺序约定。一般规则：百分比修正在外层，绝对值修正在内层。

交叉引用

  • composite-pattern-组合 — 组合模式也是递归结构，但组合是树状（一个节点多个子节点），装饰是链式（一个节点一个内层）
  • proxy-pattern-代理 — 代理与装饰结构相同（都持有内部引用并委托），但代理控制访问，装饰增加行为
  • adapter-pattern-适配器 — 适配器改变接口，装饰不改变接口只增加行为
  • chain-of-responsibility-责任链 — 责任链也是链式传播，但每个节点可以选择是否处理；装饰器每层都处理
  • strategy-pattern-策略 — 策略替换整个算法，装饰叠加多个行为

变体与演进

用委托链实现轻量装饰器（C# 特有）

C# 的委托/事件机制可以实现更轻量的装饰效果，无需定义装饰器类层次：

委托链 vs 装饰器类

委托链更轻量、增减更方便（直接 Remove），但缺少类型安全和结构化。装饰器类更正规、支持有状态的装饰（如护盾 HP），但增减需要重建链。建议：无状态的修饰用委托链，有状态的修饰用装饰器类。

装饰器与中间件模式

装饰模式的思想在中间件/管道模式中被广泛应用——ASP.NET Core 的中间件管道就是装饰模式的变体：

中间件是装饰模式的高级变体

中间件模式 = 装饰模式 + 责任链。每个中间件可以选择调用 next()（传播给下一层）或直接返回（短路）。这比纯装饰器更灵活，但也更复杂。

变体对比

变体说明适用场景
经典装饰器装饰器类层次，持有 _inner 引用有状态的修饰（护盾 HP、Buff 计时）
委托链List<Func<int, int>>无状态的修饰（纯计算）
中间件管道Use(next => ...) 风格需要短路、日志、前置/后置处理
生成器构建PipelineBuilder.WithX().WithY()构建时确定装饰顺序

反模式

装饰器层次过深（调试困难）

多层装饰嵌套后，调用栈变深，断点难以命中具体层。hero.TakeDamage(30) 的调用栈可能经过 5-6 层装饰器，在 Debugger 中跳来跳去。建议：限制装饰器层数（如最多 10 层），或在装饰基类中添加诊断日志：Debug.Log($"{GetType().Name}: input={rawDamage}")。

装饰器与代理混淆

装饰器和代理结构几乎相同（都持有内部引用并委托），但意图完全不同：装饰器增加行为，代理控制访问。例如，ArmorDecorator 是装饰器（增加了减伤行为），而 LazyLoadingProxy 是代理（延迟加载控制访问）。混淆两者会导致设计混乱。

装饰器成为万能管道

所有逻辑都往装饰器里塞，原本简单的计算变成 10 层装饰器嵌套。如果装饰器之间有数据依赖（如 A 的输出格式必须是 B 的输入格式），说明装饰链的耦合度过高，应该重新设计。装饰器的每层应该是独立的——不依赖其他装饰器的顺序。

权衡与选择

  • 用装饰：需要动态增减行为、且行为可叠加时
  • 用子类：行为固定不变、编译期可确定时——简单直接
  • 用策略：行为互斥（只能选一个算法）时——策略替换，装饰叠加
  • 用组合：树状结构而非链式包装时
  • 用责任链：请求需要被某一层拦截（不一定传播到底）时

常见陷阱

装饰链过长导致调试困难

多层装饰嵌套后，调用栈变深，断点难以命中具体层。建议限制装饰层数或增加调试日志。

装饰器顺序依赖未文档化

ArmorDecorator → ShieldDecorator 和 ShieldDecorator → ArmorDecorator 的计算结果不同，但调用方可能不知道顺序会影响结果。建议：用 Builder 模式固定装饰顺序，并在文档中说明顺序约定。

忘记调用 _inner

装饰器中忘记调用 _inner.Operation() 会导致链断裂——后续所有装饰器和原始对象都不会被调用。这是装饰模式最常见的 bug 之一。
