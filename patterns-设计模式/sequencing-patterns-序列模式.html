序列模式（Sequencing Patterns）

核心思想

游戏是帧驱动的实时模拟——每帧必须完成输入采集、逻辑计算、画面渲染，在 16.6ms（60fps）内交付。序列模式解决的不是”做什么”，而是”何时执行”和”多快执行”：同一帧内的读写冲突如何消解、帧率波动时时间步如何适配、每帧该通知哪些对象更新。

这是 GoF 完全未触及的领域——GoF 的模式中没有时序概念，但游戏的本质就是帧驱动的时序系统。序列模式是 GPP 与 GoF 最大的差异点。

问题动机

传统软件对时序几乎没有约束——请求来了就处理，响应返回即可。游戏的本质区别：

  1. 硬实时：每帧必须按时交付，否则画面卡顿
  2. 帧原子性：一帧内的状态必须一致——半成品状态不能被其他系统读到
  3. 帧率不确定：设备性能差异导致帧率波动，逻辑必须适配

序列模式正是应对这三个约束的设计手段。

  • 游戏循环是时序骨架，决定”一帧从哪开始到哪结束”
  • 更新方法是游戏循环的执行手段——循环不知道具体对象，只负责遍历
  • 双缓冲是更新方法的保底措施——即使更新过程中状态被部分修改，外部读到的始终是上一帧的完整状态

三种模式缺一不可：

  • 没有游戏循环 → 没有帧的概念，无法控制时间步
  • 没有更新方法 → 游戏循环必须知道所有对象类型，无法扩展
  • 没有双缓冲 → 更新过程中的半成品状态会泄漏给其他系统

三种模式详解

双缓冲（Double Buffer）

核心意图：用序列操作模拟瞬间或同时发生的事情。读写分离到两个缓冲区，帧边界原子切换，观察者永远看到完整快照。

经典场景：渲染管线双缓冲（防画面撕裂）、物理状态双缓冲（保证碰撞检测基于完整快照）、GPU ComputeBuffer 乒乓。

Unity 映射：

  • GPU 前后缓冲交换（VSync 控制 QualitySettings.vSyncCount）
  • ComputeBuffer / RenderTexture 乒乓（GPGPU 和后处理链）
  • PhysX 内部物理状态缓冲（FixedUpdate 中 Rigidbody.position 是上一物理步完整结果）

详见 double-buffer-双缓冲。

游戏循环（Game Loop）

核心意图：游戏的主循环——处理输入、更新状态、渲染，循环往复。解耦游戏速度与硬件速度。

经典场景：整个游戏的主循环、固定/可变时间步、服务器 tick rate。

Unity 映射：PlayerLoop 就是引擎级游戏循环——Unity 开发者通常不需要手写游戏循环，但必须理解其调度语义：

Unity 采用”半固定”方案：物理用固定步长（FixedUpdate），逻辑用可变步长（Update）。这是大多数游戏的最佳平衡。

详见 game-loop-游戏循环、player-loop-主循环。

更新方法（Update Method）

核心意图：每帧通知对象更新自身状态。游戏循环不再知道”哪些对象需要更新”，将”每帧做什么”分发给各个对象。

经典场景：所有需要逐帧逻辑的实体——玩家、敌人、子弹、粒子、动画。

Unity 映射：MonoBehaviour.Update()/FixedUpdate()/LateUpdate() 就是引擎级更新方法。引擎在 PlayerLoop 各阶段遍历所有活跃 MonoBehaviour，调用对应虚方法。

方法调用时机用途deltaTime
FixedUpdate()PlayerLoop.FixedUpdate物理、碰撞Time.fixedDeltaTime
Update()PlayerLoop.Update输入、逻辑、动画Time.deltaTime
LateUpdate()PlayerLoop.PostLateUpdate相机跟随、后处理Time.deltaTime

DOTS 中 ISystem.OnUpdate 替代了 MonoBehaviour.Update，实现数据驱动的批量更新——不再逐对象虚调用，而是按 Archetype 批量遍历，数据连续排列利于缓存命中。

详见 update-method-更新方法、monobehaviour-lifecycle-生命周期。

与 Unity PlayerLoop 的关系

Unity 的 player-loop-主循环 是序列模式的引擎级实现——三个模式在引擎中都有直接对应：

GPP 模式Unity 对应说明
游戏循环PlayerLoop 系统Unity 主循环定义了各子系统的执行顺序
更新方法MonoBehaviour.Update() 等引擎自动遍历所有活跃 MonoBehaviour
双缓冲渲染管线 + Transform 状态缓存当前帧写入 Transform，渲染管线读取上一帧提交的状态

Unity 开发者通常不需要手动实现序列模式——引擎已内置。但理解这些模式能帮助你：

  • 理解 Update / FixedUpdate / LateUpdate 的调度语义与时序差异
  • 理解为什么 Transform 在同一帧内修改后不能立即被渲染管线反映
  • 在自定义系统（如 ECS SubSystem 调度、自定义渲染管线）中正确设计时序

深入：帧驱动对架构的影响

序列模式不只是”怎么写循环”，它塑造了整个游戏架构：

  1. 所有逻辑都必须是”可帧切分”的：不能有跨帧阻塞调用。这就是 coroutine-协程 和 async/await 在 Unity 中存在的原因——它们是跨帧流程控制的解决方案
  2. 帧边界是天然的事务边界：双缓冲、脏标识都利用帧边界做原子切换
  3. 帧率波动驱动架构选择：固定时间步（物理）vs 可变时间步（渲染）的分裂，直接导致 FixedUpdate 和 Update 的分治

序列模式还深刻影响其他 GPP 分类的选择：帧驱动要求每帧遍历大量对象 → 遍历必须缓存友好 → data-locality-数据局部性；帧驱动要求对象频繁创建销毁 → 分配必须零 GC → object-pool-对象池；帧驱动要求状态通知延迟到帧边界 → 同步观察者不够用 → event-queue-事件队列。可以说序列模式是 GPP 体系的根基，其他三类模式都是在帧驱动约束下的进一步优化。

服务器-客户端时间步分裂

网络多人游戏中，序列模式面临额外挑战：服务器以固定 tick rate（如 20Hz）推进逻辑，客户端以高帧率（60Hz）渲染，两者时间步不同步。标准解法：

这是序列模式在跨进程场景的延伸：游戏循环分裂为服务器循环和客户端循环，更新方法分裂为服务器逻辑更新和客户端插值更新，双缓冲变成”当前快照/上一快照”的插值源。

变体与演进

变体说明适用场景
固定时间步 + 插值渲染游戏循环用固定步进保证逻辑一致性，渲染时用插值平滑视觉物理密集游戏、需要确定性
时间池（Time Pooling）固定时间步的变体，防止螺旋死亡——帧率过低时跳过物理步而不是累积帧率不稳定平台（移动端）
累积器模式（Accumulator）将帧间余量累积到下次计算，防止固定步与实际帧率的漂移半固定方案（Unity 默认）
ECS System 调度DOTS 中用 [UpdateInGroup] 和 ComponentSystemGroup 替代手写游戏循环——仍是序列模式，只是声明式而非命令式DOTS 项目
解耦更新/渲染服务器高频率逻辑更新（无渲染），客户端低频率逻辑 + 插值渲染网络多人游戏

ECS System 调度——序列模式的声明式演进

DOTS 中不再手写游戏循环，而是用特性声明 System 的执行顺序：

反模式

帧率依赖逻辑

不乘 deltaTime 的运动/计时逻辑，在帧率波动时行为不一致。所有时间相关的计算必须乘以 Time.deltaTime（Update 中）或 Time.fixedDeltaTime（FixedUpdate 中）。

在 Update 中做重计算

Update() 每帧调用（60fps 时每秒 60 次）。如果单个 Update 耗时超过 1ms，100 个对象就吃掉整帧预算。重计算应移到 job-system-作业系统（并行）、coroutine-协程（分帧）或 InvokeRepeating（降频）。

混淆 FixedUpdate 与 Update 的时序语义

FixedUpdate 按固定时间步调用（默认 0.02s），一帧内可能调用 0 次或多次。物理逻辑放 FixedUpdate，视觉逻辑放 Update，混用会导致物理不稳定或视觉抖动。

双缓冲的半帧状态泄漏

如果在更新过程中读取了”当前正在写入”的缓冲而非”上一帧已完成”的缓冲，就会读到半成品状态。必须严格区分读缓冲与写缓冲。

固定时间步的螺旋死亡

帧率低于固定步长频率时，一帧内需要执行多次 FixedUpdate 来追赶。如果 FixedUpdate 本身计算量很大，追赶会导致帧率进一步下降——形成恶性循环。Unity 默认 Time.maximumDeltaTime = 0.333s 来限制追赶。
