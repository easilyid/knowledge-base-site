数据局部性（Data Locality）

核心思想

将同时使用的数据在内存中连续排列，利用 CPU 缓存行预取提升性能。现代 CPU 访问主内存比访问 L1 缓存慢 100-200 倍——算法的时间复杂度再好，如果每次访问都 cache miss，性能照样崩溃。数据局部性要求我们先想数据怎么排列，再想代码怎么组织。

GPP 关键洞察：面向对象编程的”数据散布”问题——每个对象在堆上随机分布，遍历对象就是追逐指针，CPU 缓存几乎无效。数据导向设计（DOD）的核心：连续排列同类数据，让 CPU 的缓存行预取机制为你工作。

反模式

过早优化——先 Profile 再优化

数据局部性优化会牺牲代码可读性。不要在项目早期就对所有数据做 SoA——先用自然的方式写代码，用 Profiler 确认瓶颈后再针对性优化。Nystrom 的建议：“先让它跑起来，再让它跑得快，最后让它跑得优雅。”

SoA 化不需要高频遍历的数据

只在配置界面出现的 Settings 对象、只在死亡时访问的 Loot 数据，SoA 化没有意义——它们不会被高频遍历，Cache 优化无效。只对每帧遍历数千次的热路径数据做 SoA。

忽略 false sharing（伪共享）

多线程环境下，不同线程修改同一 Cache Line 的不同变量会导致 Cache Line 在核心间反复失效。SoA 布局下如果多个线程写同一个 positions[i] 的不同分量，仍可能伪共享。解决：按 Cache Line 对齐，或 Job System 的 ScheduleParallel 自动分块。
