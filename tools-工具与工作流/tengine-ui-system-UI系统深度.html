TEngine UI 系统架构深度分析（UIModule Deep Dive）

是什么

UIModule 是 TEngine 的 UI 管理系统——一个基于 Layer 分组的窗口栈管理器，配合 Attribute 声明式配置和全屏遮挡优化。与 ModuleSystem 不同，UIModule 使用 Singleton 模式而非服务定位器注册。

声明式配置（WindowAttribute）

WindowAttribute 声明：

  • WindowLayer：所属层级
  • Location：Prefab 资源路径（默认用类名）
  • FullScreen：是否全屏（影响下层窗口可见性）
  • HideTimeToClose：隐藏后多久自动关闭（秒）

全屏遮挡优化

设计启示

全屏遮挡是 UI 系统的经典优化——当一个全屏窗口覆盖时，下方窗口的 Canvas 被禁用，节省 draw call。TEngine 通过 FullScreen 标记 + 从栈顶向下遍历实现，简单有效。

HideTimeToClose 延迟关闭

窗口隐藏后不立即销毁，而是启动定时器——如果在 HideTimeToClose 秒内重新打开，直接复用已加载的实例，避免重复加载。

设计模式分析

1. Singleton vs ModuleSystem

UIModule 用 Singleton<UIModule> 而非 ModuleSystem.GetModule<IUIModule>()。原因：

  • UIModule 在 HotFix 层（GameLogic 命名空间），不在 TEngine Runtime Core
  • 它需要直接访问 Unity API（GameObject、Canvas、Camera）
  • 作为热更代码，不适合通过 Runtime 层的 ModuleSystem 管理

架构边界

这体现了 TEngine 的热更分层：Runtime Core 的模块通过 ModuleSystem 管理（接口隔离），HotFix 层的模块用 Singleton（直接访问）。UIModule 属于后者。

2. Attribute 声明式 vs 配置文件

TEngine 用 [WindowAttribute] 在代码中声明窗口元数据。对比：

方式优势劣势
Attribute 声明（TEngine）代码即配置，IDE 可跳转改配置需重新编译
ScriptableObject 配置设计师可改，无需编译代码和配置分离，易失同步
JSON/Excel 配表批量管理方便类型不安全

TEngine 选择 Attribute 是因为：窗口的 Layer/FullScreen 属性几乎不会运行时变化，放代码里最安全。

3. DI 注入点

UIBase.Injector 是一个静态委托——外部可以设置它来在 UI 创建时注入依赖。这是一个轻量 DI 接入点，让 UIModule 可以与 VContainer 等容器配合而不强依赖。

4. GameEventMgr 生命周期绑定

每个 UIBase 持有一个 GameEventMgr（从 MemoryPool 获取），通过它注册的事件在 UI 销毁时自动清理：

这解决了 UI 系统最常见的 bug——事件泄漏（窗口关闭后 handler 仍在全局事件总线中）。

优化空间

P0：GetWindow 的 O(n) 查找

每次 ShowUI/CloseUI/HasWindow 都线性扫描。窗口数量通常 < 20，影响有限，但可以用 Dictionary<string, UIWindow> 做 O(1) 索引。

P1：ShowUIAwaitImp 的轮询等待

用轮询等待加载完成，不如用 UniTaskCompletionSource 在加载完成时直接 SetResult——避免每帧检查。

P2：OnUpdate 的集合修改检测

如果 Update 期间有窗口被关闭（Count 变化），直接 break 跳过剩余窗口。这比 GameEvent 的 Three-List 方案简单但更粗暴——可能导致某些窗口的 Update 被跳过一帧。
