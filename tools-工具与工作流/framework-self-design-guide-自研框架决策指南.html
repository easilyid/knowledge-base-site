自研框架架构决策指南 v1（底层决策）

本页定位

不是新知识——是把现有 12 篇框架分析重组成决策路径。你按顺序回答 5 个底层问题，输出就是你自己框架的核心架构骨架。

阅读方式

这页不是从头读到尾的科普。是带着你自己项目的问题查询：每个决策处停下来，对照你的实际情况选 A/B/C，链接到证据页验证理由，记下你的选择，再走下一个决策。

决策依赖图（先看这个）

底层决策的核心特征：一旦定下，下游决策几乎自动展开。所以底层错了，整个框架就跑偏。

决策 0：选范式（OOP-Module vs ECS-Entity vs 混合）

这是什么问题

你的框架用什么作为”基本组合单元”？是类（OOP，TEngine 路线）还是实体+组件（ECS，ET/Fantasy 路线）。

选项

选项代表心智模型
A. OOP-ModuleTEngine / DGame / GameFramework / QFramework模块是服务，行为内聚在类，通过接口访问
B. ECS-EntityET / Fantasy / Unity DOTS实体是数据，行为外置在静态系统
C. 混合客户端 OOP + 服务端 ECS（DGame_Fantasy 模式）不同层用不同范式

证据与判断标准

完整对比见 paradigm-comparison-范式对比，关键判断点：

你的项目特征选什么
需要双端共享代码（前后端共用 logic）B ECS（这是 ECS 的硬优势）
战斗是大量同类对象（射击/塔防/RTS）B ECS（数据局部性 + 批量处理）
团队没有 ECS 经验 + 纯客户端项目A OOP
大量同质数据对象 + 数据驱动 SystemB ECS（数据/行为分离天然适配批量处理）
中小客户端、快速迭代A OOP
大型 MMORPGC 混合

关于"行为热更"

不要把”行为可热更”当成 ECS 的差异化优势——HybridCLR 让 OOP 范式同样可以热更行为代码。ECS 真正的差异化是数据局部性 + 批量并行处理，不是热更能力。

一旦选了，下游被强制成什么

  • 选 A → 决策 4 倾向 Service Locator + Facade（也可选 DI 容器，不是强制）
  • 选 B → 决策 4 强制 Entity-Component-System 三件套
  • 选 C → 必须在每层单独走 0-5 全套决策

反模式（直接的失败案例）

"我先 OOP，以后加 ECS"

同一项目同时维护两套范式 = 心智撕裂。可以”客户端 OOP + 服务端 ECS”，不要”同一层既 OOP 又 ECS”。证据见 paradigm-comparison-范式对比 §结论与权衡。

决策 1：是否需要代码热更新

这是什么问题

不是 “我以后想不想热更”，是 “首次上线时是否需要绕过应用商店审核更新代码”。

选项

选项含义代价
A. 完全不要所有代码 AOT 编译进主包任何代码改动需重新提审
B. HybridCLRC# 原生热更，社区主推多一层程序集分层 + DLL 加载流程
C. Lua/JavaScript 等脚本层逻辑写脚本（xLua / Puerts），引擎层 C#团队需学双语言
D. ILRuntime老一代 IL 解释执行仍在维护但更新降速；社区已主推 HybridCLR

证据与判断标准

你的情况选什么
单机/Steam/主机游戏A 完全不要（强制审核 + 不联网）
中国手游运营 + 国内分发B HybridCLR（事实主流，少数项目仍用 xLua）
海外 Google/Apple 主推看运营节奏：A 或 B
团队有 Lua/JS 历史包袱C Lua（xLua）或 JavaScript（Puerts）
双端共享代码 + 服务端为主A + 服务端按需热更

一旦选了，下游被强制成什么

  • 选 A → 不需要决策 5（程序集分层），所有代码可一个 dll
  • 选 B → 决策 5 强制三层（Launcher/AOT/HotFix），ModuleSystem 必须在 AOT 层
  • 选 C → 框架核心 C# + 业务逻辑脚本，需要桥接层（一般用 xLua/ToLua）

重要事实（来自源码分析）

TEngine/DGame 几乎所有架构复杂性都源于 HybridCLR 热更约束——程序集分层、Module vs Singleton 双轨、MonoDriver 桥接层、Procedure FSM 启动链全部是热更约束的产物。详见 tengine-design-decisions-设计决策分析 §总结：设计决策的统一逻辑。

如果你不需要热更，就不要照抄 TEngine 的复杂度。 直接用 VContainer + MonoBehaviour 就够了。

决策 2：平台目标（客户端 / 服务端 / 双端）

这是什么问题

框架代码要在哪里跑？这直接决定了哪些 Unity API 能用、能依赖什么第三方库。

选项

选项限制
A. 纯 Unity 客户端可全力依赖 Unity 生态（UniTask/HybridCLR/YooAsset）
B. 纯 .NET 服务端不能依赖 Unity 程序集，需 .NET 8+ Native AOT 友好
C. 双端共享代码核心层必须零 Unity 依赖（接口隔离）

证据与判断标准

你的情况选什么
单机游戏A
手游联网 + 后端用其他语言（Go/Java）A（C# 框架只管客户端）
想前后端 C# 一致C
服务端为主、客户端轻量B + 客户端用 Unity 包接入（Fantasy 模式）

一旦选了，下游被强制成什么

  • 选 A → 决策 3 选 UniTask（Unity 专用零 GC）
  • 选 B → 决策 3 选 FTask 或纯 Task + ValueTask（AOT 友好）
  • 选 C → 决策 3 必须选 ETTask（双端共用，依赖最少）

关键洞察（源码验证）

et-framework-ET框架 §ETTask 部分指出：ET 不直接用 UniTask 的根本原因是 UniTask 依赖 Unity，服务端无法使用。如果你选 C（双端共享），异步原语就被锁死了。

决策 3：异步原语

这是什么问题

框架内部和业务代码写 await 时，背后用什么实现。

选项

选项来源适用
A. Unity CoroutineUnity 内置简单脚本 / 不追求零 GC
B. UniTaskCysharpUnity 客户端首选
C. ETTaskegametang/ET双端共享场景
D. FTaskqq362946/Fantasy服务端 + Native AOT
E. 原生 Task/ValueTask.NET 内置不在意 GC 的服务端工具

选择标准（与决策 2 联动）

决策 2 选项决策 3 选什么原因
A（纯客户端）B UniTask性能、API 设计、生态都最好
B（纯服务端 .NET）D FTask 或 E Task不依赖 Unity，AOT 友好
C（双端共享）C ETTask 或 E 原生 TaskETTask 与 ET 配套；纯 Task 也可（Fantasy 路线证明可行），但需自行处理服务端调度

不要做的事

不要同框架混用多种异步方案

比如同一框架既用 UniTask 又用 Coroutine——业务代码会困惑哪个该用、何时该用，且二者的取消传播机制完全不同，混用导致内存泄漏。

不要在选了 UniTask 后想着"以后双端"

一旦用了 UniTask，业务代码深度依赖 UniTask<T> 类型签名，迁移到 ETTask 工作量等同重写。要双端就从一开始选 ETTask。

决策 4：模块组织方式

这是什么问题

框架内部”功能服务”如何组织和访问。

选项

选项实现复杂度心智负担
A. 静态服务定位器低低
B. DI 容器中高
C. ECS 组合（无传统模块）高极高
D. 全静态单例极低中（散乱）

选择标准（与决策 0 强联动）

决策 0 范式决策 4 选什么证据
OOP-ModuleA 服务定位器tengine-module-system-模块系统深度 §设计模式分析
ECS-EntityC ECS 组合et-framework-ET框架 §ECS 实现
不用热更 + 大团队B DI 容器 (VContainer)tengine-module-system-模块系统深度 §与 DI 容器的根本区别

实施建议（来自现有 bug 分析）

如果你选 A（服务定位器），直接抄 TEngine 是有 bug 的。看 tengine-module-system-模块系统深度 列出的：

  1. 缓存 key 不一致 bug（line 105）——自研时第一时间修：注册和查找必须用同一个 key
  2. Substring(1) 命名约定脆弱——用 [ModuleImplementation(typeof(X))] Attribute 替代
  3. OnInit 在 RegisterUpdate 内调用——分离注册和初始化，保证初始化顺序 = Priority 顺序
  4. 更优方案：用 ModuleCache<T> 静态泛型缓存（零 Dictionary 查找）

自研时的最小实现

这是经典优化模式（CommunityToolkit / EFCore 内部都用），比 TEngine 的 Dictionary 实现简单且更快。注意：VContainer 内部走 Resolver + 表达式树/Source Generator 路线，并非此模式——不要把它当 VContainer 的核心机制。详见 tengine-module-system-模块系统深度 §P1 静态泛型缓存。

决策 5：程序集分层（依赖决策 1）

这是什么问题

如果决策 1 选了 B（HybridCLR 热更），你必须把代码切成 AOT 层和 HotFix 层。这个切割决定了什么能热更、什么不能。

切割原则（源码验证）

必须在 AOT 层必须在 HotFix 层
ModuleSystem（注册中心）业务逻辑
Procedure（启动流程，含加载 DLL 步骤本身）UIModule（业务级）
接口定义（IResourceModule 等）具体业务 Singleton
MonoDriver / RootModule（MonoBehaviour 入口）DataCenter

证据见 tengine-design-decisions-设计决策分析 §3 热更边界如何划分。

关键约束（不可逾越）

实施清单

步骤做什么
1划出三个 asmdef：Framework.Core（AOT 接口）、Framework.Runtime（AOT 实现）、GameLogic（HotFix）
2所有需要在 DLL 加载前存在的服务接口和实现都放 Framework.Runtime
3留一个反射入口点（如 GameApp.Entrance 静态方法）作为 AOT→HotFix 的控制反转点。机制是：Assembly.Load(dllBytes) → assembly.GetType("...GameApp") → typeInfo.GetMethod("Entrance").Invoke(null, args)
4业务 Singleton 全部在 HotFix 层，通过 Singleton<T> 基类管理
5验证：能否在 Framework.Runtime 里 using GameLogic？应该报错

反模式

把 UI 模块放在 AOT 层

UIModule 涉及大量业务逻辑（窗口配置、布局、交互），一旦放 AOT，业务改动需重新出包。证据见 tengine-ui-system-UI系统深度——UIModule 设计上就在 HotFix 层。

把业务 Singleton 注册到 ModuleSystem

ModuleSystem 在 AOT 层，无法引用 HotFix 层类型。业务 Singleton 只能走 Singleton<T> + SingletonSystem。详见 tengine-design-decisions-设计决策分析 §4 Singleton vs ModuleSystem 的选择标准。
