OOP-Module vs ECS-Entity：游戏框架两大范式对比

主线

中国 Unity 游戏框架生态实际上分裂为两大范式阵营，它们对”如何组织游戏代码”给出了根本不同的答案：

这不是”谁更好”，而是两套互不兼容的心智模型。理解差异比选择阵营更重要。

关键节点

节点 1：抽象单元的根本差异

维度OOP-Module (TEngine)ECS-Entity (ET/Fantasy)
抽象单元模块（功能服务）实体（数据容器）
模块/实体数量10-30 个数百到数万个
模块/实体生命周期全局单例频繁创建销毁
模块/实体职责系统级能力（资源/UI/网络）游戏对象（玩家/敌人/道具）
数据归属模块内字段实体的组件

根本差异：OOP 模型中”行为是名词”（ResourceModule、UIModule），ECS 模型中”行为是动词”（Move、Attack、Render）。

节点 2：行为定义方式

为什么 ECS 选择”数据-行为分离”？三个理由：

  1. 热更新友好：行为在 Hotfix 程序集，数据在 Model 程序集。重载 Hotfix.dll 时数据布局不变
  2. 可测试：System 是静态无状态函数，单元测试不需要 Mock
  3. 数据驱动：相同 Component 可被多套 System 处理（战斗 System / AI System / UI System 都消费 HP）

OOP 模型不这样做的代价：行为绑死在类内→修改行为必须改类→热更时类结构变化导致序列化失败。

节点 3：通信机制的范式差异

通信场景OOP 模型解法ECS 模型解法
模块/实体直接调用GameModule.UI.Show<MainWindow>()entity.GetComponent<HpComponent>().TakeDamage()
跨模块/实体事件GameEvent.Send(int eventID, args)EventSystem.Publish(scene, struct evt)
同模块函数式分发直接调用EventSystem.Invoke(type, struct args)
跨进程消息框架不管Actor model + Address routing

关键发现：ET 的 EventSystem 区分 Publish（事件，多对多）vs Invoke（函数，一对一）——这是 OOP 系框架完全没有的设计。理由直接来自源码注释：“publish 是事件，抛出去可以没人订阅…Invoke 类似函数，必须有被调用方”。

节点 4：多态机制——虚函数 vs 静态分发

ECS 范式的硬规定：绝不使用虚函数。理由：

虚函数EventSystem 分发
调用方知道接口调用方只发事件
修改需改基类修改加新 Handler
难以跨程序集跨程序集随意
热更新破坏 vtable热更新无影响

ET 的实现（源码验证）：

OOP 模型的虚函数在 ECS 看来是”反热更”的——任何继承层次变化都破坏 vtable，热更时 IL2CPP 直接崩溃。

节点 5：异步原语的选择

框架异步方案设计理由
TEngine/DGameUniTaskUnity 专用，零 GC
ET 9ETTask双端共用，服务端不依赖 Unity
FantasyFTask现代化重写，AOT 友好

关键洞察：异步方案选择 = 平台耦合选择。

  • UniTask 与 Unity 深度绑定（依赖 PlayerLoop）→ 不能在服务端用
  • ETTask 跨平台（基于 SynchronizationContext + Fiber）→ 双端共用
  • FTask 进一步去反射 → 支持 AOT

自研框架启示：先确定平台范围，再选异步方案。“用 UniTask 然后想着以后双端”是死路。

节点 6：反射依赖度的演化

Fantasy 完全消除反射的代价：

  • 失去运行时动态注册能力（必须编译期决定所有类型）
  • 必须依赖 Source Generator 工具链
  • 重构对 Generator 的影响要测试

收益：

  • 支持 Native AOT（启动 10x 快，内存 5x 小）
  • IL2CPP 完全兼容（无需 link.xml）
  • 性能稳定（无 JIT 抖动）

节点 7：数据序列化与持久化

框架序列化方案设计哲学
TEngineJSON + Luban（配表二进制）业务无关
ET 9MemoryPack + MongoDBEntity 数据天然可持久化
FantasyMemoryPack + LightProto极致性能

ECS 的隐藏好处：数据和行为分离 → Entity 的字段就是数据库 schema → 持久化几乎免费（直接序列化 Entity 树）。OOP 模型需要写大量 DTO 转换代码。

跨范式集成模式

经验：客户端 UI 层适合 OOP（用户视角是”窗口”），战斗/AI 适合 ECS（大量同类对象），服务端整体适合 ECS（数据驱动 + 分布式 + 持久化）。

结论与权衡

范式选择的决策树

范式无法兼得的硬权衡

你想要必须放弃
OOP 的直观（类即行为）ECS 的热更友好
ECS 的数据驱动OOP 的代码组织清晰度
零反射 + AOT运行时动态注册的灵活性
双端代码共享客户端框架的成熟生态（UI/特效）
Fiber 多进程单进程内的简单性

跨范式可复用的设计原则

无论选哪个范式，以下原则通用（来自framework-design-principles-框架设计原则）：

  1. 约束决定架构（不是偏好）
  2. 事件系统：安全性 > 性能
  3. 对象池要有 maxSize
  4. Attribute 用于编译期元数据
  5. 框架 = 约束集合

范式选择的终极建议

小项目 / 客户端项目 / 团队不熟 ECS → 选 OOP-Module 范式（TEngine）

大项目 / 双端共享 / 战斗复杂 / 服务端为主 → 选 ECS-Entity 范式（ET / Fantasy）

不要混用：同一项目内同时维护 OOP 模块和 ECS 实体会导致心智撕裂。可以”客户端 OOP + 服务端 ECS”，但不要”客户端内既 OOP 又 ECS”。
