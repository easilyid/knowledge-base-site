是什么

UGUIGenerator 是 MyFramework 的 Prefab → C# UI 脚本代码生成器。它解决一个手游/商业项目的高频痛点：UI Prefab 上有几十上百个节点，业务代码要写大量 transform.Find("xxx") + 类型转换 + 事件绑定的样板。UGUIGenerator 让你在 Prefab 上可视化勾选要访问的节点，一键生成成员变量定义、节点绑定（assignWindow）、点击事件注册（init）、构造函数，并把界面注册信息注入框架。

它不是模板引擎（不依赖 .tt/.liquid），而是纯 C# 字符串拼接 + 锚点注释增量替换的生成器——这决定了它的全部优点（零依赖、完全可控）和全部约束（手写区必须守边界）。

与 TEngine 声明式 Attribute 的根本区别

TEngine 用 [Window] Attribute + 运行时反射绑定；MyFramework 用 Editor 期生成显式代码。前者运行时找节点（有反射开销、错误推迟到运行时），后者编译期就把 newObject(out mXxx, ...) 写死（零运行时开销、节点缺失编译期可见）。这是”显式控制 > 隐式行为”设计哲学（见 myframework-design-decisions-设计决策分析）在 UI 层的直接体现。

为什么用 delayCall 而不是直接 DestroyImmediate

OnValidate 在序列化回调栈中执行，直接 DestroyImmediate 会触发 “Destroying object multiple times” 报错。延迟到下一个编辑器 tick 销毁是 Unity Editor 脚本的标准防御写法。

智能推断：减少人工配置

MemberData.setObject() 在拖入节点时按规则自动猜测类型与数组性，这是生成器”少配置”体验的关键：

触发条件自动推断
节点名以 0 结尾且倒数第二位非数字设为 STATIC_ARRAY + 调 autoSetArrayLength() 探测 Xxx0..XxxN 连号长度
节点挂了 UGUISubGenerator设为 SUB_UI + 类型取子生成器类名
名字含 Checkbox/Tab/Progress/Slider/DropList设为 COMMON_CONTROL + 对应控件类型
名字含 Button，或子节点仅一个名为 Text设为 COMMON_CONTROL + LegendButton

命名约定即契约

静态数组、按钮推断、SUB_UI 名字匹配都强依赖节点命名。Item0/Item1 连号必须无缺口，否则 autoSetArrayLength 提前截断；纯数字节点名会让 removeEndNumber() 产出空串并报错。约定省了配置，代价是重命名脆弱性。

generateLayoutScript() 分两条路径：

  • 文件不存在 → 一次性拼出完整文件（含五个锚点骨架 + 手写区占位），首行写 // generate from:<prefab 路径> 溯源
  • 文件已存在 → 对五个锚点逐个 findCustomCode 替换；锚点缺失时有兜底（定位 class Xxx/public Xxx()/base.init() 就近插入整段锚点）

误改自动区会被覆盖

五个锚点之间的任何手写代码，下次”生成代码”都会被整段删除替换。业务逻辑必须写在锚点外。onXxxClick 回调体例外——生成器只在回调不存在时补空壳（{ ; }），已存在则不动，所以点击逻辑可以安全写在回调里。

generate from 溯源 + 防误生成

已存在文件若 // generate from: 记录的源 Prefab 与当前不符，会弹窗 发现代码文件不是由当前UI界面生成的,是否确认要生成?，避免两个 Prefab 互相覆盖对方脚本。

配套两个前置步骤：

  • sortMemberList()：先按 generateNodeTree() 的 DFS 序排序，POOL/SCROLL_LIST 强制排到最后（它们的模板节点可能被普通成员引用，必须后建）

用 Attribute 标记类型而非接口扫描

这是声明式元数据的典型用法（见 framework-design-principles-框架设计原则 原则 9）——给控件类打 [CommonControl]，生成器就能在下拉里发现它，无需改生成器代码。新增一个控件类型对生成器是零侵入的。

三类代码注入

“生成代码”一次按钮触发三处文件写入，不止生成 UI 脚本：

注入目标文件内容锚点
① UI 脚本本体HotFix/UI/<Class>.cs成员/构造/assignWindow/init/回调五锚点（上文）
② 界面注册HotFix/UI/LayoutRegisterHotFix.csregisteLayout<T>(script => mT = script)// auto generate start/end
③ 全局静态变量HotFix/Common/GameBaseHotFix.cspublic static <Class> m<Class>;// auto generate LayoutScript start/end

注册扫描遍历整个 UI Prefab 目录，对每个挂了 UGUIGenerator 的 Prefab 生成注册行；常驻界面用 registeLayoutPersist<T>，子目录界面补路径参数。appendWithAlign() 用 Tab 对齐到 64 列，生成代码保持竖直对齐美观。

注册即"约定优于配置"的落点

界面类名 = Prefab 文件名 = 注册键，三者强绑定（见 myframework-ui-system-UI系统深度 注册约定）。生成器一次性维护这条约定链，避免手写注册遗漏——代价是重命名要同步三处，否则运行时报”没有找到界面的注册信息”。

设计评价

优点

  • 零运行时开销：绑定在编译期写死成显式 newObject/assignWindow，无反射、无字符串查找（对比 TEngine Attribute 运行时绑定）。
  • 零外部依赖：纯 C# 字符串拼接，不引模板引擎，生成逻辑完全可读可改可断点。
  • 手写/自动共存：五锚点 + 回调增量是这套生成器最成熟的设计，业务逻辑与生成代码安全隔离。
  • 一键三注入：UI 脚本 + 注册 + 全局变量一次维护，消除手写注册的遗漏类 bug。
  • Attribute 类型发现：新增控件/池类型对生成器零侵入。

风险与局限

字符串拼接生成器的固有脆弱性

没有 AST，全靠锚点注释定位。手动删错一行锚点注释，增量替换就会失败或错位（findCustomCode 找不到 end 锚点会 logError 中止）。

强命名约定的多点耦合

类名 = Prefab 名 = 注册键 = 静态变量名，四处耦合。数组靠连号、控件靠名字关键词、SUB_UI 靠名字匹配——重命名要全链路同步。

依赖已编译的热更 DLL

类型下拉靠 Assembly.LoadFrom 加载 Library/ScriptAssemblies/*.dll。如果热更程序集未编译或编译失败，下拉列表为空，生成会用 myUGUIObject 兜底——可能默默生成错类型。

WorldSpace Canvas 前提

配套运行时 LayoutManager.newLayout() 要求 Canvas 为 RenderMode.WorldSpace，与普通 UGUI 的 ScreenSpace 默认不同（见 myframework-ui-system-UI系统深度）。

借鉴价值

借鉴点适用性
锚点注释增量替换（保留手写区）★★★★ 任何代码生成器通用，比”全量覆盖 + partial class”更灵活
拓扑排序 + 临时父变量★★★ 任何”按树结构生成依赖性代码”场景
Attribute 标记 + 反射 DLL 发现类型★★★ 让生成器对新类型零侵入
generate from 溯源行★★ 防多源覆盖的低成本手段
拖入节点智能推断类型★★ 提升配置效率，但耦合命名约定，需权衡

与 Unity 主流方案的对照

Unity 官方现在推 UI Toolkit（UXML + C# binding）或 partial class + [SerializeField] 拖引用。UGUIGenerator 的路线是”老 UGUI + 显式生成代码”，适合重度自研、要完全掌控生成过程、且团队已习惯命名约定的商业项目，不适合追求标准化/快速原型的团队。
