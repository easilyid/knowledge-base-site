TEngine ModuleSystem 深度分析（ModuleSystem Deep Dive）

是什么

ModuleSystem 是 TEngine 的骨架——一个静态服务定位器，管理所有运行时模块的注册、检索、帧更新和关闭。源自 EllanJiang 的 GameFramework，TEngine 在此基础上增加了热更新支持和 GameModule 门面。

脆弱的命名约定

Substring(1) 假设接口名以 “I” 开头且去掉 “I” 就是实现类名。如果接口在不同程序集、或命名不遵循约定，运行时才会抛异常——编译期无法发现。

OnInit() 在 RegisterUpdate 内调用，意味着初始化顺序取决于首次访问顺序，而非 Priority。如果低优先级模块先被访问，它会先初始化。

设计模式分析

本质：service-locator-服务定位 + Facade + 懒加载单例

模式在 ModuleSystem 中的体现
Service Locator_moduleMaps Dictionary 按类型检索
FacadeGameModule 静态类统一入口
Lazy SingletonGetModule<T>() 首次调用时创建
Priority Queue_updateModules 按优先级排序

与 DI 容器的根本区别

维度服务定位器（TEngine）DI 容器（VContainer）
依赖声明隐式——调用处才知道显式——构造函数声明
可测试性差——需初始化全局状态好——注入 mock
热更兼容好——接口隔离差——泛型/反射在 AOT 下受限
上手成本极低高（Scope/Lifetime 概念）
运行时性能Dictionary O(1)VContainer 零 GC，5-10x 快于 Zenject

优化空间

P0：已有的 GameModule 缓存（已实现）

??= 模式已经消除了热路径的重复 Dictionary 查找。这是最重要的优化，TEngine 已经做了。

P1：静态泛型缓存（零查找）

这是 VContainer 和 SparseInject 内部使用的技巧。访问等同于读一个静态字段，比 Dictionary 快 5-10x。

P1：分离注册与初始化

保证初始化顺序严格等于优先级顺序。

P2：工厂注册表替代 Activator.CreateInstance

P2：Attribute 标注替代命名约定

P3：引入 Scope 概念

当前所有模块都是全局单例。如果需要场景级模块（如场景专属 UI 管理器），需要引入 Scope 层级——但这会大幅增加复杂度，通常不值得。

更好的变种

变种 A：数组索引（ECS 风格）

缺点：失去动态注册灵活性，模块 ID 需要手动维护。

变种 B：VContainer（现代 DI）

适合不用热更新的大型团队项目。

变种 C：混合方案（推荐）

适用场景判断

TEngine ModuleSystem 最适合：

  • 使用 HybridCLR 热更新的项目（DI 容器在 AOT + 热更下问题多）
  • 中小团队快速迭代（零仪式感）
  • 模块粒度粗（10-30 个系统级服务）
  • 不需要大量单元测试

应考虑替代方案：

  • 大型团队（10+ 程序员）需要架构约束 → VContainer
  • 需要细粒度依赖注入（数百个服务类）→ VContainer/SparseInject
  • 重度单元测试需求 → DI 容器
  • 不用热更新的纯 IL2CPP 项目 → VContainer SourceGenerator 模式
