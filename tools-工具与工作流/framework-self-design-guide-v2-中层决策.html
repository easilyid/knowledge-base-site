自研框架架构决策指南 v2（中层决策）

本页定位

接续 v1 底层决策——v1 决定了范式/热更/平台/异步/模块组织/程序集分层，v2 在这些底层之上决定 4 个中层子系统的设计选项。

v1 是骨架，v2 是骨架上挂的器官：事件系统、启动流程、对象池、帧驱动。每个都依赖 v1 的某个底层决策——v1 选什么，v2 的选项就被收窄了。

阅读前提

必须先完成 v1 的 5 个底层决策。如果 v1 没填，v2 的判断标准用不上。

决策依赖图

决策 6：事件系统

这是什么问题

模块/实体之间如何通信。决定了业务代码的解耦程度和性能开销。

选项

选项实现复杂度GC类型安全适用
A. C# event / Action极低0（已订阅后）编译期直接通信、紧耦合
B. Int Key + 委托表低0运行时TEngine GameEvent 风格
C. Source Generator + Int Key中0编译期类型安全 + 零开销
D. struct 事件 + 泛型分发中0编译期ET EventSystem 风格
E. MessagePipe / R3中（库本身简单，DI 接入有学习成本）0编译期DI 容器项目
F. UniRx（响应式流）中非 0（链式算子分配 IDisposable + 闭包）编译期数据流场景，不推荐用作通用事件总线

UniRx ≠ 零 GC

UniRx 的链式 Where().Select().Subscribe() 每个算子都会分配 IDisposable 包装和闭包。如果想要”零 GC + 响应式”，用 R3（UniRx 续作，by Cysharp）或 MessagePipe。

选择标准（与 v1 决策强联动）

决策 0 = OOP + 决策 1 = 热更C Int Key + Source Generatortengine-game-event-事件系统深度 §零 GC 实现机制
决策 0 = ECSD struct 事件et-framework-ET框架 §EventSystem 双轨分发
决策 0 = OOP + 决策 1 = 无热更 + 团队小A C# event最简单、最快
决策 4 = DI 容器（VContainer）E MessagePipeDI 同生态

必须避开的设计陷阱（来自 TEngine 源码 bug）

如果你抄 B 或 C 路线，直接复制 TEngine 的实现会带 3 个生产级缺陷。详见 tengine-game-event-事件系统深度 §优化空间：

缺陷自研时的修法
无 try-finally：一个 handler 抛异常 → _isExecute=true 永不复位 → 系统僵死dispatch 循环必须 try { ... } finally { CheckModify(); } 包裹
O(n) Contains 防重复：每次 AddHandler 线性扫描用 HashSet<Delegate> 做 O(1) 去重，或只在 Debug 模式检查
递归 dispatch 无防护：内层 Send 同一事件会覆盖 _isExecute 状态用 int _dispatchDepth 计数器，仅最外层合并 add/delete 列表

不要为了零 GC 牺牲异常安全

“零 GC” 的代价是手写状态管理。手写状态管理的代价是状态恢复必须保证。两者不可兼得就保异常安全——一个 NullRef 导致整个事件系统僵死，影响远大于多几个字节 GC。

设计原则提取

无论选哪个，遵守这 3 条（证据见 tengine-game-event-事件系统深度 §重入安全机制）：

  1. dispatch 期间允许增删订阅，但延迟生效——三 List 模式（_listExist / _addList / _deleteList）
  2. handler 异常不能影响其他 handler——每个 handler 独立 try/catch
  3. 订阅必须有生命周期绑定——参考 TEngine 的 GameEventMgr，UI 销毁时自动取消所有订阅（详见 tengine-ui-system-UI系统深度 §GameEventMgr 生命周期绑定）

反向视角：事件总线不是万能（来自 BigCat）

bigcat-framework-BigCat框架 作者 wjybxx 明确反对纯事件驱动，理由值得在做决策 6 时纳入考虑：

反对理由解释
子节点自加调度队列 → 父节点失控Unity 项目尤为严重——监听器满天飞、生命周期脆弱
事件是跳跃性思维 vs 心跳是顺序思维跨 4 跳 callback 的代码无法 Step Through 调试
错失信号导致状态机僵死玩家碰到的很多 bug 都源于此
”脱离你掌控的代码一定不是好代码”异步派发 + 订阅生命周期 + 循环触发让代码失控

给决策 6 的修正：

事件系统应该用在跨模块解耦，不是替代每帧 Update

  • 跨模块通知（玩家升级 / 网络断开 / 进入战斗）→ 用事件总线 ✓
  • 同模块时序逻辑（技能流程 / UI 状态切换 / AI 决策）→ 用心跳 + Context（任务树/状态机/Update）✗ 不用事件
  • 判断准则：如果你需要”按顺序读懂这段流程”，就别用事件。事件适合”广播 + 多个独立反应”。

bigcat-framework-BigCat框架 的 TaskTree + Context 三件套（Blackboard / CancelToken / SharedProps）就是”心跳为主、事件为辅”的具体落地——可作为决策 6 之外的第三条路。

决策 7：启动流程编排

这是什么问题

从 App 启动到游戏主逻辑跑起来的中间阶段（资源初始化、版本检查、DLL 加载、玩家登录），代码怎么组织。

选项

选项心智模型适用
A. 纯 FSM（每步一个状态类）显式状态机需要不可逆操作 + 回退/重试
B. 纯 async 链线性 await简单线性流程
C. FSM 管阶段 + async 管细节分层组合推荐——兼顾两者优势
D. ScriptableObject 配置链数据驱动设计师可改启动顺序

选择标准

你的情况选什么证据
v1 决策 1 = HybridCLR 热更C FSM 管阶段 + async 管细节tengine-design-decisions-设计决策分析 §FSM 启动 vs Async Pipeline
启动有不可逆步骤（如加载 DLL）A 或 C同上
启动有可并行步骤（音频/网络/资源系统）B 或 C（用 UniTask.WhenAll）tengine-pool-procedure-池化与启动深度 §Async 替代方案示例
启动需要重试（下载失败重新下）A 或 CFSM 可 ChangeState<DownloadState>()
启动需要 Inspector 可视化当前状态A 或 CFSM 状态可序列化

FSM 启动的标准链（参考 TEngine 12 步）

详见 tengine-pool-procedure-池化与启动深度 §Part 2 Procedure 启动系统。如果你需要热更，至少要有这些不可省略的状态：

关键设计点：ProcedureLoadAssembly 之前的代码必须在 AOT 层（v1 决策 5）；之后的代码可以在 HotFix 层。这是控制反转点，由反射跨过——典型实现：Assembly.Load(dllBytes) → assembly.GetType("...GameApp") → typeInfo.GetMethod("Entrance").Invoke(null, args)。

必须避开的陷阱

不要把启动逻辑写在 RootModule.Awake

启动是异步流程（要等下载、等加载），但 MonoBehaviour.Awake 是同步的。强行同步会卡主线程；强行 async void 会丢异常。用 FSM 或 async 方法显式管理。

不要让业务逻辑（如登录）混入 Procedure

Procedure 应该只管”框架启动完成”为止。玩家登录、加载存档等是业务，应该在 ProcedureStartGame 之后由业务代码自己管。

代码示意见 tengine-pool-procedure-池化与启动深度 §推荐：混合方案。

决策 8：对象池设计

这是什么问题

哪些对象需要池化、用什么池、如何控制池容量、如何防止双重释放。

选项

池化目标推荐方案理由
纯 C# 小对象（事件、状态、数据载体）自研 Pool<T> 或 Unity ObjectPool<T>需要业务逻辑 Clear
GameObject（子弹、特效、UI Item）专用 GameObject 池需要 SetActive + Transform 管理
临时字节缓冲区（网络包、序列化）.NET ArrayPool<T>.Shared已经原生、线程安全、分桶优化
需要自动过期的资源句柄时间+优先级策略池TEngine ObjectPoolModule 设计

证据见 tengine-pool-procedure-池化与启动深度 §Part 1 MemoryPool 内存池系统 + §与 Unity 内置 ObjectPool 对比。

必须遵守的 3 条铁律

来自 TEngine MemoryPool 已发现的 3 个生产级缺陷（tengine-pool-procedure-池化与启动深度 §线程安全分析 / 双重释放检测）：

  1. 池必须有 maxSize——TEngine 没有，导致池可无限膨胀。修法：Release 时检查 if (_pool.Count < _maxSize) _pool.Enqueue(obj); else 丢弃
  2. 双重释放至少在 Debug 模式检测——TEngine 默认关闭（_enableStrictCheck = false），同一对象入池两次 → 两个消费者拿到同一实例 → 数据污染。修法：用 HashSet<T> 在 Debug 模式跟踪 in-pool 状态
  3. 统计计数器要么全在 lock 内要么用 Interlocked——TEngine 计数器在 lock 外修改导致并发竞态。修法：Interlocked.Increment(ref _count) 或全部移入 lock 块

数据结构选择：Stack vs Queue

选择行为适用
Stack（LIFO）栈顶对象被反复使用缓存友好（热对象在 CPU cache），但底部对象沉底
Queue（FIFO）对象均匀复用避免内存碎片，TEngine 采用此方案

选择决策

创建/销毁频率是否池化备注
每秒 100+ 次（如子弹、特效、伤害飘字）必须池化GC 压力显著
每秒 10-100 次看实测用 Profiler 看 Allocations 再决定，不要凭感觉
每秒 < 10 次不池化现代设备 GC 影响微乎其微，池化成本（管理 + Clear + 双重释放风险）反而是负优化

阈值不是绝对值

上面是手游 / 中端设备的经验阈值。低端机或主机 60+ FPS 的项目阈值要降低；PC / 高端机阈值可放宽。最终标准是 Profiler 的 GC.Alloc 报告，不是固定数字。

必须避开的陷阱

不要给所有类型加池

池化有维护成本：必须实现 Clear/Reset、必须考虑双重释放、必须避免持有外部引用。低频对象池化是负优化。

池中对象不能持有强引用到 Unity Object

池化的纯 C# 对象如果持有 GameObject/Component 引用，Unity 重载场景时 C# 引用未清理 → 内存泄漏。Release 时必须 gameObject = null。

决策 9：帧驱动机制

这是什么问题

Unity 只有 MonoBehaviour.Update 是帧入口，但框架代码大量是纯 C# 类。如何让纯 C# 代码获得帧更新能力。

选项

选项实现适用
A. 单 MonoBehaviour 驱动一个 GameLoop : MonoBehaviour 遍历 ITickable 列表不要热更的简单项目
B. ModuleSystem 驱动RootModule.Update → ModuleSystem.Update → IUpdateModuleTEngine 风格，OOP 框架默认
C. MonoDriver 桥接层Module 提供 AddUpdateListener 回调注册接口TEngine/DGame 热更项目
D. EntitySystem 分发按 Entity 类型批量分发 UpdateET/ECS 范式
E. VContainer ITickableDI 容器自动注册到 PlayerLoopVContainer 项目

选择标准（与 v1 联动）

v1 你选了什么决策 9 选什么证据
决策 1 = 无热更 + 决策 4 = 服务定位器A 或 B简单优先
决策 1 = HybridCLR 热更C MonoDriver 桥接层tengine-design-decisions-设计决策分析 §帧驱动如何统一
决策 0 = ECSD EntitySystem 分发et-framework-ET框架 §ECS 实现
决策 4 = DI 容器E ITickableVContainer 原生支持

三层驱动的常见结构（热更架构下的事实模式）

如果你 v1 选了 HybridCLR 热更（决策 1 = B），决策 9 通常会演化成三层驱动结构（也可以更扁平，但 TEngine/DGame 的演化路径走到了三层），原因见 tengine-design-decisions-设计决策分析 §帧驱动如何统一：

为什么演化成这样：HotFix 层不能直接 new MonoBehaviour（程序集依赖方向不允许从 AOT 反向），所以需要 MonoDriver 这种”AOT 层提供接口、HotFix 层注册回调”的桥梁。这不是过度设计，是热更架构下的事实模式——你也可以做得更扁平（如 HotFix 直接 await UniTask.Yield()），但模块/系统多了之后会自然演化到三层。如果你不需要热更，三层全部可以省略。

Priority 排序：要不要

是否需要 Priority原因
需要Update 顺序影响逻辑正确性（物理在渲染前、输入在逻辑前）
不需要模块互相独立，顺序不敏感

如果需要 Priority，参考 tengine-module-system-模块系统深度 §优先级插入与初始化——但注意 TEngine 的 bug：OnInit 在 RegisterUpdate 内调用 → 初始化顺序 ≠ Priority 顺序。自研时分离注册和初始化：先全部注册（排序），再统一调用 OnInit。

必须避开的陷阱

不要在 Update 期间 Add/Remove 监听器

集合在迭代中被修改 → 抛 InvalidOperationException 或跳过元素。如果业务确实需要，参考事件系统的”延迟生效”模式（三 List）或 UIModule 的”集合长度变化检测”（tengine-ui-system-UI系统深度 §OnUpdate 集合修改检测）。

不要混用多个 MonoBehaviour 驱动

项目里有的模块挂自己的 MonoBehaviour、有的用框架驱动 → 帧顺序不可预测、生命周期混乱。统一走框架驱动。

中层决策的反馈环

v2 决策做完后，请反过来检查 v1：

如果中层卡住…可能 v1 决策错了
事件系统怎么选都不对范式选错了（OOP/ECS 决定通信方式）

决策是双向的

v1 → v2 是默认路径，但中层卡住说明底层选错。不要硬扛中层复杂度，回去重新审视底层。
