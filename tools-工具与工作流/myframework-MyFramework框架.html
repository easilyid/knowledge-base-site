MyFramework 框架（MyFramework）

定位：偏传统游戏引擎开发思路的 Unity 客户端框架 + 热更分层 + 工程工具链，重点不是单纯封装 Unity API，而是围绕商业项目开发流程整理出的工程体系。

概述

MyFramework 由 ZHOURUIH 开发并持续迭代 5+ 年，已应用于个人 MMORPG 项目和公司手游项目，客户端+服务端规模均达 20万+ 行代码。

核心关注点：

  • 热更新分层（Frame_Base / Frame_Game / Game / Frame_HotFix / HotFix）
  • UI 代码生成（UGUIGenerator）
  • 配置表工具链（CSV 编辑器 + 检查 + 代码生成）
  • 网络协议代码生成（客户端 + 服务器消息生成）
  • 资源管理（统一封装 AssetBundle / AssetDatabase）
  • 对象池（类 / List / GameObject / Prefab / Effect）
  • 工程检查（代码规范检查 + 资源引用检查）
  • 低 GC（工具函数优化 + 对象池）
  • 强生命周期控制（显式 init / update / destroy）
  • 客户端与服务器协作（配套服务器框架）

仓库地址：https://github.com/ZHOURUIH/MyFramework
配套服务器：https://github.com/ZHOURUIH/MyServerFramework
验证情况：GitHub Star 596+ / Unity 6000.2 / 支持 Windows / Android / iOS / WebGL

设计理念

MyFramework 并不追求最新潮的架构或最少代码量，而是关注：

1. 可维护

代码定位清晰，问题出现后能够快速查找。

2. 可控

尽量减少对 Unity 自动行为和第三方插件的过度依赖。框架中很多地方倾向于显式执行，而不是依赖隐藏生命周期。

3. 可落地

优先解决商业项目中真正会遇到的问题：

  • 性能优化
  • GC 控制
  • 热更新
  • 工具链
  • 资源管理
  • UI 开发效率
  • 客户端与服务器协议一致性

4. 长期维护

框架更偏向传统游戏引擎开发思路，强调明确的生命周期、明确的调用关系和统一的代码风格。

设计倾向

  • 显式控制 > 隐式行为：例如 UI 通过代码显式控制位置和尺寸，而不依赖 UGUI 锚点和自动布局
  • 自定义实现核心功能：自定义输入系统（不依赖 UGUI EventSystem 作为主要派发）、自定义序列化（Json / 字节 / 按位）
  • 强生命周期管理：明确的 preInitAsync → initAsync → resourceAvailable → update → destroy 流程

核心亮点

1. UI 自动生成

通过在 UI Prefab 上配置需要访问的节点，自动生成 UI 脚本代码与注册逻辑，减少大量重复的查找节点和绑定代码。

支持：

  • 单节点生成
  • 数组节点生成
  • 自动生成成员变量
  • 自动生成 assignWindow
  • 自动生成构造代码
  • 自动生成注册代码
  • 保留手写逻辑代码

2. 配置表工具链

使用 CSV 作为配置表格式，并配套自研表格编辑器。

支持：

  • 字段类型检查
  • 枚举合法性检查
  • ID 唯一性检查
  • 表格引用检查
  • 资源路径检查
  • 客户端代码生成
  • 服务器代码生成
  • 运行时代码检查逻辑生成

配置表编辑阶段即可发现大量错误，减少运行时问题。

3. 网络协议代码生成

根据协议配置自动生成客户端与服务器消息代码。

支持：

  • 消息类生成
  • 字段序列化生成
  • 字段反序列化生成
  • 消息注册代码生成
  • 客户端消息代码生成
  • 服务器消息代码生成
  • 手写逻辑代码保留

4. 客户端 + 服务器配套

MyFramework 有配套服务器框架：https://github.com/ZHOURUIH/MyServerFramework

客户端与服务器可以共享协议生成、配置表生成等工具链，适合需要长期维护的中大型项目。

5. 热更新分层

框架代码按照是否可热更进行了明确分层。

依赖关系：

这种分层方式可以让框架层和业务层都有较高的热更新能力，同时又保留必要的启动稳定性。

技术特性

UI 框架

提供完整 UI 封装，避免业务层直接访问 Unity 原生组件。

支持：

  • 无限滚动列表
  • CheckBox / Slider / Progress / DropList
  • 长按 / 双击 / 拖拽
  • 点击穿透
  • UI 对象池
  • UI 代码自动生成

设计倾向：框架尽量不依赖 UGUI 的锚点和自动布局组件，而是倾向于通过代码显式控制 UI 的位置、尺寸、显示状态和输入逻辑。

自定义输入系统

不使用 UGUI 默认 EventSystem 作为主要输入派发方式，而是自己实现统一输入检测。

支持：

  • 鼠标输入 / 触摸输入
  • 点击 / 双击 / 长按
  • 拖拽 / 点击穿透

部分 Unity 原生组件仍然可以按需使用 EventSystem，例如 ScrollRect。

资源管理系统

统一封装资源访问。

支持：

  • AssetDatabase（编辑器模式）
  • AssetBundle（打包模式）
  • 同步加载 / 异步加载

业务层无需关心资源来自编辑器还是 AssetBundle。

网络框架

支持：

  • TCP
  • UDP
  • WebSocket（使用 async/await）
  • HTTP

提供：

  • 消息自动注册
  • 消息代码自动生成
  • Json 序列化
  • 字节序列化
  • 按位序列化（进一步降低网络带宽占用）

命令系统用于封装具有完整逻辑意义的事件。

用于：

  • 逻辑封装
  • 模块通信
  • UI 与逻辑解耦
  • 延迟执行
  • 主线程调度
  • 日志追踪

组件系统

部分逻辑使用组件思想进行组织，通过组合代替复杂继承。

适合拆分可复用、可独立更新的功能逻辑。

对象池设计

包含：

  • 类对象池（ClassPool）
  • List 对象池（ListPool）
  • GameObject 对象池（GameObjectPool）
  • Prefab 对象池（PrefabPool）
  • Effect 对象池（EffectPool）

Effect 对象池：基于 PrefabPool 抽象出 EffectPool，支持：

  • Prefab 对象池
  • Effect 对象池
  • QuickEffect 快速特效
  • Trail 管理
  • 生命周期管理
  • 按标签批量销毁

QuickEffect 适用于非循环、不带拖尾、需要频繁同时播放的粒子特效。

基础工具库

包含大量基础工具函数：

  • BinaryUtility
  • StringUtility
  • MathUtility
  • FileUtility
  • TimeUtility
  • UnityUtility

同时提供大量 Scope 设计，用于实现类似 C++ RAII 的自动释放与状态恢复。

工程检查工具

Editor 中提供了大量项目检查和辅助工具：

  • 代码规范检查
  • 空行检查 / 空格检查 / 单行长度检查
  • 命名规范检查 / 函数排版检查 / 注释检查
  • 命令命名规范检查
  • 热更引用检查
  • 资源引用查找 / 未引用资源检查
  • 材质引用丢失检查 / 图集引用检查
  • 多语言文本检查
  • UI 适配组件检查
  • 资源文件名规范检查
  • 预设根节点变换检查
  • 热更与非热更资源互相引用检查

这些工具主要用于减少大型项目长期维护过程中的隐性错误。

关于”禁止协程/async/switch”的澄清

DeepWiki 分析错误

早期基于 DeepWiki 的分析声称 MyFramework”禁止协程/async/await/switch”，这是错误的。

源码验证结果（2026-06-15 本地 clone 验证）：

协程（IEnumerator / yield return）：✅ 大量使用

  • AsyncTaskGroup.cs：专门用于等待多个协程
  • AssetBundleLoader.cs：协程下载资源
  • ObsSystem.cs：downloadTxtWaiting / downloadBytesWaiting

async/await：✅ WebSocket 和 IAP 模块使用

  • NetConnectWebSocket.cs：startConnect / clearSocket / doSend / receiveThread
  • PurchasingSystem.cs：initPurchase

switch 语句：✅ 多处使用

  • CheckLayer.cs / TweenSequence.cs / TweenTrack.cs / SafeFloat.cs / SafeInt.cs / SafeLong.cs / UIGradient.cs

真实的设计倾向

README 中强调的不是”禁止某些语言特性”，而是：

  1. 显式控制 > 隐式行为：

    • “尽量减少对 Unity 自动行为和第三方插件的过度依赖”
    • “框架中很多地方倾向于显式执行，而不是依赖隐藏生命周期”

  2. 自定义实现核心功能：

    • 自定义输入系统（不依赖 UGUI EventSystem 作为主要派发）
    • 自定义序列化（Json / 字节 / 按位）
    • 代码显式控制 UI（不依赖锚点和自动布局）

  3. 工具链完善 > 手工编码：

    • UI 代码生成
    • 配置表工具链
    • 网络协议代码生成

  4. 强生命周期管理：

    • 明确的 Frame 层 / Game 层 / HotFix 层分离
    • GameFrameworkHotFix 统一管理 FrameSystem 生命周期

适用场景

适合

  • RPG / MMO 类长期商业项目：配套服务器框架，共享工具链
  • 需要完善工具链的团队：UI/协议/配置表代码生成，减少重复劳动
  • 强调代码规范的团队：工程检查工具覆盖代码规范、资源引用、热更分层
  • 需要明确生命周期控制的项目：显式 init / update / destroy，不依赖隐式行为

不适合

  • 快速原型开发：工具链完善但学习曲线较陡
  • 纯单机小游戏：客户端+服务器配套的工具链可能过重
  • 依赖大量第三方插件的项目：框架倾向自定义实现，可能与插件冲突
