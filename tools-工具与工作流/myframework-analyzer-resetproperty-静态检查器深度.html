是什么

AnalyzerResetProperty 是 MyFramework 自研的 Roslyn 静态分析器规则，用于强制对象池对象在 resetProperty() 中处理自身字段，避免 ClassPool 复用对象时带出上一轮使用的脏数据。

它的规则 ID 是：

在 MyFramework 的低 GC 体系中，ClassPool 不是普通缓存，而是贯穿命令、资源、音频、特效、网络、UI 的对象复用基础设施。对象池的最大风险不是”分配太慢”，而是对象被复用时字段没有归零。AnalyzerResetProperty 就是把这个风险从运行时 bug 前移到编译期错误。

底层逻辑

对象池降低 GC 的前提是：对象每次借出前都像新对象一样干净。resetProperty() 是这个契约的唯一抓手；Roslyn Analyzer 则是把”团队纪律”固化成编译器规则。

这条规则解决的真实问题

1. 脏数据复用

对象池 bug 最常见形态：字段漏清，旧状态污染新逻辑。

下一次从池里拿出来，如果只设置 mDamage，mCritical 可能保留上一次暴击状态。这个 bug 不一定每次复现，因为它依赖池对象复用顺序。

2. 资源引用泄漏

ResourceRef<T> / AudioClip / GameObject / 回调委托如果不清空，会让资源或对象被意外持有，造成资源卸载失败或生命周期错乱。

3. 命令回调串扰

Command 类有 mStartCallback / mEndCallback。如果回池不 Clear()，下一次命令可能触发上一条命令的回调。MyFramework 用 Analyzer 要求字段在 resetProperty() 出现，至少能逼开发者显式处理这些集合字段。

4. 生命周期 ID 判断失效

ClassObject 的 mAssignID 每次借出都会变，很多异步安全回调依赖它判断”回调回来时还是不是同一次分配”。如果父类 base.resetProperty() 没调用，mAssignID、mHasDestroy、mPendingDestroy 的状态链会断，Editor 检测与运行时安全判断都可能失效。

规则的局限与误报/漏报

注释也会被当成“处理过”

规则用 body.ToString() 字符串包含判断，不排除注释。因此 // mCmdID = 0; 会命中 mCmdID + " = "。Command.resetProperty() 就有这种注释：// mCmdID = 0;。这是一个明确漏报：字段没重置，但规则认为它被提到了。

只检查字段名出现，不检查语义正确

mDamage = mDamage;、Debug.Log(mDamage)、SomeMethod(mDamage) 都可能被视为处理过，但不代表字段真的被清理到安全状态。

不检查基类字段以外的继承链语义

RESET001 只扫 classSymbol.GetMembers().OfType<IFieldSymbol>()，只包含当前类型声明字段，不包含基类字段。这本来合理，但必须依赖 BASE001 补足。若 BASE001 因字符串误判被绕过（如注释中出现 base.resetProperty(），父类链仍可能断。

expression-bodied resetProperty 会被跳过

BlockSyntax body = method.Body; if (body == null) return;。如果有人写 public override void resetProperty() => mX = 0;，规则直接跳过。项目风格通常不用表达式体生命周期函数，但这是规则边界。

不区分字段是否应当保留

有些字段确实不应重置，例如 ClassObject.mObjectInstanceID、Command.mCmdID。当前做法是靠注释里写一行假赋值（// mCmdID = 0;）来“让 Analyzer 通过”。这是实用但不干净的压制方式。

为什么这仍然有价值

虽然规则粗糙，它仍然非常有工程价值，因为它把 80% 的低级遗漏挡在编译期：

  • 新增字段后忘记处理 → 立刻 RESET001
  • override 生命周期忘记 base → 立刻 BASE001
  • 集合字段至少要显式 Clear() 或传给辅助函数 → 不会无声保留旧引用
  • 对象池规范从口头约定变成 IDE/编译器红线

这符合 MyFramework 的整体风格：不追求最优雅的抽象，追求可控、可检查、能落地。Analyzer 的实现不完美，但它是“强工具链 + 强编码规范”的抓手。

可改进方向

如果继续演进这条 Analyzer，优先级如下：

P0：排除注释，避免假赋值漏报

不要用 body.ToString()，改用 Roslyn 语法树遍历：

  • AssignmentExpressionSyntax：识别左侧是否是字段
  • InvocationExpressionSyntax：识别字段作为 receiver 或 argument
  • 不读取 Trivia（注释），天然排除 // mField = 0

P1：增加“有意不重置”标记

P2：只对池化类型启用 RESET001

当前规则只要方法名叫 resetProperty 就检查，不判断是否继承 ClassObject / IResetProperty。更合理的边界：

这能减少未来非对象池类误触。

P3：支持 expression-bodied 方法

补 method.ExpressionBody，避免有人写短表达式体时规则漏掉。

P4：区分清理强度

有些字段只是被传参，不代表被清理。可按字段类型提供建议：

字段类型推荐清理方式
引用类型= null 或 Clear()
数值类型= 0 / enum 默认值
bool= false
List<T>/Dictionary<K,V>.Clear()
ResourceRef<T>= null 或释放函数

这会从“出现检测”升级到“语义检测”，但复杂度也会显著上升。

与其他框架的对比

框架对象池规范手段对 reset 的强制程度
TEngineIMemory.Clear() 接口约定运行时约定，无 Roslyn 检查
Unity ObjectPool<T>OnRelease 回调使用者自己写，编译期不检查字段
BigCat防御性编程 + reentry id更重生命周期语义，未见同类 Analyzer
MyFrameworkClassObject.resetProperty() + RESET001 + BASE001编译期强制字段出现 + base 链路

借鉴价值

如果你的项目大量使用对象池，并且对象字段经常新增，写一个类似 RESET001 的 Analyzer 比在 code review 里肉眼查 reset 更可靠。哪怕第一版只是启发式，也能显著降低脏数据复用 bug。
