Unity 游戏框架全景坐标系（Framework Landscape Synthesis）

本页定位

这是 tools 分支 7 个框架页的顶层枢纽（Hub-of-Hubs）。它不重复任何单框架的细节，只做一件事：把全部 7 个框架放进同一个坐标系，让”该选谁 / 该借鉴谁”的判断有统一参照。

本库已有两个单轴深挖 synthesis，本页是它们的上层入口，不与之重复：

  • paradigm-comparison-范式对比 — 范式轴深挖：OOP-Module vs ECS-Entity 的源码级对比（high）
  • unity-framework-comparison-Unity框架架构对比 — 选型/演化轴深挖：TEngine/ET/QFramework/GameFramework 选型矩阵 + 演化树

阅读顺序

先用本页的”两轴定位图”建立全局观 → 命中某个区域后，跳对应单轴 synthesis 看深挖 → 再下钻到具体框架页。

主线脉络

中国 Unity 生态的开源框架，沿两条正交的轴分布，几乎所有框架都能被这两轴定位：

  • 范式轴（横）：OOP-Module（模块+服务定位器+继承）↔ ECS-Entity（实体+组件+静态系统）
  • 目标轴（纵）：客户端全栈 ↔ 服务端/双端分布式

第三条隐含轴是团队 vs 个人——它不决定架构，但决定”能不能落地”：团队框架优先解决协作+交付+热更，个人精品框架优先解决”代码怎么写才是对的”，两者 KPI 不同，不可直接选型对比。

关键节点

两轴定位图

定位说明

  • 右下密集区（OOP + 客户端）是中国手游主流：TEngine / DGame / MyFramework / QFramework 都在这里，差异在”轻 vs 重""通用 vs 自研工具链”。
  • 右上（ECS + 双端）只有 ET 一家真正成熟；Fantasy 把它往”服务端 + AOT”方向重写。
  • BigCat 横跨：范式是 OOP，但用 TaskTree 心跳驱动走了第三条路（既非纯 Update 也非事件驱动），目标偏服务端 MMO。

"自研一切"是把双刃剑

MyFramework / BigCat / ET / Fantasy 都大量自研（序列化、异步、工具链）。自研的代价是生态壁垒——团队成员要先学非标方案，第三方工具不可用。单人/小团队作者能维护得起（他们最懂自己的代码），但作为被借鉴方时，要区分”借鉴思想”和”照抄实现”：BigCat 的 Dson、自研协程、自研 DI 都在”不建议照抄”之列（见 bigcat-framework-BigCat框架），思想可借鉴，落地用 MemoryPack/UniTask/VContainer 等工业标准。

演化谱系

两条主谱系（GameFramework 系 / ET 系）+ 三个独立演化者（QFramework / BigCat / MyFramework）。谱系内是”继承+优化”，谱系间是”范式对立”。

横向连接

同范式内的差异（不是范式之争，是工程取向之争）

OOP 阵营内部（TEngine/DGame/QFramework/MyFramework/BigCat）的真正分歧不在范式，而在三个工程取向：

取向一端另一端
依赖第三方 vs 自研TEngine（YooAsset+HybridCLR+Luban 拼装）MyFramework（几乎全自研工具链）
轻量通用 vs 重业务QFramework（~1000行核心）DGame（叠满红点/存档/GM 业务模块）
事件驱动 vs 心跳驱动TEngine（GameEvent 全局总线）BigCat（明确反对纯事件，用 TaskTree 心跳）

异构架构：范式可以混搭

范式轴不是”二选一”——客户端和服务端可以用不同范式，因为通信层只传数据不传行为：

DGame 的 DGame_Fantasy 分支、MyFramework 的 MyServerFramework 都是这种异构落地。这说明：选客户端框架和选服务端框架是两个独立决策。

与自研决策指南的关系

7 框架是”别人怎么选”的现成样本；要把这些选择转成”我自己怎么选”，走决策指南：

  • framework-self-design-guide-自研框架决策指南 — v1 底层决策（范式/热更/平台/异步/模块组织/程序集分层）
  • framework-self-design-guide-v2-中层决策 — v2 中层（事件/启动/池/帧驱动）
  • framework-self-design-guide-v3-上层决策 — v3 上层（UI 系统）
  • framework-design-principles-框架设计原则 — 10 条跨框架通用原则

本页与决策指南的分工

本页回答”生态里有哪些选择、它们在坐标系哪个位置”；决策指南回答”给定我的约束，该走哪条决策路径”。前者是地图，后者是导航。

结论与权衡

选型速查（按硬约束定位）

硬约束落点理由
客户端 + 要热更 + 快速上线TEngineHybridCLR 开箱即用，社区最活跃
客户端 + 要现成业务模块（红点/存档/GM）DGameTEngine 增强版，省去自己造轮子
前后端共享代码 + 分布式ET唯一成熟双端框架
服务端 + Native AOT + 极致性能Fantasy零反射，.NET 8，多协议一等公民
小团队 / 快速原型QFramework最轻量，CQRS 约束有价值
想统一 AI/技能/副本逻辑组织借鉴 BigCatTaskTree + Context 三件套（借思想非抄码）
要传统引擎式显式控制 + 自研工具链MyFramework显式生命周期，低 GC，5 年商业验证

三条跨框架通用启示

  1. 框架的价值不在功能多少，在于它强制了什么约束——QFramework 的 CQRS 约束比它的 UIKit 更有价值；ET 的 Model/Hotfix 分离强制了热更架构。
  2. 范式选择跟着平台目标走，不跟着流行度走——纯客户端没必要上 ECS（ET/Fantasy 是杀鸡用牛刀），双端分布式 OOP 又撑不住。
  3. 借鉴个人精品框架时，分清”思想”与”实现”——BigCat 的 reentry 检测/协作式取消/Context 三件套是普适思想，Dson/自研协程/自研 DI 是个人选择，照抄是技术债。
