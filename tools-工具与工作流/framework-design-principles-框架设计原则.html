Unity 游戏框架设计原则（自研框架指南）

本页定位

从 TEngine / DGame / GameFramework / ET / QFramework 的源码分析中提炼出的可复用设计原则。不是某个框架的文档，而是”如果你要自研框架，这些是经过验证的设计决策和已知陷阱”。

原则 1：先确定约束，再选架构

核心洞察

TEngine 的所有复杂性都源于一个约束：热更新。如果去掉热更需求，ModuleSystem + Singleton 双轨、MonoDriver 桥接层、AOT/HotFix 程序集分离全部不需要。

决策框架

可复用原则

约束决定架构，不是偏好决定架构。 先列出你的硬约束（热更？跨平台？团队规模？），再从约束推导架构选择。不要因为”DI 更优雅”就选 DI——如果你需要热更，DI 在 IL2CPP + HybridCLR 下会给你制造无穷的泛型问题。

原则 2：模块组织——粒度决定模式

核心洞察

粒度数量级最佳模式原因
系统级服务10-30 个Service LocatorDictionary 查找够快，注册简单
业务级服务30-200 个DI 容器需要 Scope 管理、自动装配
游戏对象能力数千个ECS 组合数据局部性、批量处理

TEngine 用 Service Locator 管 15 个系统模块——完全合理。如果它用 Service Locator 管 200 个业务类——那就是滥用。

实现模板

这比 TEngine 的 Dictionary<Type, Module> + Activator.CreateInstance + Substring(1) 命名约定更简单、更快、更安全。

已知陷阱

  • TEngine 的缓存 key bug：CreateModule 按具体类型存，GetModule<T> 按接口类型查——永远 miss。教训：注册和查找必须用同一个 key。
  • 命名约定推导类型：IFoo → Foo 的 Substring(1) 假设太脆弱。教训：用显式注册或 Attribute 标注，不要靠命名约定。

原则 3：事件系统——安全性 > 性能

核心洞察

TEngine 的 GameEvent 追求零 GC，但忽略了异常安全和递归防护。在生产环境中，一个 handler 抛异常导致整个事件系统僵死——这比多分配几个字节严重得多。

设计优先级

实现模板

这个设计：

  • 泛型特化：EventBus<DamageEvent> 和 EventBus<GoldChanged> 是独立的静态类，零 Dictionary 查找
  • struct 事件：值类型不装箱
  • 数组存储：比 List<Delegate> 更 cache-friendly，无 as cast
  • 异常隔离：try-catch 包裹每个 handler

已知陷阱

  • TEngine 无 try-finally：handler 异常 → _isExecute 永远 true → 系统僵死。教训：dispatch 循环必须有异常隔离。
  • TEngine 递归 dispatch 无防护：内层 CheckModify 重置外层状态。教训：用深度计数器，仅最外层合并修改。
  • O(n) 重复检查：_listExist.Contains(handler) 每次订阅都线性扫描。教训：用 HashSet 做 O(1) 去重，或仅在 Debug 模式检查。

原则 4：对象池——有上限、有检测、分场景

核心洞察

TEngine 的 MemoryPool 无容量上限——如果突发大量对象被释放回池，内存永远不会降下来。Unity 内置的 ObjectPool<T> 用 maxSize 解决了这个问题。

设计规则

场景推荐方案原因
纯 C# 小对象（事件、状态、数据载体）自定义池 + maxSize控制内存上限
GameObject（子弹、特效、UI 项）专用 GameObject 池需要 SetActive/Transform 管理
临时字节缓冲区（网络包、序列化）ArrayPool<T>.Shared.NET 原生，线程安全，分桶优化
需要自动过期释放的资源句柄时间+优先级策略池TEngine ObjectPoolModule 的设计

实现模板

已知陷阱

  • TEngine 无 maxSize：池无限膨胀。教训：永远设上限，超出直接丢弃。
  • TEngine 计数器在 lock 外：统计数据竞态。教训：要么全在 lock 内，要么用 Interlocked。
  • 双重释放默认不检测：同一对象入池两次 → 两个消费者拿到同一实例。教训：至少在 Editor 模式检测。

原则 5：帧驱动——一个入口，多种接入方式

核心洞察

Unity 只有一个 Update 入口（MonoBehaviour），但框架需要让纯 C# 代码也能获得帧更新。TEngine 的三层方案（RootModule → MonoDriver → SingletonSystem）是热更约束的产物。

设计规则

实现模板（无热更版本）

如果需要优先级排序，加一个 Priority 属性 + 注册时插入排序即可。

原则 6：启动流程——FSM 管边界，Async 管细节

核心洞察

TEngine 用 12 步 FSM 管理启动。纯 FSM 的问题是天然串行——互不依赖的初始化不能并行。纯 Async 的问题是没有显式的”状态边界”——热更 DLL 加载这种不可逆操作需要明确的状态标记。

原则 7：UI 管理——Layer 分组 + 全屏遮挡 + 生命周期绑定

核心洞察

UI 系统的三个必解问题：深度排序、被遮挡面板的性能、事件泄漏。

设计规则

问题解法TEngine 验证
深度排序Layer 枚举 × 层内序号 = Canvas.sortingOrderlayer * 2000 + index * 100
被遮挡性能FullScreen 标记 → 从栈顶向下遍历，遇到全屏后隐藏下方OnSetWindowVisible()
事件泄漏Scoped Subscription → UI 销毁时自动取消所有订阅GameEventMgr 池化
重复打开Pop + Re-push → 刷新而非重建TryGetWindow → OnRefresh
延迟关闭Hide + Timer → 短时间内重开免加载HideTimeToClose

原则 8：不要修底层 bug 的 fork 策略是技术债

核心洞察

DGame 继承了 TEngine 的所有底层 bug（缓存 key 不一致、异常安全缺陷、递归 dispatch、O(n) Contains），只在上层加业务模块。这是一种”不动底层，只加上层”的策略。

教训

  • 短期有效：快速叠加业务价值，不碰风险高的底层改动
  • 长期危险：如果上游不修，bug 永远存在；如果上游修了但改了接口，合并冲突巨大
  • 自研框架时：底层 bug 必须第一时间修——你没有”上游会修”的退路

可复用原则

自研框架的底层代码必须是你完全理解且信任的。 如果你从 TEngine fork，第一件事是修掉已知的架构缺陷（缓存 key、异常安全、递归防护），而不是在有裂缝的地基上盖楼。

原则 9：Attribute 声明式用于”编译期确定 + 类型绑定”的元数据

设计规则

用 Attribute用配置文件/ScriptableObject
编译期确定，运行时不变运行时可能修改
与类型绑定（不是实例）与实例绑定
需要工具链处理（Source Generator）需要设计师编辑
改动频率极低改动频率高

好的 Attribute 用法：[Window(Layer.UI)]、[EventInterface]、[SaveData("key")] 坏的 Attribute 用法：[Damage(100)]（数值会频繁调整）、[Position(0,0,0)]（实例级数据）

原则 10：框架的价值在于它强制了什么约束

核心洞察

QFramework 的 CQRS 约束（读写分离、Command 是唯一写入路径）比它的 UIKit 更有价值。TEngine 的接口驱动约束（GetModule<IXxx>() 强制通过接口）比它的 ResourceModule 更有价值。

设计规则

自研框架时，先问自己：我要强制团队遵守什么规则？

约束收益代价
必须通过接口访问模块可替换、可 mock多写一个接口文件
数据和逻辑必须分离（ET 模式）热更安全、可测试心智负担高
上层不能直接改下层状态（QF 模式）数据流可追踪简单操作也要写 Command
所有异步必须用 UniTask（不用 Coroutine）统一异步模型、可取消学习成本

框架不是功能集合，是约束集合。 功能可以随时加，约束一旦放松就再也收不回来。

自研框架 Checklist

开始写代码前，回答这些问题：

  • 需要热更新吗？→ 决定程序集分层和服务定位方式
  • 团队规模多大？→ 决定约束强度
  • 模块粒度是什么？→ 决定 Service Locator vs DI vs ECS
  • 事件系统需要什么级别的安全性？→ 决定是否需要异常隔离和递归防护
  • 对象池需要管理什么？→ 决定是纯 C# 池、GameObject 池还是 ArrayPool
  • 启动流程有不可逆步骤吗？→ 决定 FSM vs 纯 Async
  • UI 有全屏遮挡需求吗？→ 决定是否需要 Layer + FullScreen 优化
  • 哪些元数据是编译期确定的？→ 决定 Attribute vs 配置文件
