Fantasy 框架（Fantasy Server Framework）

是什么

Fantasy 是面向大型多人在线游戏服务端的高性能 C# 框架，由 qq362946 维护。README 原话：“专为大型多人在线游戏打造的高性能分布式服务器框架”。

核心定位：在 ET Framework 的 ECS 思想基础上重写，完全去除反射以支持 Native AOT 和极致性能。

与 ET 的关系

继承自 ET：

  • 实体即组件的 ECS 思想
  • Scene 作为运行环境抽象
  • ETTask → FTask 自研异步
  • 静态 System 替代虚函数

与 ET 的根本差异：

  • 零反射：所有 Activator.CreateInstance 全部消除，靠 Source Generator 生成工厂方法
  • Native AOT 支持：可以编译为原生代码，启动快、内存小、无 JIT 抖动
  • .NET 8 现代化：拥抱 LightProto / MemoryPack 等零拷贝序列化方案
  • 多协议原生：TCP / KCP / WebSocket / HTTP 都是一等公民
  • Scene 中心化：所有 Entity 必须归属一个 Scene（ET 的 IScene 是接口，Fantasy 是具体类）

TypeHashCache：泛型静态字段的妙用

Fantasy 用了一个经典优化技巧——泛型静态字段缓存：

CLR 为每个泛型类型参数 T 生成独立的静态字段——TypeHashCache<Player>.HashCode 和 TypeHashCache<Bullet>.HashCode 是完全独立的字段，访问等同于读一个静态变量。这比 ET 每次调用 type.TypeHandle.Value.ToInt64() 更快。

Address：分布式实体寻址

Fantasy 的 RuntimeId 不只是本地 ID，而是全局分布式地址。Entity 可以跨进程被其他 Entity 引用，通过 RuntimeId 路由消息——这是大型 MMORPG 跨服通信的基础。

多协议设计

协议适用场景
TCP服务器间内网通信，稳定可靠
KCP实时对战，低延迟 UDP 可靠传输
WebSocketH5/小游戏，Unity WebGL 原生支持
HTTPRESTful API、Web 后台、GM 工具

不像 ET 需要为每种协议适配，Fantasy 把这四种作为一等公民设计——可以同一 Scene 同时监听多种协议。

适用判断

选 Fantasy 而非 ET 的硬条件：

  • 需要 Native AOT（启动时间、内存敏感、Linux 容器部署）
  • 服务端追求极致性能（零 GC、零反射）
  • 用 .NET 8+，能用最新 C# 特性
  • 想用现代化序列化（MemoryPack）而非 Protobuf
  • WebGL/H5 项目（WebSocket 原生支持）

仍选 ET 的理由：

  • 已有 ET 项目经验，团队不愿迁移
  • 需要严格的双端代码共享（Fantasy 服务端为主）
  • 需要 ET 9 的成熟生态包（aoi / lockstep / behaviortree）

与 TEngine/DGame 的集成

DGame README 提到：“Fantasy 线和 TE 同步接入服务器框架 Fantasy，区别在于 TE 接入的就更纯净简洁”——意味着：

这是一个异构架构——客户端用一种范式，服务端用另一种范式。可行的原因是通信层只传递数据（消息），不传递行为。

设计哲学

Fantasy 体现了一个重要观点：ET 的 ECS 思想是对的，但 ET 9 的实现因历史包袱有反射。Fantasy 是”如果今天重新设计一个 ET，应该长什么样”的答案：

ET 9Fantasy
Activator.CreateInstance + 反射注册泛型静态 + Source Generator
兼容老 .NET（含 Mono）拥抱 .NET 8 + AOT
Fiber 单线程模型Scene 中心化
双端共享代码（客户端代码 = 服务端代码）服务端为主，客户端通过 Unity 包接入
ProtobufMemoryPack / LightProto
30+ 业务功能包核心精简，业务自己写
