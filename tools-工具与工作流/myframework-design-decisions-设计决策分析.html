MyFramework 设计决策分析（Design Decisions）

本页定位

本页不重复模块细节，而是从源码级模块页中抽取 MyFramework 的关键设计决策：它为什么显得“重”、为什么偏传统游戏引擎思路、为什么大量自研工具和系统，以及这些选择适合什么项目。

决策 1：显式生命周期，而不是分散 MonoBehaviour

证据：myframework-startup-hotfix-启动与热更链 中 GameEntryBase 只负责转发 Unity 生命周期；真正的系统生命周期由 GameFrameworkHotFix 管理。

判断

这是典型“强控制”路线。优点是顺序可控、日志可控、销毁可控；代价是所有系统都要接入框架生命周期。

决策 2：AOT 启动壳 + HotFix 第二框架

证据：HybridCLRSystem.launchInternal() 会反射查找 GameHotFix，启动完成后销毁 AOT 框架。

判断

这比“主包框架长期持有热更业务”更激进：AOT 只负责启动和热更下载，真正业务进入 HotFix 后运行。

适合：

  • 需要大部分逻辑热更的商业项目
  • 启动/下载/热更边界清晰的团队

不适合：

  • 小型单机游戏
  • 不需要代码热更的项目

决策 3：资源管线自研，而不是接 YooAsset

证据：myframework-resource-system-资源系统深度 中 Editor 侧 MenuAssetBundle 生成 STREAMING_ASSET_FILE，运行时 AssetBundleLoader 读取并维护资源到 Bundle 的映射。

判断

自研资源管线让工具链、下载、加密、配置文件完全可控，但需要长期维护 Bundle 依赖、版本、下载、卸载、平台差异。

决策 4：UI 走代码生成 + 自定义对象树

证据：myframework-ui-system-UI系统深度 中 UGUIGeneratorUtility 负责成员配置，LayoutScript.assignWindow() 是生成代码挂载点。

判断

这条路线牺牲了 Unity 原生工作流的轻便性，换来大项目中 UI 绑定的一致性和可检查性。

决策 5：自研输入派发，统一 UI 与 3D 射线

证据：myframework-input-system-输入系统深度 中 GlobalTouchSystem 注释明确“用来代替 UGUI 的 EventSystem”。

判断

这让点击穿透、多摄像机、新手引导只允许指定对象交互等需求更可控，但与第三方 UI/Input 插件集成成本更高。

决策 6：命令对象承载可追踪动作

证据：myframework-command-system-命令系统深度 中命令支持延迟、主线程调度、中断、日志、接收者销毁清理。

判断

MyFramework 更倾向把跨系统动作显式对象化，而不是完全依赖事件广播。它追求“发生了什么动作”可追踪。

决策 7：低 GC 依赖全链路池化与规范

证据：myframework-pool-system-对象池与低GC深度 中 ClassPool、ListPool、ByteArrayPool 等贯穿网络、资源、命令、UI。

判断

低 GC 不是单个池，而是编码范式。收益是运行时分配低；代价是团队必须遵守 CLASS/UN_CLASS、LIST/UN_LIST、resetProperty 等规范。

决策 8：工具链前置错误发现

证据：myframework-editor-tooling-编辑器工具链深度 中资源引用、图集引用、UI 适配、未引用资源、AB 依赖等都在 Editor 菜单里检查。

判断

MyFramework 把“商业项目长期维护”放在“快速上手”之前。很多错误在运行时不会被优雅处理，而是要求开发阶段用工具发现。

总体画像

它不是最现代、最轻量、最贴近 Unity 原生生态的路线；它更像一个传统游戏客户端工程体系：

  • 强规范
  • 强工具
  • 强生命周期
  • 强自研
  • 强控制

适用判断

适合

  • RPG / MMO / 长期商业手游
  • 客户端与服务器需要共享协议和配置生成
  • 团队愿意接受框架规范和工具链约束
  • 对热更新、低 GC、资源检查、UI 生成有刚需

不适合

  • Game Jam / 快速原型
  • 小型单机项目
  • 强依赖 Unity 原生 UI/输入生态的项目
  • 不愿维护自研工具链的团队
