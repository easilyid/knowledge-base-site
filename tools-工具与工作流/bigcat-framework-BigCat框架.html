BigCat 框架（BigCat / 大猫）

是什么

BigCat 是 wjybxx（昵称”写代码的诗人”）的个人 MMO 框架与游戏工具集，C# 为主、Java 为辅，Apache 2.0 协议，目前 74 ⭐。单人长期维护，强调代码质量超过交付速度——作者自述”这也许将是你见过的代码质量最好的项目”。

本页只覆盖架构思维和可借鉴思想，不堆代码细节，目的是给自研框架的设计提供新视角。

这是一个不同物种

TEngine/ET/Fantasy 是面向团队的项目级框架——优先解决”多人协作 + 业务交付 + 热更”。BigCat 是单人作者多年笔记落地的精雕细琢之作，优先解决”代码该怎么写才是对的”。

不要按选型对比的角度去比 BigCat vs TEngine——它们的 KPI 不同。BigCat 的价值是”具体子系统的设计样本”，不是”端到端可替换 TEngine”。

可借鉴的核心设计思想

下面 5 个是自研框架时最值得借鉴的设计点，按价值降序。

1. TaskTree：通用任务树取代专用行为树（★★★★）

BigCat 把”行为树”重新定位为”通用任务树”——不只是 AI，技能脚本、副本脚本、任务脚本统统用同一棵树。

借鉴点：树形结构 + 心跳驱动 + 上下文三件套这一组合，能覆盖游戏中绝大多数”有时序、可中断、可组合”的逻辑。如果你做 MMO/MOBA/卡牌，技能与 AI 强行分两套是常见过度设计。

2. Context 三件套：数据/控制/配置正交分离（★★★★）

字段作用谁写谁读
Blackboard跨节点共享运行时数据节点节点
CancelToken树范围的取消信号外部触发器节点协作检查
SharedProps策划数值/公式配置仅初始化节点

借鉴点：很多自研框架把这三类数据混在一个”context”对象里，运行时读写策划配置 → 数据竞争；策划改值要改代码 → 流程僵硬。三件套正交分离是干净的解法。

SharedProps 的实战价值

作者举的例子：技能数值（伤害/范围/CD）随等级变化。如果数值散在节点字段里，策划要程序帮忙改；如果数值在 SharedProps 集中定义，策划只动配置文件，不碰逻辑代码。

这是”数据与行为分离”原则的具体落地，比口号有用。

3. 心跳驱动 vs 事件驱动的明确立场（★★★）

作者明确反对纯事件驱动，理由 4 条原话：

  1. 子节点将自己加入某个调度队列，导致父节点对子节点丧失控制权，也丧失时序保证——Unity 开发者尤为严重。
  2. 事件驱动会大幅增加代码的复杂度，因为事件是跳跃性思维，而心跳是顺序思维。
  3. 事件也是一种信号，错失信号可能导致程序陷入错误无法恢复——你玩游戏碰见的很多 bug 都源于此。
  4. 不要老拿性能说问题，首先大多数的行为树不深；另外，脱离你掌控的代码一定不是好代码。

借鉴点：这是与 v2 决策 6 事件系统 强相关的反向视角。v2 默认假设”事件系统是必备组件”，但 BigCat 提示——对树形可中断逻辑，心跳 + Context 比事件总线更可控。事件总线该用在跨模块解耦，而不是替代每帧 Update。

"脱离你掌控的代码一定不是好代码"

这句话直击事件驱动的根本问题——异步派发、订阅生命周期、事件丢失、循环触发——都让代码”脱离掌控”。当你发现某段逻辑要追 4 跳 callback 才能理清楚，停下来，换心跳。

4. Reentry 检测：防御性编程的优雅样本（★★★）

重入问题：状态机里 state.execute() 中触发 changeState(this)，新状态的 enter() 已经跑了，但旧 execute() 还没 return，继续执行就会读到错误数据。这是 List 迭代中删除元素的同构问题。

  • 事件分发期间 handler 触发对象销毁 → 用 reentryId 防御
  • UI 按钮 OnClick 期间触发 UI 关闭 → 同模式
  • FSM 状态切换期间访问旧状态字段 → 同模式

TEngine GameEvent 用三 List 模式（_listExist / _addList / _deleteList）解决类似问题，但 reentryId 模式更轻量、不需要双缓冲。

5. 协作式取消：CancelToken 不是中断（★★★）

任何的异步任务，不论单线程还是多线程，立即取消通常都是不安全的，因为取消命令的发起者通常不清楚任务当前执行的代码位置；安全的取消通常需要任务自身检测取消信号来实现，只有任务自身知道如何停止。

借鉴点：与 .NET CancellationToken 的设计哲学一致——取消是协作信号，不是强制中断。但 BigCat 把这条原则贯彻到任务树每个节点，这是 .NET 标准库没有的应用层规范。

自研框架的启示：异步流程（启动链/资源加载/AI 行为）都应统一用 CancelToken 风格，不要混用 Thread.Abort / bool isCancelled / 异常 cancel 三种方案。

UI 框架深度分析（源码级）

本章基于 unity/Assets/Scripts/UI/Runtime/ 16 个文件的源码逐文件验证（WindowMgr / Window / Controller / Desktop / WComponent / UINode / WindowCfg / WindowAgent / …），不是 README 推断。

整体定位

BigCat UI 不是”简单窗口栈”，而是一套带数据模型解析、生命周期、协程、桌面分屏、组件化的桌面级 UI 框架——结构上更像桌面 OS 窗口系统（Windows/macOS）的简化版，而不是手游 UI 框架。

五个层次抽象

抽象对应职责
WindowMgrOS 窗口管理器加载/打开/关闭/桌面切换/帧调度
Desktop虚拟桌面同桌面内 Window 的 Z 序、跨桌面切换
Window一个 Prefab UI资源管理单位、生命周期 + 重入 + 黑板 + 协程
UINodeUI 树节点可见性、绘制、数据绑定
ControllerMVC 中的 C处理事件，禁止 Update + 协程

关键判断：粒度极细，复杂度高

5 层抽象比 TEngine 的 2 层（UIWindow/UIWidget）多 1.5 倍。单体游戏几乎不需要这种粒度，但桌面级 / MMO 客户端 / 编辑器 UI 受用。

设计独到之处

1. Desktop 抽象（★★★★ 独有）

TEngine/QFramework/GameFramework 都没有 Desktop 概念。BigCat 显式建模多个虚拟桌面：

适用场景：

  • MMORPG：“主城 vs 战斗 vs 副本 vs PVP” 是 4 个桌面，切换桌面 = 切换整套 UI
  • 编辑器：编辑模式 vs 运行模式 是 2 个桌面
  • 模拟经营：地表层 vs 地下层 vs 天空层

替代方案是为每种场景手动维护 UI 列表 + 显隐——心智负担更高。

2. WindowMgr 不是 MonoBehaviour（★★★★）

对比 TEngine UIModule：TEngine 的 UIModule 是 Singleton<UIModule>, IUpdate，由 ModuleSystem 驱动（仍然在 Unity 主循环内）。BigCat 走得更彻底：UI 系统完全独立于 MonoBehaviour，由外部某个组件按需调度 5 个生命周期阶段。

为什么这么做：与 EventLoop/Worker 线程模型一致——UI 调度本质是”在某个线程的事件循环中执行帧驱动逻辑”，绑定 MonoBehaviour 限制了灵活性。

借鉴价值

如果你做多人房间在客户端模拟服务端逻辑（例如 RTS Lockstep）或编辑器面板 UI（不在 Game 主循环），这种解耦极其有用。

3. 双重并行的生命周期（★★★ 工业级）

7 个状态远多于 TEngine 的 4 个（Hide/Visible/Loading/Created）。Window 还有 Pause/Resume 主动暂停 + Reset 复用：

关键：Window 关闭后不立即销毁，进入 _closedWindowList + destroyTime，由 EndOfFrame 按时间堆延迟销毁。这样：

  • 用户秒级内重开窗口 = 复用实例（零重新加载）
  • 长时间不开 = 自动延迟释放资源

TEngine 用 HideTimeToClose 实现类似机制，但 BigCat 把”延迟销毁”做成了一等公民——优先级队列（按 destroyTime 排序）+ 每帧 EndOfFrame 检查。

维度TEngineBigCat

关闭后复用走 ShowUI 重新创建Reset + Reopen 复用实例

5. 三阶段 Update + 协程时间轴（★★★）

每个 Window 独立 GTime 时间轴 + 独立 CoroutineMgr，Window 暂停 = 协程暂停 = 时间冻结。这与 Unity Time.timeScale 全局影响不同，可单独冻结某个窗口。

对比 TEngine：UIWindow 没有独立时间轴，全局暂停由业务自己管。

6. 数据模型解析（DataAddress + DataModelResolver）（★★★ MVC 派）

每个 Window/Node 配 dataAddress 字符串（如 "player.bag.equipment[0]"），框架自动从根模型解析。这是经典 MVVM思路，Unity 端少见——TEngine/QFramework 一般让用户在代码里手动 Player.Instance.Bag 取数据。

借鉴价值

数据驱动配置（dataAddress 字符串在 Inspector 配）让策划/美术能在不改代码的前提下改 UI 数据源，但需要先沉淀 IAggregationModel 规范——成本不低。中小项目大概率不值得做。

全屏遮挡的简化处理

对比 TEngine：TEngine 的全屏遮挡只看 FullScreen flag。BigCat 多了一层”Rect 重叠检测”——即使没有标记 FullScreen，只要上层窗口物理覆盖了下层，下层也会 SetActive(false)。

源码注释承认旋转下不正确

Rect.Overlaps 不处理旋转。这是个已知缺陷，作者 TODO 标注。商业项目要保留这一点判断时需要自己补完。

不要直接抄的部分

设计不抄理由
5 层抽象单体/中小游戏过度设计
WindowMgr 完全脱离 MonoBehaviour需要配套 Worker/EventLoop 线程模型，单独剥离意义不大
WindowAgent + WComponent 双层组件概念重叠，可以折叠为单层 Component
dataAddress 字符串解析需要建 IAggregationModel 规范，没沉淀好成本高

强烈建议借鉴

设计借鉴方法
Reentry id 模式任意框架——Window/Panel 字段加 int reentryId，Open/Close/Reset 时 ++

不太建议借鉴的设计

Dson 自创序列化格式（★ 但争议大）

作者自创 Dson（Dson Object Serialization Notation），介于 JSON 和 BSON 之间。已发布到 NuGet，下载量数千。

自创序列化格式的代价

  • 生态壁垒：第三方工具/编辑器/语言支持都要重新做
  • 学习成本：团队成员要先学一个非标格式
  • 替代方案丰富：MessagePack-CSharp / MemoryPack / protobuf 都成熟

单人项目可以这么玩（作者本人能维护），团队项目几乎没有借鉴意义。

如果你不是序列化研究方向，直接用 MemoryPack 或 protobuf-net，不要走 Dson 路线。

自定义协程（★ 在 UniTask 时代）

作者实现了”自定义协程”，但 UniTask 在 Unity 客户端、原生 Task 在服务端都已经是工业标准。除非有 BigCat 特定调度需求，自研协程是负优化。

自定义 DI（★★ 在 VContainer 时代）

Wjybxx.Commons.Inject 是个人 DI 实现。Unity 端 VContainer 是事实标准，服务端 .NET 原生 Microsoft.Extensions.DependencyInjection 足够。自研 DI 适合学习，不适合落地。

关键差异化：决策 6 与决策 9

BigCat 在事件系统和帧驱动这两点上走了与 TEngine/ET 截然不同的路——把”心跳驱动 + Context”作为业务逻辑组织的主线，事件系统降为辅助工具。这是给 v2 决策的反向视角。
