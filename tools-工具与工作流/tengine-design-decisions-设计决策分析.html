TEngine/DGame 底层设计决策分析（Architecture Design Decisions）

主线

本页分析 TEngine 和 DGame 中 7 个核心架构设计决策——不是”怎么用”，而是”为什么这样设计”以及”有没有更好的设计”。

1. 状态机如何泛型化

设计问题

如何让一个 FSM 实现同时服务于 Procedure（游戏启动流程）、AI（怪物行为）、动画（状态切换）等完全不同的场景？

TEngine 的解法：Owner 类型参数化

设计分析

决策理由权衡
T 是 Owner 类型而非 State 数据类型状态可以通过 fsm.Owner 访问持有者的上下文不同 Owner 的状态不能复用
FsmState<T> 是 abstract class 而非 interface提供 ChangeState 默认实现单继承限制
状态按 Type 存储在 Dictionary<Type, FsmState<T>>O(1) 查找，类型即标识同类型不能有多个实例
Fsm<T> 实现 IMemory（可池化）FSM 实例可复用，减少 GC需要正确 Clear 所有状态

更好的变种

问题：当前设计中，状态转换用 ChangeState<TState>() 泛型方法——这意味着转换目标必须在编译期确定。动态转换（如从配置表读取下一个状态）需要用 ChangeState(Type) 重载，失去类型安全。

替代方案：枚举驱动 + 转换表

结论：TEngine 的泛型 FSM 适合编译期已知状态集的场景（Procedure、UI 流程）；数据驱动场景（AI 行为树、配表驱动流程）需要额外封装。

2. 帧驱动如何统一

设计问题

Unity 的帧更新入口是 MonoBehaviour.Update()，但框架的模块是纯 C# 类。如何让纯 C# 模块获得帧更新能力？

三层驱动架构

设计分析

层级驱动方式适用对象优先级控制
ModuleSystemPriority 属性排序Runtime Core 模块有（数值越大越先更新）
MonoDriver注册顺序HotFix 层任意代码无（FIFO）
SingletonSystem注册顺序HotFix 层 Singleton无（FIFO）

DGame 的改进：TEngine 的 UpdataDriver（注意原始拼写错误）是一个静态工具类；DGame 将其重构为 MonoDriver Module，纳入 ModuleSystem 管理，生命周期更规范。

设计启示

为什么不让所有代码都走 ModuleSystem？

因为 ModuleSystem 在 Runtime Core 层（AOT 程序集），而业务逻辑在 HotFix 层。HotFix 层的代码不能注册为 Runtime Module（程序集依赖方向不允许）。所以需要 MonoDriver 作为”桥梁”——它是 Runtime Module，但提供回调注册接口给 HotFix 层使用。

这是热更新架构对帧驱动设计的约束——不是技术选择，是架构必然。

3. 热更边界如何划分

设计问题

哪些代码能热更新？哪些不能？边界画在哪里？

程序集划分

设计规则

规则原因
ModuleSystem 在 AOT它是所有模块的注册中心，必须在 DLL 加载前就存在
Procedure 在 AOT启动流程（包括加载 DLL 的步骤本身）不能依赖热更代码
GameModule Facade 在 HotFix它引用了 HotFix 层的 UIModule 等，必须在热更程序集中
接口在 AOT，实现可在 HotFixIResourceModule 在 Runtime，ResourceModule 也在 Runtime（因为启动时就需要）
业务 Singleton 在 HotFixUIModule、DataCenter 等纯业务逻辑，可以热更

设计启示

热更边界 = 依赖方向的不可逆点。

GameApp.Entrance 的反射调用就是这个”不可逆点”的体现——AOT 层通过 Assembly.Load + 反射调用 HotFix 层的入口方法，之后控制权完全交给 HotFix。

4. Singleton vs ModuleSystem 的选择标准

设计问题

框架中同时存在两套”全局服务”机制：ModuleSystem.GetModule<T>() 和 Singleton<T>.Instance。什么时候用哪个？

源码验证的选择规则

特征ModuleSystemSingleton
所在层Runtime Core（AOT）HotFix
注册方式接口驱动，GetModule<IXxx>()类驱动，XxxModule.Instance
生命周期ModuleSystem 统一管理SingletonSystem 统一管理
帧更新IUpdateModule + Priority 排序IUpdate 接口，无优先级
销毁顺序反向 Priority反向注册顺序
热更兼容接口在 AOT，实现可跨程序集类型必须在 HotFix 层

设计决策树

设计启示

这不是”两种等价方案选一个”——而是热更架构强制的分层。ModuleSystem 是框架基础设施（必须 AOT），Singleton 是业务层的全局访问点（可以热更）。

5. DGameLinkedList：为什么自定义数据结构

设计问题

.NET 的 LinkedList<T> 每次 AddLast 都 new LinkedListNode<T>()，产生 GC。如何避免？

DGame 的解法：节点池化

设计分析

决策理由权衡
包装 LinkedList<T> 而非自己实现链表复用 .NET 实现的正确性多一层间接
用 Queue<LinkedListNode<T>> 做节点池FIFO 均匀复用池本身不会 GC（Queue 内部数组只增不减）
node.Value = default 清引用防止池中节点持有已释放对象额外赋值开销（可忽略）

适用场景

DGameLinkedList 用在 GameTimer 模块——定时器频繁增删，标准 LinkedList 每次增删都 new/GC 一个 Node。池化后，稳态运行时零 GC。

更好的变种

如果不需要链表的 O(1) 中间插入/删除，用 List<T> + swap-remove 更 cache-friendly。链表的 cache miss 在现代 CPU 上代价很高。

6. 事件生命周期绑定模式（Scoped Subscription）

设计问题

UI 窗口注册了全局事件，窗口关闭后忘记取消订阅——事件泄漏，handler 持有已销毁对象的引用，下次触发时 NullReferenceException。

TEngine/DGame 的解法

设计分析

这是 Scoped Subscription 模式——订阅的生命周期绑定到一个 scope 对象（这里是 UIBase）。

对比TEngine ScopedMessagePipe IDisposableUniRx AddTo
绑定方式手动调用 RemoveAllUIEventsubscription.Dispose().AddTo(gameObject)
自动清理需要在 OnDestroy 中调用Dispose 模式自动GameObject 销毁时自动
池化GameEventMgr 从 MemoryPool 获取无池化无池化
忘记清理的后果泄漏（但 UIModule.CloseUI 会调用）泄漏自动（最安全）

设计启示

TEngine 的方案依赖调用链的正确性——CloseUI → InternalDestroy → RemoveAllUIEvent。如果有人绕过 UIModule 直接 Destroy GameObject，事件不会被清理。

更健壮的设计是 UniRx 的 .AddTo(gameObject) 模式——利用 Unity 的 OnDestroy 回调自动清理，不依赖框架调用链。

7. Attribute 声明式设计的边界

设计问题

框架在哪些地方选择 Attribute 声明式配置？选择标准是什么？

源码中的 Attribute 使用

Attribute用途配置内容
[WindowAttribute(UILayer.UI, fullScreen: true)]UI 窗口元数据层级、全屏、资源路径
[EventInterface(EEventGroup.GroupUI)]Source Generator 触发器事件分组
[ClientSaveData("Setting", PerRoleID = false)]存档配置存档名、是否按角色
[ObfuzIgnore]混淆排除排除范围

设计规则（从源码归纳）

用 Attribute 的条件：

  1. 元数据在编译期确定，运行时不变
  2. 元数据与类型绑定（不是实例绑定）
  3. 需要被工具链处理（Source Generator、Editor 脚本、反射扫描）

不用 Attribute 的条件：

  1. 配置需要运行时修改（如音量、语言）→ ScriptableObject / PlayerPrefs
  2. 配置需要设计师编辑（如关卡数据）→ 配表 / Inspector
  3. 配置是实例级别（同一类型不同实例不同配置）→ 构造参数 / Init 方法

设计启示

Attribute 声明式的核心价值是代码即配置——IDE 可跳转、编译器可检查、重构工具可追踪。代价是改配置需要重新编译。

TEngine/DGame 的选择是合理的：WindowAttribute 的 Layer/FullScreen 属性确实几乎不会运行时变化，放 Attribute 比放配置文件更安全。

总结：设计决策的统一逻辑

这 7 个设计决策背后有一条统一的约束链：

热更新是 TEngine 系框架所有架构决策的第一因。如果去掉热更需求，大部分复杂性都可以消除（直接用 VContainer + MonoBehaviour 就够了）。
